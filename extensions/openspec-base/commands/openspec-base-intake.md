# /openspec-base-intake

Проведи пользователя по одному адаптивному опроснику и сам собери итоговый
`intake.md`. Пользователь отвечает на вопросы, но не обязан вручную переносить,
переформатировать или повторно собирать ответы.

Команда работает только с Change по schema `base-v1`. Она не заменяет Proposal,
Delta Specs, Design, Tasks или `/opsx-explore` и не запускает следующий этап
автоматически.

Её входной смысловой prerequisite — согласованный Intent. Им может быть Daily Intent
Brief из `base-intent` либо явно принятая пользователем Jira Story/другой источник,
если в нём уже определены изменение, Why Now, ожидаемое улучшение, критерии успеха и
ограничения. Не требуй повторного запуска `base-intent` при наличии такого источника.

## Жёсткие границы

- ОБЯЗАН задавать ровно один следующий вопрос за сообщение и учитывать все уже
  полученные ответы; не показывать пользователю всю анкету одним списком.
- ОБЯЗАН сначала использовать согласованный Intent из текущего диалога или явно
  переданных материалов, перенести его выводы в Intake и не переспрашивать закрытые
  им вопросы. Номер или ссылка на Jira без доступного содержания сохраняется как
  provenance, но не считается достаточным Intent автоматически.
- Когда из контекста можно честно вывести альтернативы, предлагать 2–4 коротких
  взаимоисключающих варианта с пояснением различий. Пользователь может выбрать,
  объединить, уточнить или отвергнуть варианты.
- ЗАПРЕЩЕНО читать Code Repositories, CodeGraph, реализационные тесты и
  repository-specific configuration. Источники Intake — ответы пользователя,
  переданные материалы, Master Specs и относящийся к вопросу подтверждённый
  `openspec/context/`.
- ЗАПРЕЩЕНО придумывать отсутствующее бизнес-решение, считать предположение фактом,
  превращать Intake в Requirement, Scenario, Design decision, ADR, Tasks,
  Repository Impact или evidence реализации.
- ЗАПРЕЩЕНО создавать второй questionnaire-файл, пустой `intake.md` или заполнять
  обязательные разделы фиктивным текстом. Не добавлять раздел Owner Confirmation.
- При конфликте источников, неверной schema или невозможности определить точный
  Change вернуть BLOCKER и задать один вопрос, который позволяет продолжить.

## Начало или продолжение

1. Получи точный `change-id` из аргументов команды или спроси его одним вопросом.
2. Выполни `openspec list --json` и сравни `change-id` только по точному совпадению.
   Не ищи Change через fuzzy name или обход файловой системы.
3. Если Change существует, сначала выполни:

   ```bash
   openspec status --change <change-id> --json
   ```

   Если `schemaName` не `base-v1`, остановись с `BLOCKER: SCHEMA_MISMATCH`; не вызывай
   для такого Change `instructions intake`. Для `base-v1` затем выполни:

   ```bash
   openspec instructions intake --change <change-id> --json
   ```

   Используй фактические `planningHome`, путь результата, template, instruction и
   rules из ответов OpenSpec. Затем прочитай существующий содержательный `intake.md`,
   если он есть, не затирая его template.
4. Если Change не существует, проверь согласованный Intent в текущем диалоге или явно
   переданных материалах. Если его нет, остановись с `BLOCKER: INTENT_REQUIRED` и
   предложи сначала пройти `base-intent` либо передать принятый Daily Intent
   Brief/Jira Story. Не проводи Intent-сессию внутри Intake и не запускай skill
   автоматически. После подтверждения Intent используй уже выбранный на шаге 1
   kebab-case `change-id` и создай Change штатной командой:

   ```bash
   openspec new change <change-id> --schema base-v1
   ```

   Не создавай Change до явного выбора идентификатора пользователем. После создания
   сначала выполни `status`, проверь `schemaName: base-v1` и только затем получи
   инструкции Intake:

   ```bash
   openspec status --change <change-id> --json
   openspec instructions intake --change <change-id> --json
   ```

5. Для нового или существующего Change проверь согласованный Intent в диалоге,
   явно переданных материалах или разделе Intent source существующего Intake. Само
   наличие заполненного Intake без такого источника Intent не подтверждает. Если
   источник отсутствует, верни `BLOCKER: INTENT_REQUIRED` по правилу шага 4.
6. Составь внутреннюю карту закрытых полей из Intent, переданных материалов и
   существующего `intake.md`. Сохрани подтверждённые ответы и спрашивай только первый
   действительно отсутствующий, конфликтующий или изменившийся пункт. Не начинай
   опрос заново.

## Карта опроса

Сначала определи один или несколько профилей Change:

- `new_integration` — новая интеграция;
- `ui_change` — изменение UI;
- `access_security` — доступ и безопасность;
- `existing_behavior_extension` — расширение существующего поведения;
- `technical_change` — техническое или эксплуатационное изменение.

Профили могут сочетаться. Не спрашивай неприменимые ветки; в итоговом Intake отметь
их `Не применимо` с краткой причиной только там, где раздел обязан сохраниться.

### Обязательное ядро

Собери:

1. Jira Story или явное отсутствие Jira, ссылки и другие переданные источники.
2. Проблему или возможность, затронутых пользователей/операторов и Why Now.
3. Подтверждённое текущее и ожидаемое наблюдаемое поведение.
4. Предварительные Scope, Non-Goals, ограничения и измеримые критерии успеха.
5. Основной пользовательский или системный путь, альтернативные и негативные ветки.
6. Открытые вопросы, конфликты и предположения с явной классификацией.
7. Ожидаемый способ проверки результата.

Для чисто технического Change вместо вымышленного пользовательского пути собери
эксплуатационную проблему, затронутых участников, наблюдаемый результат и способ его
измерения.

### Условные ветки

Для интеграции уточни публичные методы и направления взаимодействия, синхронный и
асинхронный обмен, события, данные, таймауты, ошибки, повторные попытки, идемпотентность
и поведение при недоступности зависимостей. Для двух и более компонентов, внешней
зависимости, асинхронного обмена или значимых error/degraded веток ОБЯЗАН собрать
PlantUML sequence diagram. Диаграмма является аналитической моделью взаимодействия,
а не принятым техническим Design.

Для UI уточни путь до функции, раздел/страницу, действия, данные и состояния
компонентов, загрузку, пустой результат, ошибки, ограничения, фильтрацию, сортировку,
пагинацию, уведомления, соответствие дизайн-системе и адаптивность. Если есть макет,
сохрани ссылку и применимые экраны/версии.

Для доступа и безопасности уточни роли, привилегии, публичные методы, место
обязательного enforcement, согласованность UI и gateway/API, скрытие чувствительных
данных, аудит и поведение при отказе в доступе. Не считать скрытие элемента UI
заменой серверной проверки.

Для расширения существующего поведения уточни изменяемые варианты использования,
сохраняемое поведение, совместимость, миграцию пользователей или данных и требуемую
актуализацию существующей аналитики/спецификации. Не предлагай новый capability-клон,
пока не подтверждено, что меняется отдельная capability.

Для любого применимого профиля проверь, не пропущены ли policy/request filtering,
конфигурация привилегий, аудит, обработка ошибок на каждой публичной границе,
degraded behavior, автотесты и сквозная проверка. Это вопросы полноты Intake, а не
готовые Tasks.

### Порядок вопросов

Не воспроизводи этот список целиком пользователю. На каждом ходе выбери первый
непокрытый вопрос, ответ на который сильнее всего влияет на маршрут:

1. Какие профили Change применимы?
2. Какая Jira Story или другой исходный запрос является источником?
3. Какую проблему решаем, для кого и почему сейчас?
4. Как выглядит подтверждённое текущее поведение?
5. Какой наблюдаемый результат должен стать новым поведением?
6. Что входит и явно не входит в Change; какие есть ограничения и критерии успеха?
7. Каков основной путь и какие альтернативные или негативные ветки значимы?
8. Какие вопросы выбранных условных профилей ещё не покрыты?
9. Как проверить результат и какие неизвестные могут изменить scope, поведение или
   системную границу?

Если одно сообщение пользователя уже отвечает на несколько пунктов, зафиксируй их и
не переспрашивай. Если ответ противоречит предыдущему, сначала уточни конфликт одним
вопросом.

## Сборка Intake

Когда информации достаточно для осмысленного решения о следующем маршруте:

1. Собери ответы в единственный файл `intake.md` по template из
   `openspec instructions intake`. Пользователь не переносит ответы вручную.
2. Сохрани аналитический смысл ответов, но убери повторы и разговорные промежуточные
   формулировки. Не повышай предположение до факта.
3. Для UI используй таблицу из template. Для доступа используй отдельную таблицу
   ролей и привилегий. Для применимого взаимодействия включи PlantUML diagram.
4. В `Facts, Assumptions, Conflicts, and Open Questions` явно раздели четыре класса.
5. Заполни `Exploration`:
   - `not_required`, если подтверждённого контекста достаточно для Proposal;
   - `pending`, если есть точные исследуемые вопросы;
   - `completed`, если пользователь передал результаты ранее выполненного Explore.
6. Установи ровно один `Planning Route`:
   - `ready_for_proposal` — контекст достаточен и непротиворечив, а оставшиеся детали
     не меняют scope или наблюдаемое поведение;
   - `explore_recommended` — недостаток можно закрыть исследованием доступных
     источников; перечисли точные вопросы Explore;
   - `blocked` — требуется отсутствующий нормативный источник, бизнес-решение или
     разрешение конфликта, которое Explore не может придумать.
7. Запиши файл только когда он содержит реальные ответы и выбранный маршрут. После
   записи снова выполни `openspec status --change <change-id> --json`.

Если команда запущена повторно после `/opsx-explore`, добавь подтверждённые findings
в `Exploration`, обнови связанные разделы Intake, пересмотри открытые вопросы и снова
выбери Planning Route. Не переносить findings автоматически в Proposal, Specs,
Design или Tasks.

## Завершение

Верни короткий результат:

```yaml
intake_result:
  change_id: <change-id>
  file: <resolved intake path>
  profiles: []
  planning_route: ready_for_proposal | explore_recommended | blocked
  explore_questions: []
  blocking_questions: []
  next_action: /opsx-continue | /opsx-explore | continue_intake
```

Не выполняй `next_action`. Решение о запуске Explore, переходе к Proposal или
продолжении уточнений всегда принимает пользователь.
