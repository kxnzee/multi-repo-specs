# Тест-кейсы для OpenSpec Change

- ОБЯЗАН выводить шаги и expected result только из принятого Requirement, Scenario
  или явного ограничения Proposal.
- ЗАПРЕЩЕНО превращать существующий тест, код, Zephyr case или предположение в новое
  требование, объявлять проверку выполненной без evidence или выдумывать coverage.
- Если источник ожидаемого поведения отсутствует или противоречив, вернуть BLOCKER
  либо unknown. НЕМЕДЛЕННО ОСТАНОВИСЬ и не заполняй пробел правдоподобным текстом.

Составлять тест-кейсы по подтверждённым требованиям выбранного Change и возвращать их
пользователю на русском языке.

## Границы

- Использовать штатные OpenSpec CLI и артефакты как источник состояния Change. Не
  создавать собственный lifecycle, команду или промежуточный формат для OpenSpec.
- Работать только на чтение. Не изменять Change, Master Specs, задачи, реализацию,
  тесты, встроенные `openspec-*` skills и `opsx-*` commands.
- По умолчанию выводить список в ответе. Записывать его в файл только по явной просьбе
  пользователя и только по согласованному пути; не добавлять нештатный файл в Change
  автоматически.
- Не выдавать предположение за требование и не объявлять тест существующим или
  пройденным без evidence.
- Быть leaf-skill: не вызывать project skills, project commands или subagents. При
  прямом запуске использовать только доступные Planning-источники и переданное
  evidence; недостающее repository evidence возвращать как unknown.

## Порядок работы

1. Определить Change из запроса или вызвать MCP `get_status`. Если выбор неоднозначен,
   попросить пользователя выбрать, не угадывая Change.
2. Вызвать `get_change_context` для выбранного Change. Использовать возвращённые
   `planningHome`, `changeRoot`, `artifactPaths` и `actionContext`, не собирать пути
   вручную.
3. Прочитать все существующие файлы из `artifactPaths.<id>.existingOutputPaths`.
   Обычно это proposal, delta specs, design и tasks, но набор определяет активная
   schema. Отметить отсутствующие или пропущенные источники. Если существует
   `openspec-orch.yaml`, прочитать допустимые Code Repository ids и Repository impact
   Change.
4. Выделить наблюдаемое поведение, предусловия, состояния, ограничения, ошибки,
   совместимость и критерии приёмки. Для каждого кандидата сохранить ссылку на
   Requirement, Scenario или принятое ограничение Proposal. Только они определяют
   шаги и expected result продуктового тест-кейса.
5. Если вызывающий meta-skill передал `repository_evidence` outputs, использовать их
   только как evidence bundle для automation placement, существующих уровней,
   паттернов тестирования и покрытия Requirement/Scenario на указанных revisions. Не
   менять шаги или expected result под существующий тест и не вызывать scout
   самостоятельно.
   При прямом запуске без bundle ограничить результат Planning-артефактами, а
   недостающее repository evidence перечислить в ограничениях и `open_questions`.
6. Добавлять только применимые варианты: позитивные, негативные, граничные, права
   доступа, ошибки интеграций, идемпотентность, конкурентность, совместимость,
   миграции, rollout и rollback. Не добавлять категорию ради полноты таблицы.
7. Удалить дубликаты и проверить, что ожидаемый результат каждого кейса однозначен и
   проверяем. Не подменять тест-кейс общим призывом «проверить корректность».

## Формат ответа

Сначала показать:

- выбранный Change и schema;
- прочитанные артефакты;
- ограничения результата из-за отсутствующих данных.

Затем вывести таблицу:

| ID | Repository ID | Уровень | Основание | Предусловия | Шаги | Ожидаемый результат | Приоритет автоматизации |
|---|---|---|---|---|---|---|---|

Использовать стабильные ID вида `TC-<область>-NNN`. В `Основание` указывать
Requirement/Scenario или `path:line`. Уровень выбирать из `unit`, `component`,
`integration`, `contract`, `e2e`, `manual` только по фактической границе проверки.
В `Repository ID` указывать место автоматизации или evidence; если placement не
подтверждён, ставить `unknown`. Для межрепозиторной
проверки перечислять точные ids, а для чисто внешней ручной проверки ставить `—`.

Если пользователь просит подготовить экспорт для Zephyr, дополнительно вернуть
нейтральные записи с `case_id`, `title`, `change_id`, `scenario_ids`, `level`,
`repository_ids`, `preconditions`, `steps`, `expected_result`,
`automation_priority` и, когда известен, `candidate_id`. Не угадывать CSV/API-схему конкретной Zephyr edition, не загружать
данные и не считать экспортированный case выполненным без явного adapter и запроса.

После таблицы перечислить:

- требования и сценарии без тест-кейсов;
- тест-кейсы без достаточного основания;
- вопросы, без ответа на которые ожидаемый результат неоднозначен;
- существующие тесты, если их удалось подтвердить, отдельно от предлагаемых.
