# Инициатива нескольких команд

Помоги пользователю описать ожидаемый общий результат и проверить его по
свидетельствам. Используй его язык, уже принятые решения и локальный процесс.

1. Определи основной Store, реестр участников и выбранный Change. Не угадывай
   соседние каталоги. Для нового Change используй schema initiative, если она
   выбрана пользователем или конфигурацией Store. Существующий Change с другой
   schema не переключай: следуй его процессу.
2. Прочитай STORE.md и контекст проекта. Получи актуальные status и инструкции
   OpenSpec через доступный Orchestrator MCP; без MCP используй
   `openspec status --change <id> --json` и
   `openspec instructions <artifact-id> --change <id> --json` из основного Store.
   Для нового Change доступен `openspec new change <id> --schema initiative`.
   Следуй возвращённым зависимостям и локальным templates/context/rules,
   не жёстко заданному списку этапов из этого навыка.
3. В Proposal уточни проблему, результат, границы и участие команд. Задавай
   вопросы только по существенным пробелам. Repository Impact использует точные
   ID code/specs из реестра и capabilities Delta Specs этого же Change.
   Согласие команды и сроки не выводятся из факта её перечисления.
4. В Specs сформулируй общие требования и наблюдаемые сценарии. Сохраняй стандартные
   заголовки OpenSpec и полное содержимое изменяемых требований. Не навязывай
   техническое решение, дизайн или кодовые задачи. При чтении командных источников
   сохраняй Store, путь и revision; явно отмечай недоступность и неопределённость.
5. В Verify сопоставь требования со свидетельствами. Различай проверку планирования
   и приёмку поставленного результата. Без свидетельств запиши «не проверено»;
   не считай отмеченные задачи, готовые документы или пустой список ошибок
   подтверждением общего результата. Не заявляй решение владельца без его ответа.
6. Проверяй артефакты штатной валидацией OpenSpec. Если подключён OpenSpec Graph,
   проверь Repository Impact через get_spec_change_impact (change_id выбранного Change)
   или `openspec-orch plugin exec --repo <store-id> openspec-graph inspect --json`.
   При отсутствии плагина не требуй его установки для подготовки инициативы.

## Настройка

Пользователь может добавлять артефакты, менять зависимости и шаблоны в Store,
задавать context/rules в openspec/config.yaml и подключать дополнительные навыки.
Не заменяй его процесс базовым. Если локальная schema переименована, уточни,
какие инструкции применимы; не считай любой похожий профиль автоматически своим.

Изменяй только запрошенные артефакты. Этот профиль не выполняет кодовый Apply,
не создаёт Changes в командах автоматически и не запускает Archive, Release
или публикацию по факту завершения документов. Существование verify.md означает
наличие отчёта, а не успешную приёмку. Покажи результат и открытые вопросы.
