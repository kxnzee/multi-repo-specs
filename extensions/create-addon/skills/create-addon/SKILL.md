# Создание дополнений Orchestrator

Помоги автору получить самостоятельный пакет и проверить его на реальной задаче.
Техническую заготовку создаёт `openspec-orch create`; содержимое готовь по задаче
пользователя. Не подменяй генератор самостоятельным изобретением manifests и SDK API.

## Выбор

Объясни варианты и выбери минимальный подходящий тип:

- Extension: инструкции и навыки для агента, основное содержание — текст.
- Plugin: исполняемая команда, обработка данных или интеграция; нужна реализация кода.
- Template: начальные файлы и контекст нового Store, копируемые при init.

Уточняй только недостающие сведения: ожидаемый результат, название, каталог,
поддерживаемые агенты и область действия. Сначала проверь `openspec-orch create --help`.
Если команды нет, сообщи, что нужна версия Orchestrator с этой командой.
В checkout Orchestrator эквивалентный запуск — `node src/bin/openspec-orch.js create`.
Не устанавливай инструменты глобально без запроса пользователя.

## Создание

Примеры вызовов (ID и путь замени согласованными значениями):

```bash
openspec-orch create extension requirements-review ./requirements-review --agent claude --target store --json
openspec-orch create plugin dependency-audit ./dependency-audit --profile commands --json
openspec-orch create template team-project ./team-project --json
```

Для Plugin начинай с `commands`. `repository` нужен для connect/status конкретного
репозитория; `native` — для передачи argv отдельному runtime. Эти два профиля
содержат незавершённые обработчики: реализуй их и проверь наблюдаемое поведение.
`--extension` добавляет инструкции к repository/native Plugin; только ради текста
выбирай самостоятельный Extension.

CLI не требует Store, не подключает пакет и не перезаписывает существующий каталог.
При доработке существующего пакета прочитай его содержимое и вызови validate;
повторная генерация поверх него не нужна. Передавай пути как отдельные argv, не
собирай shell-команду конкатенацией пользовательского текста.

В JSON результатах `editable` показывает файлы для содержимого, `next` содержит
команду и массив аргументов проверки. При ошибке прочитай `error.code` и
`error.message`; исправь причину, сохраняя существующие пользовательские файлы.

## Содержание и проверка

Extension: заполни SKILL.md конкретными входами, действиями, результатом и способом
проверки. Общий контекст находится в agent-instructions.md. Не объявляй выполненными
действия, для которых нет подтверждений.

Plugin: реализуй согласованную логику через публичный Plugin SDK. После установки
зависимостей выполни npm test и validate с --load. --load импортирует JavaScript
пакета в отдельном процессе; он не является песочницей и не проверяет действия команд.

Template: заполни копируемые файлы. Минимальный Template заменяет содержимое default
и не наследует его схемы. Schema steps должны работать без необязательных Plugins.
Не добавляй Plugin lifecycle или автоматическую установку пакетов в Template.

После редактирования выполни:

```bash
openspec-orch create validate ./requirements-review --kind extension --json
openspec-orch create validate ./dependency-audit --kind plugin --load --json
openspec-orch create validate ./team-project --kind template --json
```

Проверка относится только к перечисленным в `checks` контрактам. `behavior:
not-tested` означает, что прикладной результат ещё не проверен. Проверяй реальный
сценарий отдельно: команду Plugin, копирование Template в тестовый Store или работу
Extension в новой сессии выбранного агента. Для подключения следуй README пакета;
команды init/connect выполняются из тестового Store, а npm test — из пакета.

В отчёте различай структуру, подключение и фактическое поведение. Если тестового
Store или агента нет, явно назови эту непроверенную часть. Создание пакета не означает
его публикацию или установку в рабочий проект пользователя.
