# План общих доработок SDD после пилота 00–06

> Статус документа: `proposed`.
>
> Основание: изолированный прогон шагов 00–06 выявил общие дефекты процесса,
> которые применимы к Qwen, GigaCode и Claude. Специфичные особенности конкретного
> агента в этот план не входят.

## 1. Цель

Доработать общий SDD-процесс так, чтобы:

- OpenSpec получал все проектные правила без потери данных при разборе YAML;
- Apply не маскировал нарушение обратной совместимости переписыванием существующих
  тестов;
- Explore перепроверял отрицательные выводы по точным ожидаемым путям;
- одинаковые гарантии действовали для всех поддерживаемых agent adapters.

## 2. Обязательные доработки

### SDD-001 — Структурная проверка `openspec/config.yaml`

- **Приоритет:** P1
- **Статус:** `planned`
- **Область:** Qwen, GigaCode, Claude
- **Проблема:** пункт `rules.proposal`, содержащий двоеточие, разбирается YAML как
  объект. OpenSpec выводит `Rules for 'proposal' must be an array of strings` и
  игнорирует правила Proposal.

Требуется:

1. формировать все элементы `rules.<artifact>` как YAML-строки независимо от их текста;
2. добавить runtime-проверку конфигурации перед завершением `sdd init`;
3. отклонять конфигурацию, если `rules` не является объектом либо любой
   `rules.<artifact>` не является массивом непустых строк;
4. добавить unit-тест валидатора на синтетических YAML-данных и интеграционный тест
   результата `sdd init`;
5. не проверять в тестах конкретные формулировки правил.

Критерии готовности:

- `openspec instructions proposal --json` и `openspec instructions apply --json`
  выполняются без предупреждений о типе rules;
- все правила Proposal, Specs, Design и Tasks доходят до структурированного ответа
  OpenSpec;
- некорректный YAML с объектом вместо строки блокируется до начала planning.

### SDD-002 — Защита обратной совместимости на Apply

- **Приоритет:** P1
- **Статус:** `planned`
- **Область:** Qwen, GigaCode, Claude
- **Проблема:** агент может изменить публичный контракт и переписать старые тесты под
  новое поведение. Проверки останутся зелёными, хотя существующие потребители будут
  сломаны.

Требуется:

1. считать существующие публичные контракты и подтверждающие их тесты входными
   ограничениями реализации;
2. запретить изменять старые assertions только для согласования с новым несовместимым
   поведением;
3. при необходимости несовместимого изменения останавливать Apply и возвращать вопрос
   владельцу Change;
4. для совместимого расширения требовать отдельный API или сохранение прежнего вызова;
5. в итоговом отчёте Apply отдельно показывать сохранённые существующие контракты и
   добавленные сценарии.

Критерии готовности:

- прежний вызов публичного API возвращает прежний тип и значение;
- старые тесты продолжают проходить без смыслового переписывания;
- новые тесты проверяют только добавленное поведение;
- намеренное breaking change требует явного planning-решения, миграции и review.

### SDD-003 — Перепроверка отрицательных выводов Explore

- **Приоритет:** P1
- **Статус:** `planned`
- **Область:** Qwen, GigaCode, Claude
- **Проблема:** агент может ошибочно объявить ожидаемый файл или контекст
  отсутствующим после неполного поиска и использовать этот вывод при планировании.

Требуется:

1. перед утверждением об отсутствии источника проверять его точный ожидаемый путь;
2. перечислять проверенный путь и результат чтения в evidence;
3. не переносить отрицательный вывод из неудачного широкого поиска;
4. при противоречии между ожидаемой структурой Store и результатом чтения выполнять
   один адресный повтор до формирования итогового Explore;
5. применять то же правило к обязательным инструкциям Code Repository.

Критерии готовности:

- существующий context pack читается с первого прохода;
- отрицательный вывод содержит точный проверенный путь и зафиксированную ревизию;
- отсутствие файла не выводится только из результатов `grep`, `glob` или широкого
  поиска;
- ошибочный отрицательный вывод не попадает в Proposal, Specs или Design.

## 3. Повторный общий пилот

После SDD-001–SDD-003 повторить полный прогон в новом изолированном workspace.

Обязательные сценарии:

1. `sdd init` создаёт валидную конфигурацию выбранного агента;
2. `/sdd-context` изменяет только `openspec/context/` после подтверждения владельца;
3. `sdd explore` фиксирует точные пути и ревизии Store и Code Repositories;
4. Explore корректно читает существующий context pack и не создаёт ложных
   отрицательных выводов;
5. `/sdd-change` и последовательные Continue создают валидные Proposal, Specs,
   Design и Tasks;
6. OpenSpec instructions не выводят предупреждений о project rules;
7. `sdd load` выбирает только назначенные машинные task IDs и immutable Baseline;
8. независимые Apply-сессии согласуют межрепозиторный контракт;
9. старые публичные контракты и тесты остаются совместимыми;
10. новые проверки покрывают добавленное поведение;
11. component и composite проверки проходят;
12. текущий рабочий репозиторий и пользовательский OpenSpec registry возвращаются в
    исходное состояние после теста.

Пилот необходимо выполнить минимум для одного нативного адаптера и для GigaCode,
который использует перенос совместимого Qwen pack. При изменениях provider-specific
путей дополнительно выполняется прогон каждого затронутого адаптера.

```text

```

предупреждений OpenSpec, ручного исправления артефактов и нарушения существующих
публичных контрактов.
