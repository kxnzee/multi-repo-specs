**Редакция:** 1.1
**Относится к:** «Профиль Pilot Core», редакция 1.1; регламент 3.5.1 (Scale Profile)
**Документ одновременно:** план работ на пять дней · трекер подготовки · предполётный чек-лист · инструмент Go/No-Go
**Владелец:** сопровождающий обвязки (внутренняя дорожка), Spec Owner (внешняя дорожка)

**Заменяет** для целей первого пилота «План внедрения и предполётный чек-лист, ред. 3.5». Тот документ остаётся в силе для Scale Profile и не патчится.

## 0. Как пользоваться

Работы разделены на две дорожки, потому что у них разные исполнители и разные риски срыва.

| Дорожка | Кто исполняет | Чем рискует |
|---|---|---|
| **Внешняя** | Администратор хостинга, владелец нормы, администратор Zephyr | Сроком, который вам не принадлежит |
| **Внутренняя** | Один разработчик, пять дней | Объёмом работы |

**Внешняя дорожка запускается в день 0, до начала внутренней.** Если она станет критическим путём, разработка упрётся в невозможность проверить сделанное: без защиты ветки и маски тегов `sdd check --code` нечего проверять, а первый Baseline некуда создавать.

Классы: `HARD` — незакрытый пункт означает No-Go; `WAIVABLE` — старт допустим с письменным риском, владельцем и сроком; `INFO` — на решение не влияет. Одно правило запуска, оно в разделе 5.

Статус: `Not started` → `In progress` → `Done` → `Waived`.

## 1. Внешняя дорожка

Все заявки уходят в один день. Формулировки — готовые, чтобы не согласовывать по кругу.

| ID | Что запрашивается | У кого | Класс | Статус |
|---|---|---|---|---|
| В-01 | Исход по расхождениям с корпоративной нормой (I.32.2): шесть вопросов, по каждому — согласовано / отклонено / временный waiver на срок пилота | Владелец нормы | `HARD` | Not started |
| В-02 | Защита основной ветки `project-specs`: прямая запись запрещена | Администратор хостинга | `HARD` | Not started |
| В-03 | Маска защиты тегов `spec-baseline/*`: запрет перезаписи, запрет удаления, **ограничение круга лиц с правом создания** | Администратор хостинга | `HARD` | Not started |
| В-04 | Read-only credentials на remote репозиториев `ui` и `backend` для окружения разработки. **Права на свой репозиторий не ограничиваются** | Администратор хостинга | `HARD` | Not started |
| В-05 | `CODEOWNERS`: каталоги областей — владельцам, `changes/archive/**` — Spec Owner и заместителю | Администратор репозитория | `HARD` | Not started |
| В-06 | Профиль установки без команды досрочного применения дельт и без агентской архивации | Сопровождающий обвязки | `HARD` | Not started |
| В-07 | **Fixture-Change для приёмки `sdd load`**: игрушечная дельта на два требования, три Work Package (`ui`, `backend` — `implements`; `configuration` — `enables` с одним `AC-*`) | Spec Owner | `HARD` | Not started |
| В-08 | Поле `OpenSpec Scenario ID` в Zephyr | Администратор Zephyr | `WAIVABLE` | Not started |
| В-09 | Метка SDD и типы связей в трекере (I.25) | Администратор трекера | `WAIVABLE` | Not started |

**Смягчение при задержке.** В-08 и В-09 замещаются таблицей в `verification.md` со ссылками на конкретные прогоны — доказательность не теряется, теряется удобство. В-01…В-07 не замещаются ничем.

**Почему fixture готовит Spec Owner, а не разработчик.** Это содержательная работа — придумать два требования со сценариями и три пакета работ, — а не работа обвязки. Отданная разработчику, она съедает полдня из пяти. Разработчик на дне 4 только прогоняет по ней `sdd load`.

## 2. Пять дней

Слой A из внутренней дорожки вынесен: это в основном заявки (В-02…В-06), а не работа разработчика. Освободившиеся полдня отданы ручному smoke.

### День 1 — замеры и формы

| Часть | Работа | Результат | Evidence |
|---|---|---|---|
| 0,5 дня | **Ручной smoke protocol.** Четыре вопроса из IV.9: явное указание хранилища во всех нужных командах; работа пользовательской схемы с дополнительным артефактом; фактический состав установленных команд; совпадает ли результат агентской архивации с CLI. Изменение на выброс, полный цикл, наблюдение по каждому пункту | Протокол с датой, исполнителем и исходом по каждому вопросу | Файл протокола |
| 0,5 дня | **Слой B.** Схема артефактов, шаблоны планировочного и Code PR с чек-листами, образец требования в контекст-пак | Формы доступны | Шаблоны в репозитории |

**Если smoke даёт отрицательный ответ по схеме с дополнительным артефактом** — `impact-and-design.md` заводится обычным файлом без валидации схемой. Остановки пилота это не требует; требует записи в протокол.

### День 2 — контекст

| Работа | Результат | Evidence |
|---|---|---|
| Контекст-пак: старт, глоссарий, ландшафт, карта системы, реестр префиксов Scenario ID | Пять файлов, каждый не длиннее экранной страницы | Каталог `context/` |
| Файлы правил агента в `project-specs`, `ui`, `backend` | Три файла: как собирать, как тестировать, что не трогать автономно | Корни трёх репозиториев |

Проверка объёма контекста — обязательна: при превышении он отбрасывается целиком и молча (I.6).

### День 3 — подключение и чтение

| Работа | Результат | Evidence |
|---|---|---|
| `sdd setup` | Проверка версии CLI, регистрация хранилища, **подтверждение содержательного чтения требований** — числом областей и активных изменений, а не отсутствием ошибок | Вывод команды на двух машинах |
| `sdd fetch-repos` | Восемь гарантий раздела 7 профиля; список кандидатов читается из `candidate_repositories` черновика влияния; проверка чистоты клона; каталог клонов, фиксация ревизий, шаблон `read-log.md` | Вывод команды, `read-log.md` тестового прогона |

Наибольший риск пятидневки здесь: внешнее хранилище OpenSpec в статусе beta. Если день 3 не закрыт к вечеру — см. раздел 6.

### День 4 — передача требований

| Работа | Результат | Evidence |
|---|---|---|
| `sdd load <change-id>` | Определение Work Packages репозитория, приведение локальной копии к ревизии Baseline, запись `.sdd/change.yaml`, печать выжимки | Прогон в `ui`, `backend` и `configuration` по fixture (В-07) |

Две ветки поведения, обе обязательны:

- пакет `implements` — печатается выжимка требований и связанных Scenario;
- пакет `enables` — печатается условие готовности, перечень зависимых пакетов и технические критерии `AC-*`. **Сценариев нет и не должно быть** (I.16.1).

Отказывается работать, если изменение не найдено, Work Packages для репозитория нет или Baseline отсутствует. Все три — ошибка планирования.

**Это единственная команда, которая напрямую отвечает на исходную задачу.** При нехватке времени переносится что угодно, кроме неё.

### Процедура приёмки через fixture

Настоящий Baseline появляется только на первой неделе пилота, поэтому день 4 воспроизводится на подготовительном изменении:

```text
fixture-Change (В-07)
→ тестовый аннотированный тег spec-baseline/_load-fixture/v1
→ sdd load в ui, backend, configuration
→ проверка трёх карточек .sdd/change.yaml
→ каталог изменения удаляется отдельным PR (I.24.1, первые две строки)
```

**Fixture-Change не архивируется.** Архивация применяет дельты к Master Specs, то есть тестовые требования уехали бы в нормативный источник — ровно то, что I.33.6 запрещает делать в боевом репозитории. Единственный допустимый исход — отмена: дельты не применялись, следов в Master Specs нет.

**Fixture-тег удалить нельзя** — маска В-03 это запрещает, и ослаблять её ради уборки недопустимо. Тег остаётся в репозитории под зарезервированным префиксом `_` (раздел 8 профиля) и игнорируется проверками.

### День 5 — проверки и защита

| Часть | Работа | Результат |
|---|---|---|
| 0,5 дня | `sdd check --change` и `sdd check --code`: блокирующие правила 1, 4, 5 профиля. Каждое сообщение содержит что не так, где именно и что сделать. Пре-коммит-хук | Три правила блокируют фактически |
| 0,25 дня | `check --code` и карточка изменения в `configuration`: четвёртый репозиторий со своим пайплайном | Прогон в `configuration` |
| 0,25 дня | Поведенческая проверка защиты на теге `spec-baseline/_protection-test/v1`: перезапись отклонена, удаление отклонено, прямой push в основную ветку отклонён | Снимки трёх отказов |

**Резерва дня 5 больше нет.** Включение `configuration` в трассировку — правильное решение, но бесплатным оно не было: четвёртый репозиторий, вторая ветка `load`, второй fixture-прогон. Компенсация одна и она частичная: `fetch-repos` для `configuration` не нужен (раздел 7 профиля). Если день 3 или 4 съедят больше отведённого, срабатывает раздел 6.

## 3. Предполётный чек-лист

Шестнадцать `HARD`, пять `WAIVABLE`. Все — фактические условия: описанный в документе шаг выполненным не считается.

| ID | Условие | Критерий завершения | Класс | Статус |
|---|---|---|---|---|
| П-01 | Корпоративный гейт закрыт | По каждому из шести вопросов есть исход с датой и автором. Отправленное письмо без ответа разрешением не считается | `HARD` | |
| П-02 | Основная ветка защищена | Прямой push **фактически отклонён**, снимок сохранён | `HARD` | |
| П-03 | Маска тегов настроена и проверена | Перезапись и удаление тестового тега отклонены; круг создающих ограничен; тестовый тег попадает под ту же маску, что боевые | `HARD` | |
| П-04 | `CODEOWNERS` действует | Утверждение требований принадлежит владельцу области, архив — Spec Owner и заместителю | `HARD` | |
| П-05 | Опасные команды отсутствуют | Досрочное применение дельт и агентская архивация не установлены и не могут быть предложены агентом | `HARD` | |
| П-06 | Ручной smoke выполнен | Исход записан по каждому из четырёх вопросов IV.9; ни одного «не измерено» | `HARD` | |
| П-07 | `sdd setup` подтверждает чтение требований | Вывод содержит непустой список областей у каждого участника | `HARD` | |

| П-13 | Пилотная фича выбрана и проверена по границам | Межрепозиторная аддитивная; гейт I.26.1 не срабатывает; внешних зависимостей нет; оценка 3–5 дней подтверждена Tech Lead | `HARD` | |

## 4. Критический путь

```text
В-01 (корпоративный гейт) ──────────────────────────────────► старт
В-02, В-03, В-04 (защита и доступы) ──► Д5 (проверки) ──────► старт
В-07 (fixture-Change) ────────────────► Д4 (приёмка load) ──► старт
Д1 smoke ──► Д3 (setup, fetch-repos) ─► Д4 (load) ► Д5 (check) ► старт
```

**В-07 стал зависимостью дня 4.** Fixture должен быть готов к вечеру дня 3, иначе `sdd load` негде принять: настоящий Baseline появляется только на первой неделе пилота.

Две независимые цепочки, и **длиннее почти наверняка внешняя.** В-01 начинается первым действием: это единственный пункт, срок которого вам не подконтролен и который невозможно смягчить выбором простой фичи.

## 6. Что переносится при просрочке

Если день 3 или день 1 съели больше отведённого, переносится на первую неделю пилота — в этом порядке:

1. Автоматизация `sdd baseline` (первый тег создаётся вручную по разделу 8 профиля);
2. Автоматизация блокирующих правил 2 и 3 (исполняет Spec Owner по чек-листу);
3. Пре-коммит-хук (проверки остаются в пайплайне).

**Не переносится ни при каких обстоятельствах:**

- `sdd setup` с подтверждением содержательного чтения;
- `sdd fetch-repos` с восемью гарантиями;
- `sdd load`, обе ветки — `implements` и `enables`;
- фиксация ревизии в карточке изменения;
- защита основной ветки;
- проверка карточки в Code PR (правило 4).

Первые три — это и есть проверяемая гипотеза. Последние три — условие, без которого результат пилота недостоверен.

## 8. Что не входит в этот план

Финализация (третья неделя), автоматизация `sdd finalize`, репозиторий автотестов, сабагенты, агентские команды `/sdd:*`, `fetch-repos` для `configuration`.

Всё перечисленное имеет событие включения в разделе 13 профиля. Отсутствие пункта здесь означает «позже», а не «не нужно».
