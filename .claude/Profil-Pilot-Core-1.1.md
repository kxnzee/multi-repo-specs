**Редакция:** 1.1
**Относится к:** «SDD и OpenSpec: процесс, инструкция, обвязка», редакция 3.5.4 (далее — Scale Profile)
**Область действия:** первый пилот, одно изменение, одна capability, репозитории `project-specs`, `ui`, `backend`, `configuration`
**Владелец:** Spec Owner

## 0. Статус документа

**Это не регламент.** Это таблица применимости: какие пункты Scale Profile действуют в первом пилоте, какие отложены и по какому событию включаются.

Три правила, без которых профиль за месяц превратится во второй регламент:

**Правило 1. Профиль не переформулирует норму.** Каждая строка ссылается на пункт 3.5.4 и не повторяет его текст. При расхождении профиля и 3.5.4 источником нормы является 3.5.4.

**Правило 2. Отложенный пункт не отменён.** Столбец «Событие включения» обязателен для каждой отложенной строки. Строка без события — ошибка профиля, а не разрешение не делать.

**Правило 3. Профиль фиксируется в карточке состояния изменения** рядом с редакцией регламента (0.6 Scale Profile). Изменение доводится до архивации по тому профилю, при котором было утверждено планирование.

**Одно исключение из правила 1.** Раздел 7 (`fetch-repos`) добавляет то, чего в 3.5.4 нет. Это единственное место, где профиль расширяет норму, а не сужает её, и по итогам пилота оно вносится в 3.5.4 — см. раздел 13.

## 1. Границы пилота

Профиль действителен только при выполнении всех условий. Нарушение любого означает переход на Scale Profile, а не продолжение по Pilot Core.

| Условие | Почему |
|---|---|
| Ровно одно активное изменение | Вся отложенная механика (манифест, очереди, проекция) существует ради второго |
| Одна capability | Пересечения по требованиям невозможны |
| Класс — межрепозиторное аддитивное (I.10.2) | Проверяется исходная гипотеза, но без ломающих изменений |
| Гейт ИБ (I.26.1) не срабатывает | Ни ПДн, ни прав доступа, ни денег, ни изменения включённого флага, ни внешних интеграций |
| Внешних зависимостей нет (I.14.4) | Готовность смежной команды не должна блокировать пилот |
| Реализация 3–5 рабочих дней (I.33.2) | Иначе метрики измеряют размер задачи, а не процесс |
| Релизный флаг создаётся новый | Защитный критерий (I.16.2) — часть проверяемого |

**Состав репозиториев: `project-specs`, `ui`, `backend`, `configuration`.** Конфигурационный репозиторий входит в пилот полностью, а не «в объёме создания флага»: релизный флаг живёт в нём, значит он затронут по факту, получает пакет работ типа `enables` и участвует в трассировке наравне с кодовыми (I.5.3). Оставить его затронутым, но вне трассировки — худший из вариантов: защитный критерий флага (I.16.2) оказался бы обязательным и непривязанным ни к чему.

Календарный срок — 3–4 недели. Окно самостоятельности — недели 2–3.

## 2. Жизненный цикл Pilot Core

Девять шагов вместо двадцати переходов I.11. Каждый шаг — тот же по смыслу, что в Scale Profile; отличается состав артефактов, а не порядок.

```text
1. Explore и Proposal            → каркас изменения, обоснование, границы, Non-scope
2. Delta Specs                   → требования и сценарии со стабильными ID (I.7 целиком)
3. Черновик impact-and-design.md → предварительный анализ (I.14.1): candidate_repositories
4. Чтение кандидатов             → fetch-repos, ограничения или подтверждение их отсутствия
5. Закрытие impact-and-design.md → подтверждённый состав (I.14.2), контракты, развёртывание,
                                    откат, Work Packages
6. Планировочный PR и Baseline   → согласование сокращённым составом, аннотированный защищённый тег
7. Реализация                    → sdd load в каждом репозитории, Local Design, Code PR с карточкой
8. Проверка и активация          → документ проверок, защитный критерий на ИФТ, флаг, обе приёмки
9. Финализация                   → один вызов CLI внутри отдельного PR, архивация
```

**Шаги 3–5 — это две стадии I.14, а не одна.** Предварительный анализ (I.14.1) называет предполагаемые репозитории, проверка реализуемости (I.14.2) идёт читать код и подтверждает, добавляет или исключает их. Схлопывание стадий даёт круг: `fetch-repos` берёт список из раздела влияния, которого ещё нет.

**Шаг 4 не является подэтапом шага 5.** Он выделен отдельно, потому что именно он проверяет исходную гипотезу пилота, и его результат должен быть виден как самостоятельный факт.

Девять шагов вместо восьми: разделение I.14 на две стадии восстановлено. Это не удлинение процесса — обе стадии были в Scale Profile с самого начала.

## 3. Артефакты

| Артефакт | Где | В Scale Profile |
|---|---|---|
| `proposal.md` | `changes/<change-id>/` | I.13.1, без изменений |
| `specs/` (дельта) | там же | I.7, I.8 — без изменений |
| `impact-and-design.md` | там же | объединяет I.14 и I.15 в один файл; заполняется в две стадии |
| `tasks.md` (Work Packages) | там же | I.16.1, без изменений |
| `verification.md` | там же | объединяет скелет проверок (I.16.3) и документ проверок (I.22.2) |
| `state.yaml` | там же | I.23.1, сокращённый набор состояний |
| `.sdd/change.yaml` | `ui`, `backend`, `configuration` | I.17.6, без манифеста |
| `read-log.md` | `changes/<change-id>/` | **новое**, см. раздел 7 |

**Черновик `impact-and-design.md` содержит машиночитаемое поле:**

```yaml
candidate_repositories: [ui, backend, configuration]
```

`fetch-repos` читает список **только отсюда**. Из аргументов командной строки репозитории не добавляются. Если после чтения выясняется, что нужен ещё один — он дописывается в поле и команда перезапускается. Тогда перечень рассмотренных кандидатов сам становится артефактом, и на вопрос «почему не смотрели в такой-то репозиторий» есть ответ в файле, а не в памяти.

Не заводятся: `system-impact-analysis.md` и `design.md` по отдельности, `change-manifest.yaml`, `operations.yaml`, `verification-waivers.yaml` (при одном изменении исключения оформляются строкой в `verification.md` с согласующим и сроком).

**Раздел Design обязателен даже когда пуст.** Если новых межрепозиторных решений нет, он содержит ровно одну строку: «Новых межрепозиторных решений нет». Отсутствие раздела и его пустота — разные факты.

## 4. Пять блокирующих правил

Бюджет III.3 соблюдён: правил ровно пять, шестое обязано вытеснить одно из них. Все действуют с первого дня; различается исполнитель (переходный режим I.17.2).

| № | Правило | Где срабатывает | Исполнитель в пилоте | Автоматизация |
|---|---|---|---|---|
| 1 | Change структурно валиден, формат требований соблюдён | Планировочный PR | `sdd check --change` | день 5 подготовки |
| 2 | Каждый затронутый репозиторий зарегистрирован и имеет владельца | Планировочный PR | Spec Owner по чек-листу шаблона | неделя 1–2 пилота |
| 3 | Каждый затронутый репозиторий имеет Work Package: `implements` связан со Scenario, `enables` связан с `AC-*` | Планировочный PR | Spec Owner, там же | неделя 1–2 пилота |
| 4 | Code PR ссылается на существующий Baseline и верную ревизию; тег аннотированный, имя по шаблону, коммит достижим из основной ветки | Code PR | `sdd check --code` | день 5 подготовки |
| 5 | В кодовом репозитории нет собственного корня OpenSpec | Code PR | `sdd check --code` | день 5 подготовки |

**Правило 3 — это I.16.1 дословно**, а не новая норма: `implements` без сценариев — ошибка, `enables` со сценариями — ошибка, `enables`, от которого никто не зависит, — ошибка. Формулировка «репозиторий имеет Work Package и Scenario» была бы неверной: пакет `configuration` сценариев не имеет и иметь не может.

**Правила 2 и 3 срабатывают один раз на изменение**, в том же PR, где человек и так читает состав. Цена ручного режима здесь близка к нулю — поэтому автоматизируются они последними.

**Гейт финализации в пятёрку не входит.** Непокрытые сценарии и отсутствие приёмок проверяет Spec Owner (I.26): при одном изменении документ проверок читается целиком глазами, автоматизация здесь ничего не экономит.

Обход любой из пяти проверок: принцип III.16 действует полностью — глобального пропуска не существует, обход относится к одной проверке и одному запуску. Форма в пилоте упрощена: запись в журнал пилота с указанием проверки, причины и решения Spec Owner. Реестр YAML-файлов с отдельным PR — отложен.

## 6. Роли пилота

| Роль пилота | Кого закрывает в I.28 | Обязательность |
|---|---|---|
| Product Owner | Product Owner, бизнес-аналитик | Обязательно |
| Spec Owner | Spec Owner, системный аналитик, владелец capability | Обязательно |
| Заместитель Spec Owner | те же права | **Обязательно.** Без него отпуск владельца останавливает финализацию |
| Архитектор | Архитектор | Обязательно; совмещение со Spec Owner допустимо (I.28) |
| Tech Lead `ui`, Tech Lead `backend` | Tech Lead, разработчик | Обязательно, поимённо по каждому репозиторию |
| QA | QA | Обязательно |
| Release Owner | Release Owner, владелец конфигурации | Обязательно. Отвечает за пакет `enables` и карточку изменения в `configuration` |

Не назначаются в пилоте: ответственный по ИБ (гейт не срабатывает по границам раздела 1), заместитель архитектора, QA Lead как отдельная роль. **Если фича изменилась и гейт I.26.1 сработал — ответственный по ИБ назначается, а пилот переходит на Scale Profile.**

### Решения, которые не принимает агент

Действуют без изъятий на всех шагах (перенесено из плана внедрения 3.5, раздел 9; норма — I.3.5):

утверждение бизнес-требований · архитектурные решения без ревью · признание тестового покрытия достаточным · согласование исключений, включая отступление от защитного критерия · включение релизного флага в production · финализация · согласование редакционной правки · авторизация обхода · решение о масштабировании.

## 7. Чтение соседних репозиториев

Расширение профиля относительно 3.5.4. Именно этот раздел проверяет исходную гипотезу пилота; всё остальное — условия, при которых проверка осмысленна.

**Гарантии `sdd fetch-repos`** — обязательны, каждая проверяется до первого использования:

| Гарантия | Как обеспечивается |
|---|---|
| Клонируются только кандидаты из черновика влияния | Список читается из `candidate_repositories`, не из аргументов команды |
| **Удалённая запись физически невозможна** | Read-only credentials **на remote соседних репозиториев**. Свой репозиторий сохраняет обычные права: иначе агент не сможет писать код |
| Клон одноразовый и чистый | Перед чтением `git status --porcelain` пуст, иначе клон пересоздаётся |
| Локальные правки источником анализа не являются | Следствие предыдущей гарантии, проверяемое ею же |
| Изоляция по изменению | Каталог клонов принадлежит конкретному `change-id` |
| Каталог вне рабочего дерева | Либо вне его, либо в `.gitignore`. Иначе чужой репозиторий уедет в Code PR |
| Прочитанная ревизия зафиксирована | Таблица «репозиторий → ревизия → дата» в `read-log.md` |
| Результат — выжимка, а не клон | Объём ограничен: контекст при превышении отбрасывается целиком и молча (I.6) |

**Почему гарантия формулируется по remote, а не по сессии.** «В сессии нет токена на запись» невыполнимо: в своём репозитории агент обязан писать. Проверяемая формулировка — только «на соседние remotes прав записи нет».

**Настоящий риск здесь не push, а тихая правка.** Агент меняет файл в клоне соседнего репозитория и через час цитирует собственную правку как фактическое поведение системы. Проверка чистоты клона и зафиксированная ревизия закрывают это полностью; ничего сверх них не нужно.

**`configuration` в чтение не входит.** Legacy-кода с неожиданными ограничениями там нет — есть соглашения об именовании флагов, читаемые глазами один раз. Репозиторий участвует в Work Packages, карточке изменения и трассировке, но не в `fetch-repos`.

**Результат чтения по каждому репозиторию** записывается в `read-log.md` в одной из двух форм:

```text
<репозиторий> @ <ревизия>, <дата>
Найденные ограничения:
  — <ограничение>, файл:строка
ЛИБО
  Новых ограничений не обнаружено.
```

Утверждение без ссылки «файл:строка» удаляется (III.14). **Ноль найденных ограничений — допустимый и осмысленный результат**, он означает, что постановка была верна. Критерия «найти не менее N» не существует и вводить его нельзя: он награждает за производство текста.

## 8. Baseline в переходном режиме

Тег создаётся вручную одной командой. Машиной проверяются три условия (входят в блокирующее правило 4):

- объект тега аннотированный, а не коммит;
- имя соответствует шаблону `spec-baseline/<change-id>/v<N>`;
- коммит тега достижим из основной ветки.

Человеком проверяются два:

- тег указывает на merge commit **планировочного** PR;
- имя тега и ревизия записаны в карточку состояния изменения.

**Защита проверяется до создания первого настоящего Baseline** и только на тестовом теге:

```text
spec-baseline/_protection-test/v1
```

Условие осмысленности проверки: тестовый тег обязан попадать под **ту же маску защиты**, что и боевые. Если правило перечисляет конкретные имена, а не маску `spec-baseline/*`, проверка не доказывает ничего и правило переделывается.

Маска ограничивает три вещи, а не две: перезапись, удаление и **круг лиц с правом создания** (I.17.4). Без третьего «тег создаёт Spec Owner» остаётся соглашением, а в ручном режиме соглашения не наблюдаемы.

Попытки удаления или перезаписи реального Baseline пилотного изменения запрещены при любых обстоятельствах.

### Служебное пространство имён

Маска защищает от удаления и служебные теги тоже — значит `_protection-test` и fixture-тег (раздел 3 плана подготовки) останутся в репозитории навсегда. Вырезать для них исключение из маски нельзя: это ослабило бы ровно то свойство, которое проверка и доказывает.

**Поэтому префикс `_` в пространстве Baseline зарезервирован:**

```text
spec-baseline/_<назначение>/v<N>
```

Имя, начинающееся с `_`, **никогда не обозначает настоящий Baseline**. Такой тег несёт это в аннотации, остаётся в репозитории и игнорируется всеми проверками и отчётами. Два лишних тега — приемлемая цена за неослабленную защиту.

Имя изменения по I.7.1 — нижний регистр kebab-case, с `_` не начинается, поэтому пересечение исключено конструктивно.

## 9. Финализация в переходном режиме

Координация ручная, редактирование Master Specs — нет.

```text
Подтягивается основная ветка (I.21.3.3)
→ Spec Owner открывает PR финализации
→ человек проверяет документ проверок и обе приёмки (гейт I.22.4)
→ применение дельт и архивация выполняются ОДНИМ вызовом CLI
→ ревьюер проверяет дифф
→ PR сливается
```

**Ревьюер подтверждает, что в диффе нет ничего, кроме** изменений мастер-спек затронутой области и переноса каталога изменения в архив. Это единственная проверка, ловящая реальный сценарий порчи — руками поправленную мастер-спеку внутри якобы автоматической операции.

Флаги, отключающие валидацию, не используются. Отката нет: откат — это откат коммита финализации.

## 10. Метрики

Собираются с первого дня, задним числом не восстанавливаются.

| Метрика | На какой вопрос отвечает |
|---|---|
| Число ручных пересылок требований мимо harness | Работает ли передача требований |
| Число репозиториев, добавленных или исключённых после чтения | Даёт ли чтение соседних репозиториев результат |
| Число предположений влияния, подтверждённых и опровергнутых чтением | То же, с другой стороны |
| Время, разложенное на: настройка платформы · обучение · работа над Change · ожидание согласований | Где именно уходит время первой задачи |
| Активное время Proposal → Baseline против времени реализации | Окупаемость. Порог применяется со второго изменения |
| Число обходов по каждой проверке, с причиной | Какая проверка врёт |
| Число обращений к автору процесса за окно самостоятельности | Исполнимость без автора |
| Число отказов валидации и их причины | Что дописать в I.7 |

## 11. Критерии успеха

| # | Критерий |
|---|---|
| 1 | Число ручных пересылок требований и Work Packages мимо harness — **ноль** |
| 2 | Ни один PR в `ui`, `backend`, `configuration` не слит без карточки, указывающей на существующий Baseline |
| 3 | Ни один разработчик и ни один агент не написал код против устаревшей ревизии требований незамеченно |
| 4 | Все кандидаты, кроме `configuration`, прочитаны через `fetch-repos`; по каждому записаны ограничения либо подтверждение их отсутствия; ревизии зафиксированы |
| 5 | Изменение прошло цикл до архивации; Master Specs после финализации соответствуют проду |
| 6 | Защитный критерий релизного флага получил `Verified` до развёртывания в production |
| 7 | Финализация выполнена одним вызовом CLI; дифф содержит только мастер-спеки и перенос в архив |

Критерии 1–4 проверяют исходную гипотезу, 5–7 — целостность процесса. Успехом считается выполнение всех семи.

## 12. Условия остановки

Пилот признаётся неудачным, если выполнено хотя бы одно:

- изменение не дошло до архивации за объявленный срок, и причина в процессе, а не во внешних обстоятельствах;
- больше половины календарного времени ушло в ожидание согласований;
- понадобилось больше двух правок, меняющих **шаги**, а не формулировки;
- за окно самостоятельности группа обошла процесс больше чем в половине случаев.

**Отношение «планирование против реализации» условием остановки не является.** Первая задача включает обучение и настройку, и коэффициент по одному наблюдению статистически ничего не показывает. Он остаётся метрикой; сигналом становится устойчивое превышение начиная со второго изменения.

Неудача означает возврат к конкретному пункту, а не отказ от подхода.
