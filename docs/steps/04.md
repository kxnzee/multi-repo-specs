## 04. Planning PR и фиксация Spec Baseline

> Статус: шаг зафиксирован на штатных командах OpenSpec и обычном Git PR; отдельные команды SDD не требуются.

Если вам нужно только пройти шаг 04, достаточно раздела «Пользовательская инструкция». Техническая спецификация ниже предназначена для ревью процесса.

### Пользовательская инструкция

#### 1. Проверьте вход

Перед продолжением должны выполняться условия шага 03:

- существует ровно один активный Change с каноническим `change-id`;
- Change находится только в центральном Store и использует схему `spec-driven`;
- текущая ветка Store имеет имя `feature/<change-id>`;
- Proposal, Delta Specs, Design и Tasks имеют официальный статус `done`;
- изменения planning-ветки ограничены текущим Change;
- кодовые ветки, реализация и Archive ещё не начинались.

Статус OpenSpec `done` означает только то, что planning-артефакт создан и завершён. Он не означает, что Work Packages выполнены или код уже реализован. Задачи в `tasks.md` на этом этапе остаются невыполненными.

Planning PR рассматривает Proposal, Specs, Design и Tasks одним набором. Для отдельных planning-артефактов не создаются отдельные PR и последовательные человеческие гейты.

#### 2. Проверьте полный Change

Из planning-ветки центрального Store выполните штатные команды:

```bash
openspec status \
  --change <change-id> \
  --store <store-id> \
  --json

openspec show <change-id> \
  --type change \
  --no-interactive \
  --store <store-id> \
  --json

openspec validate <change-id> \
  --type change \
  --strict \
  --no-interactive \
  --store <store-id> \
  --json

git diff --check
git status --short
```

Проверки должны подтвердить:

- `status` относится к тому же Store и Change;
- `proposal`, `specs`, `design` и `tasks` имеют статус `done`;
- `show` успешно читает тот же Change;
- строгая `validate` возвращает единственный успешный результат `type: change`;
- Git не обнаруживает whitespace errors;
- изменённые пути находятся только внутри `openspec/changes/<change-id>/`.

OpenSpec `validate` проверяет структуру и содержание Delta Specs, но не заменяет содержательное ревью Proposal, Design и Tasks. В частности, он не гарантирует, что каждый Work Package представлен отдельным стандартным checkbox с числовым ID вида `1.1` и явной целью. Change Owner проверяет это по diff `tasks.md`, а применимые владельцы подтверждают в Planning PR; пакет без ID или цели блокирует merge.

#### 3. Синхронизируйте, зафиксируйте и опубликуйте planning-ветку

Перед синхронизацией рабочее дерево должно быть чистым: все подготовленные изменения текущего Change уже находятся в локальном commit, а посторонних изменений нет. Шаг не выполняет автоматический `stash` и не пытается сохранить несвязанные файлы.

Добавьте только текущий Change и создайте локальный commit:

```bash
git add -- openspec/changes/<change-id>
git commit -m "<change-id> <что сделано>"
```

Пример:

```bash
git commit -m "pay-412-payment-status Добавлены planning-артефакты"
```

Затем синхронизируйте planning-ветку с актуальной основной веткой через rebase — так же, как остальные feature-ветки проекта:

```bash
git fetch origin <default-branch>
git rebase origin/<default-branch>
git diff --check origin/<default-branch>...HEAD
git diff --name-only origin/<default-branch>...HEAD
```

При конфликте Change Owner:

1. проверяет конфликтующие пути через `git status --short`;
2. разрешает только понятные конфликты, не выбирая автоматически целиком одну из сторон;
3. добавляет разрешённые файлы командой `git add -- <path>` и продолжает `git rebase --continue`;
4. если корректное объединение неочевидно, выполняет `git rebase --abort` и останавливает публикацию до уточнения у владельца затронутой части.

После успешного rebase повторите команды `openspec status`, `openspec show`, строгий `openspec validate` и Git-проверки из раздела 2. Если основная ветка изменила относящиеся к Change Master Specs, context или другой активный Change, актуализируйте зависимые planning-артефакты через `/opsx-update <change-id>`, повторите проверки и зафиксируйте согласование отдельным commit. Новая внешняя система или изменение подтверждённого бизнесового scope возвращает процесс в Explore.

При первой публикации используйте обычный push:

```bash
git push -u origin feature/<change-id>
```

Если ветка уже опубликована и Planning PR открыт, rebase меняет SHA её commit. После повторных проверок обновите только свою planning-ветку безопасным push:

```bash
git push --force-with-lease origin feature/<change-id>
```

Обычный `--force` запрещён. `--force-with-lease` не заменяет проверку: если удалённая ветка изменилась после последнего `fetch`, push должен остановиться, а Change Owner сначала выясняет источник новых commit. После переписывания SHA прежние approvals и результаты валидации считаются устаревшими; Change Owner публикует новый результат проверки и повторно запрашивает применимых reviewers в том же PR.

#### 4. Откройте единый Planning PR

Откройте PR из `feature/<change-id>` в основную ветку центрального Store штатным интерфейсом Git-провайдера.

В PR должны быть доступны:

- исходный ticket и `change-id`;
- полный diff Proposal, Delta Specs, Design и Tasks;
- результат последнего строгого `openspec validate`;
- затронутые `repository-id` и внешние системы из Design;
- известные неблокирующие вопросы и риски.

Владельцы работают только через PR: читают diff, оставляют inline comments, создают review threads и подтверждают принадлежащие им части. Им не требуется отдельно открывать рабочее дерево Store или запускать команды SDD.

| Роль | Что подтверждает в Planning PR |
|---|---|
| Change Owner | Проблему, ожидаемое поведение, scope и полноту бизнесовых сценариев |
| Spec Owner | Корректность Delta Specs, целостность Change и соответствие Master Specs |
| Technical Owner | Межсистемный Design, impact по репозиториям, совместимость, rollout и Work Packages |
| QA | Проверяемость Scenarios, quality gates и план Composite Verification |
| Security Owner | Security/compliance-часть только при соответствующем impact |
| Apply Owner затронутого репозитория | Выполнимость назначенного Work Package без переноса локального implementation plan в Store |

Применимые владельцы определяются содержанием Change, CODEOWNERS и правилами проекта. Отсутствующая роль не создаёт формальное подтверждение от имени несуществующего владельца: Change Owner запрашивает нужного участника адресно.

#### 5. Исправьте замечания в том же PR

По умолчанию замечания к planning-артефактам исправляются агентом через официальную команду OpenSpec. Change Owner запускает агента из checkout центрального Store на ветке `feature/<change-id>` и передаёт ему точный список незакрытых замечаний:

```text
/opsx-update <change-id>

Исправь только следующие unresolved comments Planning PR <planning-pr>:
- <thread или file:line>: <точный текст замечания>
- <thread или file:line>: <точный текст замечания>

Работай с Store <store-id>. Согласуй между собой все уже существующие
planning-артефакты Change. Не создавай код, новые артефакты, Apply или Archive.
```

Если агент не имеет доступа к интерфейсу Git-провайдера, Change Owner копирует в запрос точный текст unresolved comments и их ссылки или `file:line`; пересказ замечаний агентом не допускается. `/opsx-update` перечитывает существующие Proposal, Specs, Design и Tasks, предлагает согласованные изменения по артефактам и запрашивает подтверждение перед записью. Команда не закрывает review threads, не создаёт commit, не выполняет push и не подтверждает PR от имени владельцев.

До merge используется один цикл исправлений:

1. владелец создаёт review comment или блокирующий thread в Planning PR;
2. Change Owner передаёт точное замечание агенту через `/opsx-update <change-id>` и подтверждает предложенное исправление;
3. Change Owner повторяет `openspec status`, `openspec show`, строгий `openspec validate` и Git-проверки;
4. исправление фиксируется новым commit вида `<change-id> <что сделано>`;
5. обычный `git push` обновляет тот же Planning PR;
6. автор замечания повторно проверяет изменённый блок и закрывает thread;
7. merge остаётся заблокирован, пока применимые владельцы и правила Git-провайдера не разрешат его.

Пример corrective commit:

```bash
git commit -m "pay-412-payment-status Уточнены бизнес-сценарии"
```

Простую опечатку Change Owner может исправить вручную, но после этого выполняет те же полные проверки. Содержательные замечания по умолчанию проходят через `/opsx-update`, чтобы связанные артефакты не разошлись.

Исправления не маскируются через amend или squash уже опубликованных review-fix commit. Исключение — rebase на актуальную основную ветку по правилам раздела 3: после него разрешён только `--force-with-lease`, повторная валидация и повторный запрос review.

Если замечание не меняет подтверждённый бизнесовый scope, оно исправляется в текущем Change. Новая внешняя система, изменение наблюдаемого поведения или факт, отменяющий подтверждённый Explore, останавливает Planning PR и возвращает процесс в Explore. Единый бизнесовый Change не разделяется на дополнительные фичи без отдельного бизнесового решения.

Если ошибка найдена после merge, но шаг 05 ещё не начался:

1. Change Owner обновляет локальную основную ветку и создаёт `fix/<change-id>-planning`:

   ```bash
   git switch <default-branch>
   git pull --ff-only origin <default-branch>
   git switch -c fix/<change-id>-planning
   ```

2. запускает `/opsx-update <change-id>` с точным описанием дефекта и ссылкой на принятый Planning PR;
3. повторяет полный набор OpenSpec- и Git-проверок;
4. создаёт corrective commit, публикует ветку и открывает correction PR;
5. те же применимые владельцы проверяют изменённые части;
6. после merge полная SHA correction PR становится окончательным Spec Baseline;
7. если implementation subtasks уже созданы, Change Owner обновляет в них `spec_baseline` и добавляет `correction_pr` до назначения работы разработчикам.

Прежняя SHA в этом случае была только кандидатом и не передаётся в реализацию.

Если шаг 05 уже начался на прежнем Baseline, Change Owner не меняет его молча: приостанавливает затронутые Work Packages, определяет затронутые Code Repositories, проводит correction PR с повторными approvals, фиксирует прежнюю и новую SHA и обновляет каждую затронутую implementation subtask. Продолжение разрешает Apply Owner соответствующего репозитория после явного подтверждения новой SHA. Полный процесс amendment Baseline проектируется вместе с шагом 05; обычным review-fix шага 04 он не является.

Отмена уже принятого Planning PR выполняется отдельным revert PR. До отката Change Owner останавливает или закрывает ещё не завершённые implementation subtasks и связанные implementation PR, если они уже появились. Change не удаляется вручную и не архивируется вместо отката; отменённые subtasks сохраняют ссылку на revert PR.

#### 6. Слейте Planning PR и зафиксируйте Spec Baseline

Merge разрешён, когда:

- последняя строгая OpenSpec-валидация успешна для опубликованного HEAD planning-ветки;
- все применимые владельцы подтвердили свои части через Planning PR;
- блокирующие review threads закрыты;
- каждый Work Package представлен отдельным стандартным checkbox `tasks.md`, имеет уникальный внутри Change числовой ID вида `1.1` и цель `store`, конкретный `repository-id` либо `composite-verification`;
- diff PR ограничен текущим Change;
- правила Git-провайдера разрешили merge.

**Spec Baseline** — полная Git SHA ревизии центрального Store, получившей принятый planning-набор после merge Planning PR. Все Code Repositories на следующих шагах используют именно эту ревизию требований, даже если основная ветка Store позже изменится.

Получите точную принятую SHA из результата merge в Git-провайдере. Это должна быть итоговая merge-, squash- или rebase-ревизия в основной ветке, а не прежний commit исходной feature-ветки.

```text
change_id: pay-412-payment-status
spec_baseline: <accepted-40-character-revision>
```

Git commit SHA уже является неизменяемой ссылкой на состояние Store. Отдельный tag, state-файл или команда `sdd baseline` не создаются. Связь PR с принятой ревизией хранится Git-провайдером, а точная SHA передаётся шагу 05 вместе с `change-id`.

Если после merge в основную ветку попали другие изменения, Baseline не сдвигается на новый HEAD: он остаётся SHA, которую Git-провайдер зафиксировал как результат принятия Planning PR.

#### 7. Передайте реализацию командам Code Repositories

После фиксации Spec Baseline Change Owner создаёт в исходной Story по одной implementation subtask на каждый окончательно затронутый `repository-id` из Design и Tasks. Это техническое распределение одного Change, а не разбиение бизнесовой фичи на несколько Stories или OpenSpec Changes.

Название subtask:

```text
<change-id> <repository-id> Реализация
```

Описание не копирует Proposal, Specs, Design, Tasks или локальный план реализации. Оно содержит только параметры, ведущие к принятой спецификации и назначенным Work Packages:

```yaml
parent_ticket: PAY-412
change_id: pay-412-payment-status
store_id: payments-specs
spec_path: openspec/changes/pay-412-payment-status
spec_baseline: <accepted-40-character-revision>
planning_pr: <provider-pr-reference>
repository_id: payments-api
work_packages:
  - "2.1"
  - "2.2"
```

Если до начала реализации был принят correction PR, рядом добавляется `correction_pr: <provider-pr-reference>`, а `spec_baseline` указывает уже на его итоговую SHA. Числовые ID в `work_packages` берутся из принятых checkbox `tasks.md`; после Planning PR существующие ID не перенумеровываются, а новый пакет получает новый ID. Текст пакетов в ticket не дублируется. Разработчик открывает центральный Store на указанной SHA и получает нормативные требования, межсистемный Design и свои Work Packages из одного источника истины. На шаге 04 не создаются ветки Code Repositories и не запускается реализация.

Создание subtasks выполняется Change Owner через штатный интерфейс Jira/SberTrack. Интеграция с Jira API и новая команда SDD не вводятся.

> **Открытое решение по QA-subtask.** Нужна ли отдельная subtask для тестирования и Composite Verification, будет определено после консультации с QA. До этого решения шаг 04 не создаёт её автоматически и не требует её как гейт. QA-работа остаётся в принятом `tasks.md` и в области будущего шага 07; неопределённость не блокирует создание implementation subtasks по Code Repositories.

#### 8. Завершите шаг

Шаг 04 завершён, когда:

- единый Planning PR слит в основную ветку центрального Store;
- применимые владельцы подтвердили свои части через PR;
- строгая OpenSpec-валидация успешна;
- известны `change-id` и полная `spec_baseline` принятого PR;
- в исходной Story создана одна implementation subtask на каждый затронутый Code Repository с параметрами принятого Change;
- Code Repositories, Master Specs и Archive не изменялись.

После этого можно переходить к шагу 05 — подготовке реализации на одном Spec Baseline. `/opsx-apply`, `/sdd-apply` и Archive на шаге 04 не запускаются.

## Техническая спецификация шага 04

Шаг использует только существующие границы OpenSpec и Git:

```text
OpenSpec status/show/validate
        ↓
commit + push planning-ветки
        ↓
Planning PR: comments + approvals + merge
        ↓
Spec Baseline = принятая Git SHA Store
        ↓
implementation subtasks: одна на repository-id
```

Собственная команда SDD, provider-specific PR API, tag Baseline и постоянный state-файл не вводятся.

### Источники истины

- содержимое планирования — `openspec/changes/<change-id>/**` центрального Store;
- машинный статус артефактов — официальный `openspec status`;
- структурированное представление Change — официальный `openspec show`;
- формальная проверка Delta Specs — официальный строгий `openspec validate`;
- содержательное подтверждение — review и approvals единого Planning PR;
- Spec Baseline — точная принятая Git SHA основной ветки Store.

Ни один из источников не подменяет остальные. `done` не доказывает реализацию, `validate` не подтверждает архитектурное решение, а merge без требуемых approvals нарушает процесс даже при корректном Git commit.

### Контракт Planning PR

Planning PR содержит изменения только текущего Change. Изменения Master Specs, project config, context pack, другого активного Change или Code Repositories должны быть вынесены в соответствующий отдельный процесс и не маскироваться внутри PR фичи.

PR является единственным человеческим гейтом после принятого Proposal и до начала реализации. Все применимые владельцы работают с одним diff. Подтверждение отдельного файла вне PR не считается заменой review.

Git-провайдер отвечает за:

- представление полного diff;
- inline comments и review threads;
- requested reviewers и CODEOWNERS;
- approvals и branch protection;
- историю corrective commit;
- merge и связь принятого PR с итоговой SHA.

Проектный процесс отвечает за назначение применимых ролей и запрет merge до снятия блокирующих замечаний. Если основная ветка не защищена технически, соблюдение гейта остаётся организационной обязанностью Change Owner и Spec Owner.

### Проверка и повторный запуск

Штатные OpenSpec-команды выполняются перед первым push и после каждого содержательного исправления. Ошибка любой команды блокирует новый commit или обновление PR до устранения причины.

`openspec status` должен вернуть тот же Store, Change, schema `spec-driven`, `isComplete: true` и четыре статуса `done`. `openspec show` должен успешно прочитать тот же активный Change. Строгий `openspec validate` должен вернуть один `valid: true` для `type: change` без validation issues.

Стандартные checkbox и числовые ID вида `1.1` сохраняют штатный формат `tasks.md`; запрет перенумерации после Planning PR и обязательная цель Work Package являются содержательным контрактом проекта, а не частью стандартной OpenSpec schema. Отдельный SDD-валидатор и собственный формат `tasks.md` на этом шаге не вводятся. Их соблюдение проверяется Change Owner и владельцами репозиториев в едином Planning PR; нарушение блокирует merge даже при `valid: true`.

Git diff проверяется относительно основной ветки и ограничивается `openspec/changes/<change-id>/`. PR-провайдер остаётся финальным представлением фактически публикуемого diff.

### Исправление и откат

До merge все исправления добавляются в ту же planning-ветку новыми commit. Другой Planning PR и другой Change не создаются, пока бизнесовый scope остаётся прежним. Review threads закрывает их автор либо назначенный владелец после повторной проверки.

Correction PR после merge допустим без amendment-гейта только до начала шага 05. Его итоговая принятая SHA заменяет ещё не использованный кандидат Baseline, а уже созданные subtasks обновляются до назначения работы. После начала шага 05 ранее переданная SHA считается зафиксированной; её изменение требует остановки затронутых Work Packages, нового согласования и подтверждения Apply Owners.

Revert PR отменяет принятый planning-набор на уровне Git. Он не равен Archive: Master Specs не обновляются, а Change не объявляется реализованным.

### Контракт Spec Baseline

Baseline идентифицируется парой:

```text
change-id + accepted Store commit SHA
```

Шаг 05 обязан принимать оба значения и проверять, что указанная ревизия существует в истории основной ветки Store и содержит активный Change. Текущий HEAD, имя planning-ветки, номер PR или пересказ агента не заменяют точную SHA.

Дополнительный Git tag не требуется: он дублировал бы commit SHA, вводил права на публикацию и отдельный жизненный цикл mutable ref. Если пилот покажет, что поиск merge SHA по PR создаёт устойчивую операционную проблему, provider-neutral alias можно рассмотреть отдельно, не меняя определение Baseline.

### Разрешённые записи

До merge пользователь изменяет только:

```text
openspec/changes/<change-id>/**
refs/heads/feature/<change-id>
```

Для correction PR после merge та же область Change изменяется в `refs/heads/fix/<change-id>-planning`. Другие активные Changes и Master Specs в correction-ветку не добавляются.

Merge записывает принятый Change в основную ветку Store штатным действием Git-провайдера. После merge Change Owner создаёт только parameter-only implementation subtasks в исходной Story. Шаг не создаёт SDD metadata, Git tags, Code Repository branches, implementation plans, progress/evidence и не изменяет Master Specs.

### Результат и переход к шагу 05

Выход шага:

```text
step_status: planning_accepted
store_id: <store-id>
change_id: <change-id>
planning_pr: <provider-pr-reference>
spec_baseline: <accepted-40-character-revision>
implementation_subtasks:
  <repository-id>: <tracker-subtask-reference>
qa_subtask: pending_decision
next_step: 05
```

Этот результат является handoff процесса, а не новым файлом в Store. Постоянными доказательствами остаются merged PR и Git commit центрального репозитория.
