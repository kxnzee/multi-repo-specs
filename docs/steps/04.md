## 04. Planning PR и передача работы разработчикам

На этом шаге Proposal, Specs, Design и Tasks проверяются одним набором. После слияния PR его принятая Git SHA становится Spec Baseline для всех Code Repositories.

### 1. Проверьте Change

Из planning-ветки центрального Store выполните:

```bash
openspec status \
  --change <change-id> \
  --store <store-id>

openspec show <change-id> \
  --type change \
  --no-interactive \
  --store <store-id>

openspec validate <change-id> \
  --type change \
  --strict \
  --no-interactive \
  --store <store-id>
```

| Команда | Успешно | Если результат другой |
|---|---|---|
| `openspec status` | Показаны ожидаемые Store и Change, все четыре артефакта завершены | Вернитесь к шагу 03 и завершите Change |
| `openspec show` | Показан ожидаемый Change без ошибки | Проверьте `change-id`, Store и файлы Change |
| `openspec validate --strict` | `Change '<change-id>' is valid` | Передайте ошибки агенту через `/opsx-update <change-id>`, затем повторите проверки |

`ExperimentalWarning` Node.js можно игнорировать, если команда завершилась успешно.

### 2. Создайте commit и опубликуйте ветку

Добавьте только текущий Change:

```bash
git status --short
git add -- openspec/changes/<change-id>
git diff --cached --check
git diff --cached --name-only
```

`git diff --cached --check` не должен выводить ошибок, а `git diff --cached --name-only` должен показывать только файлы текущего Change.

Создайте commit:

```bash
git commit -m "<change-id> Добавлены planning-артефакты"
```

Синхронизируйте ветку с основной веткой Store:

```bash
git fetch origin <default-branch>
git rebase origin/<default-branch>
```

После rebase повторите OpenSpec-проверки из раздела 1 и выполните:

```bash
git diff --check origin/<default-branch>...HEAD
git diff --name-only origin/<default-branch>...HEAD
git status --short --branch
```

Опубликуйте ветку:

```bash
git push -u origin feature/<change-id>
```

Если опубликованная ветка была перебазирована, используйте только:

```bash
git push --force-with-lease origin feature/<change-id>
```

### 3. Откройте Planning PR

Откройте один PR в основную ветку центрального Store. Добавьте в описание:

- ticket и `change-id`;
- результат `openspec validate --strict`;
- затронутые репозитории и внешние системы;
- известные вопросы и риски.

Change Owner, Spec Owner, Technical Owner, QA и другие применимые владельцы проверяют свои части в этом PR.

### 4. Исправьте замечания

Передавайте агенту только точные незакрытые замечания:

```text
/opsx-update <change-id>

Исправь только следующие unresolved comments Planning PR <planning-pr>:
- <thread или file:line>: <точный текст замечания>

Работай с Store <store-id>. Не создавай код, Apply или Archive.
```

После исправлений:

1. повторите OpenSpec- и Git-проверки;
2. создайте новый commit;
3. выполните обычный `git push`;
4. попросите автора замечания повторно проверить изменение.

Если замечание меняет согласованное поведение или добавляет внешнюю систему, остановите PR и вернитесь к Explore.

### 5. Слейте PR и зафиксируйте Baseline

Сливайте Planning PR только после успешной валидации, закрытия блокирующих замечаний и необходимых approvals.

После merge сохраните полную 40-символьную SHA принятой ревизии основной ветки Store:

```text
change_id: <change-id>
spec_baseline: <accepted-40-character-revision>
```

Используйте SHA результата merge, squash или rebase в основной ветке, а не SHA прежней feature-ветки.

### 6. Создайте implementation subtasks

Получите список Work Package ID на принятом Baseline:

```bash
openspec instructions apply \
  --change <change-id> \
  --store <store-id> \
  --json
```

Для удобного отображения при наличии `jq`:

```bash
openspec instructions apply \
  --change <change-id> \
  --store <store-id> \
  --json |
jq -r '.tasks[] | "\(.id)\t\(.description)"'
```

Создайте в исходной Story одну subtask на каждый затронутый Code Repository:

```text
<change-id> <repository-id> Реализация
```

Описание subtask:

```yaml
parent_ticket: PAY-412
change_id: pay-412-payment-status
store_id: payments-specs
spec_baseline: <accepted-40-character-revision>
planning_pr: <planning-pr-reference>
repository_id: payments-api
work_packages:
  - "1"
  - "2"
```

В каждой subtask должен быть один `repository_id` и только относящиеся к нему Work Package ID. Не копируйте в subtask Proposal, Specs, Design или текст Tasks. Отдельная QA-subtask в первом пилоте не требуется.

Если planning-документация меняется после merge, не обновляйте Baseline или Work Package ID вручную во время реализации: остановите передачу работы и согласуйте correction PR с Change Owner.

### Успешный результат

Переходите к [шагу 05](05.md), когда:

- Planning PR слит;
- известна полная `spec_baseline`;
- на каждый затронутый Code Repository создана implementation subtask;
- реализация ещё не начиналась.
