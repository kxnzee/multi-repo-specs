## 01. Запрос, предпроверка и Explore

Шаг выполняется для каждого запроса, запущенного во внешнем процессе с Jira ticket key после принятого шага 00. Его задача — проверить исходный запрос, при необходимости подготовить свежий read-only workspace выбранных Code Repositories и исследовать проблему до появления обязательств по реализации.

На этом шаге OpenSpec Change ещё не существует. Команды не создают `openspec/changes/<change-id>/`, `state.yaml`, планировочные артефакты, ветку или PR, не изменяют код, Master Specs и нормативный context pack. Первое постоянное состояние процесса появляется на шаге 02.

### Владелец

Change Owner отвечает за формулировку проблемы, ожидаемый результат, исходный выбор репозиториев и решение о продолжении SDD-процесса. Агент собирает и сопоставляет факты, но не создаёт Change и не принимает решение вместо Change Owner.

Technical Owner и Spec Owner не являются обязательными участниками шага 01. Change Owner обращается к ним адресно только при блокирующем техническом вопросе. Spec Owner подключается к созданию Change на шаге 02; формальное ревью содержания и подтверждение Technical Owner начинаются на шаге 03.

### Вход

- initialization PR шага 00 слит, а Spec Owner разрешил принимать рабочие запросы;
- инициатор передал постоянный Jira key вида `PAY-412` как внешний идентификатор запуска работы;
- Change Owner передал агенту формулировку проблемы и ожидаемый результат без обязательства реализовать заранее выбранное решение;
- назначены Change Owner и инициатор;
- в `sdd.yaml` зарегистрирован `project-specs`, а предполагаемые Code Repositories добавлены, если они уже известны;
- read-only credential для выбранных Git-репозиториев настроен вне Git, если Explore требует чтения кода;
- OpenSpec `1.7.0` доступен как команда `openspec`.

Первая реализация не интегрируется с Jira API и не проверяет существование или статус задачи по сети. SDD синтаксически проверяет ticket key и далее использует его только как внешний идентификатор. Git credential и другие секреты не записываются в `sdd.yaml`, временный workspace, логи или Git.

### Команды

Из Spec Root Repository или любого его вложенного каталога пользователь запускает:

```bash
sdd explore --ticket <ticket-id>
```

После успешной подготовки в Qwen Code из того же Spec Root запускается:

```text
/opsx-explore <ticket-id>
```

| Команда | Что делает | Результат |
|---|---|---|
| `sdd explore --ticket ...` | Проверяет среду, ticket key и дубликаты, предлагает выбрать Code Repositories и при необходимости атомарно готовит их свежие checkout | Read-only workspace и команда следующего действия |
| `/opsx-explore <ticket-id>` | Читает запрос, нормативные источники и подготовленный код, исследует текущее поведение, альтернативы и неизвестные | Структурированный итог для решения Change Owner |

### Предпроверка Spec Root и agent action

`sdd explore` находит ближайший родительский каталог, в котором одновременно существуют `sdd.yaml`, `openspec/config.yaml`, `openspec/context/00-start-here.md` и `openspec/context/system-map.yaml`. Если Spec Root определить нельзя, команда прекращает работу и не использует соседние репозитории по догадке.

До загрузки кода CLI проверяет:

- OpenSpec имеет ожидаемую версию `1.7.0`;
- `openspec list --specs --json` выполняется из найденного Spec Root;
- для Qwen Code установлено управляемое действие `.qwen/commands/opsx-explore.md`;
- временный корень `.sdd/checkouts/explore/` не является symlink;
- `sdd.yaml` содержит корректную запись `project-specs`; наличие других Code Repositories не обязательно.

Управляемое `/opsx-explore` использует исследовательскую модель OpenSpec, но дополняет её обязательными границами этого процесса: оно читает workspace конкретного ticket, не создаёт OpenSpec-артефакты и всегда возвращает структурированный итог. Совместимая версия action входит в поставку адаптера `sdd`; отсутствие файла считается ошибкой подготовки среды.

### Проверка ticket key и существующих Changes

CLI принимает только key формата `<PROJECT>-<number>` в верхнем регистре и использует его без преобразования как процессный идентификатор. Корректный формат не доказывает существование задачи; её состояние во внешнем трекере находится вне ответственности SDD.

До внешних Git-вызовов команда проверяет `ticket` в `state.yaml` существующих Changes:

- активный Change с тем же ticket блокирует новый Explore и показывается пользователю;
- архивный Change с тем же ticket показывается как предупреждение и требует явного подтверждения Change Owner в интерактивном запуске; в non-TTY команда завершается ошибкой;
- нечитаемый или невалидный `state.yaml`, из-за которого нельзя надёжно исключить дубликат, блокирует Explore с указанием проблемного Change;
- похожая цель с другим ticket определяется агентом во время Explore, а не эвристикой CLI.

### Выбор репозиториев

Команда показывает checklist всех Code Repositories из `sdd.yaml`. `project-specs` в checklist не включается, потому что он всегда доступен действию как нормативный источник из текущего Spec Root.

Change Owner может выбрать один или несколько Code Repositories либо явно подтвердить пустой набор для Explore только по `project-specs`. Автоматически выбирать все репозитории или требовать хотя бы один Code Repository запрещено.

Первая реализация не предоставляет флаг обхода checklist. Если stdin не является TTY, команда завершается ошибкой.

Выбранный набор, включая пустой, является исходной областью исследования, а не окончательным system impact. Если агент обнаружил необходимость прочитать код зарегистрированного репозитория, Change Owner повторяет `sdd explore`, выбирает полный расширенный набор и заново запускает `/opsx-explore`. Нерегистрированный репозиторий, без которого исследование нельзя завершить, является пробелом реестра и блокирует завершение шага.

### Подготовка временного workspace

Для каждого выбранного Code Repository CLI выполняет эквивалент:

```bash
git clone --single-branch --no-tags --branch <default-branch> <url> <temporary-path>
git rev-parse HEAD
```

Каждый URL и `default_branch` берутся только из `sdd.yaml`. Credential предоставляет настроенный Git credential helper или другой внешний read-only механизм; команда не добавляет их в URL и не выводит в терминал.

Готовый workspace имеет вид:

```text
.sdd/checkouts/explore/<ticket-id-lowercase>/
├── api/
└── ui/
```

Путь `.sdd/checkouts/` обязательно игнорируется точным правилом в `.gitignore`. Каталог `.sdd/` целиком не игнорируется, потому что на последующих шагах в нём могут находиться версионируемые файлы процесса.

При Explore только по `project-specs` итоговый каталог ticket создаётся пустым: это успешный workspace без Code Repository checkout, а не ошибка подготовки.

После получения lock CLI удаляет прежний итоговый workspace того же ticket, собирает полный набор в отдельном временном каталоге и публикует итоговый путь атомарным переименованием. Если проверка или загрузка любого репозитория завершилась ошибкой, временный каталог удаляется, а итоговый workspace не создаётся.

Одновременную подготовку одного ticket блокирует локальный lock-файл. Повторный успешный запуск целиком заменяет прежний workspace; частичное добавление репозитория в готовое дерево запрещено.

После загрузки checkout переводятся в режим только для чтения. `/opsx-explore` перед исследованием проверяет для каждого каталога `repository-id`, точную 40-символьную Git-ревизию и отсутствие локальных изменений. Перед завершением действие повторно убеждается, что checkout остались чистыми.

После успешной подготовки `sdd explore` печатает:

- ticket key;
- выбранные `repository-id` либо явное указание, что Explore выполняется только по `project-specs`;
- абсолютный read-only путь и Git-ревизию каждого созданного checkout;
- следующую команду `/opsx-explore <ticket-id>`.

Отдельный runtime manifest не создаётся. Источником локального состояния является атомарно опубликованный workspace; постоянный SDD-артефакт на шаге 01 отсутствует.

### Действия `/opsx-explore`

Действие принимает обязательный `<ticket-id>` и разрешает соответствующий workspace по детерминированному пути. Пустой workspace означает подтверждённый Explore только по `project-specs`. Отсутствующий, неполный или изменённый workspace блокирует исследование и требует повторного `sdd explore`.

Агент:

1. получает от Change Owner проблему и ожидаемый результат из текущего диалога; если их нет, задаёт уточняющий вопрос до чтения кода;
2. читает `openspec/context/00-start-here.md` и только назначенные им файлы нормативного контекста;
3. читает индекс и подходящие Master Specs, включая `Purpose` capabilities;
4. фиксирует отсутствие Code Repositories либо выбранные `repository-id`, ветки и точные Git-ревизии;
5. сопоставляет запрос, `system-map.yaml`, Master Specs и подготовленные checkout;
6. исследует текущее поведение, контракты, точки расширения, внешние системы, альтернативы и неизвестные;
7. отличает расхождение кода с действующей Spec от запроса на новое поведение;
8. проверяет чистоту checkout и формирует структурированный итог для Change Owner.

На шаге 01 агент не вызывает `/sdd-context`, не изменяет нормативный context pack и не создаёт TODO, ADR или OpenSpec-артефакты. Пробел, относящийся только к Story, фиксируется в результате Explore и позднее переносится в `research.md`. Подтверждённое общее знание может обновить context pack позже в составе Planning PR.

Если без недостающей информации невозможно понять проблему, выбрать репозитории, отличить дефект от нового поведения или соблюсти архитектурные, межсистемные либо security-инварианты, Explore не завершается. Change Owner получает уточнение у нужного специалиста и продолжает ту же сессию; PR для этого не создаётся.

Глобальное обслуживание context pack вне конкретного тикета может использовать отдельный `/sdd-context` и собственный PR, но не является частью шага 01.

### Структурированный итог Explore

Итог существует в агентской сессии и не является новым статусом или постоянным SDD-артефактом. Он содержит:

- ticket key;
- уточнённую проблему и ожидаемый наблюдаемый результат;
- прочитанные Master Specs;
- исследованные `repository-id`, ветки и Git-ревизии;
- найденное текущее поведение;
- репозитории-кандидаты и внешние системы;
- рассмотренные альтернативы и причины отказа от них;
- подтверждённые факты и их источники;
- неподтверждённые предположения;
- открытые вопросы, владельцев ответов и явное указание блокирующих вопросов.

История чата и временный workspace не являются постоянной записью. SDD не читает Jira, не изменяет её поля или статусы и не управляет жизненным циклом задачи в трекере.

### Завершение Explore

Если гейт 01 выполнен, Change Owner разрешает перейти к созданию Change на шаге 02. Название и контракт команды этого перехода определяются в шаге 02 и не являются частью шага 01.

Если данных недостаточно, Change Owner получает недостающую информацию и продолжает Explore. При изменении набора Code Repositories он повторяет `sdd explore`, подтверждает новый полный набор и заново запускает `/opsx-explore`. Пока гейт не выполнен, Explore остаётся незавершённым.

Отдельная команда `approve`, локальный approval-файл или machine-readable статус шага 01 не используются. Отмена, закрытие или отправка исходной задачи на доработку относятся к внешнему процессу и не моделируются в SDD.

Временный workspace игнорируется Git, не является источником истины и может быть безопасно удалён после перехода к шагу 02, прекращения внешней работы над запросом или перед повторной подготовкой.

### Результат и гейт 01

Переход к шагу 02 разрешён, когда:

- инициатор передал ticket key как внешний идентификатор запуска работы;
- проблема и ожидаемый результат понятны;
- активного Change с тем же ticket нет;
- подходящие нормативный контекст и Master Specs прочитаны;
- Explore выполнен по `project-specs`, а для каждого выбранного Code Repository зафиксирована точная свежая ревизия;
- известны репозитории-кандидаты и внешние системы;
- отсутствуют блокирующие неизвестные;
- остальные вопросы имеют владельцев;
- Change Owner разрешил перейти к созданию Change на шаге 02.

Если требуемое поведение уже описано Master Specs, а код ему не соответствует, Change Owner решает, продолжать ли запрос как исправление дефекта. Spec Owner проверяет создание Change на шаге 02 и его содержательную корректность начиная с шага 03.

Шаг 01 не создаёт Git-ветку или PR. Первый Change появляется на шаге 02, а первый PR процесса конкретной Story — Planning PR шага 07.
