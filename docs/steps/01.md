## 01. Запрос, предпроверка и Explore

Если вам нужно только пройти шаг 01, достаточно раздела «Пользовательская инструкция». Техническая спецификация ниже предназначена для разработчиков CLI и ревью процесса.

### Пользовательская инструкция

#### 1. Проверьте вход

Перед началом:

- шаг 00 завершён, а `sdd connect` успешно отработал на этой машине;
- у вас есть Jira ticket key вида `PAY-412`;
- сформулировано исходное намерение: что вы хотите исследовать и зачем;
- центральный Store и Code Repositories находятся в чистом состоянии.

#### 2. Обновите репозитории

`sdd` не выполняет массовый `pull`: `sdd connect` обновляет только состав workspace, а `sdd explore` делает `fetch` и проверяет результат. Поэтому перед каждым Explore вручную подтяните основную ветку центрального Store и каждого Code Repository, который собираетесь выбрать. Если область исследования пока неизвестна, обновите все Code Repositories из `sdd.yaml`.

В корне Store выполните:

```bash
git checkout <default-branch>
git pull --ff-only
```

Затем повторите для каждого нужного Code Repository в `<workspace>/src/`:

```bash
git -C <workspace>/src/<repository-id> checkout <default-branch>
git -C <workspace>/src/<repository-id> pull --ff-only
```

Пути, `repository-id` и `default_branch` перечислены в `sdd.yaml`. Отдельной команды массовой актуализации в первой реализации нет. Если рабочее дерево содержит локальные изменения или fast-forward невозможен, остановитесь и приведите checkout в чистое актуальное состояние без автоматического удаления изменений.

#### 3. Запустите Explore

Из корня центрального Store выполните:

```bash
sdd explore --ticket <ticket-id>
```

Команда проверит Store, ticket и локальный workspace, затем покажет список Code Repositories. Выберите номера одного или нескольких репозиториев либо подтвердите пустой набор для исследования только по Store. После подтверждения выбора команда попросит кратко описать намерение запроса.

Намерение — это исходная цель исследования, а не готовый диагноз, решение или ожидаемый результат. Достаточно написать, что требуется понять. Например:

```text
Code Repositories для Explore:
  [ ] 1. payments-ui (main)
  [ ] 2. payments-api (main)
Введите номера через запятую; Enter — Explore только по Spec Root: 1,2
Подтвердить область Explore: payments-ui, payments-api? [y/N] y
Кратко опишите намерение запроса: Понять, как показывать пользователю актуальный статус платежа в UI на основе данных API.
```

Введённое намерение не запускает агента и не сохраняется в файл. Оно включается в единственную готовую slash-команду; уточнённую проблему и ожидаемый наблюдаемый результат агент сформирует во время Explore по прочитанным источникам.

#### 4. Передайте исследование агенту

После проверки Store, workspace, выбранных репозиториев и намерения `sdd explore` завершит работу и напечатает готовую строку. Например:

```text
/opsx-explore PAY-412. Это Explore шага 01 SDD. Исходное намерение: "Понять, как показывать пользователю актуальный статус платежа в UI на основе данных API". Используй OpenSpec Store "payments-specs" и Spec Root ...
```

Эта строка является непосредственным результатом `sdd explore`: составлять или дополнять её вручную не нужно. Откройте новую сессию поддерживаемого AI-агента из корня Store и первой командой вставьте строку целиком. Не отправляйте описание запроса отдельным сообщением до `/opsx-explore`: исходное намерение уже передано внутри команды. Агент только читает выбранные источники, уточняет проблему и ожидаемый результат и возвращает структурированный итог исследования.

#### 5. Завершите шаг

Шаг завершён, когда:

- проблема и ожидаемый результат понятны;
- подходящие контекст, Master Specs и код исследованы;
- известны затронутые репозитории и внешние системы;
- блокирующих вопросов нет;
- Change Owner разрешил создать Change и подготовить Proposal на шаге 02.

Шаг 01 не создаёт Change, файлы, ветки или PR и не изменяет код. Если `sdd explore` остановился, выполните указанную им подготовку и повторите команду; репозитории на этом шаге не клонируются и не исправляются автоматически.

## Техническая спецификация шага 01

Шаг выполняется для каждого запроса, запущенного во внешнем процессе с Jira ticket key после принятого шага 00. Его задача — проверить исходный запрос, выбрать нужные из уже загруженных Code Repositories, подтвердить их свежесть и исследовать проблему до появления обязательств по реализации. Загрузка и первичное подключение репозиториев относятся только к `sdd connect` шага 00.

На этом шаге OpenSpec Change ещё не существует. Команды не создают `openspec/changes/<change-id>/`, дополнительную SDD-метадату, планировочные артефакты, ветку или PR, не изменяют код, Master Specs и нормативный context pack. Первое постоянное состояние изменения появляется на шаге 02.

### Владелец

Change Owner отвечает за исходное намерение, начальный выбор репозиториев и решение о продолжении SDD-процесса. Агент уточняет проблему и ожидаемый результат, собирает и сопоставляет факты, но не создаёт Change и не принимает решение вместо Change Owner.

Technical Owner и Spec Owner не являются обязательными участниками шага 01. Change Owner обращается к ним адресно только при блокирующем техническом вопросе. Spec Owner подключается к созданию Change и проверке структуры Proposal на шаге 02; формальное подтверждение технического решения начинается с Design на шаге 04.

### Вход

- initialization PR шага 00 слит, а Spec Owner разрешил принимать рабочие запросы;
- Spec Root зарегистрирован на рабочей машине как OpenSpec Store под ID из `.openspec-store/store.yaml`;
- инициатор передал постоянный Jira key вида `PAY-412` как внешний идентификатор запуска работы;
- Change Owner подготовил исходное намерение без готового диагноза или обязательства реализовать заранее выбранное решение и передаёт его интерактивному `sdd explore`;
- назначены Change Owner и инициатор;
- в `sdd.yaml` зарегистрирована ровно одна запись `role: store`, чей `id` равен Store ID, и полный известный набор записей `role: code`;
- `sdd connect` шага 00 успешно завершён на этой машине: все Code Repositories из `sdd.yaml` уже находятся в `<workspace>/src/<repository-id>` и содержат принятый project pointer на тот же Store;
- непосредственно перед Explore основная ветка Store и Code Repositories, выбранных для исследования, обновлена через `git pull --ff-only`;
- read-only credential для выбранных Git-репозиториев настроен вне Git, если Explore требует чтения кода;
- установлена точная версия OpenSpec из `versions.openspec` файла `sdd.yaml`.

Первая реализация не интегрируется с Jira API и не проверяет существование или статус задачи по сети. SDD синтаксически проверяет ticket key и далее использует его только как внешний идентификатор. Git credential и другие секреты не записываются в `sdd.yaml`, логи или Git.

### Технический контракт `sdd explore`

Пользователь запускает команду из центрального Store либо из подключённого Code Repository:

```bash
sdd explore --ticket <ticket-id> [--workspace <workspace-path>]
```

При рекомендуемой структуре `<workspace>/openspec/<store-checkout>` и `<workspace>/src/<repository-id>` путь workspace определяется автоматически. Для другой структуры пользователь передаёт тот же `--workspace`, который использовал в `sdd connect`.

После успешной проверки workspace и выбора Code Repositories `sdd explore` запрашивает одно исходное намерение. Пустой ответ не принимается. Команда не запускает агента и не сохраняет значение в файл, а включает его в одну готовую строку. Проблему и ожидаемый результат до Explore указывать не требуется: их уточняет агент по фактам.

Пользователь открывает новую сессию поддерживаемого AI-агента из корня зарегистрированного Store и передаёт напечатанную строку первым сообщением:

```text
/opsx-explore <ticket-id>. Это Explore шага 01 SDD. Исходное намерение: "...". Используй OpenSpec Store "<store-id>" и Spec Root ...
```

| Команда | Что делает | Результат |
|---|---|---|
| `sdd explore --ticket ... [--workspace ...]` | Через OpenSpec разрешает общий Store, проверяет ticket и дубликаты, сверяет уже подключённый workspace, предлагает выбрать Code Repositories, подтверждает свежесть выбранных checkout и запрашивает исходное намерение | Проверенные Store и локальные пути с точными ревизиями, единая готовая строка `/opsx-explore ...` |
| Готовая строка `/opsx-explore ...` | Запускает оригинальное действие OpenSpec, явно передаёт ticket, исходное намерение, Store ID, workspace, SDD-границы, абсолютные пути и выбранные ревизии; агент исследует нормативные источники и выбранный код только для чтения | Уточнённые проблема и ожидаемый результат вместе со структурированным итогом для решения Change Owner |

### Разрешение Store и предпроверка agent action

`sdd explore` не выбирает Store по одному найденному `sdd.yaml`:

- в центральном Store сначала распознаётся обязательный SDD skeleton, затем ID читается из `.openspec-store/store.yaml` и подтверждается официальными командами с явным `--store`;
- в Code Repository команда `openspec context --json` должна разрешить config-only pointer с `source: declared` и вернуть Store ID;
- `sdd.yaml` после этого читается только из фактически разрешённого Store root.

При запуске из Code Repository его Git top-level, origin и текущий checkout должны однозначно соответствовать одной непротиворечивой записи `repository-id` в `sdd.yaml`. Наличие корректного pointer без регистрации репозитория в SDD недостаточно.

Если запуск выполнен из Code Repository, CLI сначала выполняет без `--store`:

```bash
openspec doctor --json
openspec context --json
```

Так проверяется именно командная связь репозитория со Store. Локальный planning root с `openspec/specs/` или `openspec/changes/`, `source: nearest`, `source: global_default` и Store ID, не совпадающий с metadata центрального root, блокируют Explore. После разрешения все операции над specs и Changes используют явный ID.

CLI выполняет эквивалент:

```bash
openspec store list --json
openspec store doctor <store-id> --json
openspec doctor --store <store-id> --json
openspec context --store <store-id> --json
openspec list --specs --store <store-id> --json
openspec list --changes --store <store-id> --json
```

Каждый JSON разбирается структурно. Нулевой exit code `store doctor` или `doctor` сам по себе не означает успех: диагностика severity `error` блокирует Explore. Команда проверяет, что Store существует ровно под ожидаемым ID, metadata валидна, registry указывает на текущий checkout, OpenSpec root исправен, `context.root` содержит ожидаемые `path`, `source: store` и `store_id`, а `list` разрешил тот же root. Несовпадение пути не исправляется автоматически, потому что OpenSpec допускает только один локальный checkout на Store ID.

Если Store не зарегистрирован на рабочей машине либо Code Repository не содержит корректный pointer, Explore прекращается до выбора области и чтения specs, Changes или кода и предлагает выполнить `sdd connect --workspace <workspace>` из центрального репозитория. Отсутствующая или невалидная версионируемая Store metadata означает повреждённый либо неверный checkout: повторный `sdd init` в нём запрещён, пользователь должен получить корректную основную ветку центрального репозитория или обратиться к Technical Owner. Конфликт registry с другим путём также не исправляется автоматически. `sdd explore` не регистрирует Store, не загружает репозитории и не меняет pointer самостоятельно.

До выбора репозиториев CLI проверяет:

- установлена OpenSpec `1.7.0`, точно совпадающая с `versions.openspec` в `sdd.yaml`;
- discovery из Code Repository возвращает `source: declared`, а последующие OpenSpec-команды с явным `--store <store-id>` возвращают тот же root;
- секция `agent` из `sdd.yaml` соответствует поддерживаемому адаптеру, а в сохранённом `commands_directory` установлен оригинальный action OpenSpec `/opsx-explore`;
- `sdd.yaml` содержит ровно одну корректную запись `role: store`, чей `id` совпадает с Store ID из metadata;
- каждый зарегистрированный Code Repository уже существует по пути `<workspace>/src/<repository-id>`, является обычным каталогом, а не symlink, и соответствует canonical URL из `sdd.yaml`.

`sdd explore` не изменяет, не копирует и не проверяет содержимое provider-specific файла действия `/opsx-explore`. CLI читает выбранный adapter и его путь из `sdd.yaml` и проверяет только наличие обычного файла внутри Store root, поэтому отсутствие оригинального action считается ошибкой подготовки среды. Для `qwen` файл восстанавливается штатным `openspec update --force`. Для `gigacode` прямой update создаёт `.qwen/` вместо `.gigacode/`, поэтому повреждённый или обновляемый pack должен быть подготовлен Technical Owner через совместимую версию SDD adapter.

### Свежесть Git checkout Store

Store registry разрешает локальный путь, но не гарантирует свежесть его Git-состояния. Пользователь перед запуском обновляет основную ветку Store через `git pull --ff-only`. До чтения Master Specs `sdd explore` находит единственную запись `role: store`, проверяет совпадение её `id` с Store ID и валидирует центральный checkout:

```bash
git status --porcelain --untracked-files=all
git branch --show-current
git fetch origin <default-branch>
git rev-parse HEAD
git rev-parse origin/<default-branch>
```

Рабочее дерево должно быть чистым, текущая ветка должна совпадать с `default_branch`, а `HEAD` после `fetch` — с `origin/<default-branch>`. Explore не выполняет `pull`, merge, rebase или checkout: предварительный pull является обязанностью пользователя, а команда только подтверждает свежесть. Локальные незакоммиченные изменения, другая ветка, отсутствие remote либо расхождение ревизий блокируют шаг с инструкцией обновить Store вручную.

Проверенная 40-символьная ревизия Store включается в готовую строку `/opsx-explore ...` и структурированный итог. Она фиксирует нормативный вход исследования, но не является Spec Baseline последующих шагов и не создаёт постоянный артефакт.

### Проверка ticket key и существующих Changes

CLI принимает только key формата `<PROJECT>-<number>` в верхнем регистре и использует его без преобразования как процессный идентификатор. Корректный формат не доказывает существование задачи; её состояние во внешнем трекере находится вне ответственности SDD.

После разрешения Store и до выбора Code Repositories команда получает активные Changes через официальный `openspec list --changes --store <store-id> --json`. Отдельной SDD-метадаты Change на шаге 01 нет, поэтому принадлежность к ticket определяется по единому соглашению о `change-id`: `<ticket>` либо `<ticket>-<краткое-название>`, без учёта регистра. Архивные Changes проверяются по тем же именам после стандартного префикса даты `YYYY-MM-DD-` в `openspec/changes/archive/` разрешённого Store root:

- активный Change с тем же ticket блокирует новый Explore и показывается пользователю;
- архивный Change с тем же ticket показывается как предупреждение и требует явного подтверждения Change Owner в интерактивном запуске; в non-TTY команда завершается ошибкой;
- неожиданный формат элемента в ответе OpenSpec или ошибочная диагностика в JSON блокируют Explore, потому что дубликат нельзя исключить надёжно;
- похожая цель с другим ticket определяется агентом во время Explore, а не эвристикой CLI.

### Выбор репозиториев

Команда показывает checklist всех записей `role: code` из `sdd.yaml`. Запись `role: store` в checklist не включается, потому что Store уже разрешён и проверен как нормативный источник. До показа checklist CLI подтверждает, что каждый зарегистрированный Code Repository уже загружен командой `sdd connect`; отсутствие хотя бы одного каталога блокирует Explore с инструкцией повторить шаг 00.

Change Owner может выбрать один или несколько Code Repositories либо явно подтвердить пустой набор для Explore только по Store Repository. Автоматически выбирать все репозитории или требовать хотя бы один Code Repository запрещено.

Первая реализация не предоставляет флаг обхода checklist. Если stdin не является TTY, команда завершается ошибкой.

Выбранный набор, включая пустой, является исходной областью исследования, а не окончательным system impact. Если агент обнаружил необходимость прочитать код зарегистрированного репозитория, Change Owner повторяет `sdd explore`, выбирает полный расширенный набор и запускает новую готовую строку `/opsx-explore ...`. Нерегистрированный репозиторий, без которого исследование нельзя завершить, является пробелом реестра и блокирует завершение шага.

### Проверка подключённого workspace

`sdd explore` использует постоянные локальные checkout, подготовленные на шаге 00:

```text
<workspace>/
├── openspec/
│   └── payments-specs/
└── src/
    ├── api/
    └── ui/
```

Команда не клонирует, не удаляет и не заменяет репозитории. Для каждого выбранного Code Repository она проверяет:

```bash
git status --porcelain --untracked-files=all
git branch --show-current
git fetch origin <default-branch>
git rev-parse HEAD
git rev-parse origin/<default-branch>
```

Рабочее дерево должно быть чистым, текущая ветка — `default_branch` из `sdd.yaml`, а `HEAD` после `fetch` — совпадать с `origin/<default-branch>`. Каждый выбранный Code Repository должен быть предварительно обновлён пользователем через `git pull --ff-only`; если набор заранее неизвестен, пользователь обновляет все репозитории. Explore не выполняет массовый или одиночный `pull`, checkout, merge или rebase и не исправляет состояние пользователя. Несвежий либо изменённый checkout блокирует исследование с инструкцией привести постоянный локальный репозиторий в актуальное состояние и повторить команду.

Каждый Code Repository обязан содержать принятый config-only pointer:

```yaml
store: <store-id>
```

Из корня каждого выбранного checkout CLI выполняет `openspec doctor --json` и `openspec context --json`. Оба вызова должны разрешить зарегистрированный центральный Store с `source: declared`, ожидаемым `store_id` и тем же абсолютным Store root. Отсутствующий pointer, локальные `openspec/specs/` или `openspec/changes/`, другой Store ID и любая диагностика severity `error` блокируют Explore. Исправление выполняется через `sdd connect` и setup PR шага 00, а не внутри Explore.

CLI не меняет файловые права checkout. Режим «только чтение» является контрактом команды и инструкции агенту: перед исследованием фиксируются `repository-id`, абсолютный путь, точная 40-символьная Git-ревизия и чистота каждого выбранного каталога, а перед завершением проверяется, что Store и Code Repositories не изменились.

При Explore только по Store Repository Code Repositories не выбираются и дополнительный каталог не создаётся. Это штатный сценарий для продуктового или доменного исследования без привязки к существующему коду.

После успешной проверки `sdd explore` печатает:

- ticket key;
- исходное намерение, введённое Change Owner;
- Store ID, абсолютный путь Spec Root и его точную Git-ревизию;
- выбранные `repository-id` либо явное указание, что Explore выполняется только по Store Repository;
- абсолютный локальный путь, Git-ревизию и подтверждённый Store pointer каждого выбранного checkout;
- одну готовую строку `/opsx-explore ...`, включающую ticket, исходное намерение, workspace, абсолютные пути, выбранные ревизии, read-only-границы и обязательную структуру результата.

Отдельный runtime manifest и ticket-specific workspace не создаются. `sdd explore` только читает существующий workspace; постоянный SDD-артефакт на шаге 01 отсутствует.

### Передача SDD-контракта в `/opsx-explore`

Оригинальное действие OpenSpec задаёт исследовательский режим и получает весь остальной контракт через аргумент slash-команды. `sdd explore` формирует этот аргумент автоматически: ticket, исходное намерение, Store ID, workspace, абсолютные пути Spec Root и выбранных локальных Code Repositories, точную ревизию Store, пустой или выбранный набор репозиториев, их ветки и ревизии, запрет записи, необходимые источники и структуру итога. Пользователь не собирает эту инструкцию вручную и копирует напечатанную строку целиком первым сообщением новой агентской сессии.

Workspace задаёт общую multi-repo-территорию запроса, но не разрешает агенту сканировать её целиком. Разрешёнными корнями чтения являются только явно переданные Spec Root и выбранные Code Repositories. Родительские каталоги, remotes, соседние пути и невыбранные репозитории не читаются. Если области недостаточно, агент останавливает Explore и просит повторить `sdd explore` с полным набором.

Инструкция явно называет Store и требует сначала подтвердить его через `openspec store list --json`. Project pointer в Code Repositories используется как проверяемая командная связь с центральным Store, а все непосредственные чтения specs и Changes выполняются с явным `--store <store-id>`. Агент не использует nearest root, `defaultStore` или Store, выбранный по истории предыдущей сессии. Если pointer либо явная команда разрешили другой Store ID или путь, исследование блокируется и требует повторного `sdd explore` после исправления подключения.

Пустой набор Code Repositories в переданной инструкции означает подтверждённый Explore только по Store Repository. Отсутствующий либо изменённый выбранный checkout блокирует исследование и требует восстановить workspace через шаг 00, затем повторить `sdd explore`. Дополнительная инструкция шага 01 запрещает обращаться к Jira API, создавать OpenSpec-артефакты или изменять файлы, даже если универсальный режим оригинального `/opsx-explore` допускает другие исследовательские сценарии вне этого процесса.

Агент:

1. получает исходное намерение из аргумента текущей `/opsx-explore`, не используя для запуска исследования предыдущие сообщения; при необходимости задаёт уточняющий вопрос, затем по прочитанным фактам формулирует уточнённую проблему и ожидаемый наблюдаемый результат;
2. подтверждает Store ID, путь и ревизию из готовой инструкции;
3. читает `openspec/context/00-start-here.md` и только назначенные им файлы нормативного контекста;
4. через явный Store читает индекс и подходящие Master Specs, включая `Purpose` capabilities;
5. фиксирует отсутствие Code Repositories либо выбранные `repository-id`, ветки, точные Git-ревизии и подтверждённую связь каждого checkout с тем же Store;
6. сопоставляет запрос, `system-map.yaml`, Master Specs и выбранные локальные checkout;
7. исследует текущее поведение, контракты, точки расширения, внешние системы, альтернативы и неизвестные, связывает каждый факт с источником и явно отделяет гипотезы;
8. отличает расхождение кода с действующей Spec от запроса на новое поведение;
9. проверяет неизменность Store и чистоту code checkout, затем формирует структурированный итог для Change Owner.

На шаге 01 агент не вызывает `/sdd-context`, не изменяет нормативный context pack и не создаёт TODO, ADR или OpenSpec-артефакты. Подтверждённые выводы Explore становятся входом объединённого шага 02, который создаёт Change и Proposal. Подтверждённое общее знание может обновить context pack позже в составе Planning PR.

Если без недостающей информации невозможно понять проблему, выбрать репозитории, отличить дефект от нового поведения или соблюсти архитектурные, межсистемные либо security-инварианты, Explore не завершается. Change Owner получает уточнение у нужного специалиста и продолжает ту же сессию; PR для этого не создаётся.

Глобальное обслуживание context pack вне конкретного тикета может использовать отдельный `/sdd-context` и собственный PR, но не является частью шага 01. `/sdd-context` работает только с центральным Store и не читает Code Repositories; доступ к выбранным checkout на этом шаге получает только оригинальный `/opsx-explore` через область, подготовленную `sdd explore`.

### Структурированный итог Explore

Итог существует в агентской сессии и не является новым статусом или постоянным SDD-артефактом. Он содержит:

- ticket key;
- исходное намерение Change Owner;
- Store ID и точную Git-ревизию Spec Root;
- уточнённую проблему и ожидаемый наблюдаемый результат;
- прочитанные Master Specs;
- исследованные `repository-id`, ветки, Git-ревизии и результаты разрешения их Store pointer;
- найденное текущее поведение;
- репозитории-кандидаты и внешние системы;
- рассмотренные альтернативы и причины отказа от них;
- подтверждённые факты и их источники;
- неподтверждённые предположения;
- открытые вопросы, владельцев ответов и явное указание блокирующих вопросов.

История чата не является постоянной записью. SDD не читает Jira, не изменяет её поля или статусы и не управляет жизненным циклом задачи в трекере.

### Завершение Explore

Если гейт 01 выполнен, Change Owner разрешает перейти к созданию Change и Proposal на шаге 02. Название и контракт команды этого перехода определяются в шаге 02 и не являются частью шага 01.

Если данных недостаточно, Change Owner получает недостающую информацию и продолжает Explore. При изменении набора Code Repositories он повторяет `sdd explore`, подтверждает новый полный набор и запускает новую готовую строку `/opsx-explore ...`. Пока гейт не выполнен, Explore остаётся незавершённым.

Отдельная команда `approve`, локальный approval-файл или machine-readable статус шага 01 не используются. Отмена, закрытие или отправка исходной задачи на доработку относятся к внешнему процессу и не моделируются в SDD.

### Возможная будущая эволюция

Первая реализация намеренно использует оригинальный `/opsx-explore`, чтобы обновления OpenSpec могли заменять action без конфликта с кодом SDD. Если композиции через аргумент slash-команды станет недостаточно либо OpenSpec предоставит подходящую точку расширения, процесс можно отдельным согласованным изменением перевести на собственную команду `/sdd-explore`.

Такая команда должна жить только в пространстве имён `sdd-*` и не может перезаписывать файлы `opsx-*`. Контракт проверки уже подключённого workspace командой `sdd explore` желательно сохранить; изменится только передача управления агенту. До принятия отдельной ревизии процесса нормативным вариантом остаётся оригинальный `/opsx-explore` с полной инструкцией, напечатанной CLI.

### Результат и гейт 01

Переход к шагу 02 разрешён, когда:

- инициатор передал ticket key как внешний идентификатор запуска работы;
- проблема и ожидаемый результат понятны;
- активного Change с тем же ticket нет;
- подходящие нормативный контекст и Master Specs прочитаны;
- Store однозначно разрешён по ID, зарегистрирован на ожидаемый чистый checkout основной ветки и зафиксирован точной свежей Git-ревизией;
- Explore выполнен по единому Store, а для каждого выбранного Code Repository зафиксированы точная свежая ревизия и корректный pointer на этот Store;
- известны репозитории-кандидаты и внешние системы;
- отсутствуют блокирующие неизвестные;
- остальные вопросы имеют владельцев;
- Change Owner разрешил перейти к созданию Change и Proposal на шаге 02.

Если требуемое поведение уже описано Master Specs, а код ему не соответствует, Change Owner решает, продолжать ли запрос как исправление дефекта. На шаге 02 Spec Owner проверяет структуру Change, а Change Owner — содержание Proposal.

Шаг 01 не создаёт Git-ветку или PR. Первый Change и Proposal появляются на шаге 02, а первый PR процесса конкретной Story — Planning PR шага 06.

Высокоуровневое продолжение процесса зафиксировано в [дорожной карте](README.md). Реализованный контракт следующего этапа описан в `02.md`.
