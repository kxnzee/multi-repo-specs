# Дорожная карта SDD-процесса

Этот файл фиксирует высокоуровневую последовательность процесса. Подробный контракт каждого этапа описывается отдельно в `NN.md` перед реализацией соответствующих команд. Если между roadmap и детальным шагом появится расхождение, сначала обновляется и согласовывается roadmap.

Основа последовательности — командный жизненный цикл из документа [«OpenSpec для команды»](../OpenSpec%20для%20команды.md): Change → планирующие артефакты → реализация во всех затронутых репозиториях → Composite Verification → Archive → обновлённые Master Specs.

Процесс использует центральный OpenSpec Store и стандартную схему `spec-driven`: `proposal → specs → design → tasks`. Собственная схема OpenSpec не вводится. Точные пользовательские команды, форматы служебных данных и правила восстановления определяются только при проектировании соответствующего шага.

| Шаг | Этап | Высокоуровневый результат | Гейт перехода |
|---|---|---|---|
| [00](00.md) | Инициализация и подключение | Центральный Store создан, рабочая машина подключена, Code Repositories загружены и связаны с единым Store | `sdd connect` вернул `ready`, initialization и setup PR приняты |
| [01](01.md) | Запрос и Explore | По исходному намерению исследованы нормативный контекст и выбранный код; уточнены проблема, ожидаемый результат и область влияния | Блокирующих вопросов нет, Change Owner разрешил создать Change |
| 02 | Создание Change | Выбран единый `change-id` формата `<JIRA>-<краткое-название>`, в центральном Store создан OpenSpec Change | Change однозначно связан с ticket и не дублирует активную работу |
| 03 | Proposal | В `proposal.md` зафиксированы проблема, ценность, scope, затронутые репозитории и риски совместимости | Change Owner подтвердил содержание Proposal |
| 04 | Delta Specs | В Delta Specs описано проверяемое изменение поведения и единый межрепозиторный контракт | Requirements и Scenarios полны, а отличие от Master Specs сформулировано явно |
| 05 | Design | В `design.md` зафиксированы системное решение, ответственность компонентов, совместимость, rollout и rollback | Technical Owner подтвердил реализуемость и безопасный порядок поставки |
| 06 | Tasks | В `tasks.md` работа разделена на Work Packages по Store, Code Repositories и Composite Verification | Для каждого пакета известны владелец, результат и проверка |
| 07 | Planning PR и Baseline | Все артефакты прошли строгую OpenSpec-валидацию и ревью в Planning PR; принятая ревизия Store стала Spec Baseline | Planning PR слит, Baseline неизменяем и разрешено начинать реализацию |
| 08 | Подготовка реализации | Для затронутых Code Repositories подготовлены связанные ветки и runtime-контекст на одном Baseline | Репозитории готовы, границы записи и назначенные Work Packages однозначны |
| 09 | Реализация | Work Packages реализованы и проверены в своих репозиториях; открыты связанные implementation PR | Компонентные, контрактные проверки и строгая валидация Baseline проходят |
| 10 | Composite Verification | Контракт, точные ревизии компонентов и пользовательские сценарии проверены как единая система; собрано Evidence | QA принял составную проверку, блокирующих расхождений нет |
| 11 | Merge и rollout | Связанные PR слиты и компоненты поставлены в безопасном порядке из `design.md` | Rollout завершён, совместимость подтверждена, все задачи выполнены |
| 12 | Finalization и Archive | Change архивирован, Delta Specs применены к Master Specs, история и фактическое состояние зафиксированы в центральном Store | Finalization PR принят, Master Specs соответствуют работающей системе |

## Сквозные правила

- Один ticket получает один общий Change и один `change-id` во всех связанных репозиториях.
- Сначала согласуются Proposal, Delta Specs, Design и Tasks, затем изменяется код.
- Стандартные артефакты можно уточнять при появлении новых фактов, но изменение принятого Baseline требует отдельного согласованного процесса.
- OpenSpec validation проверяет требования, но не заменяет тесты реализации и Composite Verification.
- Archive выполняется только после завершения всех затронутых репозиториев и rollout.
- Master Specs описывают только фактически работающее поведение; до Archive планы остаются внутри Change.

## Статус проектирования

- Шаги 00 и 01 зафиксированы и реализованы.
- Следующим подробно проектируется шаг 02.
- Шаги 03–12 пока являются высокоуровневым планом и не задают готового пользовательского интерфейса.
