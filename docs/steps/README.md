# Дорожная карта SDD-процесса

Этот файл фиксирует высокоуровневую последовательность процесса. Подробный контракт каждого этапа описывается отдельно в `NN.md` перед реализацией соответствующих команд. Если между roadmap и детальным шагом появится расхождение, сначала обновляется и согласовывается roadmap.

Основа последовательности — командный жизненный цикл из документа [«OpenSpec для команды»](../OpenSpec%20для%20команды.md): Change → планирующие артефакты → реализация во всех затронутых репозиториях → Composite Verification → Archive → обновлённые Master Specs.

Процесс использует центральный OpenSpec Store и стандартную схему `spec-driven`: `proposal → specs → design → tasks`. Собственная схема OpenSpec не вводится. Точные пользовательские команды, форматы служебных данных и правила восстановления определяются только при проектировании соответствующего шага.

| Шаг | Этап | Высокоуровневый результат | Гейт перехода |
|---|---|---|---|
| [00](00.md) | Инициализация и подключение | Центральный Store создан, рабочая машина подключена, Code Repositories загружены и связаны с единым Store | `sdd connect` вернул `ready`, initialization и setup PR приняты |
| [01](01.md) | Запрос и Explore | По исходному намерению исследованы нормативный контекст и выбранный код; уточнены проблема, ожидаемый результат и область влияния | Блокирующих вопросов нет, Change Owner разрешил создать Change и подготовить Proposal |
| [02](02.md) | Создание Change и Proposal | Выбран канонический `change-id`, в planning-ветке центрального Store созданы Change и `proposal.md` из подтверждённого Explore | Change Owner подтвердил Proposal, а следующие planning-артефакты ещё не создавались |
| [03](03.md) | Планирование Change | Последовательные `/opsx-continue` создали Delta Specs, `design.md` и `tasks.md` без промежуточных человеческих гейтов | Все planning-артефакты имеют статус `done` и готовы к общей проверке в Planning PR |
| 04 | Planning PR и Baseline | Все артефакты прошли строгую OpenSpec-валидацию и ревью в Planning PR; принятая ревизия Store стала Spec Baseline | Planning PR слит, Baseline неизменяем и разрешено начинать реализацию |
| 05 | Подготовка реализации | Для затронутых Code Repositories подготовлены связанные ветки и runtime-контекст на одном Baseline | Репозитории готовы, границы записи и назначенные Work Packages однозначны |
| 06 | Реализация | Work Packages реализованы и проверены в своих репозиториях; открыты связанные implementation PR | Компонентные, контрактные проверки и строгая валидация Baseline проходят |
| 07 | Composite Verification | Контракт, точные ревизии компонентов и пользовательские сценарии проверены как единая система; собрано Evidence | QA принял составную проверку, блокирующих расхождений нет |
| 08 | Merge и rollout | Связанные PR слиты и компоненты поставлены в безопасном порядке из `design.md` | Rollout завершён, совместимость подтверждена, все задачи выполнены |
| 09 | Finalization и Archive | Change архивирован, Delta Specs применены к Master Specs, история и фактическое состояние зафиксированы в центральном Store | Finalization PR принят, Master Specs соответствуют работающей системе |

## Сквозные правила

- Один ticket получает один общий Change и один `change-id` во всех связанных репозиториях.
- До открытия Planning PR один назначенный Change Owner ведёт ticket на одной рабочей машине и изменяет единственную planning-ветку. Он готовит Proposal, Delta Specs, Design и Tasks; параллельные planning-ветки для того же ticket не создаются.
- В Planning PR владельцы соответствующих блоков оставляют замечания и подтверждают свои части. Change Owner вносит согласованные исправления в ту же planning-ветку и повторно запрашивает ревью.
- Proposal подтверждается до подготовки planning-артефактов; Delta Specs, Design и Tasks согласуются вместе в Planning PR, и только затем изменяется код.
- Стандартные артефакты можно уточнять при появлении новых фактов, но изменение принятого Baseline требует отдельного согласованного процесса.
- OpenSpec validation проверяет требования, но не заменяет тесты реализации и Composite Verification.
- Archive выполняется только после завершения всех затронутых репозиториев и rollout.
- Master Specs описывают только фактически работающее поведение; до Archive планы остаются внутри Change.

## Статус проектирования

- Шаги 00–02 зафиксированы и реализованы.
- Шаг 03 объединяет подготовку Delta Specs, Design и Tasks и зафиксирован на последовательных вызовах официальной `/opsx-continue`; отдельные CLI, agent command и промежуточные человеческие гейты не требуются.
- Изоляция чтения крупных Code Repositories на шаге 03 выполняется native subagents по руководству [«Работа с subagents при планировании Change»](../subagents.md); harness пока не предоставляет provider-neutral orchestration.
- Шаги 04–09 пока являются высокоуровневым планом и не задают готового пользовательского интерфейса.
