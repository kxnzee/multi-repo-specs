## 05. Подготовка реализации на Spec Baseline

### Цель шага

Шаг 05 подготавливает один затронутый Code Repository к реализации назначенных ему Work Packages на принятой ревизии центрального OpenSpec Store.

На входе уже существуют:

- слитый Planning PR;
- полная 40-символьная `spec_baseline` из основной ветки Store;
- parameter-only implementation subtask для целевого `repository-id`;
- принятые Proposal, Delta Specs, Design и Tasks;
- назначенные этому репозиторию `task.id` из OpenSpec на принятом Baseline.

На выходе разработчик получает implementation-ветку, проверяемый immutable worktree Store на указанной SHA и локальный runtime-контекст, связывающий Change, Baseline, Code Repository и Work Packages.

Шаг ничего не реализует. Он не начинает Apply, не изменяет код, planning-артефакты, Master Specs и Tasks, не создаёт commit, push или implementation PR.

### Базовый принцип

OpenSpec Store и штатный OpenSpec API остаются основой процесса. `sdd load` не копирует их модель и не вводит собственную schema, parser Tasks, validator Change или формат Work Packages.

```text
OpenSpec Store и штатный API
  ├─ разрешают центральный root
  ├─ возвращают статус Change и Tasks
  ├─ выполняют строгую validation
  └─ формируют apply instructions

Тонкий слой sdd
  ├─ фиксирует Store на spec_baseline
  ├─ выбирает repository-id и Work Package ID
  ├─ подготавливает implementation-ветку
  └─ задаёт границы записи
```

Дополнительная логика допустима только там, где OpenSpec API не покрывает multi-repo-процесс. В частности, `--store <id>` выбирает зарегистрированный Store, но не умеет выбрать произвольную Git SHA. Для этого `sdd` использует стандартный detached Git worktree того же Store.

## Пользовательский процесс

### 1. Получите implementation subtask

Apply Owner начинает работу только по subtask, созданной после принятия Planning PR на шаге 04:

Источники и правила формирования каждого поля определены единой таблицей [шага 04](04.md#7-передайте-реализацию-командам-code-repositories). Apply Owner не восстанавливает отсутствующие значения самостоятельно.

```yaml
parent_ticket: PAY-412
change_id: pay-412-payment-status
store_id: payments-specs
spec_baseline: 0123456789abcdef0123456789abcdef01234567
planning_pr: <provider-pr-reference>
repository_id: payments-api
work_packages:
  - "1"
  - "2"
```

Если до начала шага принят correction PR, subtask дополнительно содержит `correction_pr`, а `spec_baseline` уже указывает на его принятую SHA.

Subtask передаёт параметры и ссылки, но не заменяет Store. Текст спецификаций или Work Packages, скопированный в tracker, не считается источником истины.

`work_packages` в subtask содержит полный набор, назначенный этому Code Repository. Для небольшой работы Apply Owner может передать весь набор в одну Apply-сессию. Для объёмной работы он выбирает на каждый запуск `sdd load` один или несколько ID из этого списка и последовательно выполняет их в той же implementation-ветке и Draft PR. Это не создаёт новый Change, subtask или PR.

### 2. Перейдите в целевой Code Repository

Команда запускается из checkout, ранее подготовленного `sdd connect`:

```bash
cd <workspace>/src/<repository-id>
```

До запуска должны выполняться условия:

- текущий checkout соответствует записи `role: code` с тем же `repository-id` в `sdd.yaml`;
- `origin` совпадает с каноническим URL этой записи;
- `openspec/config.yaml` содержит принятый pointer `store: <store-id>`;
- рабочее дерево чистое;
- незавершённые Git-операции отсутствуют;
- тот же Store зарегистрирован и доступен локально.

Команда не применяет stash и не исправляет Git-состояние автоматически.

### 3. Выполните `sdd load`

Передайте значения из subtask. Например, для subtask выше команда выглядит так:

```bash
sdd load \
  --store payments-specs \
  --repo payments-api \
  --change pay-412-payment-status \
  --baseline 0123456789abcdef0123456789abcdef01234567 \
  --work-package 1 \
  --work-package 2
```

`--store`, `--repo`, `--change` и `--baseline` переносятся из implementation subtask без изменений. `--work-package` повторяется для одного или нескольких ID, выбранных для текущей Apply-сессии из полного списка `work_packages` этой subtask. Каждый ID является точным `tasks[].id` из `openspec instructions apply --change <change-id> --json` на указанном Baseline. OpenSpec возвращает общий список Tasks Change, но не хранит структурированное назначение Task конкретной repository-subtask. Поэтому принадлежность выбранных ID полному списку subtask сверяет Apply Owner; `sdd load` без tracker-интеграции проверяет только их наличие и состояние в OpenSpec.

Например, тот же полный список `1, 2` можно выполнить за два подхода. В первой рабочей сессии передаётся только `--work-package 1`. После её завершения Apply Owner остаётся в той же ветке и повторяет `sdd load` с теми же Store, repository, Change и Baseline, но с `--work-package 2`. Новый `next_action` относится только ко второй порции; первый пакет сохраняется в истории общей ветки, Draft PR и полном списке subtask.

`sdd load` не обращается к Jira/SberTrack и не изменяет subtask: Apply Owner переносит её параметры в команду вручную.

Команда выполняет только следующий маршрут:

1. сверяет переданный `store-id` с project pointer и разрешает зарегистрированный Store;
2. сверяет переданный `repository-id` с cwd, `origin` и `sdd.yaml` на Baseline;
3. обновляет remote refs Store и проверяет, что `spec_baseline` является точной доступной Git commit;
4. создаёт отдельный detached worktree этого Store внутри runtime текущего репозитория;
5. читает `sdd.yaml` из worktree и проверяет наличие инструкции `sdd-apply.md` выбранного агента;
6. из worktree вызывает строгий `openspec validate` и `openspec instructions apply`;
7. проверяет, что каждый переданный Work Package ID существует в структурированном результате OpenSpec и ещё не выполнен;
8. обновляет remote refs Code Repository;
9. подготавливает `feature/<change-id>` по ограниченным правилам ниже;
10. сохраняет минимальный runtime-контекст и возвращает `implementation_ready`.

Отдельная команда `sdd open` не вводится. Дополнительный digest Work Package также не нужен: пара `spec_baseline + Work Package ID` уже однозначно определяет принятую задачу.

### 4. Проверьте результат

Успешный результат содержит:

```text
step_status: implementation_ready
store_id: payments-specs
change_id: pay-412-payment-status
spec_baseline: 0123456789abcdef0123456789abcdef01234567
repository_id: payments-api
implementation_branch: feature/pay-412-payment-status
branch_status: created
work_packages: 1, 2
selected_tasks:
  - id: "1"
    description: "Реализовать API для payments-api"
  - id: "2"
    description: "Добавить контрактные проверки для payments-api"
next_step: 06
next_action: Прочитай и выполни инструкцию "<absolute-runtime-store-path>/<agent-commands-directory>/sdd-apply.md" с параметрами: --store payments-specs --repo payments-api --change pay-412-payment-status --baseline 0123456789abcdef0123456789abcdef01234567 --work-package "1" --work-package "2"
```

Для агента доступен тот же результат с `--json`. `next_action` является готовым первым сообщением новой сессии: оно указывает точный `sdd-apply.md` внутри runtime Store и передаёт те же явные параметры, которые получил `sdd load`. Поэтому команда не должна обнаруживаться как slash-команда в Code Repository, а Apply не вычисляет параметры повторно и только сверяет их с runtime. `selected_tasks` показывает descriptions непосредственно из структурированного ответа OpenSpec на выбранном Baseline, чтобы Apply Owner мог заметить ошибочно назначенный ID до реализации. Эти descriptions не записываются в runtime и не становятся новым источником истины. Успех означает только готовность входных данных и ветки. Он не означает, что реализация или проверки выполнены.

Apply Owner сверяет показанные ID и descriptions с implementation subtask и текущим `repository_id`. Назначение Work Packages репозиторию уже подтверждено в Planning PR и передано через subtask; `sdd load` показывает Tasks, но не пытается автоматически вывести назначение из их текста.

Если subtask содержит другие ещё не выполненные ID, успешный результат завершает подготовку только текущей Apply-сессии. Полный прогресс репозитория остаётся виден в subtask и Draft PR; runtime не является журналом выполнения.

### 5. Повторный запуск

Повтор той же команды с теми же параметрами идемпотентен:

- существующий worktree того же Baseline и repository-id переиспользуется;
- совпадающий runtime-контекст обновляется из тех же источников;
- implementation-ветка не пересоздаётся и не перебазируется;
- Store, Change, validation, Tasks и Git-состояние проверяются заново.

Если implementation-ветка уже существует, команда возобновляет её только при чистом checkout, совпадающем `origin` и непротиворечивом upstream. Она не выполняет merge, rebase, reset, force-push или удаление веток.

Каждый повторный запуск определяется неизменными параметрами Change из implementation subtask и выбранным для текущей сессии непустым подмножеством её `work_packages`. После успешной проверки команда заменяет локальный runtime этим выбранным набором; она не объединяет его с прежним context, не ведёт progress-state и не определяет, требовался ли amendment. Полный назначенный набор и история согласований остаются в subtask под ответственностью Change Owner и шага 06.

Если runtime потерян или работа перенесена на другую машину, Apply Owner запускает ту же команду с актуальными параметрами subtask. Существующая implementation-ветка не перебазируется и не переписывается.

### 6. Завершите шаг

Шаг 05 завершён для Code Repository, когда:

- Change Owner передал в subtask принятую SHA Store как `spec_baseline`;
- Change на этой SHA завершён и проходит строгую OpenSpec-валидацию;
- назначенные Work Package ID найдены в штатном выводе OpenSpec;
- detached worktree Store объявлен immutable input и не входит в границы записи;
- implementation-ветка создана или безопасно возобновлена;
- runtime-контекст сохранён вне Git-репозиториев;
- `sdd load` вернул `implementation_ready`;
- код и OpenSpec-артефакты не изменялись.

Шаг выполняется независимо для каждой implementation subtask. Все репозитории продолжают ссылаться на один бизнесовый Change и один принятый Spec Baseline.

## Техническая спецификация шага 05

### Пользовательская поверхность

Шаг добавляет одну CLI-команду:

```text
sdd load --store <store-id>
         --repo <repository-id>
         --change <change-id>
         --baseline <40-char-sha>
         --work-package <id>...
         [--json]
```

Все параметры обязательны. Store, repository, Change и Baseline переносятся из текущей implementation subtask без изменений. `--work-package` указывается хотя бы один раз для выбранной рабочей порции, не допускает пустых значений и дубликатов и принимает точный строковый `task.id`, возвращённый OpenSpec для выбранного Baseline. Выбранные ID должны входить в полный `work_packages` subtask; это процессная проверка Apply Owner, поскольку harness не обращается к tracker. Harness не задаёт формат ID. Переданные `store-id` и `repository-id` не вычисляются автоматически: команда только сверяет их с project pointer, cwd, `origin` и `sdd.yaml`.

Команда запускается из корня выбранного Code Repository в стандартной структуре `<workspace>/src/<repository-id>`, которую создаёт `sdd connect`. Workspace выводится из пути Code Repository, поэтому Store может находиться вне `<workspace>/openspec/`, если при подключении использовался явный `sdd connect --workspace`. Новый параметр `--workspace` для `sdd load` не требуется. `sdd-apply.md` остаётся агентской инструкцией шага 06 и читается по точному пути из `next_action`.

### Использование OpenSpec API

| Проверка | Базовый механизм |
|---|---|
| Зарегистрированный Store и его состояние | `openspec store doctor <store-id> --json` |
| Корректность Change | `openspec validate <change-id> --type change --strict --no-interactive --json` |
| Стандартные Tasks и apply-контекст | `openspec instructions apply --change <change-id> --json` |

`sdd` структурно проверяет JSON-контракты этих команд и передаёт их ошибки пользователю. Собственные аналоги status, validation и apply instructions не создаются.

Проверка ограничена Change, переданным в implementation subtask. Она повторяет принятое на шаге 04 осознанное отклонение от референсного `validate --all`: один независимый активный Change центрального Store не должен блокировать загрузку другой фичи. Строгая валидация выполняется для того же `change-id` на точном `spec_baseline`, а не для плавающего HEAD Store.

Наличие Baseline проверяется штатным Git как точная commit в зарегистрированном Store. `sdd load` не восстанавливает историю Planning PR и не доказывает, что SHA является результатом merge: это уже зафиксировано Change Owner в implementation subtask на шаге 04. На выбранной SHA команда проверяет конфигурацию Store, Change и Tasks.

### Почему нужен detached worktree

OpenSpec `--store <id>` всегда разрешает текущий зарегистрированный checkout и не принимает Git SHA. Но шаг 05 обязан читать требования ровно на `spec_baseline`, даже если основная ветка Store уже продвинулась.

Поэтому harness создаёт стандартный Git worktree:

```text
<workspace>/.sdd/runtime/<store-id>/<change-id>/<repository-id>/store/
```

Worktree создаётся отдельно для каждого `repository-id` от уже зарегистрированного Store и не является отдельным clone или вторым Store. Основной checkout Store, его локальная ветка и глобальная регистрация не переключаются. Его текущая ветка и незакоммиченные рабочие файлы не блокируют `sdd load`: команда использует только Store identity, remote и Git-объекты, а planning-артефакты читает исключительно из detached worktree Baseline.

OpenSpec-команды для Change запускаются с точным cwd worktree без `--store`, иначе CLI снова выбрал бы зарегистрированный текущий checkout. Harness проверяет:

- абсолютный `root.path` OpenSpec равен корню worktree;
- Store metadata содержит ожидаемый `store-id`;
- `git rev-parse HEAD` равен `spec_baseline`;
- worktree не содержит изменений до запуска Apply.

Это единственное отклонение от передачи `--store`: используется тот же OpenSpec root и тот же базовый API, но на зафиксированной Git-ревизии.

Worktree не защищается через `chmod` или платформенный sandbox. Он исключён из `allowed_edit_roots` и считается проверяемым immutable input. Инструкция Apply проверяет его Git-состояние до и после работы; при изменении операция останавливается, а следующий `sdd load` воспроизводит worktree из того же Baseline.

Если каталог runtime worktree отсутствует, но его точная регистрация сохранилась в данном Store, повторный `sdd load` удаляет только эту потерянную регистрацию и воспроизводит worktree. Глобальный `git worktree prune` и удаление незарегистрированных каталогов не выполняются.

### Work Packages

Источник Tasks — только массив `tasks` из `openspec instructions apply --json` на выбранном Baseline.

Для переданных ID проверяется:

- запись с таким ID существует;
- ID не передан дважды;
- задача не имеет `done: true`.

Сопоставление выполняется только по точному `tasks[].id`. Поле `description`, включая визуальный номер вроде `2.1` в тексте checkbox, не разбирается и не считается машинным ID. При correction PR набор ID заново получают из структурированного ответа на новом Baseline.

Repository assignment не вычисляется из свободного текста Tasks. Его источники — принятый Planning PR и implementation subtask. Отдельный parser Markdown, специальный формат Tasks, digest или SDD-валидатор не вводятся.

Один запуск может выбрать весь назначенный набор либо только его часть. Все последовательные запуски одного репозитория используют те же `change-id`, `spec_baseline`, `feature/<change-id>` и Draft PR. Передача следующей порции заменяет `work_packages` локального runtime, но не означает выполнение или отмену ранее выбранных пакетов.

### Implementation-ветка

Для нового запуска команда:

1. выполняет fetch `origin/<default-branch>` Code Repository;
2. проверяет чистоту и отсутствие незавершённых Git-операций;
3. фиксирует SHA `origin/<default-branch>` как `code_base_revision`;
4. создаёт локальную `feature/<change-id>` от этой SHA;
5. не создаёт commit и не публикует ветку.

Если `feature/<change-id>` отсутствует локально и удалённо, команда создаёт её от свежей `origin/<default-branch>`. Если существует только удалённая ветка, создаётся обычная tracking-ветка без изменения истории. Существующая локальная ветка принимается только тогда, когда пользователь уже находится на ней.

Diverged upstream, другая текущая ветка, ветка в другом worktree или незавершённая Git-операция блокируют шаг. `sdd load` никогда не выполняет merge, rebase, reset, push или удаление веток.

### Runtime-контекст

Runtime и принадлежащий ему Store worktree хранятся локально:

```text
<workspace>/.sdd/runtime/<store-id>/<change-id>/<repository-id>/
├── context.json
└── store/
```

Минимальная структура:

```json
{
  "version": 1,
  "step_status": "implementation_ready",
  "store_id": "payments-specs",
  "change_id": "pay-412-payment-status",
  "spec_baseline": "<accepted-40-character-revision>",
  "spec_root": "<absolute-runtime-store-path>",
  "repository_id": "payments-api",
  "code_root": "<absolute-code-repository-path>",
  "implementation_branch": "feature/pay-412-payment-status",
  "code_base_revision": "<40-character-code-revision>",
  "work_packages": ["1", "2"],
  "allowed_edit_roots": ["<absolute-code-repository-path>"],
  "immutable_roots": ["<absolute-runtime-store-path>"]
}
```

Descriptions Tasks, digest, ticket content, credential и исходный код в runtime не копируются. Контекст является воспроизводимым локальным указателем текущей Apply-сессии, а не новым источником истины или журналом прогресса. Полный назначенный набор остаётся в implementation subtask. После потери runtime параметры Change и нужная следующая порция Work Packages восстанавливаются из актуальной subtask; существующая ветка сама по себе не содержит полную привязку к Baseline и назначенному scope.

### Ограничение контекста агента

`sdd load` не загружает целиком Store или Code Repository в prompt. На шаге 06 агент получает пути, Work Package ID и границы доступа, затем:

1. читает Proposal, применимые Specs, Design и выбранные Tasks из точного worktree;
2. ищет Repository Knowledge Pack в provider-specific каталоге целевого репозитория;
3. при отсутствии достаточной документации выполняет адресное чтение кода;
4. не загружает другие Code Repositories автоматически.

Read-only исследование другого репозитория при необходимости остаётся отдельным изолированным контекстом и не расширяет `allowed_edit_roots` текущей subtask.

### Ошибки и повторный запуск

OpenSpec- и Git-ошибки передаются пользователю с исходной причиной. Большой собственный справочник дублирующих кодов не вводится.

Проектный слой добавляет один успешный статус `implementation_ready`: переданные Store, Baseline, repository и Work Package ID проверены, а реализация может начинаться. Несовпадение явных параметров с pointer, cwd, `origin` или `sdd.yaml`, отсутствие commit, невалидный Change, неизвестная Task и нарушение целостности Store worktree являются обычными ошибками команды, а не отдельными состояниями процесса.

При ошибке команда не изменяет рабочие файлы, не применяет recovery-операции Git и не оставляет новый runtime со статусом ready.

### Разрешённые записи

Шаг изменяет только:

```text
Git metadata зарегистрированного Store для fetch/worktree
Git metadata целевого Code Repository для fetch/branch
<workspace>/.sdd/runtime/<store-id>/<change-id>/<repository-id>/**
```

Рабочие файлы и ветка центрального Store, кодовые файлы, OpenSpec-артефакты, другие Code Repositories, tracker и глобальная регистрация Store не изменяются.

`selected_tasks` присутствует только в результате команды; `context.json` по-прежнему хранит только `work_packages`. На шаге 06 агент получает `next_action` первым сообщением из корня Code Repository, читает указанную инструкцию, открывает runtime по прямому пути, проверяет совпадение Store, repository, Change, Baseline, Work Packages и текущих branch/HEAD, затем повторно получает `openspec instructions apply` из того же worktree. До этого момента агент не изменяет код.
