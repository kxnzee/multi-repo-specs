## 02. Создание OpenSpec Change

Если вам нужно только пройти шаг 02, достаточно раздела «Пользовательская инструкция». Техническая спецификация ниже предназначена для разработчиков CLI и ревью процесса.

### Пользовательская инструкция

#### 1. Проверьте, что Explore завершён

Перед созданием Change должны выполняться условия шага 01:

- есть Jira ticket key вида `PAY-412`;
- проблема и ожидаемый результат понятны;
- подходящие нормативный контекст, Master Specs и код исследованы;
- известны репозитории-кандидаты и внешние системы;
- блокирующих вопросов нет;
- Change Owner разрешил создать Change;
- центральный Store находится на чистой и актуальной основной ветке.

Шаг 02 не повторяет Explore и не переносит историю чата в OpenSpec. Его задача — выбрать постоянный идентификатор работы и создать пустой Change в центральном Store.

#### 2. Выберите краткое название

Пользователь передаёт Jira key и короткое имя изменения отдельно. Например:

```text
ticket: PAY-412
name: payment-status
```

`name` должно быть коротким lowercase kebab-case и описывать изменение, а не решение или конкретный репозиторий. Например: `payment-status`, `team-update`, `session-timeout`.

Итоговый `change-id` формируется автоматически:

```text
<jira-key-lowercase>-<name>
```

Для примера выше:

```text
pay-412-payment-status
```

Такой формат одновременно соответствует связи с внешним ticket и ограничениям OpenSpec на имя Change: lowercase kebab-case, начало с буквы, без пробелов, подчёркиваний, заглавных букв и повторных дефисов.

#### 3. Создайте Change

Из центрального Store выполните:

```bash
sdd change --ticket PAY-412 --name payment-status
```

Команда:

1. разрешит зарегистрированный OpenSpec Store и проверит его состояние;
2. убедится, что Store находится на чистой актуальной основной ветке;
3. сформирует `change-id` `pay-412-payment-status`;
4. повторно проверит активные и архивные Changes, чтобы не создать дубликат;
5. создаст в Spec Root рабочую ветку `feature/pay-412-payment-status`;
6. вызовет официальный OpenSpec CLI с явным Store и стандартной схемой `spec-driven`;
7. проверит созданный Change через официальный `openspec status`.

Эквивалентная операция OpenSpec, которую выполняет SDD после своих проверок:

```bash
openspec new change pay-412-payment-status \
  --schema spec-driven \
  --store payments-specs \
  --json
```

Пользователю не нужно запускать эту команду отдельно.

#### 4. Проверьте результат

После успешного запуска ожидается один Change только в центральном Store:

```text
openspec/changes/
└── pay-412-payment-status/
    └── .openspec.yaml
```

Точный набор служебных файлов контролируется установленной версией OpenSpec. На шаге 02 не должны появляться `proposal.md`, Delta Specs, `design.md` или `tasks.md`: они создаются последовательно на шагах 03–06.

Команда печатает итог примерно такого вида:

```text
change_status: created
store_id: payments-specs
ticket: PAY-412
change_id: pay-412-payment-status
branch: feature/pay-412-payment-status
schema: spec-driven
next_step: 03
```

#### 5. Завершите шаг

Шаг 02 завершён, когда:

- существует ровно один активный Change для ticket;
- его ID однозначно связан с Jira key;
- Change находится только в центральном Store;
- используется схема `spec-driven`;
- рабочая ветка Spec Root называется `feature/<change-id>`;
- `openspec status` успешно читает созданный Change;
- planning-артефакты и код ещё не создавались.

После этого можно переходить к шагу 03 — Proposal.

Шаг 02 не создаёт PR, не изменяет Code Repositories, не создаёт ветки реализации и не запускает AI-агента. Первый PR конкретного изменения остаётся Planning PR шага 07.

## Техническая спецификация шага 02

Шаг создаёт первое постоянное состояние конкретного запроса в SDD-процессе: единый OpenSpec Change в центральном Store. Он выполняется только после принятого Explore шага 01 и до создания любого planning-артефакта.

Change является общим контейнером будущих Proposal, Delta Specs, Design и Tasks. Он принадлежит только Spec Root Repository. Code Repositories на шаге 02 не читаются и не изменяются: их набор был исследован на шаге 01, окончательный impact будет зафиксирован в следующих planning-артефактах, а ветки реализации появятся только после принятого Spec Baseline.

SDD не заменяет механизм создания Change OpenSpec. Команда `sdd change` добавляет только проектные инварианты — связь с ticket, однозначный Store, проверку дубликатов, Git-границу и фиксированную схему — после чего делегирует создание официальному `openspec new change`.

### Владельцы

| Роль | Ответственность на шаге 02 |
|---|---|
| Change Owner | Подтверждает завершение Explore, выбирает краткое имя и разрешает создание Change |
| Spec Owner | Подтверждает, что Change создаётся в правильном Store и соответствует принятому процессу |
| Technical Owner | Подключается только при ошибке Store, Git-конфигурации или неоднозначном техническом состоянии |
| Apply Owner | Не участвует; реализация ещё не началась |
| QA | Не участвует; Evidence и verification появятся позже |
| Security Owner | Подключается только если уже на входе остаётся блокирующее security/compliance-ограничение; в таком случае шаг 01 нельзя считать завершённым |

Change Owner не обязан самостоятельно знать внутреннюю структуру OpenSpec. Spec Owner не утверждает содержание Proposal на шаге 02: содержательное ревью начинается на шаге 03.

### Вход

- шаг 01 завершён и Change Owner явно разрешил создать Change;
- Jira ticket key передан в формате `<PROJECT>-<number>` в верхнем регистре, например `PAY-412`;
- выбрано непустое краткое имя `name` в lowercase kebab-case;
- Spec Root зарегистрирован как OpenSpec Store под ID из `.openspec-store/store.yaml`;
- `sdd.yaml` содержит ровно одну запись `role: store`, чей `id` совпадает с Store ID;
- центральный checkout находится на `default_branch` из `sdd.yaml`, рабочее дерево чистое и `HEAD` совпадает с `origin/<default_branch>` после `fetch`;
- OpenSpec версии из `versions.openspec` файла `sdd.yaml` доступен CLI;
- активного Change для того же ticket нет, кроме допустимого точного повторного запуска уже созданного состояния;
- отсутствует неоднозначное частичное состояние от предыдущего неуспешного создания.

Итог Explore не передаётся в `sdd change` как JSON и не сохраняется в дополнительный SDD-файл. На шаге 02 достаточно решения Change Owner о продолжении, ticket key и короткого имени. Содержание Explore становится входом Proposal на шаге 03.

Первая реализация не обращается к Jira API. Корректный ticket key является внешним идентификатором процесса, но SDD не подтверждает по сети существование, тип или статус задачи.

### Технический контракт `sdd change`

Команда запускается из центрального Store либо из его вложенного каталога:

```bash
sdd change --ticket <ticket-id> --name <short-name>
```

Запуск из Code Repository запрещён для первой реализации. В отличие от `sdd explore`, шаг 02 меняет центральный Store и создаёт Git-ветку, поэтому точка записи должна быть очевидной пользователю и находиться непосредственно в Spec Root.

Обязательные параметры:

| Параметр | Значение |
|---|---|
| `--ticket <ticket-id>` | Jira key вида `PAY-412`; используется для связи Change с внешней задачей |
| `--name <short-name>` | Короткое lowercase kebab-case имя изменения без ticket prefix |

Флаг ручного `--change-id` не предоставляется. Это исключает разные способы кодирования одного ticket и позволяет CLI самостоятельно сформировать канонический ID.

Команда не принимает описание проблемы, Proposal, список репозиториев, готовое техническое решение или содержимое будущих артефактов.

### Разрешение Store

`sdd change` использует те же базовые инварианты Store, что шаги 00 и 01, но запись разрешена только в центральном checkout.

CLI:

1. определяет Git top-level текущего каталога;
2. требует наличие SDD skeleton центрального Store;
3. читает Store ID из `.openspec-store/store.yaml`;
4. подтверждает тот же ID через `openspec store list --json` и `openspec store doctor <store-id> --json`;
5. выполняет `openspec doctor --store <store-id> --json` и `openspec context --store <store-id> --json`;
6. читает `sdd.yaml` только из подтверждённого Store root;
7. проверяет единственную запись `role: store`, совпадение `repository-id`, канонического remote и `default_branch`.

Любая диагностика OpenSpec severity `error`, другой Store ID, другой root либо несовпадение registry с текущим checkout блокируют создание.

Nearest root, `defaultStore`, Store из предыдущей агентской сессии и pointer Code Repository не используются.

### Проверка Git-состояния

До любой записи команда выполняет для Spec Root эквивалент:

```bash
git status --porcelain --untracked-files=all
git branch --show-current
git fetch origin <default-branch>
git rev-parse HEAD
git rev-parse origin/<default-branch>
```

Требуется:

- пустой вывод `git status`;
- текущая ветка равна `default_branch`;
- remote `origin` соответствует записи `role: store`;
- `HEAD` равен `origin/<default-branch>` после `fetch`.

`sdd change` не выполняет `pull`, reset, stash, merge или rebase. Если основная ветка отстала, пользователь обновляет её вручную через `git pull --ff-only` и повторяет команду.

Свежесть проверяется повторно на шаге 02, даже если она уже подтверждалась во время Explore: между исследованием и созданием Change центральный Store мог измениться.

### Формирование `change-id`

Ticket и краткое имя имеют разные правила:

- `--ticket` принимается только как `<PROJECT>-<number>` в верхнем регистре;
- ticket-компонент `change-id` переводится в lowercase без изменения цифр и дефиса;
- `--name` уже должен быть lowercase kebab-case и не нормализуется молча;
- итог строится как `<ticket-lowercase>-<name>`.

Пример:

```text
PAY-412 + payment-status
↓
pay-412-payment-status
```

Итоговый ID дополнительно проверяется по ограничениям OpenSpec для Change name: начинается со строчной буквы, содержит только строчные латинские буквы, цифры и одиночные дефисы, не имеет пробелов, `_`, последовательных дефисов и дефиса в начале или конце.

Запрещены:

```text
PAY-412-payment-status   # заглавные буквы
pay-412                 # нет краткого имени
payment-status          # потеряна связь с ticket
pay-412_PaymentStatus   # не kebab-case
pay-412--payment-status # повторный дефис
```

SDD не пытается автоматически придумать `name` из текста Explore. Краткое имя является осознанным стабильным идентификатором, который выбирает Change Owner.

### Повторная проверка дубликатов

Перед созданием CLI получает активные Changes через:

```bash
openspec list --changes --store <store-id> --json
```

И дополнительно проверяет архив `openspec/changes/archive/` по соглашению имён, принятому на шаге 01.

Принадлежность к ticket определяется по префиксу `<ticket-lowercase>-` без учёта регистра для уже существующих исторических имён.

Правила:

- другой активный Change с тем же ticket блокирует создание независимо от его краткого имени;
- точный активный `<change-id>` может быть принят только как безопасный повторный запуск, если одновременно существует ожидаемая ветка и состояние Change прошло все проверки ниже;
- архивный Change с тем же ticket не запрещает повторное использование ticket автоматически, но выводится как предупреждение и требует явного подтверждения Change Owner в TTY;
- в non-TTY при найденном архивном совпадении команда завершается ошибкой;
- неожиданный формат ответа OpenSpec либо невозможность надёжно проверить архив блокируют запись.

Проверка повторяется после шага 01, потому что между Explore и созданием другой участник процесса мог создать Change для того же ticket.

### Рабочая ветка Spec Root

Planning-артефакты шагов 03–06 должны накапливаться отдельно от основной ветки центрального Store. Поэтому шаг 02 создаёт единственную planning-ветку Spec Root:

```text
feature/<change-id>
```

Например:

```text
feature/pay-412-payment-status
```

Перед созданием CLI проверяет отсутствие одноимённой локальной и remote-ветки, если точного активного Change ещё нет. Ветка создаётся строго от проверенного `HEAD` основной ветки:

```bash
git switch -c feature/pay-412-payment-status
```

На шаге 02 ветка создаётся только в Spec Root. Code Repositories остаются на основных ветках; их ветки реализации создаются на шаге 08 после принятого Spec Baseline.

Команда не делает commit, push и PR. Planning PR открывается только на шаге 07 после появления Proposal, Delta Specs, Design и Tasks и прохождения строгой валидации.

### Создание через официальный OpenSpec CLI

После всех SDD-проверок команда вызывает только официальный механизм создания Change:

```bash
openspec new change <change-id> \
  --schema spec-driven \
  --store <store-id> \
  --json
```

`--schema spec-driven` задаётся явно, даже если эта схема является default в проекте. SDD-процесс зависит от порядка `proposal → specs → design → tasks` и не должен меняться из-за персональной или глобальной конфигурации пользователя.

SDD не реализует собственный шаблонизатор Change, не создаёт `.openspec.yaml` вручную и не копирует OpenSpec templates в `harness`. Формат служебных файлов принадлежит установленной версии OpenSpec.

На этом шаге намеренно не используются:

- `/opsx:propose` — он создаёт сразу все planning-артефакты и нарушает разделение шагов 03–06;
- `/opsx:new` — расширенный agent workflow не нужен для операции, которую официальный CLI уже предоставляет напрямую;
- пользовательская схема OpenSpec — roadmap проекта закрепляет `spec-driven`;
- собственный Change metadata-файл SDD — связь с ticket кодируется единым `change-id`, а schema metadata принадлежит OpenSpec.

Так SDD не модифицирует и не дублирует встроенные `opsx-*` команды и skills.

### Проверка созданного Change

После успешного `openspec new change` CLI выполняет:

```bash
openspec status --change <change-id> --store <store-id> --json
```

и повторно получает список активных Changes.

Проверяется, что:

- Change существует ровно по ожидаемому пути `openspec/changes/<change-id>/` внутри разрешённого Store;
- OpenSpec распознаёт его как активный Change;
- схема равна `spec-driven`;
- первый planning-артефакт доступен в соответствии с графом схемы;
- никакой второй Change того же ticket не появился;
- все созданные или изменённые файлы находятся только внутри `openspec/changes/<change-id>/`;
- текущая ветка остаётся `feature/<change-id>`;
- Code Repositories не изменялись.

На шаге 02 отсутствие `proposal.md`, Delta Specs, `design.md` и `tasks.md` является ожидаемым состоянием, а не ошибкой.

### Повторный запуск и частичное состояние

`sdd change` должен быть безопасен к повторному запуску после успешного создания.

Если найден точный `change-id`, текущий Store содержит корректный Change с `schema: spec-driven`, существует ожидаемая ветка `feature/<change-id>` и нет конфликтующего Change того же ticket, команда ничего не создаёт и возвращает:

```text
change_status: already_created
```

Перед этим она всё равно проверяет Store, Change и Git-состояние. Повторный запуск не означает разрешение продолжить с произвольного состояния.

Следующие комбинации считаются неоднозначным частичным состоянием и блокируют автоматическое восстановление:

- ветка `feature/<change-id>` существует, а Change отсутствует;
- Change существует, а ожидаемая ветка отсутствует;
- каталог Change существует, но OpenSpec его не распознаёт;
- schema отличается от `spec-driven`;
- одновременно существуют два Change одного ticket;
- официальный `openspec new change` завершился ошибкой после частичной записи.

CLI не удаляет Change, ветки или пользовательские файлы и не выполняет reset автоматически. Он показывает найденные факты; Technical Owner вручную определяет безопасное восстановление, после чего команда запускается снова.

Если создание ветки уже выполнено, а официальный OpenSpec CLI затем завершился ошибкой, `sdd change` сохраняет фактическое состояние для диагностики и не маскирует его автоматическим rollback.

### Границы записи

На шаге 02 разрешены только:

- создание локальной ветки `feature/<change-id>` в Spec Root;
- файлы, которые официальный `openspec new change` создаёт внутри `openspec/changes/<change-id>/`.

Запрещено:

- изменять `openspec/specs/`;
- изменять `openspec/context/`;
- создавать или редактировать Proposal, Delta Specs, Design и Tasks;
- создавать ADR;
- менять `sdd.yaml`, Store metadata или project pointer;
- читать или менять Code Repositories;
- создавать implementation branches;
- делать commit, push или PR;
- обращаться к Jira API;
- запускать AI-агента;
- создавать второй Change для того же ticket.

Перед завершением команда проверяет `git status --porcelain --untracked-files=all` и отклоняет неожиданные изменения вне разрешённого каталога Change.

### Результат команды

Успешный запуск печатает как минимум:

- `change_status`: `created` или `already_created`;
- Store ID и абсолютный путь Spec Root;
- ticket key в исходном внешнем формате;
- сформированный `change-id`;
- имя planning-ветки;
- используемую схему `spec-driven`;
- относительный путь Change;
- результат официального `openspec status` в краткой форме;
- явный `next_step: 03`.

Команда не печатает готовую slash-команду для агента: шаг 02 не требует agent action.

### Результат и гейт 02

Переход к шагу 03 разрешён, когда:

- гейт шага 01 был принят Change Owner;
- ticket key прошёл синтаксическую проверку;
- сформирован канонический `change-id` `<ticket-lowercase>-<short-name>`;
- для ticket существует ровно один активный Change;
- Change создан официальным OpenSpec CLI только в центральном Store;
- Change использует стандартную схему `spec-driven`;
- `openspec status --change <change-id> --store <store-id> --json` успешно разрешает его;
- Spec Root находится в planning-ветке `feature/<change-id>`;
- изменения рабочего дерева ограничены каталогом созданного Change;
- planning-артефакты, Code Repository branches, commit, push и PR ещё не создавались;
- Spec Owner не обнаружил нарушения project ownership или Store identity.

Следующий шаг создаёт и согласовывает только `proposal.md`. Delta Specs, Design и Tasks остаются отдельными этапами дорожной карты.

Высокоуровневое продолжение процесса зафиксировано в [дорожной карте](README.md).
