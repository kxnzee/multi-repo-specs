## 02. Создание OpenSpec Change и Proposal

> Статус: шаг зафиксирован и реализован в CLI и agent pack.

Если вам нужно только пройти шаг 02, достаточно раздела «Пользовательская инструкция». Техническая спецификация ниже предназначена для разработчиков CLI, agent command и ревью процесса.

### Пользовательская инструкция

#### 1. Проверьте итог Explore

Перед продолжением должны выполняться условия шага 01:

- есть Jira ticket key вида `PAY-412`;
- уточнённые проблема и ожидаемый наблюдаемый результат понятны;
- подходящие нормативный контекст, Master Specs и код исследованы;
- известны репозитории-кандидаты и внешние системы;
- подтверждённые факты отделены от предположений;
- блокирующих вопросов нет;
- Change Owner разрешил создать Change и подготовить Proposal;
- центральный Store находится на чистой и актуальной основной ветке.

Продолжайте в той же агентской сессии, в которой завершён `/opsx-explore`: структурированный итог Explore является входом шага 02. Если сессия потеряна, повторите read-only Explore. Шаг 02 не восстанавливает результат по Jira, истории других сессий или неподтверждённому пересказу.

#### 2. Выберите краткое название

Передайте Jira key и короткое имя изменения отдельно. Например:

```text
ticket: PAY-412
name: payment-status
```

`name` должно быть коротким lowercase kebab-case и описывать изменение, а не готовое решение или конкретный репозиторий. Например: `payment-status`, `team-update`, `session-timeout`.

Итоговый `change-id` формируется автоматически:

```text
<jira-key-lowercase>-<name>
```

Для примера выше получится `pay-412-payment-status`. Такой ID начинается с буквы и содержит только строчные латинские буквы, цифры и одиночные дефисы, как требует OpenSpec.

#### 3. Создайте Change и Proposal

В той же агентской сессии из центрального Store выполните:

```text
/sdd-change PAY-412 payment-status
```

Команда агента:

1. возьмёт только подтверждённый структурированный итог текущего Explore;
2. проверит Store, ticket, дубликаты и Git-состояние;
3. сформирует `change-id` `pay-412-payment-status`;
4. создаст planning-ветку `feature/pay-412-payment-status`;
5. через внутренний CLI `sdd change` вызовет официальный `openspec new change`;
6. получит официальные OpenSpec instructions и template для `proposal`;
7. создаст только `proposal.md` из подтверждённого Explore и нормативного контекста;
8. покажет Proposal и внесёт только подтверждённые Change Owner уточнения;
9. завершит шаг после явного подтверждения Proposal.

`/sdd-change` не использует `/opsx-propose`, потому что эта команда создаёт сразу весь комплект planning-артефактов. Встроенные `opsx-*` команды и skills не изменяются.

#### 4. Проверьте результат

После успешного запуска ожидается один Change только в центральном Store:

```text
openspec/changes/
└── pay-412-payment-status/
    ├── .openspec.yaml
    └── proposal.md
```

Точный набор служебных файлов контролируется установленной версией OpenSpec. На шаге 02 не должны появляться Delta Specs, `design.md` или `tasks.md`.

Итоговый отчёт имеет вид:

```text
step_status: proposal_accepted
change_status: created
store_id: payments-specs
ticket: PAY-412
change_id: pay-412-payment-status
branch: feature/pay-412-payment-status
schema: spec-driven
proposal_status: accepted
next_step: 03
```

#### 5. Завершите шаг

Шаг 02 завершён, когда:

- для ticket существует ровно один видимый активный Change;
- Change находится только в центральном Store;
- используется схема `spec-driven`;
- Spec Root находится в planning-ветке `feature/<change-id>`;
- `openspec status` успешно читает Change;
- `proposal.md` создан через официальные instructions и отражает подтверждённый Explore;
- Change Owner явно подтвердил Proposal;
- Delta Specs, `design.md`, `tasks.md`, код, commit, push и PR ещё не создавались.

После этого можно переходить к шагу 03 — планированию Change с последовательным созданием Delta Specs, Design и Tasks.

Первый PR конкретного изменения остаётся Planning PR шага 04. Ветки Code Repositories создаются только на шаге 05 после принятого Spec Baseline.

## Техническая спецификация шага 02

Шаг объединяет создание постоянного контейнера Change и первого стандартного planning-артефакта. Пустой Change не является отдельным результатом процесса: после завершения шага в нём всегда существует подтверждённый `proposal.md`.

Proposal является долговечной передачей существенных выводов Explore. Отдельный `research.md`, `handoff.md`, runtime manifest или собственный state-файл SDD не создаётся. История чата, отвергнутые гипотезы и промежуточные рассуждения в Change не переносятся.

### Владельцы

| Роль | Ответственность на шаге 02 |
|---|---|
| Change Owner | Подтверждает завершение Explore, выбирает краткое имя, уточняет и принимает Proposal |
| Spec Owner | Не является отдельным гейтом шага; формально проверяет структуру и целостность полного planning-набора в Planning PR шага 04 |
| Technical Owner | Разрешает блокирующее техническое состояние и проверяет спорный system impact |
| Security Owner | Подтверждает оставшееся security/compliance-решение; блокирующий вопрос возвращает процесс в Explore |
| Apply Owner | Не участвует; реализация ещё не началась |
| QA | Не участвует; Evidence и verification появятся позже |

Агент не принимает решения за владельцев. Неподтверждённое утверждение не переносится в Proposal как факт.

### Вход и граница с шагом 01

Обязательный вход:

- гейт шага 01 принят Change Owner;
- текущая агентская сессия содержит полный структурированный итог `/opsx-explore`;
- Jira ticket key соответствует `<PROJECT>-<number>` в верхнем регистре;
- выбрано непустое `name` в lowercase kebab-case;
- Store и выбранные во время Explore checkout остались на зафиксированных ревизиях либо Explore повторён;
- блокирующих вопросов нет;
- Spec Root зарегистрирован как Store и находится на чистой актуальной основной ветке.

Структурированный итог Explore содержит ticket, исходное намерение, проблему, ожидаемый результат, прочитанные источники, точные ревизии, текущее поведение, репозитории-кандидаты, внешние системы, альтернативы, факты, предположения и открытые вопросы. `/sdd-change` использует его как вход текущей сессии, но сохраняет в Proposal только сведения, необходимые для дальнейшего planning.

Если для Proposal требуется новый Code Repository, новая ревизия или дополнительное исследование, шаг 02 не расширяет область чтения самостоятельно. Пользователь возвращается к шагу 01 и повторяет `sdd explore` с полным набором.

### Два уровня команды

Пользовательский интерфейс шага — agent command:

```text
/sdd-change <ticket-id> <short-name>
```

Она координирует текущий Explore, детерминированный CLI и согласование Proposal. Внутренний CLI выполняет только проверяемые операции Store, Git и OpenSpec:

```bash
sdd change --ticket <ticket-id> --name <short-name> --store <store-id>
```

Agent command передаёт `store-id` только из структурированного итога Explore. CLI не выбирает по нему другой Store: он разрешает текущий checkout и требует совпадения ID. CLI не генерирует содержимое Proposal и не читает историю чата. После успешного создания или разрешения существующего каркаса он возвращает JSON с Store root, `change-id`, веткой, путём Change и статусом OpenSpec. Agent command затем создаёт Proposal по официальным instructions.

### Разрешение Store

`sdd change` запускается только из центрального Store либо его вложенного каталога. Запуск из Code Repository запрещён.

CLI:

1. определяет Git top-level;
2. требует SDD skeleton центрального Store;
3. читает Store ID из `.openspec-store/store.yaml`;
4. подтверждает тот же ID через `openspec store list --json` и `openspec store doctor <store-id> --json`;
5. выполняет `openspec doctor --store <store-id> --json` и `openspec context --store <store-id> --json`;
6. читает `sdd.yaml` только из подтверждённого Store root;
7. проверяет единственную запись `role: store`, canonical remote и `default_branch`.

Другой Store ID, другой root, конфликт registry или диагностика severity `error` блокируют запись. Nearest root, `defaultStore` и Store из предыдущей агентской сессии не используются.

### Git-состояние первого запуска

Перед первым созданием требуется:

- чистое рабочее дерево, включая untracked-файлы;
- текущая ветка равна `default_branch` из `sdd.yaml`;
- `origin` соответствует записи `role: store`;
- после `git fetch origin <default-branch>` локальный `HEAD` равен `origin/<default-branch>`;
- локальная ветка `feature/<change-id>` отсутствует;
- адресный `git ls-remote --heads origin refs/heads/feature/<change-id>` не находит remote-ветку.

Команда не выполняет `pull`, reset, stash, merge или rebase. Несвежую основную ветку пользователь обновляет вручную через `git pull --ff-only`.

### Формирование `change-id`

Правила:

- `--ticket` принимается только в верхнем регистре как `<PROJECT>-<number>`;
- ticket-компонент переводится в lowercase;
- `--name` уже должен быть lowercase kebab-case и не нормализуется молча;
- итог строится как `<ticket-lowercase>-<name>` и повторно проверяется по правилам OpenSpec.

Пример: `PAY-412` и `payment-status` дают `pay-412-payment-status`.

### Проверка дубликатов

Активные Changes читаются через:

```bash
openspec list --changes --store <store-id> --json
```

Архив проверяется внутри разрешённого `openspec/changes/archive/`. После удаления стандартного префикса даты Change принадлежит ticket, если его имя без учёта регистра:

- точно равно `<ticket-lowercase>`; или
- начинается с `<ticket-lowercase>-`.

Другой активный Change того же ticket блокирует создание. Архивное совпадение требует подтверждения Change Owner в TTY; в non-TTY CLI завершает работу без записи. Неожиданный JSON или невозможность безопасно проверить архив также блокируют создание.

Проверка гарантирует отсутствие дубликата только в разрешённом локальном Store и доступных remote refs. До Planning PR межмашинная уникальность обеспечивается процессом: один назначенный Change Owner ведёт ticket на одной рабочей машине и не создаёт параллельную planning-ветку. CLI не заявляет техническую межмашинную резервацию.

### Создание каркаса Change

После проверок CLI создаёт planning-ветку от подтверждённого `HEAD` основной ветки:

```bash
git switch -c feature/pay-412-payment-status
```

Затем вызывает официальный OpenSpec CLI:

```bash
openspec new change <change-id> \
  --schema spec-driven \
  --store <store-id> \
  --json
```

`sdd` не создаёт `.openspec.yaml` вручную и не копирует OpenSpec templates. Успешный JSON проверяется структурно: ожидаются правильные Store root, `change-id`, путь и schema.

### Создание Proposal

После появления каркаса `/sdd-change` выполняет:

```bash
openspec instructions proposal \
  --change <change-id> \
  --store <store-id> \
  --json
```

Agent command проверяет schema, зависимости, `outputPath`, разрешённый Store root и template из ответа. Затем читает `openspec/context/00-start-here.md`, назначенный контекст и подходящие Master Specs с явным `--store`.

Proposal как минимум фиксирует:

- исходный Jira key;
- проблему и ожидаемую ценность;
- ожидаемый наблюдаемый результат;
- границы изменения и out of scope;
- Store, репозитории-кандидаты и внешние системы;
- риски совместимости;
- существенные источники и ревизии Explore;
- оставшиеся неблокирующие вопросы.

Proposal не выдаёт предположения за факты, не закрепляет преждевременно конкретную реализацию и не переносит полную историю Explore. Архитектурное решение, подробный межсистемный контракт и decomposition остаются соответственно шагами Design, Delta Specs и Tasks.

После записи агент показывает полный Proposal Change Owner. До явного подтверждения возвращается `proposal_status: needs_confirmation`; переход к шагу 03 запрещён. Если пользователь изменил scope так, что требуется новое исследование, Proposal не принимается и процесс возвращается к шагу 01.

### Повторный запуск и частичное состояние

Первичный и повторный запуск используют разные Git-инварианты.

Безопасное продолжение разрешено, когда:

- текущая ветка равна `feature/<change-id>`;
- Change существует в ожидаемом Store и использует `spec-driven`;
- рабочее дерево содержит изменения только внутри `openspec/changes/<change-id>/`;
- Delta Specs, `design.md` и `tasks.md` отсутствуют;
- другого Change того же ticket нет.

Состояния:

- Change существует, а `proposal.md` отсутствует — повторно получить instructions и создать Proposal;
- Proposal существует, но не подтверждён — показать текущий файл, продолжить уточнение и снова запросить подтверждение;
- Proposal существует и пользователь повторно подтвердил его — вернуть `step_status: proposal_accepted` без перезаписи;
- появились последующие артефакты — не возвращать процесс к шагу 02 и указать фактический следующий этап;
- ветка существует без Change, Change находится не в ожидаемой ветке, schema отличается или официальный CLI оставил нераспознаваемое состояние — `needs_recovery` без удаления и reset.

Подтверждение Proposal является человеческим гейтом текущей сессии и не выводится автоматически из наличия файла. После потери сессии агент повторно показывает Proposal и запрашивает подтверждение.

### Границы записи

Разрешены только:

- локальная planning-ветка `feature/<change-id>` в Spec Root;
- служебные файлы официального `openspec new change` внутри Change;
- `proposal.md` по официальному `outputPath`.

Запрещено:

- изменять `openspec/specs/`, `openspec/context/`, Master Specs или ADR;
- создавать Delta Specs, `design.md` или `tasks.md`;
- менять `sdd.yaml`, Store metadata или project pointer;
- менять либо создавать ветки Code Repositories;
- делать commit, push или PR;
- обращаться к Jira API;
- запускать реализацию;
- создавать второй Change того же ticket.

Code Repositories на шаге 02 заново не читаются и не проверяются. Команда гарантирует только отсутствие обращений и записей в них; фактические ревизии берутся из принятого Explore.

### Результат и гейт 02

Переход к шагу 03 разрешён, когда:

- гейт шага 01 принят;
- сформирован канонический `change-id`;
- Change создан официальным OpenSpec CLI только в центральном Store;
- Change использует `spec-driven` и находится в planning-ветке;
- `proposal.md` создан по официальным instructions;
- Proposal отражает существенный подтверждённый результат Explore;
- Change Owner явно подтвердил Proposal;
- `openspec status --change <change-id> --store <store-id> --json` успешно читает Change и показывает Delta Specs следующим доступным артефактом;
- изменения ограничены каталогом Change;
- Delta Specs, `design.md`, `tasks.md`, Code Repository branches, commit, push и PR отсутствуют.

Следующий шаг 03 последовательно создаёт Delta Specs, Design и Tasks без промежуточных человеческих гейтов. Полный комплект согласовывается вместе в Planning PR шага 04; высокоуровневое продолжение процесса зафиксировано в [дорожной карте](README.md).
