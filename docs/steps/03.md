## 03. Планирование Change: Delta Specs, Design и Tasks

> Статус: шаг зафиксирован на штатном расширенном workflow OpenSpec; отдельные SDD-команды и промежуточные человеческие гейты не требуются.

Если вам нужно только пройти шаг 03, достаточно раздела «Пользовательская инструкция». Техническая спецификация ниже предназначена для ревью процесса и настройки официального agent pack.

### Пользовательская инструкция

#### 1. Проверьте вход

Перед продолжением должны выполняться условия шага 02:

- существует один активный Change с каноническим `change-id`;
- Change находится только в центральном Store и использует схему `spec-driven`;
- текущая ветка Store имеет имя `feature/<change-id>`;
- `proposal.md` создан и явно подтверждён Change Owner;
- Proposal перечисляет новые и изменяемые capabilities;
- блокирующих вопросов нет;
- Delta Specs, `design.md`, `tasks.md`, код, commit, push и PR ещё не создавались.

Если работа продолжается в новой агентской сессии, агент перечитывает Proposal как принятый вход. Повторное человеческое подтверждение не требуется, пока не обнаружено расширение scope или противоречие подтверждённому контексту.

Из корня центрального Store проверьте состояние Change:

```bash
openspec status --change <change-id> --store <store-id> --json
```

Ожидается `proposal: done`, а первым артефактом со статусом `ready` должен быть `specs`. Если первым готов другой артефакт, остановитесь и разберите расхождение: `/opsx-continue` всегда создаёт первый `ready`-артефакт из официального статуса.

#### 2. Последовательно создайте три артефакта

В одной planning-ветке и, по возможности, в одной агентской сессии последовательно выполните:

```text
/opsx-continue <change-id>  # Delta Specs
/opsx-continue <change-id>  # Design
/opsx-continue <change-id>  # Tasks
```

Например:

```text
/opsx-continue pay-412-payment-status
```

Один вызов создаёт ровно один тип артефакта и возвращает управление пользователю. Это техническая граница команды, а не точка согласования. После сообщения об успешном создании артефакта сразу вызывайте `/opsx-continue` снова, пока `specs`, `design` и `tasks` не получат статус `done`.

Последовательность штатной схемы `spec-driven`:

1. первый вызов создаёт `specs/<capability>/spec.md`;
2. второй вызов создаёт `design.md`;
3. третий вызов создаёт `tasks.md`.

Между вызовами не проводятся отдельная строгая валидация, человеческое ревью или подтверждение владельцев. Агент только убеждается, что текущий артефакт создан полностью и следующий ожидаемый артефакт получил статус `ready`.

#### 3. Выполните рабочую самопроверку

Самопроверка нужна для того, чтобы не переносить заведомо неполный файл в следующий артефакт. Она не является гейтом и не требует ответа владельца.

Для Delta Specs проверьте, что:

- каждая capability из Proposal представлена отдельным `specs/<capability>/spec.md`;
- Requirements описывают наблюдаемое поведение и содержат `MUST` или `SHALL`;
- у добавленных и изменённых требований есть сценарии `#### Scenario:` с `WHEN`/`THEN`;
- `MODIFIED` содержит полную новую версию requirement block со всеми сохраняемыми сценариями;
- детали реализации не попали в Specs.

Для Design проверьте, что:

- решение покрывает все Delta Specs и затронутые репозитории;
- определены границы компонентов, интеграции и ответственность за данные;
- зафиксированы совместимость, миграция, rollout, rollback и существенные риски;
- спорные решения и отклонённые альтернативы объяснены.

Для Tasks проверьте, что:

- работа разделена на проверяемые Work Packages;
- каждый пакет привязан к Store, конкретному Code Repository или Composite Verification;
- для пакета понятны владелец, результат, зависимости и способ проверки;
- Tasks не объявляют реализацию выполненной и не создают кодовые ветки.

Если артефакт создан частично или явно противоречит его входам, завершите или исправьте его напрямую либо через `/opsx-update <change-id>`. Только после этого продолжайте цикл. Это восстановление корректного рабочего состояния, а не человеческое согласование.

#### 4. Проверьте готовность к Planning PR

После третьего вызова выполните только проверку состояния:

```bash
openspec status --change <change-id> --store <store-id> --json
```

Ожидается:

```text
proposal: done
specs: done
design: done
tasks: done
```

Строгая OpenSpec-валидация и содержательное ревью всего набора выполняются вместе в Planning PR шага 04. На шаге 03 не требуется отдельно показывать Specs, Design или Tasks владельцам и ждать подтверждения между вызовами `/opsx-continue`.

Итоговый рабочий отчёт:

```text
step_status: planning_artifacts_ready
store_id: payments-specs
change_id: pay-412-payment-status
branch: feature/pay-412-payment-status
schema: spec-driven
proposal_status: done
specs_status: done
design_status: done
tasks_status: done
validation: pending_planning_pr
next_step: 04
```

#### 5. Завершите шаг

Шаг 03 завершён, когда:

- Proposal, Delta Specs, Design и Tasks существуют в одном Change;
- официальный статус всех четырёх артефактов равен `done`;
- рабочая самопроверка не выявила явной неполноты, препятствующей общему ревью;
- изменения рабочего дерева ограничены `openspec/changes/<change-id>/`;
- строгая валидация и человеческие подтверждения ещё не объявлены пройденными;
- код, commit, push и PR ещё не создавались.

Следующий шаг — 04, единый Planning PR и Spec Baseline. Design и Tasks уже включены в непрерывный шаг 03. Master Specs не изменяются до Archive шага 09.

## Техническая спецификация шага 03

### Место в процессе

Шаг объединяет три стандартных planning-артефакта встроенной схемы OpenSpec `spec-driven`:

```text
             ┌─→ specs ──┐
proposal ────┤            ├─→ tasks ─→ Planning PR
             └─→ design ─┘
```

В OpenSpec 1.7.0 после Proposal одновременно доступны Specs и Design. `/opsx-continue` читает массив `artifacts` из `openspec status`, выбирает первый элемент со статусом `ready`, создаёт ровно один артефакт и останавливается. В штатном порядке `specs` расположен перед `design`, а `tasks` становится готов после обоих.

Нумерация шага и единый Planning PR являются правилами проектного SDD-процесса. Создание каждого файла остаётся стандартным действием OpenSpec. Собственная schema, `/sdd-specs`, `sdd specs`, копии templates и изменения встроенной `/opsx-continue` не создаются.

### Граница согласования

У шага 03 нет промежуточного человеческого гейта. Создание Specs, Design и Tasks — единая подготовительная работа Change Owner.

Владельцы могут быть привлечены во время подготовки только для снятия действительно блокирующего вопроса. Отсутствие такого вопроса не требует ожидания подтверждений. Формальное ревью выполняется один раз в Planning PR:

| Роль | Область ревью в Planning PR |
|---|---|
| Change Owner | Соответствие всего Change исходному намерению и границам Proposal |
| Spec Owner | Capabilities, delta operations, Requirements и Scenarios |
| Technical Owner | Системное решение, реализуемость, совместимость, rollout и rollback |
| Security Owner | Затронутые security, privacy и compliance-инварианты |
| Владельцы Code Repositories | Реализуемость и границы назначенных Work Packages |
| QA | Проверяемость сценариев и план Composite Verification |

Замечания ко всем артефактам исправляются в той же planning-ветке и проходят повторную общую проверку. Кодовая реализация начинается только после принятия Planning PR и фиксации Spec Baseline.

### Обязательный вход

- Store зарегистрирован и `sdd connect` возвращает `ready`;
- официальный expanded agent pack содержит обычный файл `opsx-continue.md` в `agent.commands_directory`;
- активный Change однозначно выбран по переданному `change-id` и принадлежит центральному Store;
- Change использует `spec-driven` без `skip_specs: true`;
- текущая ветка равна `feature/<change-id>`, ещё не опубликована и не содержит собственных commit;
- изменения рабочего дерева ограничены `openspec/changes/<change-id>/`;
- `proposal.md` имеет статус `done` и был подтверждён Change Owner на шаге 02;
- первым `ready`-артефактом официального статуса является `specs`;
- `design.md` и `tasks.md` отсутствуют;
- блокирующих вопросов нет.

Если уточнение не меняет исследованный scope, артефакты можно привести в соответствие до открытия Planning PR. Новый репозиторий, новая внешняя система, новая ревизия кода или существенное расширение scope требует возврата в Explore. До закрытия `BL-001` такой возврат после создания Change является известным блокирующим сценарием и не должен маскироваться ручным удалением Change или planning-артефактов.

### Официальный agent pack

`/opsx-continue` должна происходить из установленной версии OpenSpec. `sdd init` устанавливает официальный custom profile со всем expanded-набором в изолированном окружении и не изменяет глобальный профиль пользователя. В Store коммитятся сгенерированные provider-specific команды и skills.

Для нового checkout `sdd connect` проверяет наличие как минимум `opsx-explore.md`, `opsx-continue.md`, `sdd-context.md` и `sdd-change.md`. Он не восстанавливает и не редактирует agent pack автоматически.

В Qwen-проекте официальный pack обновляет Technical Owner через `openspec config profile` с выбранным expanded-набором и затем `openspec update --force`. Для GigaCode совместимый pack обновляется вместе с SDD adapter, пока OpenSpec не поддерживает этот provider напрямую.

### Цикл `/opsx-continue`

Для каждого очередного артефакта официальная команда самостоятельно выполняет эквивалент:

```bash
openspec status --change <change-id> --store <store-id> --json
openspec instructions <artifact-id> --change <change-id> --store <store-id> --json
```

Store выбирается по встроенному Store guidance OpenSpec. Работа из центрального Store и явный `change-id` обязательны; nearest root, `defaultStore` и неявный выбор Change проектным процессом не допускаются.

`instructions` установленной версии является авторитетным источником `template`, `instruction`, `context`, `rules`, зависимостей и `resolvedOutputPath`. Ожидаемый цикл:

| Вызов | `artifactId` | Результат | Зависимости |
|---|---|---|---|
| 1 | `specs` | `specs/<capability>/spec.md` | `proposal` |
| 2 | `design` | `design.md` | `proposal` |
| 3 | `tasks` | `tasks.md` | `specs`, `design` |

Стандартная команда перечитывает dependency-файлы с диска, создаёт файлы по официальному пути, показывает прогресс и прекращает работу после одного артефакта. Проект не копирует эту логику в harness и не добавляет поверх неё отдельную команду оркестрации.

### Источники и границы артефактов

Общими входами являются Proposal, подтверждённый context pack, релевантные ADR, Master Specs и другие активные Changes. `_raw/` не является нормативным источником. Code Repositories и Jira API на шаге 03 заново не читаются. Если постоянных источников недостаточно, агент задаёт адресный вопрос владельцу или возвращает процесс в Explore.

Границы содержания:

- Delta Specs фиксируют изменение наблюдаемого поведения относительно Master Specs;
- Design фиксирует системное техническое решение и межрепозиторные границы;
- Tasks раскладывает принятое решение на Work Packages и проверки;
- ни один артефакт не утверждает, что код уже реализован или проверен;
- Master Specs, код и implementation plans Code Repositories на этом шаге не изменяются.

Для существующего требования `MODIFIED` содержит его полную новую версию вместе со всеми сохраняемыми и изменёнными сценариями. Частичная вставка при Archive заменит прежний блок и потеряет пропущенное содержание.

### Восстановление и повторный запуск

OpenSpec определяет завершённость артефакта по наличию файла по ожидаемому пути. Поэтому перед повторным `/opsx-continue` нужно проверить не человеческое одобрение, а техническую полноту только что созданного артефакта.

- если ожидаемый артефакт отсутствует, вызывается `/opsx-continue`;
- если он создан полностью, цикл сразу продолжается следующим вызовом;
- если создан частично, он завершается напрямую либо через `/opsx-update` до следующего вызова;
- если входы изменены, зависимые артефакты актуализируются перед Planning PR;
- если `status` не соответствует ожидаемой последовательности, процесс останавливается без удаления файлов и автоматического перехода дальше.

Человеческое подтверждение не выводится из наличия файлов. Оно появляется только по результатам ревью Planning PR.

### Валидация

На шаге 03 не выполняется отдельная формальная валидация после каждого артефакта. Проверка `status` подтверждает только завершение графа и не подменяет проверку содержания.

В шаге 04 весь Change валидируется как единое целое:

```bash
openspec show <change-id> \
  --type change \
  --no-interactive \
  --store <store-id> \
  --json

openspec validate <change-id> \
  --type change \
  --strict \
  --no-interactive \
  --store <store-id> \
  --json
```

Результаты прикладываются к Planning PR вместе с полным diff Proposal, Delta Specs, Design и Tasks. После исправлений в том же PR строгая проверка повторяется для всего Change.

### Разрешённые записи

На шаге разрешено создавать и исправлять только:

```text
openspec/changes/<change-id>/specs/**/*.md
openspec/changes/<change-id>/design.md
openspec/changes/<change-id>/tasks.md
```

`proposal.md` можно уточнить только без расширения подтверждённого scope и с последующей актуализацией зависимых артефактов. Нельзя изменять Master Specs, context pack, ADR, Store metadata, Code Repositories, `.qwen/skills/openspec-*` или `.qwen/commands/opsx-*`.

На этом шаге также нельзя создавать commit, push, PR, Spec Baseline, кодовые ветки, implementation plans и Evidence.

### Результат и переход к шагу 04

Результат шага — полный, но ещё не принятый комплект planning-артефактов в рабочем дереве центрального Store:

```text
openspec/changes/<change-id>/
├── .openspec.yaml
├── proposal.md
├── specs/
│   └── <capability>/spec.md
├── design.md
└── tasks.md
```

Переход разрешён, когда `proposal`, `specs`, `design` и `tasks` имеют статус `done`, а незакоммиченные изменения ограничены текущим Change. Никакие содержательные артефакты на этом переходе ещё не считаются утверждёнными.

Шаг 04 открывает единый Planning PR, выполняет строгую OpenSpec-валидацию, собирает подтверждения владельцев и после merge фиксирует Spec Baseline.
