## 03. Планирование Change: Delta Specs, Design и Tasks

> Статус: шаг зафиксирован на штатном расширенном workflow OpenSpec; отдельные SDD-команды и человеческие гейты между planning-артефактами не требуются.

Если вам нужно только пройти шаг 03, достаточно раздела «Пользовательская инструкция». Техническая спецификация ниже предназначена для ревью процесса и настройки официального agent pack.

### Пользовательская инструкция

#### 1. Проверьте вход

Перед продолжением должны выполняться условия шага 02:

- существует один активный Change с каноническим `change-id`;
- Change находится только в центральном Store и использует схему `spec-driven`;
- текущая ветка Store имеет имя `feature/<change-id>`;
- `proposal.md` создан и явно подтверждён Change Owner;
- Proposal перечисляет новые и изменяемые capabilities;
- блокирующих вопросов нет;
- Delta Specs, `design.md`, `tasks.md`, код, commit, push и PR ещё не создавались.

Если работа продолжается в новой агентской сессии, до первого `/opsx-continue` агент перечитывает и показывает Change Owner полный Proposal, затем получает явное подтверждение того, что это принятый вход шага 03. Наличие `proposal.md` и статус OpenSpec `done` не заменяют этот человеческий гейт. Повторять Explore, пересоздавать Proposal или вводить отдельный approval-файл не нужно. Если Change Owner не подтвердил Proposal либо обнаружено расширение scope или противоречие подтверждённому контексту, `/opsx-continue` не запускается.

Из корня центрального Store проверьте состояние Change:

```bash
openspec status --change <change-id> --store <store-id> --json
```

Ожидается `proposal: done`, а первым артефактом со статусом `ready` должен быть `specs`. Если первым готов другой артефакт, остановитесь и разберите расхождение: `/opsx-continue` всегда создаёт первый `ready`-артефакт из официального статуса.

#### 2. Последовательно создайте три артефакта

В одной planning-ветке и, по возможности, в одной агентской сессии последовательно выполните:

```text
/opsx-continue <change-id>  # Delta Specs
/opsx-continue <change-id>  # Design
/opsx-continue <change-id>  # Tasks
```

Например:

```text
/opsx-continue pay-412-payment-status
```

Один вызов создаёт ровно один тип артефакта и возвращает управление пользователю. Это техническая граница команды, а не точка согласования. После сообщения об успешном создании артефакта сразу вызывайте `/opsx-continue` снова, пока `specs`, `design` и `tasks` не получат статус `done`.

Последовательность штатной схемы `spec-driven`:

1. первый вызов создаёт `specs/<capability>/spec.md`;
2. второй вызов создаёт `design.md`;
3. третий вызов создаёт `tasks.md`.

Между вызовами не проводятся отдельная строгая валидация, человеческое ревью или подтверждение владельцев. Агент только убеждается, что текущий артефакт создан полностью и следующий ожидаемый артефакт получил статус `ready`.

Пользователь не запускает subagents отдельной командой. Если для текущего артефакта требуется техническое чтение нескольких или крупных Code Repositories, основной агент внутри `/opsx-continue` создаёт native subagents и получает от них ограниченные Repository Context Passes. Практический контракт описан в руководстве [«Работа с subagents при планировании Change»](../subagents.md).

#### 3. Выполните рабочую самопроверку

Самопроверка нужна для того, чтобы не переносить заведомо неполный файл в следующий артефакт. Она не является гейтом и не требует ответа владельца.

Для Delta Specs проверьте, что:

- каждая capability из Proposal представлена отдельным `specs/<capability>/spec.md`;
- Requirements описывают наблюдаемое поведение и содержат `MUST` или `SHALL`;
- у добавленных и изменённых требований есть сценарии `#### Scenario:` с `WHEN`/`THEN`;
- каждый Requirement и Scenario прямо следует из подтверждённого Proposal, а Scenario не расширяет и не опровергает свой Requirement;
- новые наблюдаемые состояния, значения, внешние системы или scope возвращаются Change Owner на шаг Proposal, а не добавляются в Specs;
- `MODIFIED` содержит полную новую версию requirement block со всеми сохраняемыми сценариями;
- детали реализации не попали в Specs.

Для Design проверьте, что:

- решение покрывает все Delta Specs и затронутые репозитории;
- перечислен окончательный технический impact по `repository-id` и точным ревизиям исследованных checkout;
- определены межсистемные границы, интеграции и ответственность за данные;
- зафиксированы совместимость, миграция, rollout, rollback и существенные риски;
- спорные решения и отклонённые альтернативы объяснены.
- локальное устройство репозитория, файлы, классы, функции, хуки, внутренние модули и конкретные библиотеки не перенесены в центральный Design.

Для Tasks проверьте, что:

- работа разделена на проверяемые Work Packages;
- каждый Work Package представлен отдельным стандартным checkbox `tasks.md` и явно указывает свой `repository-id` либо `composite-verification`;
- для последующей передачи реализации используется только `task.id` из структурированного ответа `openspec instructions apply` на принятом Spec Baseline, а не номер или текст внутри checkbox;
- каждый пакет привязан к Store, конкретному Code Repository или Composite Verification;
- для пакета понятны владелец, результат, зависимости и способ проверки;
- пакет не перечисляет файлы, классы, функции и локальные implementation steps;
- Tasks не объявляют реализацию выполненной и не создают кодовые ветки.

Если артефакт создан частично или явно противоречит его входам, завершите или исправьте его напрямую либо через `/opsx-update <change-id>`. Только после этого продолжайте цикл. Это восстановление корректного рабочего состояния, а не человеческое согласование.

#### 4. Проверьте готовность к Planning PR

После третьего вызова выполните только проверку состояния:

```bash
openspec status --change <change-id> --store <store-id> --json
```

Ожидается:

```text
proposal: done
specs: done
design: done
tasks: done
```

Строгая OpenSpec-валидация и содержательное ревью всего набора выполняются вместе в Planning PR шага 04. На шаге 03 не требуется отдельно показывать Specs, Design или Tasks владельцам и ждать подтверждения между вызовами `/opsx-continue`.

Итоговый рабочий отчёт:

```text
step_status: planning_artifacts_ready
store_id: payments-specs
change_id: pay-412-payment-status
branch: feature/pay-412-payment-status
schema: spec-driven
proposal_status: done
specs_status: done
design_status: done
tasks_status: done
validation: pending_planning_pr
next_step: 04
```

#### 5. Завершите шаг

Шаг 03 завершён, когда:

- Proposal, Delta Specs, Design и Tasks существуют в одном Change;
- официальный статус всех четырёх артефактов равен `done`;
- рабочая самопроверка не выявила явной неполноты, препятствующей общему ревью;
- изменения рабочего дерева ограничены `openspec/changes/<change-id>/`;
- строгая валидация и человеческие подтверждения ещё не объявлены пройденными;
- код, commit, push и PR ещё не создавались.

Следующий шаг — 04, единый Planning PR и Spec Baseline. Design и Tasks уже включены в непрерывный шаг 03. Master Specs не изменяются до Archive шага 09.

## Техническая спецификация шага 03

### Место в процессе

Шаг объединяет три стандартных planning-артефакта встроенной схемы OpenSpec `spec-driven`:

```text
             ┌─→ specs ──┐
proposal ────┤            ├─→ tasks ─→ Planning PR
             └─→ design ─┘
```

В OpenSpec 1.7.0 после Proposal одновременно доступны Specs и Design. `/opsx-continue` читает массив `artifacts` из `openspec status`, выбирает первый элемент со статусом `ready`, создаёт ровно один артефакт и останавливается. В штатном порядке `specs` расположен перед `design`, а `tasks` становится готов после обоих.

Нумерация шага и единый Planning PR являются правилами проектного SDD-процесса. Создание каждого файла остаётся стандартным действием OpenSpec. Собственная schema, `/sdd-specs`, `sdd specs`, копии templates и изменения встроенной `/opsx-continue` не создаются.

### Границы знаний

| Понятие | Владелец и место хранения | Допустимое содержание |
|---|---|---|
| Business Specs | Центральный Store: Master Specs и Delta Specs | Наблюдаемое бизнес-поведение, Requirements, Scenarios и доменные термины |
| System Design | Центральный Change: `design.md` | Межсистемная ответственность, интеграционные контракты, владение данными, совместимость, rollout и rollback |
| Repository Knowledge Pack | Соответствующий Code Repository; поддерживают его разработчики | Устойчивое устройство кода, внутренние модули, точки расширения, локальные ограничения, сборка и тестирование |
| Local Implementation Plan | Implementation PR соответствующего Code Repository | Конкретные файлы, классы, функции, хуки и последовательность изменения кода текущей фичи |
| Work Package | Центральный Change: `tasks.md` | Ожидаемый результат для `repository-id`, зависимости и способ проверки без локального плана изменений |

Один бизнесовый Change может затрагивать любое обоснованное количество Code Repositories. Repository Knowledge Packs и Work Packages являются единицами технического анализа и исполнения, но не отдельными фичами и не отдельными OpenSpec Changes.

Центральный Store идентифицирует технический источник по `repository-id`, точной Git-ревизии и выбранному в `sdd.yaml` агенту, но не хранит отдельный `knowledge_path` и не копирует техническое содержание. Business Specs не содержат имён файлов, классов, функций, хуков, внутренних модулей, библиотек и команд сборки. System Design также не опускается до этих локальных деталей: он сохраняет только информацию, необходимую для согласования нескольких систем и безопасной поставки общей фичи.

Repository Knowledge Pack является предпочтительным, но не обязательным источником. Его отсутствие, неполнота или отсутствие ответа на вопрос текущего Change сами по себе не блокируют шаг. В этом случае агент адресно исследует Code Repository на зафиксированной ревизии: начинает с вопроса текущей фичи, использует поиск и существующие точки входа, читает только релевантные фрагменты и не загружает репозиторий целиком. Размер репозитория не является основанием разделять единый бизнесовый Change.

Блокирующим считается не отсутствие документации, а конкретный неразрешённый факт, без которого нельзя достоверно определить межсистемный контракт, совместимость или безопасную поставку. Если адресное чтение выявило устойчивое техническое знание, `tasks.md` добавляет outcome-based Work Package на обновление Knowledge Pack в implementation PR соответствующего репозитория; само знание и детали его оформления в центральный Store не копируются.

#### Автоматическое обнаружение Knowledge Pack

Дополнительная ручная настройка репозитория в `sdd.yaml` не требуется. Центральная конфигурация уже содержит `agent.id` и проверенный `agent.commands_directory`. Корнем каталога агента считается родитель `commands_directory`: `.qwen/` для Qwen и `.gigacode/` для GigaCode.

Для каждого затронутого Code Repository агент:

1. получает сохранённый agent root из центрального `sdd.yaml`;
2. строит ограниченный список обычных Markdown- и YAML-файлов внутри одноимённого provider-specific каталога репозитория;
3. сначала рассматривает файлы верхнего уровня и явно названные разделы `README`, `start-here`, `context`, `knowledge`, `architecture`, `integration`, `testing`, `deployment`, `security` и `ownership`;
4. следует только релевантным текущему Change ссылкам и не загружает все найденные документы;
5. не принимает generated `commands/` и `skills/openspec-*` за техническое описание репозитория;
6. при отсутствии достаточной информации переходит к адресному поиску и чтению исходного кода.

Каталог агента является первой областью поиска, но не обязан иметь единый внутренний layout. Разработчики репозитория могут структурировать Knowledge Pack согласно его технологии и масштабу, не меняя центральный registry и flow `/opsx-continue`.

#### Изоляция технического контекста

Единицей бизнесового планирования остаётся один OpenSpec Change. Чтобы размер нескольких Code Repositories не переполнял контекст основного агента, техническое чтение разделяется между изолированными Repository Context Passes — по одному `repository-id` на subagent. Это техническое разбиение анализа, а не отдельные фичи, Changes, Specs или человеческие гейты.

Практический порядок работы, шаблон задания, контракт результата и обработка ошибок описаны в руководстве [«Работа с subagents при планировании Change»](../subagents.md). Это руководство описывает использование native subagents agent runtime и не вводит новую команду `sdd` или OpenSpec.

Основной planning-agent является единственным писателем `proposal.md`, Delta Specs, `design.md` и `tasks.md`. Каждый изолированный контекст:

- работает read-only с одним Code Repository на точной ревизии из текущего workspace;
- получает только вопрос текущей фичи, относящиеся к нему бизнесовые границы и нужный межсистемный контекст;
- сначала использует provider-specific каталог агента и доступный Knowledge Pack;
- при необходимости адресно читает исходный код, не загружая репозиторий целиком;
- не изменяет Code Repository, центральный Store или другие Repository Context Passes;
- возвращает основному агенту краткий структурированный результат без больших фрагментов кода.

Минимальный результат Repository Context Pass содержит `repository-id`, точную ревизию, исследованный вопрос, относящиеся к System Design ограничения, интеграции, совместимость, поставку, уровень уверенности и открытые вопросы. Имена файлов, классов, функций и другие локальные детали могут использоваться внутри изолированного анализа для доказательства, но не переносятся в Business Specs или центральный System Design.

Subagents передают сжатые результаты основному агенту внутри текущей planning-сессии. Основной агент сопоставляет их между собой и создаёт очередной стандартный артефакт через `/opsx-continue`. Если выводы репозиториев противоречат друг другу, запускается адресный повторный pass, а не новый бизнесовый Change. Flow и порядок артефактов OpenSpec от количества и порядка Repository Context Passes не меняются.

Текущий процесс не создаёт отдельный `research.md`, `handoff.md`, runtime cache или другой файл для межсессионного хранения результатов subagents. Завершённые стандартные артефакты OpenSpec остаются долговечными контрольными точками `/opsx-continue`. Если основная сессия потеряна до переноса результата subagent в очередной артефакт, новая сессия сначала восстанавливает гейт Proposal по правилу выше, затем повторяет только соответствующий ограниченный Repository Context Pass на той же ревизии. Сам результат pass не требует отдельного человеческого подтверждения. Это восстановление не требует нового Change или возврата в Explore. Устойчивый provider-neutral handoff между агентскими сессиями вынесен в `BL-006` как отдельное улучшение.

Лимит контекста не фиксируется числом в schema или `sdd.yaml`, поскольку зависит от выбранного агента. Инвариант процесса состоит в том, что основной planning-context не получает совокупный сырой код нескольких репозиториев и сохраняет достаточный резерв для синтеза Specs, Design и Tasks.

#### Техническое расширение состава репозиториев

Перечисленные в Proposal Code Repositories являются кандидатами, известными на момент Explore, а не закрытым техническим scope. Окончательный системный impact определяется на шаге 03 и фиксируется в `design.md` и `tasks.md`.

Если Repository Context Pass обнаружил ещё один затронутый Code Repository, основной агент проверяет, что:

1. его `repository-id` уже зарегистрирован с `role: code` в центральном `sdd.yaml`;
2. checkout уже подключён к тому же Store, находится в чистом состоянии и доступен на точной Git-ревизии;
3. находка не меняет подтверждённые бизнесовые capabilities, наблюдаемое поведение, внешние системы, scope и out of scope Change.

При выполнении этих условий новый репозиторий сам по себе не требует возврата в Explore или повторного подтверждения Proposal в текущей сессии. Если одновременно началась новая сессия, сначала действует общий входной гейт шага 03. Для репозитория запускается отдельный read-only Repository Context Pass. Основной агент добавляет в `design.md` только его межсистемную ответственность и исследованную ревизию, а в `tasks.md` — outcome-based Work Package. Delta Specs не изменяются, если наблюдаемое поведение осталось прежним. Окончательный состав репозиториев проверяется владельцами в едином Planning PR шага 04.

Если репозиторий отсутствует в `sdd.yaml`, его нельзя исследовать или назначать ему подтверждённый Work Package. Текущий happy path шага 03 расширяет технический impact только среди уже зарегистрированных и подключённых Code Repositories. Существующий Change сохраняется без ручного изменения registry или planning-артефактов; поддержанный способ добавить новый репозиторий в registry при активном Change вынесен в `BL-009`.

Возврат в Explore требуется, только если находка вводит новую capability, меняет наблюдаемое поведение, добавляет внешнюю систему либо расширяет подтверждённые бизнесовые scope или out of scope. Обнаружение дополнительного технического участника внутри прежних бизнесовых границ само по себе таким расширением не является.

### Граница согласования

Между Specs, Design и Tasks нет промежуточного человеческого гейта. Их создание — единая подготовительная работа Change Owner. Повторное подтверждение Proposal в новой сессии лишь восстанавливает несохраняемый гейт шага 02 и не является одобрением очередного planning-артефакта.

Владельцы могут быть привлечены во время подготовки только для снятия действительно блокирующего вопроса. Отсутствие такого вопроса не требует ожидания подтверждений. Формальное ревью выполняется один раз в Planning PR:

| Роль | Область ревью в Planning PR |
|---|---|
| Change Owner | Соответствие всего Change исходному намерению и границам Proposal |
| Spec Owner | Capabilities, delta operations, Requirements и Scenarios |
| Technical Owner | Системное решение, реализуемость, совместимость, rollout и rollback |
| Security Owner | Затронутые security, privacy и compliance-инварианты |
| Владельцы Code Repositories | Реализуемость и границы назначенных Work Packages |
| QA | Проверяемость сценариев и план Composite Verification |

Замечания ко всем артефактам исправляются в той же planning-ветке и проходят повторную общую проверку. Кодовая реализация начинается только после принятия Planning PR и фиксации Spec Baseline.

### Обязательный вход

- Store зарегистрирован и `sdd connect` возвращает `ready`;
- официальный expanded agent pack содержит обычный файл `opsx-continue.md` в `agent.commands_directory`;
- активный Change однозначно выбран по переданному `change-id` и принадлежит центральному Store;
- Change использует `spec-driven` без `skip_specs: true`;
- текущая ветка равна `feature/<change-id>`, ещё не опубликована и не содержит собственных commit;
- изменения рабочего дерева ограничены `openspec/changes/<change-id>/`;
- `proposal.md` имеет статус `done` и был подтверждён Change Owner на шаге 02;
- первым `ready`-артефактом официального статуса является `specs`;
- `design.md` и `tasks.md` отсутствуют;
- блокирующих вопросов нет.

Если уточнение не меняет исследованный бизнесовый scope, артефакты можно привести в соответствие до открытия Planning PR. Дополнительный зарегистрированный и подключённый Code Repository внутри прежних бизнесовых границ обрабатывается как техническое расширение на этом шаге. Новая внешняя система, новая ревизия кода или существенное расширение бизнесового scope требует возврата в Explore. До закрытия `BL-001` такой возврат после создания Change является известным блокирующим сценарием и не должен маскироваться ручным удалением Change или planning-артефактов.

### Официальный agent pack

`/opsx-continue` должна происходить из установленной версии OpenSpec. `sdd init` устанавливает официальный custom profile со всем expanded-набором в изолированном окружении и не изменяет глобальный профиль пользователя. В Store коммитятся сгенерированные provider-specific команды и skills.

Для нового checkout `sdd connect` проверяет наличие как минимум `opsx-explore.md`, `opsx-continue.md`, `opsx-update.md`, `sdd-context.md`, `sdd-change.md` и `sdd-apply.md`. Он не восстанавливает и не редактирует agent pack автоматически.

В Qwen-проекте официальный pack обновляет Technical Owner через `openspec config profile` с выбранным expanded-набором и затем `openspec update --force`. Для GigaCode совместимый pack обновляется вместе с SDD adapter, пока OpenSpec не поддерживает этот provider напрямую.

### Цикл `/opsx-continue`

Для каждого очередного артефакта официальная команда самостоятельно выполняет эквивалент:

```bash
openspec status --change <change-id> --store <store-id> --json
openspec instructions <artifact-id> --change <change-id> --store <store-id> --json
```

Store выбирается по встроенному Store guidance OpenSpec. Работа из центрального Store и явный `change-id` обязательны; nearest root, `defaultStore` и неявный выбор Change проектным процессом не допускаются.

`instructions` установленной версии является авторитетным источником `template`, `instruction`, `context`, `rules`, зависимостей и `resolvedOutputPath`. Ожидаемый цикл:

| Вызов | `artifactId` | Результат | Зависимости |
|---|---|---|---|
| 1 | `specs` | `specs/<capability>/spec.md` | `proposal` |
| 2 | `design` | `design.md` | `proposal` |
| 3 | `tasks` | `tasks.md` | `specs`, `design` |

Стандартная команда перечитывает dependency-файлы с диска, создаёт файлы по официальному пути, показывает прогресс и прекращает работу после одного артефакта. Проект не копирует эту логику в harness и не добавляет поверх неё отдельную команду оркестрации.

### Источники и границы артефактов

Общими входами являются Proposal, подтверждённый business context pack, релевантные ADR, Master Specs, другие активные Changes и доступные Repository Knowledge Packs затронутых Code Repositories на зафиксированных ревизиях. `_raw/` не является нормативным источником. Если Knowledge Pack отсутствует или недостаточен, агент адресно читает исходный код по вопросам Change, не загружая репозиторий целиком. Техническое содержание Knowledge Packs и найденные локальные детали в Store не копируются. Возврат в Explore требуется только при изменении бизнесового scope, состава внешних систем или других подтверждённых границ Change, а не из-за отсутствия документации.

Границы содержания:

- Delta Specs фиксируют изменение наблюдаемого бизнес-поведения относительно Master Specs и не содержат деталей реализации;
- Design фиксирует межсистемное техническое решение, но не локальное устройство Code Repositories;
- Tasks раскладывает принятое решение на outcome-based Work Packages и проверки без файлового implementation plan;
- ни один артефакт не утверждает, что код уже реализован или проверен;
- Master Specs, код и implementation plans Code Repositories на этом шаге не изменяются.

Для существующего требования `MODIFIED` содержит его полную новую версию вместе со всеми сохраняемыми и изменёнными сценариями. Частичная вставка при Archive заменит прежний блок и потеряет пропущенное содержание.

### Восстановление и повторный запуск

OpenSpec определяет завершённость артефакта по наличию файла по ожидаемому пути. Поэтому перед повторным `/opsx-continue` нужно проверить не человеческое одобрение, а техническую полноту только что созданного артефакта.

- если ожидаемый артефакт отсутствует, вызывается `/opsx-continue`;
- если он создан полностью, цикл сразу продолжается следующим вызовом;
- если создан частично, он завершается напрямую либо через `/opsx-update` до следующего вызова;
- если входы изменены, зависимые артефакты актуализируются перед Planning PR;
- если `status` не соответствует ожидаемой последовательности, процесс останавливается без удаления файлов и автоматического перехода дальше.

Завершённость Specs, Design и Tasks не выводится из человеческого одобрения: на шаге 03 проверяется их техническая полнота. Подтверждение Proposal является входным гейтом шага 02, а содержательное одобрение всего planning-набора появляется только по результатам ревью Planning PR.

### Валидация

На шаге 03 не выполняется отдельная формальная валидация после каждого артефакта. Проверка `status` подтверждает только завершение графа и не подменяет проверку содержания.

В шаге 04 весь Change валидируется как единое целое:

```bash
openspec show <change-id> \
  --type change \
  --no-interactive \
  --store <store-id> \
  --json

openspec validate <change-id> \
  --type change \
  --strict \
  --no-interactive \
  --store <store-id> \
  --json
```

Результаты прикладываются к Planning PR вместе с полным diff Proposal, Delta Specs, Design и Tasks. После исправлений в том же PR строгая проверка повторяется для всего Change.

### Разрешённые записи

На шаге разрешено создавать и исправлять только:

```text
openspec/changes/<change-id>/specs/**/*.md
openspec/changes/<change-id>/design.md
openspec/changes/<change-id>/tasks.md
```

`proposal.md` можно уточнить только без расширения подтверждённого scope и с последующей актуализацией зависимых артефактов. Нельзя изменять Master Specs, context pack, ADR, Store metadata, Code Repositories, `.qwen/skills/openspec-*` или `.qwen/commands/opsx-*`.

На этом шаге также нельзя создавать commit, push, PR, Spec Baseline, кодовые ветки, implementation plans и Evidence.

### Результат и переход к шагу 04

Результат шага — полный, но ещё не принятый комплект planning-артефактов в рабочем дереве центрального Store:

```text
openspec/changes/<change-id>/
├── .openspec.yaml
├── proposal.md
├── specs/
│   └── <capability>/spec.md
├── design.md
└── tasks.md
```

Переход разрешён, когда `proposal`, `specs`, `design` и `tasks` имеют статус `done`, а незакоммиченные изменения ограничены текущим Change. Никакие содержательные артефакты на этом переходе ещё не считаются утверждёнными.

Шаг 04 выполняет штатные `openspec status`, `openspec show` и строгий `openspec validate`, открывает единый Planning PR, собирает подтверждения владельцев и использует принятую Git SHA Store как Spec Baseline.
