## 06. Реализация в Code Repositories

Новая CLI- или slash-команда для шага не требуется.

### Цель шага

Каждый затронутый Code Repository реализует назначенную ему часть принятого OpenSpec Change, выполняет свои проверки и подготавливает связанный implementation PR.

На входе для одного репозитория:

- принят точный `spec_baseline` центрального Store;
- создана implementation subtask с `store_id`, `repository_id`, `change_id`, `spec_baseline` и Work Package ID;
- `sdd load` вернул `implementation_ready` и подготовил `feature/<change-id>`;
- Apply Owner получил готовое первое сообщение `next_action` с точным путём к `sdd-apply.md`.

На выходе:

- назначенные Work Packages реализованы только в текущем Code Repository;
- компонентные и применимые контрактные проверки выполнены;
- implementation PR прошёл code review и связан с Change, Planning PR и subtask;
- в subtask зафиксирована точная `code_revision`, передаваемая в Composite Verification.

Шаг не изменяет центральный Store и `tasks.md`, не выполняет Composite Verification, merge, rollout или Archive. Связанные checkbox завершаются после реализации, составной проверки, merge и rollout — непосредственно перед Archive.

### Место шага в процессе

Последовательность выполнения Change:

```text
согласованный Change
  → реализация backend/frontend/других компонентов
  → проверки каждого репозитория
  → связанные implementation PR
  → Composite Verification
  → merge и rollout
  → завершение tasks.md
  → Archive
```

На шаге 06 действуют три multi-repo ограничения:

1. требования читаются с точной SHA `spec_baseline`, а не с плавающего HEAD Store;
2. одна Apply-сессия пишет только в один `repository_id`;
3. шаг 07 получает точную SHA готового PR каждого репозитория.

## Пользовательский процесс

### 1. Запустите Apply-сессию

Из корня Code Repository откройте новую агентскую сессию и передайте ей `next_action` из успешного `sdd load` без изменения параметров:

```text
Прочитай и выполни инструкцию
"<absolute-runtime-store-path>/.qwen/commands/sdd-apply.md"
с параметрами: --store payments-specs
--repo payments-api
--change pay-412-payment-status
--baseline 0123456789abcdef0123456789abcdef01234567
--work-package "1"
--work-package "2"
```

Инструкция читается по точному пути из immutable Store worktree. Копировать её в Code Repository или добавлять локальную slash-команду не требуется.

До изменения файлов агент проверяет:

- параметры полностью совпадают с runtime;
- cwd, `repository_id` и `feature/<change-id>` совпадают;
- текущий HEAD является потомком `code_base_revision`;
- единственный `allowed_edit_root` — текущий Code Repository;
- immutable Store worktree чист и находится на `spec_baseline`;
- строгий `openspec validate` успешен;
- все переданные ID существуют в `openspec instructions apply --change <change-id> --json`.

Несовпадение блокирует запись. Агент не исправляет runtime, ветку или параметры автоматически.

### 2. Реализуйте назначенные Work Packages

Агент читает только необходимую часть принятого Change:

- Proposal — границы изменения;
- применимые Specs и Scenarios — ожидаемое поведение;
- относящиеся к репозиторию части Design — контракт, совместимость и rollout;
- назначенные `tasks[].id` — требуемый результат и проверки.

Технический контекст берётся из Code Repository:

1. сначала агент ищет Repository Knowledge Pack в provider-specific каталоге;
2. при отсутствии достаточной документации адресно читает код и тесты;
3. не загружает весь крупный репозиторий или другие Code Repositories автоматически.

Агент изменяет только текущий Code Repository и не берёт соседние Work Packages. Repository Knowledge Pack обновляется только тогда, когда это прямо входит в назначенный Work Package. Остальные найденные проблемы перечисляются в отчёте или замечании PR без расширения diff.

#### Необязательный технический design/plan

Для простой реализации достаточно короткого плана в Apply-сессии. Если работа сложная, длительная или передаётся между разработчиками, Code Repository может использовать собственный technical design/implementation plan либо checklist Draft PR.

Такой план:

- необязателен и не создаёт дополнительный SDD-гейт;
- хранится только в Code Repository или его Draft PR;
- описывает локальные файлы, компоненты, миграции и проверки;
- не копирует центральные Specs или Tasks и не становится источником требований;
- не требует новой команды SDD.

Проблема долговременной синхронизации такого плана отдельно наблюдается на пилоте в [`BL-013`](../../BACKLOG.md#bl-013--общая-видимость-технического-плана-и-частичного-прогресса).

### 3. Откройте Draft PR и показывайте прогресс

После первого связного commit Apply Owner публикует `feature/<change-id>` и открывает Draft PR. Commit, push и PR выполняются только после явного поручения пользователя.

В незавершённой работе:

- implementation subtask показывает обычный статус tracker и блокеры;
- Draft PR показывает commit, diff и CI;
- необязательный локальный checklist показывает технические этапы сложной реализации;
- центральный checkbox Work Package остаётся `[ ]`.

При передаче работы другой разработчик использует ту же subtask, ветку и Draft PR. Новый бизнесовый Change или дополнительная feature-subtask для остатка работы того же репозитория не создаются.

### 4. Выполните проверки репозитория

Команды берутся из Knowledge Pack, agent instructions, package scripts и CI текущего Code Repository. Центральный Store их не дублирует.

По содержанию Work Packages выполняются применимые:

- lint, format и static checks;
- unit и компонентные тесты;
- contract-тесты;
- build или compile;
- проверка diff на случайные изменения.

Не выполненная проверка указывается как `Not run` с причиной. Упавшая обязательная проверка блокирует готовность PR. Если сам Work Package требует тест или контрактную проверку, созданный, но не запущенный тест не завершает Work Package. Сохранение прежнего поведения сравнивается с `code_base_revision`, а проверка указанной ревизии другого репозитория не подменяется локальной имитацией. Manual composite verification относится к шагу 07.

После работы агент повторно проверяет, что Store worktree остался чистым на том же `spec_baseline`.

### 5. Подготовьте implementation PR к проверке системы

Перед переводом Draft PR в готовый синхронизируйте feature-ветку с основной веткой Code Repository принятым в проекте rebase и повторите проверки. Для уже опубликованной собственной ветки после rebase допустим только `git push --force-with-lease`; обычный `--force` запрещён.

PR содержит ссылки на ticket, OpenSpec Change и связанные implementation PR, а также проверяемые результаты. Specs и Tasks в описание PR не копируются:

```yaml
ticket: PAY-412
change_id: pay-412-payment-status
store_id: payments-specs
spec_baseline: 0123456789abcdef0123456789abcdef01234567
repository_id: payments-api
work_packages:
  - "1"
  - "2"
planning_pr: <provider-pr-reference>
implementation_subtask: <tracker-reference>
related_implementation_prs:
  - <repository-id>: <provider-pr-reference>
checks:
  - command: npm test
    result: passed
```

Если связанный PR другого репозитория ещё не открыт, ссылка добавляется после его появления.

Reviewers проверяют соответствие назначенным Work Packages и Scenarios, совместимость контракта, достаточность тестов и отсутствие несвязанного scope.

Обычные замечания исправляются в той же ветке и PR. Apply Owner продолжает текущую сессию либо запускает новую тем же `next_action` и передаёт точные unresolved comments. Повторный `sdd load` не нужен, пока Baseline и runtime не изменились.

После успешных проверок и code review Apply Owner один раз фиксирует в subtask текущую полную `code_revision`. Любой следующий commit делает прежнюю передачу шагу 07 устаревшей; после повторной проверки SHA заменяется.

Implementation PR на шаге 06 не сливается. Сначала выполняется Composite Verification, затем — безопасные merge и rollout.

### 6. Завершите шаг

Шаг 06 завершён для Code Repository, когда:

- назначенные Work Packages реализованы;
- обязательные проверки успешны;
- blocking review comments устранены;
- implementation PR готов и связан с Planning PR и subtask;
- `code_revision` совпадает с HEAD готового PR;
- Store worktree остался чистым на `spec_baseline`;
- центральный Store и `tasks.md` не изменялись.

Общий шаг завершён после готовности всех implementation PR Change. Следующий этап — Composite Verification шага 07, а не Archive.

## Изменение принятого Baseline

Если после начала реализации принят correction/amendment:

1. Change Owner приостанавливает затронутую работу;
2. новый planning-набор проходит обычный PR, approvals и строгую OpenSpec-валидацию;
3. новый `spec_baseline` и текущие `tasks[].id` заново сопоставляются со всеми implementation subtasks активного Change до Archive, независимо от их статуса;
4. Apply Owners повторяют `sdd load` с актуальными параметрами;
5. затронутые implementation PR исправляются и проверяются повторно.

OpenSpec 1.7.0 формирует `task.id` по порядку checkbox, поэтому прежний ID нельзя переносить без повторного сопоставления. На пилоте эту операцию контролирует Change Owner вручную. Ручной процесс не считается production-ready и должен быть заменён до запуска по [`BL-014`](../../BACKLOG.md#bl-014--перепривязка-work-packages-после-изменения-baseline-без-ручной-работы).

Изменение бизнесового scope, наблюдаемого поведения или состава внешних систем сначала возвращает процесс в Explore. Отдельный OpenSpec Change для той же бизнесовой фичи без бизнесовой причины не создаётся.

## Технический контракт

### Пользовательская поверхность

Новая команда не добавляется. Шаг использует `next_action` от `sdd load` и существующую project instruction `sdd-apply.md`.

### Источники истины

| Данные | Источник |
|---|---|
| Требования и межсистемный контракт | Change на `spec_baseline` |
| Назначенные Work Packages | `tasks[].id` OpenSpec и implementation subtask |
| Границы записи | runtime шага 05 |
| Устройство кода и команды проверок | Code Repository и его Knowledge Pack |
| Фактическая реализация | implementation PR, commit и CI |

### OpenSpec API

Из `spec_root` повторно используются только штатные операции:

```bash
openspec validate <change-id> --type change --strict --no-interactive --json
openspec instructions apply --change <change-id> --json
```

Собственный parser `tasks.md`, Apply API или формат Work Package не создаются.

### Разрешённые записи

Apply-сессия изменяет только текущий Code Repository внутри `allowed_edit_roots`.

Не изменяются:

- центральный Store и immutable runtime worktree;
- другие Code Repositories;
- tracker и Git-провайдер без отдельного явного действия Apply Owner;
- встроенные `.qwen/skills/openspec-*` и `.qwen/commands/opsx-*`.

### Повторный запуск

Повтор инструкции с теми же параметрами допустим для продолжения реализации и code-review fixes. Агент заново проверяет runtime, ветку и Store, читает текущий diff и выполняет только недостающую работу. Новый локальный progress-state не создаётся.

При потере runtime Apply Owner воспроизводит его обычным `sdd load` из актуальной subtask. Грязное рабочее дерево сначала разбирается обычными правилами Code Repository; автоматический stash или reset не выполняется.

### Переход к шагу 07

Для каждого репозитория передаются:

```yaml
repository_id: payments-api
implementation_pr: <provider-pr-reference>
code_revision: <full-40-character-pr-head-sha>
spec_baseline: <full-40-character-store-sha>
work_packages:
  - "1"
  - "2"
checks:
  - command: <repository-command>
    result: passed
```

Evidence шага 07 должно идентифицировать точную комбинацию `spec_baseline + repository_id/code_revision[]`. Способ сборки и запуска несмерженных ревизий определяется после инфраструктурного пилота в [`BL-012`](../../BACKLOG.md#bl-012--composite-verification-точных-ревизий-несмерженных-pr).

### Критерии реализации инструкции

Реализация `sdd-apply.md` подтверждает:

1. несовпадение параметров, cwd, ветки, runtime или Baseline блокирует запись;
2. несколько Work Package выбираются по точным `tasks[].id`;
3. агент изменяет только текущий Code Repository;
4. отсутствие Knowledge Pack приводит к адресному чтению кода, а не к блокировке;
5. необязательный локальный design/plan не становится SDD-гейтом;
6. обычное продолжение и review-fix не требуют нового runtime;
7. провал обязательной проверки не выдаётся за готовый PR;
8. инструкция не создаёт commit, push, PR или tracker update без явного поручения;
9. центральный `tasks.md` не изменяется на шаге 06;
10. успешный результат направляет в Composite Verification, но не предлагает Archive.
