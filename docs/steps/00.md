## 00. Инициализация центрального проекта

Шаг выполняется один раз при создании Spec Root Repository `project-specs` или при подключении существующего репозитория в этой роли к процессу SDD + OpenSpec. Его задача — разложить заранее подготовленный и версионируемый скелет проекта. Jira Story, OpenSpec Change и артефакты отдельного изменения на этом шаге не создаются.

`sdd init` не пытается сначала определить состояние проекта и не строит отдельную систему ошибок и статусов инициализации. Команда создаёт отсутствующие файлы из встроенного skeleton bundle, заполняет известные значения из входных параметров и оставляет понятные `TODO`-блоки внутри соответствующих файлов контекста.

Повторный запуск без дополнительных флагов идемпотентен: уже существующие файлы не перезаписываются и не анализируются, отсутствующие файлы скелета создаются. Флаг `--force` является явным исключением и заново раскладывает все управляемые файлы из текущего skeleton bundle.

### Термины репозиториев

**Spec Root Repository** — корневой репозиторий спецификаций со стабильным `repository-id: project-specs`. Он хранит нормативный бизнес-контекст, Master Specs, OpenSpec Changes, schema и общие команды процесса. Далее в этом шаге выражения «центральный репозиторий», «Spec Root» и `project-specs` используются как синонимы.

**Code Repository** — отдельный зарегистрированный репозиторий с исходным кодом. Каждый Code Repository имеет устойчивый `repository-id` в `sdd.yaml`, читает бизнес-контекст из Spec Root и реализует только назначенные ему Work Packages. Общий context pack и Master Specs в Code Repository не дублируются как нормативный источник.

Во время реализации `sdd` подключает к Code Repository изолированный read-only checkout Spec Root на точной ревизии Baseline. Поэтому агент может читать подтверждённый бизнес-контекст рядом с кодом, но не может изменить спецификации из кодового репозитория. Root в названии обозначает источник истины, а не общий файловый каталог и не монорепозиторий.

### Владельцы

| Роль | Ответственность на шаге 00 |
|---|---|
| Spec Owner | Структура процесса, project schema, templates, каркас context pack и правила владения |
| Technical Owner | Реестр репозиториев, system map, архитектурный контекст, основные ветки и доступ к исходному коду |
| Change Owner | Первичный продуктовый и доменный контекст, глоссарий и ожидаемое наблюдаемое поведение будущих изменений |
| Apply Owner | Сведения для разработки, встроенные agent commands и требования к рабочей среде |
| QA | Общие quality gates и требования к Evidence |
| Release Owner | Общий процесс поставки, миграции и отката |
| Ответственный по ИБ | Безопасность, данные, приватность, credential и compliance |

Spec Owner принимает созданный скелет и решает, достаточно ли первичного контекста для перехода к рабочим запросам. Technical Owner подтверждает сведения о code repo вместо отдельных владельцев каждого репозитория. Остальные владельцы подтверждают только принадлежащий им контекст; агент не принимает решения за них.

`Change Owner` объединяет продуктовую и аналитическую ответственность. `Apply Owner` отвечает за разработку и выполнение Work Packages, но на шаге 00 предоставляет только общие сведения, необходимые будущей реализации.

### Вход

- пустой или существующий центральный Git-репозиторий;
- канонический Git URL центрального репозитория и его основная ветка;
- известный на момент инициализации список code repo с устойчивыми `repository-id`, URL и основными ветками;
- назначенные владельцы контекста;
- credential с доступом на чтение зарегистрированных репозиториев;
- OpenSpec версии `1.7.0`, доступный встроенному адаптеру `sdd`.

Credential может быть service account token, deploy key или другим машинным способом аутентификации. Он хранится в secret storage или переменных среды и никогда не записывается в `sdd.yaml`, runtime manifest, логи или Git.

Project schema, templates, каркас context pack и agent commands не передаются пользователем. Они входят во встроенный skeleton bundle той же ревизии процесса, что выполняет `sdd init`.

Неизвестные репозитории, владельцы и источники не мешают разложить скелет. Они записываются как конкретные `TODO` в целевом context-файле. Пока целевой файл определить нельзя, вопрос временно находится в разделе `Open questions` файла `00-start-here.md`.

### Первый локальный запуск

До первой инициализации зарегистрируйте CLI из этого репозитория. Для этого требуются Node.js `20+` и OpenSpec `1.7.0`, доступный как команда `openspec`.

Из корня репозитория выполните:

```bash
cd harness
npm link
cd ..
sdd --help
```

`npm link` выполняется один раз на рабочей машине. Если Node.js управляется через NVM, ссылку нужно создать отдельно для той версии Node.js, под которой будет запускаться `sdd`. Успешный `sdd --help` означает, что CLI зарегистрирован в `PATH` и можно переходить к инициализации.

Без регистрации CLI тот же код можно запустить из корня напрямую:

```bash
node harness/bin/sdd.js init
```

Этот прямой вызов предназначен для разработки и диагностики. Нормативный пользовательский маршрут после установки — `sdd init`.

### Команды

В центральном репозитории пользователь запускает:

```bash
sdd init [path] [--force] [--repo <repository-id>=<git-url>#<default-branch>]...
```

`path` по умолчанию равен текущему каталогу. `--repo` можно повторить для каждого известного code repo. Центральный `project-specs` определяется по `origin` и текущей ветке; для ещё не созданного Git-репозитория его можно передать тем же параметром с `repository-id` `project-specs`.

`--force` перезаписывает все пути, входящие в skeleton bundle, включая context files, agent commands, `QWEN.md`, `openspec/config.yaml`, `sdd.yaml`, `CODEOWNERS` и `.gitignore`. `sdd.yaml` формируется заново из обнаруженного центрального репозитория и переданных `--repo`. Дополнительные пользовательские файлы, отсутствующие в bundle, не удаляются. Перед запуском следует сохранить нужные изменения в Git или сделать резервную копию.

После создания скелета в Qwen Code запускается:

```text
/sdd-context
```

| Команда | Что делает | Результат |
|---|---|---|
| `sdd init [path] [--force] [--repo ...]` | Инициализирует OpenSpec через встроенный адаптер и раскладывает готовый skeleton bundle; с `--force` перезаписывает все управляемые файлы | Перечни созданных, перезаписанных и сохранённых файлов |
| `/sdd-context` | Сначала инвентаризирует все Markdown-файлы в `openspec/context/`, затем обрабатывает `_raw/**/*.md`, сверяет контекст с Master Specs и свежими Git-ревизиями и только потом переходит к остальным пробелам | `current`, `updated` либо `needs_confirmation`, diff context files и ADR |

`sdd init` заканчивается после раскладки skeleton. Корректность встроенной schema, templates и agent commands обеспечивается при разработке bundle, а не повторно проверяется в каждом проекте во время инициализации.

### Что создаёт `sdd init`

```text
project-specs/
├── openspec/
│   ├── config.yaml
│   ├── context/
│   │   ├── 00-start-here.md
│   │   ├── 01-product-context.md
│   │   ├── 02-domain-glossary.md
│   │   ├── 03-architecture.md
│   │   ├── 04-domain-model.md
│   │   ├── 05-security-and-compliance.md
│   │   ├── 06-cross-system-invariants.md
│   │   ├── 07-quality-gates.md
│   │   ├── 08-release-process.md
│   │   ├── system-map.yaml
│   │   ├── ADR/
│   │   │   └── README.md
│   │   └── _raw/
│   │       └── README.md
│   ├── schemas/
│   │   └── multi-repo-sdd/
│   │       ├── schema.yaml
│   │       └── templates/
│   ├── specs/
│   └── changes/
├── .qwen/
│   └── commands/
│       ├── sdd-context.md
│       ├── sdd-apply.md
│       └── sdd-verify.md
├── QWEN.md
├── sdd.yaml
├── CODEOWNERS
└── .gitignore
```

`specs/` и `changes/` создаются пустыми. Файлы `00-start-here.md`–`08-release-process.md`, `system-map.yaml` и два README создаются с готовой структурой, инструкциями и локальными `TODO`, а не пустыми.

Корневой `QWEN.md` задаёт постоянную инструкцию проекта: Qwen начинает каждый новый диалог и продолжает общение на русском языке. Код, команды, пути и машинные идентификаторы при этом не переводятся.

### Назначение контекстных заготовок

| Файл | Что содержит после `sdd init` | Как обновляется `/sdd-context` |
|---|---|---|
| `00-start-here.md` | Правила подтверждения, маршрутизация файлов и временный раздел `Open questions` | Обновляет маршруты чтения и переносит вопросы в целевые context-файлы, когда их назначение становится известно |
| `01-...md`–`08-...md` | Постоянные предметные разделы и inline TODO с владельцем и ожидаемым источником | Заменяет TODO подтверждённым содержимым или уточняет вопрос и его источник |
| `system-map.yaml` | Каркас систем, связей и `repository-id` | Добавляет только подтверждённые системы, репозитории и связи |
| `ADR/README.md` | Когда нужен ADR, его обязательные разделы, минимальный шаблон и демонстрационные примеры; после init всё находится в одном README без отдельных файлов примеров | Создаёт отдельный `NNNN-short-title.md` только для реального принятого решения и добавляет его в индекс |
| `_raw/README.md` | Назначение и правила обработки неподтверждённых raw-материалов | При каждом вызове заново читает все raw-файлы; отдельный индекс и статусы обработки не ведёт |

Каждый TODO имеет поля `question`, `owner` и `expected_source`. `/sdd-context` заменяет TODO подтверждённым содержимым, но не меняет назначение файла и не удаляет обязательные разделы.

Контекст-пак хранит только долговечные общие правила. Команды сборки, линтинга и тестов остаются в code repositories и их CI configuration. История ошибок не ведётся отдельным нормативным журналом: подтверждённый вывод из инцидента переносится в подходящий context-файл, ADR или Master Spec.

### Граница `sdd` и OpenSpec

`sdd` является единой пользовательской и процессной поверхностью. OpenSpec используется под капотом как core engine для OpenSpec root, графа артефактов, instructions, validation рабочих Changes и archive. Прямой запуск `openspec ...` не является нормативным пользовательским маршрутом.

| Операция `sdd` | Возможности OpenSpec под капотом | Что добавляет `sdd` |
|---|---|---|
| Инициализация | Создание OpenSpec root и project config | Версионируемый skeleton bundle с context pack, schema, commands и README для специальных каталогов |
| Планирование | `status` и `instructions` | Нумерованные гейты, владельцы и общий multi-repo контекст |
| Реализация | `instructions apply` | Точный Baseline, `repository-id`, разрешённые пути записи и отдельный прогресс |
| Проверка Change | `validate` и сведения Change | Composite Verification нескольких репозиториев и Evidence |
| Финализация | `archive` | Проверка acceptance, Git-ревизий и финального diff |

Отказ от runtime-валидации относится только к созданию встроенного скелета на шаге 00. Структурная validation конкретных OpenSpec Changes в последующих шагах остаётся частью OpenSpec core.

### Конфигурация OpenSpec

`sdd init` создаёт готовый `openspec/config.yaml`:

```yaml
schema: multi-repo-sdd

context: |
  Перед созданием артефакта прочитай openspec/context/00-start-here.md
  и загрузи только назначенные им файлы для текущего артефакта.
  Спецификации нескольких code repo находятся в центральном project-specs.
  Requirements описывают наблюдаемое поведение без деталей реализации.
  Master Specs меняются только при Finalization.
```

Beta Stores, `store`, `references`, working context и worksets не используются. Multi-repo доступ, получение свежего Git-состояния и выбор точных ревизий принадлежат адаптеру `sdd`.

### Конфигурация `sdd`

`sdd init` создаёт `sdd.yaml` и заполняет известные репозитории:

```yaml
version: 1

versions:
  process: draft
  openspec: "1.7.0"

repositories:
  - id: project-specs
    url: "<canonical-git-url>"
    default_branch: main
  - id: ui
    url: "<canonical-git-url>"
    default_branch: main
```

Если сведения о репозитории ещё неизвестны, в `sdd.yaml` не создаётся фиктивная запись. Пробел фиксируется в `Open questions` файла `00-start-here.md` и закрывается позже Technical Owner. Credential в конфигурацию не записывается.

Capabilities, Requirements, Scenarios и состояние Changes в `sdd.yaml` не хранятся.

### Как `/sdd-context` наполняет скелет

При каждом вызове порядок приоритетов фиксирован: **структура и Markdown-файлы → raw-материалы → inline TODO и дополнительный опрос**. Агент не начинает свободный опрос пользователя, пока найденные raw-файлы не обработаны или пользователь явно не отложил конкретный материал.

Агент:

1. рекурсивно и только для чтения сканирует `openspec/context/` и строит полный перечень находящихся внутри `.md`-файлов;
2. классифицирует найденные пути как нормативный context, ADR, служебный README или raw-материал и отмечает отсутствующие элементы skeleton;
3. читает `00-start-here.md`, inline TODO, README специальных каталогов, существующий подтверждённый контекст, `sdd.yaml`, CODEOWNERS и действующие Master Specs только для чтения;
4. находит все `_raw/**/*.md`, кроме служебного `_raw/README.md`, и обрабатывает их по одному в устойчивом порядке путей;
5. для каждого raw-файла извлекает отдельные утверждения, предполагаемый целевой context-файл и недостающие подтверждения;
6. по каждому утверждению просит пользователя подтвердить, исправить, отклонить или отложить его; при возможности сверяет утверждение с кодом, контрактами, конфигурацией, Master Specs и ADR;
7. после разбора каждого raw-файла формирует diff целевых файлов, показывает его пользователю и применяет подтверждённые изменения до перехода к следующему raw-файлу;
8. неподтверждённые утверждения не переносит из `_raw/` в нормативный контекст;
9. проверяет основные ветки зарегистрированных в `sdd.yaml` репозиториев, фиксирует действительно проверенные Git-ревизии и сверяет с ними нормативный контекст;
10. только после обработки или явного откладывания raw-файлов и проверки доступных источников спрашивает роль пользователя, проходит inline TODO и задаёт по одному адресному вопросу за раз;
11. обновляет `00-start-here.md` последним, приводит в соответствие inline TODO и индекс ADR, показывает оставшийся diff по каждому файлу и применяет только подтверждённые пользователем изменения.

Инвентаризация структуры всегда предшествует чтению содержания. Наличие файла определяется по файловой системе, а не по истории чата. Неожиданный Markdown-файл не игнорируется: агент показывает его путь и просит определить назначение до использования содержащихся в нём сведений.

При каждом новом вызове агент заново читает все raw-файлы и сравнивает утверждения с нормативным контекстом. Уже перенесённый факт повторно не добавляется, а новое, изменённое или противоречащее утверждение снова выносится на уточнение пользователю.

Правила маршрутизации:

| Полученная информация | Куда записывается |
|---|---|
| Устойчивый факт о продукте, домене, архитектуре, ИБ, качестве или поставке | Соответствующий нормативный файл `01-...md`–`08-...md` |
| Долговечное принятое техническое решение и его основания | Новый ADR и ссылка на него из архитектурного контекста |
| Неизвестный факт или вопрос | Inline TODO в целевом context-файле; если цель неизвестна — `Open questions` в `00-start-here.md` |
| Неподтверждённое утверждение или исходный материал | `_raw/`; нормативные README и context files на него как на факт не ссылаются |

Самоназванная роль определяет маршрут диалога, но не является доказательством полномочий. Право принять diff определяется CODEOWNERS и правилами проекта.

Команда возвращает `context_status: current` только при подтверждённой свежести обязательных источников и отсутствии противоречий. После принятого diff при тех же условиях возвращается `updated`. Недоступный обязательный источник, нерешённое противоречие, неизвестный `repository-id` или ожидающее владельца решение дают `needs_confirmation`; в этом случае контекст не объявляется актуальным.

### Правила `.gitignore` и владения

В Git попадает весь skeleton и его дальнейшее содержимое: schema, templates, agent commands, подтверждённый контекст, inline TODO, `_raw/`, ADR, Master Specs, конфигурация, progress и Evidence.

Игнорируются только временные клоны и checkout, runtime manifest с локальными путями, кэши, логи и локальные credential. Широкие правила вроде `.qwen/`, `openspec/` или `.sdd/` целиком запрещены.

CODEOWNERS покрывает как минимум:

- `openspec/specs/**` и `openspec/changes/**` — Spec Owner;
- `openspec/schemas/**` — Spec Owner и Apply Owner;
- продуктовый и доменный контекст — Change Owner;
- архитектурный контекст и `system-map.yaml` — Technical Owner;
- `.qwen/commands/sdd-*.md` и `sdd.yaml` — Apply Owner и Technical Owner;
- файлы quality gates — QA;
- файлы поставки — Release Owner;
- `00-start-here.md` и README специальных каталогов — Spec Owner.

### Действия

1. Собрать известные параметры центрального и code repositories.
2. Выполнить `sdd init` и создать отсутствующие элементы skeleton bundle.
3. Заполнить известные значения в `sdd.yaml`, CODEOWNERS и context skeleton; неизвестное оставить в inline TODO.
4. Настроить read-only credential вне Git.
5. Выполнить первичный `/sdd-context`.
6. Обработать `_raw/`, пройти inline TODO и наполнить нормативные context files подтверждёнными сведениями.
7. На основании полученного контекста обновить `00-start-here.md` и ADR index.
8. Зафиксировать skeleton и принятый первичный контекст отдельным PR в центральный репозиторий.

### Результат шага 00

После шага:

- skeleton bundle создан и находится в Git;
- `00-start-here.md` объясняет маршрутизацию и порядок чтения контекста;
- неизвестные сведения представлены конкретными inline TODO с владельцами и ожидаемыми источниками;
- первичный `/sdd-context` наполнил доступный подтверждённый контекст;
- `_raw/` отделён от нормативных фактов;
- ADR создаются только из подтверждённого контекста;
