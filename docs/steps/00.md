## 00. Инициализация центрального проекта

Если вам нужно только пройти шаг 00, достаточно раздела «Пользовательская инструкция». Техническая спецификация ниже предназначена для разработчиков CLI и ревью процесса.

### Пользовательская инструкция

#### 1. Подготовьте инструменты

Требуются Node.js `20+`, OpenSpec `1.7.0` и CLI `sdd`. Версия OpenSpec закреплена в `sdd.yaml`; другая версия блокирует команды SDD. CLI поддерживает macOS, Linux и Windows; внешние команды запускаются через кроссплатформенный runner без зависимости от конкретной shell. Для локальной версии CLI выполните из корня репозитория с `harness`:

```bash
cd harness
npm install
npm link
cd ..
sdd --help
```

#### 2. Выберите свой сценарий

##### Создание нового проекта

Этот сценарий один раз выполняет Technical Owner из чистого центрального Git-репозитория с настроенными `origin` и основной веткой:

```bash
sdd init --store <store-id> --agent <agent-id> [--repo <repository-id>=<git-url>#<default-branch>]...
```

Например, для центрального Store `payments-specs` и двух Code Repositories:

```bash
sdd init --store payments-specs --agent qwen \
  --repo "payments-ui=git@github.com:company/payments-ui.git#main" \
  --repo "payments-api=git@github.com:company/payments-api.git#main"
```

Центральный репозиторий не нужно добавлять через `--repo`: команда получает его URL из `origin`, а основную ветку — из текущей ветки Git. Каждый `--repo` описывает только Code Repository; значение рекомендуется заключать в кавычки. Если на старте нужны только бизнес-спецификации без репозиториев с кодом, достаточно:

```bash
sdd init --store payments-specs --agent qwen
```

В рамках этой однократной инициализации Technical Owner открывает созданный `CODEOWNERS`, заменяет placeholder-владельцев реальными account handles и раскомментирует правила для всех нормативных context-файлов. Файл поставки `08-release-process.md` закрепляется за Technical Owner; роль безопасности называется `Security Owner` и сопоставляется с реальным account handle проекта. Настроенный CODEOWNERS входит в initialization PR и не настраивается участниками команды при последующих запусках `sdd connect`.

После настройки CODEOWNERS подключите рабочую машину:

```bash
sdd connect
```

После успешного подключения из корня Store запустите в сессии поддерживаемого AI-агента:

```text
/sdd-context
```

Команда наполняет только `openspec/context/` центрального Store из `_raw/`, Master Specs, принятых ADR и подтверждений владельцев. Она не читает Code Repositories: исследование реализации начинается только на шаге 01 через `sdd explore` и `/opsx-explore`.

Примите initialization PR центрального репозитория и, если `sdd connect` вернул `needs_setup_pr`, setup PR соответствующих Code Repositories. После слияния обновите checkout и повторите `sdd connect`.

##### Подключение новой рабочей машины

Если проект уже создан, `sdd init` запускать нельзя. Клонируйте центральный репозиторий и выполните только `sdd connect`:

```bash
git clone <canonical-git-url> <workspace>/openspec/<store-id>
cd <workspace>/openspec/<store-id>
sdd connect
```

Команда зарегистрирует Store на этой машине, создаст `<workspace>/src/`, загрузит все Code Repositories из `sdd.yaml` и проверит их связь со Store.

#### 3. Проверьте результат

Шаг завершён на рабочей машине, когда:

- `sdd connect` вернул `connect_status: ready` без состояния `needs_setup_pr`;
- Store зарегистрирован по ожидаемому ID и пути;
- все записи `role: code` загружены в `<workspace>/src/<repository-id>`;
- каждый Code Repository разрешает тот же Store;
- CODEOWNERS содержит активные правила с реальными владельцами для нормативного контекста;
- рабочие деревья остались чистыми.

После этого можно переходить к шагу 01. Если команда остановилась, исправьте указанную причину и повторите её; `sdd` не выполняет `reset`, `stash`, `pull` или удаление пользовательских файлов автоматически.

## Техническая спецификация шага 00

Шаг покрывает два разных сценария: однократную инициализацию центрального проекта и подключение рабочей машины к уже инициализированному проекту. Jira Story, OpenSpec Change и артефакты отдельного изменения на этом шаге не создаются.

`sdd init` выполняется один раз для проекта. Команда создаёт в подготовленном центральном Git-репозитории OpenSpec Store, официальный agent pack, SDD skeleton и реестр репозиториев. Она не клонирует Code Repositories и не является командой onboarding разработчика. Наличие Store metadata с тем же ID означает, что проект уже инициализирован: повторный запуск ничего не меняет и разработчик продолжает с `sdd connect`. Специального восстановления частично завершённого `init` нет; последствия редкого прерывания проверяются вручную до повторной инициализации.

`sdd connect` выполняется создателем проекта после `sdd init`, а затем каждым разработчиком после клонирования центрального репозитория. Команда регистрирует этот checkout как Store на текущей машине, проверяет его через официальный OpenSpec API, читает `sdd.yaml`, загружает все отсутствующие Code Repositories в каталог `src/` того же workspace и проверяет их связь с общим Store.

Повторный `sdd connect` с тем же Store ID и workspace идемпотентен: он не заменяет существующие checkout, не меняет корректный pointer и клонирует только новые или отсутствующие Code Repositories. Ни одна команда не исправляет конфликт Store registry автоматически и не удаляет локальный OpenSpec root из Code Repository.

`connect_status: ready` подтверждает локальную регистрацию Store, наличие Code Repositories и корректность их pointer. Этот статус не подтверждает свежесть Git-ревизии центрального Store или Code Repositories: перед каждым запросом её отдельно проверяет шаг 01.

### Термины репозиториев

**Spec Root Repository** — корневой репозиторий спецификаций с `role: store`. Он хранит нормативный бизнес-контекст, Master Specs, OpenSpec Changes, project config и общие команды процесса. Его `repository-id` равен официальному Store ID, например `payments-specs`. Далее выражения «центральный репозиторий», «Spec Root» и «Store Repository» используются как синонимы.

**OpenSpec Store** — тот же Spec Root Repository, зарегистрированный в локальном registry OpenSpec под постоянным `store-id`. Store является базовым API разрешения OpenSpec root: команды, работающие со specs и Changes, получают его явно через `--store <store-id>`.

Store ID и `repository-id` центрального репозитория являются одним идентификатором. Каноническое значение хранится в `.openspec-store/store.yaml`, а `sdd init` записывает то же значение в запись `role: store` файла `sdd.yaml`. Это не два независимо настраиваемых ID: их несовпадение является ошибкой конфигурации. Идентификатор должен быть уникальным среди Store на рабочей машине, стабильным для команды и записанным в lowercase kebab-case.

**Code Repository** — отдельный репозиторий с исходным кодом. Он имеет `role: code`, устойчивый `repository-id` в `sdd.yaml` и config-only файл `openspec/config.yaml` с `store: <store-id>`. Этот pointer направляет обычные OpenSpec-команды в общий Store; локальных `openspec/specs/` и `openspec/changes/` в Code Repository нет.
```text
Code Repository (role: code)
└── openspec/config.yaml
    └── store: payments-specs
                 │
                 ▼
Store Repository (id: payments-specs, role: store)
└── openspec/
    ├── specs/
    └── changes/
```

Так реализуется основной принцип целевой архитектуры: общий контракт и единый Change хранятся только в Store, а каждый затронутый сервис содержит свою реализацию и проверки. Копии Master Specs и отдельные локальные Changes в Code Repositories запрещены.

На рабочих шагах Code Repository разрешает зарегистрированный Store через pointer, а `sdd` дополнительно фиксирует точную Git-ревизию нормативного входа. Механика веток и Baseline определяется последующими шагами; шаг 00 гарантирует только единый источник истины и отсутствие копий спецификаций в сервисах. Root в названии обозначает источник истины, а не общий файловый каталог и не монорепозиторий.

### Владельцы

| Роль | Ответственность на шаге 00 |
|---|---|
| Spec Owner | Project config, дополнительные правила стандартной схемы, каркас context pack и правила владения |
| Technical Owner | Store ID, канонический remote, локальная регистрация Store, pointer в Code Repositories, реестр репозиториев, system map, основные ветки и доступ к исходному коду |
| Change Owner | Первичный продуктовый и доменный контекст, глоссарий и ожидаемое наблюдаемое поведение будущих изменений |
| Apply Owner | Сведения для разработки, встроенные agent commands и требования к рабочей среде |
| QA | Общие quality gates и требования к Evidence |
| Security Owner | Безопасность, данные, приватность, credential и compliance |

`Spec Owner` принимает созданный скелет и решает, достаточно ли первичного контекста для перехода к рабочим запросам. `Technical Owner` подтверждает сведения о code repo вместо отдельных владельцев каждого репозитория. `QA` подтверждает общие quality gates и требования к Evidence. `Security Owner` подтверждает security- и compliance-ограничения. Остальные владельцы подтверждают только принадлежащий им контекст; агент не принимает решения за них.

`Change Owner` объединяет продуктовую и аналитическую ответственность. `Apply Owner` отвечает за разработку и выполнение Work Packages, но на шаге 00 предоставляет только общие сведения, необходимые будущей реализации.

### Вход

- пустой или существующий центральный Git-репозиторий;
- согласованный уникальный Store ID в lowercase kebab-case;
- выбранный поддерживаемый agent adapter;
- канонический Git URL центрального репозитория и его основная ветка;
- известный на момент инициализации список code repo с устойчивыми `repository-id`, URL и основными ветками;
- для `sdd init` — подготовленный чистый центральный Git-репозиторий без Store metadata;
- для `sdd connect` — локальный clone уже инициализированного центрального репозитория и корень workspace с каталогами `openspec/` и `src/`;
- назначенные владельцы контекста;
- credential с доступом на чтение зарегистрированных репозиториев;
- OpenSpec версии `1.7.0`, доступный встроенному адаптеру `sdd`.

Project config, каркас context pack и команды `sdd-*` не передаются пользователем. Они входят во встроенный skeleton bundle той же ревизии процесса, что выполняет `sdd init`. Схема `spec-driven`, её prompts, templates, команды и skills `opsx-*` в bundle не входят: их предоставляет и обновляет только официальный CLI OpenSpec.

При создании skeleton список репозиториев может быть ещё неполным: неизвестная система не получает фиктивную запись в `sdd.yaml`, а фиксируется как адресный TODO в `system-map.yaml`; вопрос о её границах или ответственности направляется в `03-architecture.md`. При этом все уже зарегистрированные записи обязательны для `sdd connect`. Когда Technical Owner подтверждает новый репозиторий, его добавляют в `sdd.yaml` через обычное ревью и после слияния повторяют `sdd connect` на каждой рабочей машине.

### Технический контракт команд

`sdd init` работает только из корня центрального репозитория. `--store` обязателен и одновременно задаёт Store ID и `repository-id` записи `role: store`. Обязательный `--agent` принимает `qwen` или `gigacode`. GigaCode использует формат Qwen, поэтому официальный OpenSpec вызывается с адаптером `qwen`, после чего agent pack переносится из `.qwen/` в `.gigacode/`; корневой instruction-файл называется `GIGACODE.md`. Если официальный `.qwen/` уже существует, OpenSpec использует его, а `sdd init` переносит весь обновлённый каталог в `.gigacode/`, поэтому `.qwen/` после успешной инициализации не остаётся. Это соответствие явно фиксируется в конфигурации. Выбранные ID, архитектура и provider-specific пути записываются в `sdd.yaml` и дальше не определяются по локальному окружению. URL и основная ветка определяются по `origin` и текущей ветке; если они не настроены, команда завершается с инструкцией сначала настроить Git. `--repo` можно повторить только для известных Code Repositories; он создаёт записи `role: code` и не обращается к указанным репозиториям.

До любых изменений проекта `sdd init` проверяет чистоту Git root и отсутствие конфликтующих управляемых SDD-путей. Существующий корректный OpenSpec root без Store metadata можно принять как центральный: `openspec/config.yaml` сохраняется, схема приводится к встроенной `spec-driven`, а недостающие командные `context` и `rules` добавляются без удаления существующих. Нечистое рабочее дерево или конфликт блокируют первый запуск без `stash`, `reset` и удаления файлов. Существующие `.gitignore` и `CODEOWNERS` не считаются конфликтом: их проектное содержимое сохраняется, в `.gitignore` добавляются только отсутствующие локальные правила SDD, а в `CODEOWNERS` — неактивный комментарий-шаблон владельцев SDD. До первого `/sdd-context` Technical Owner заменяет placeholder реальными account handles и активирует правила для нормативного контекста; без этого `/sdd-context` не изменяет файлы. После появления `.openspec-store/store.yaml` проект считается инициализированным; `sdd init` не содержит отдельного режима восстановления частичного запуска.

`sdd connect` читает Store ID из `.openspec-store/store.yaml`, находит ровно одну запись `role: store` и требует совпадения её `id` и URL со Store metadata. Затем команда передаёт текущий путь официальному `openspec store register`. Конфликты локального registry, Store identity и OpenSpec root обрабатывает сам OpenSpec. `sdd connect` никогда не вызывает `openspec init` и не изменяет версионируемые файлы центрального репозитория.

После регистрации команда вызывает официальные `store doctor`, `doctor --store` и `context --store`, структурно проверяет их JSON, затем обрабатывает Code Repositories из `sdd.yaml`. В рекомендуемой структуре корень workspace определяется автоматически. Для нестандартного расположения технически доступен `--workspace <path>`. Отсутствующие репозитории клонируются в `<workspace>/src/<repository-id>`. Существующие checkout не заменяются и не обновляются скрытно; локальные изменения, неверный `origin` или ветка блокируют конкретный репозиторий и сохраняются без изменений. Единственное разрешённое незакоммиченное состояние — созданный самой командой config-only pointer; до его принятия повторный запуск снова возвращает `needs_setup_pr`.

Для нового центрального проекта базовая последовательность эквивалентна:

```bash
openspec store setup <store-id> --path <absolute-spec-root> --no-init-git --remote <canonical-git-url> --json
openspec init <absolute-spec-root> --tools <agent-id> --profile custom --no-animation
openspec store doctor <store-id> --json
openspec doctor --store <store-id> --json
```

OpenSpec `store setup` принимает Git-only каталог или уже исправный OpenSpec root. Поэтому для существующего непустого центрального репозитория без конфликтующих SDD/OpenSpec-путей `sdd init` выполняет те же официальные операции в обратном порядке: сначала `openspec init ... --profile custom`, затем `openspec store setup ... --no-init-git`. Итоговая Store identity, agent pack и skeleton в обоих вариантах одинаковы; существующие файлы проекта не перезаписываются.

Для клонированного уже инициализированного центрального репозитория `sdd connect` не запускает повторную инициализацию и не раскладывает skeleton. После проверки metadata и Git identity команда выполняет:

```bash
openspec store register <absolute-spec-root> --id <store-id> --yes --json
```

Процесс использует официальный expanded-набор OpenSpec: все workflows версии 1.7.0 устанавливаются через профиль `custom`, чтобы шаги планирования выполнялись по одному артефакту через `/opsx-continue`. Для детерминированного `sdd init` список workflows передаётся OpenSpec через временный изолированный `XDG_CONFIG_HOME`; глобальный профиль пользователя не читается и не изменяется, а временная конфигурация удаляется после вызова. `sdd` передаёт сохранённый `agent.id` в OpenSpec, а собственные общие Markdown-команды устанавливает в сохранённый `commands_directory`. В `openspec/config.yaml` выбирается встроенная схема `spec-driven`; multi-repo-правила добавляются через штатные `context` и `rules`, не копируя и не переопределяя prompts и templates OpenSpec. Команды и skills `opsx-*` всегда происходят из установленной версии OpenSpec, а не из файлов SDD. `store setup` и `store register` не выполняют commit или push от имени пользователя; результат проходит обычное ревью.

`sdd` не воспроизводит внутренние правила Store-валидации OpenSpec. Ошибка официальной команды передаётся пользователю как причина остановки, а её JSON разбирается только для проверки границы адаптера: отсутствия диагностики `severity: error`, ожидаемых Store ID, абсолютного пути, `source` и признака исправного root. Дополнительно адаптер проверяет структуру `sdd.yaml`, совпадение Store ID и URL, расположение Code Repositories и безопасное состояние существующего checkout.

OpenSpec допускает только один локальный checkout для одного Store ID. Если при `sdd connect` ID уже зарегистрирован по другому пути или текущий путь зарегистрирован под другим ID, команда завершается ошибкой с инструкцией проверить `openspec store list --json`. Она никогда автоматически не вызывает `openspec store unregister` и не переключает registry между клонами.

Корректность project config, context pack и команд `sdd-*` обеспечивается при разработке bundle, а не повторно проверяется в каждом проекте во время инициализации. Корректность встроенной схемы и templates остаётся ответственностью установленной версии OpenSpec.

`/sdd-context` запускается из корня Store после успешного `sdd connect`. Регистрацию Store, workspace и Code Repositories повторно проверять не требуется: это ответственность `sdd connect`. Команда читает ID из `.openspec-store/store.yaml` и использует `--store <store-id>` во всех OpenSpec-командах чтения Master Specs; nearest root и глобальный `defaultStore` не используются. Ошибка официальной команды передаётся пользователю без попытки автоматически исправить registry.

### Загрузка и подключение Code Repositories

После успешного `sdd connect` локальный workspace соответствует рекомендуемой структуре из командной инструкции:

```text
<workspace>/
├── openspec/
│   └── payments-specs/
└── src/
    ├── api/
    └── ui/
```

Названия каталогов Code Repositories равны их `repository-id`. `sdd connect` не клонирует запись `role: store`, потому что пользователь уже находится в её checkout. Для каждой записи `role: code` команда:

1. клонирует отсутствующий репозиторий из `url` в `<workspace>/src/<repository-id>` на его `default_branch`;
2. для существующего каталога проверяет, что это обычный каталог, а не symlink, его `origin` соответствует canonical URL и checkout однозначно относится к ожидаемому `repository-id`;
3. не удаляет, не заменяет, не делает `pull`, checkout, merge или rebase существующего рабочего дерева;
4. проверяет config-only project pointer и фактическое разрешение общего Store.

Загрузка отсутствующего репозитория эквивалентна:

```bash
git clone --single-branch --no-tags --branch <default-branch> <url> <workspace>/src/<repository-id>
git -C <workspace>/src/<repository-id> rev-parse HEAD
```

URL и ветка берутся только из `sdd.yaml`. Credential предоставляет Git credential helper или другой внешний механизм; `sdd` не добавляет секрет в URL, конфигурацию или лог.

В принятом Code Repository должен находиться единственный OpenSpec-файл:

```yaml
# openspec/config.yaml
store: payments-specs
```

Это штатный project pointer OpenSpec для репозитория, планирование которого полностью вынесено в центральный Store. `sdd connect` не создаёт `openspec/specs/`, `openspec/changes/`, локальную schema или копии общего контекста и не устанавливает собственный OpenSpec root.

Из корня каждого Code Repository команда выполняет эквивалент:

```bash
openspec doctor --json
openspec context --json
```

OpenSpec сам разрешает pointer, проверяет Store relationship и возвращает свою диагностику. `sdd` не дублирует внутренние правила OpenSpec, но структурно проверяет границу ответов: отсутствие диагностики `severity: error`, ожидаемые Store ID, путь и `source: declared`.

Pointer является командной конфигурацией и должен быть принят в основной ветке Code Repository. Если его нет в только что загруженном репозитории и локальных `openspec/specs/` или `openspec/changes/` тоже нет, `sdd connect` может создать `openspec/config.yaml` локально и вернуть состояние `needs_setup_pr`. Команда не делает commit, push или PR. Пока setup PR не слит и повторный `sdd connect` не подтвердил чистый checkout основной ветки с pointer, подготовка этого репозитория и всего шага 00 не завершена.

Если в Code Repository уже существуют `openspec/specs/` или `openspec/changes/`, объявление `store:` было бы проигнорировано OpenSpec. Поэтому `sdd connect` не удаляет их и не продолжает работу: такой репозиторий требует отдельного решения о миграции локальных specs и Changes в центральный Store. Существующий `openspec/config.yaml` с любым содержимым, кроме того же единственного pointer, также не перезаписывается автоматически.

Повторный `sdd connect` клонирует только новые или отсутствующие записи `sdd.yaml` и заново валидирует все остальные. Добавление репозитория в реестр не требует нового `sdd init`: после принятия изменения `sdd.yaml` разработчик повторяет `sdd connect`, получает новый checkout и при необходимости проводит его setup PR.

Глобальный `defaultStore` для связи сервисов не используется: project pointer хранится в Git и одинаков для всей команды. `references` также не заменяют pointer — они добавляют read-only upstream-контекст к собственному OpenSpec root, тогда как в этой архитектуре Change целиком создаётся и хранится в центральном Store.

```text
payments-specs/

│   └── store.yaml
├── openspec/
│   ├── config.yaml
│   ├── context/
│   │   ├── 00-start-here.md
│   │   ├── 01-product-context.md
│   │   ├── 02-domain-glossary.md
│   │   ├── 03-architecture.md
│   │   ├── 04-domain-model.md
│   │   ├── 05-security-and-compliance.md
│   │   ├── 06-cross-system-invariants.md
│   │   ├── 07-quality-gates.md

│   │   ├── system-map.yaml
│   │   ├── ADR/
│   │   │   └── README.md
│   │   └── _raw/
│   │       └── README.md

```

`specs/`, `changes/` и `changes/archive/` создаются официальным Store API; до появления рабочих изменений в них находятся только служебные `.gitkeep`. Файлы `00-start-here.md`–`08-release-process.md`, `system-map.yaml` и два README создаются с готовой структурой, инструкциями и локальными `TODO`, а не пустыми.

`.openspec-store/store.yaml` не входит в skeleton bundle. Для нового или принимаемого существующего root его создаёт официальный `openspec store setup` сразу с ID и canonical remote. `sdd` проверяет эти значения, но не редактирует Store metadata вручную. Файл коммитится вместе с остальным результатом шага 00. Локальный registry OpenSpec находится вне репозитория и в Git не попадает.

Provider-specific команды `opsx-*` и skills `openspec-*` не входят в skeleton bundle. Это версионируемый официальный expanded agent pack, установленный OpenSpec для выбранного адаптера. Для `qwen` Technical Owner сначала выбирает expanded workflows через `openspec config profile`, затем обновляет pack штатной командой `openspec update --force`; `sdd` не редактирует эти файлы. OpenSpec `1.7.0` не знает namespace GigaCode, поэтому для `gigacode` `sdd init` переносит целиком официальный Qwen pack в `.gigacode/`. Прямой `openspec update --force` в таком проекте создаст `.qwen/` и не считается допустимым обновлением: новая версия OpenSpec принимается вместе с обновлением и проверкой GigaCode adapter в `sdd`.

Если выбранный адаптер поддерживает корневой provider-specific instruction-файл, он задаёт постоянную инструкцию проекта: AI-агент начинает каждый новый диалог и продолжает общение на русском языке. Код, команды, пути и машинные идентификаторы при этом не переводятся. Для адаптеров без такого файла те же требования находятся непосредственно в командах `sdd-*`.

### Назначение контекстных заготовок

| Файл | Что содержит после `sdd init` | Как обновляется `/sdd-context` |
|---|---|---|
| `00-start-here.md` | Правила подтверждения, маршрутизация файлов и временный раздел `Open questions` | Обновляет маршруты чтения и переносит вопросы в целевые context-файлы, когда их назначение становится известно |
| `01-...md`–`08-...md` | Постоянные предметные разделы и inline TODO с владельцем и ожидаемым источником | Заменяет TODO подтверждённым содержимым или уточняет вопрос и его источник |
| `system-map.yaml` | Каркас систем, связей и `repository-id` | Добавляет только подтверждённые системы, репозитории и связи |
| `ADR/README.md` | Когда нужен ADR, его обязательные разделы, минимальный шаблон и демонстрационные примеры; после init всё находится в одном README без отдельных файлов примеров | Создаёт отдельный `NNNN-short-title.md` только для реального принятого решения и добавляет его в индекс |
| `_raw/README.md` | Назначение и правила обработки неподтверждённых raw-материалов | При каждом вызове заново читает все raw-файлы; отдельный индекс и статусы обработки не ведёт |

Каждый TODO имеет поля `question`, `owner` и `expected_source`. `/sdd-context` заменяет TODO подтверждённым содержимым, но не меняет назначение файла и не удаляет обязательные разделы.

Контекст-пак хранит только долговечные общие правила. Команды сборки, линтинга и тестов остаются в code repositories и их CI configuration. История ошибок не ведётся отдельным нормативным журналом: подтверждённый вывод из инцидента переносится в подходящий context-файл, ADR или Master Spec.

### Граница `sdd` и OpenSpec

`sdd` является единой пользовательской и процессной поверхностью. OpenSpec Store является базовым API разрешения центрального root, а остальные возможности OpenSpec используются под капотом для графа артефактов, instructions, validation рабочих Changes и archive. Прямой запуск `openspec ...` не является нормативным пользовательским маршрутом, кроме показанной диагностики Store при устранении ошибок локальной регистрации.

| Операция `sdd` | Возможности OpenSpec под капотом | Что добавляет `sdd` |
|---|---|---|
| `sdd init` | Создание OpenSpec root, официальный agent pack и Store identity | Версионируемый SDD skeleton bundle и реестр Code Repositories |
| `sdd connect` | Локальная регистрация Store, `doctor` и project pointer | Канонический multi-repo workspace и загрузка Code Repositories |
| Создание и планирование Change | `new change`, `status` и `instructions` | Связь с ticket, planning-ветка, нумерованные гейты, владельцы и общий multi-repo контекст |
| Реализация | `instructions apply` | Точный Baseline, `repository-id`, разрешённые пути записи и отдельный прогресс |
| Проверка Change | `validate` и сведения Change | Composite Verification нескольких репозиториев и Evidence |
| Финализация | `archive` | Проверка acceptance, Git-ревизий и финального diff |

Отказ от runtime-валидации относится только к созданию встроенного скелета на шаге 00. Структурная validation конкретных OpenSpec Changes в последующих шагах остаётся частью OpenSpec core.

### Конфигурация OpenSpec

`sdd init` создаёт готовый `openspec/config.yaml`:

```yaml
schema: spec-driven

context: |
  Первое сообщение в новом диалоге начинай на русском языке.
  Общайся с пользователем, задавай вопросы и формируй отчёты на русском языке.
  Новые текстовые артефакты также пиши на русском языке.
  Не переводи код, команды, пути, идентификаторы и обязательные машинные значения.
  Перед созданием артефакта прочитай openspec/context/00-start-here.md
  и загрузи только назначенные им файлы для текущего артефакта.
  Спецификации нескольких code repo находятся в центральном Store Repository.
  Requirements описывают наблюдаемое поведение без деталей реализации.
  Master Specs меняются только командой Archive на этапе Finalization.

rules:
  proposal:
    - Укажи Jira/SberTrack key, проблему, ценность, scope, риски совместимости и затронутые repository-id.
  specs:
    - Описывай единый межрепозиторный контракт без деталей реализации.
  design:
    - В командном процессе design.md обязателен для каждого Change.
    - Зафиксируй ответственность компонентов, совместимость, rollout и rollback.
  tasks:
    - Раздели работу по Store и Code Repositories и включи composite verification.
```

Стандартная схема сохраняет четыре артефакта процесса из командной инструкции: `proposal.md`, Delta Specs, `design.md` и `tasks.md`. Подтверждённые выводы Explore становятся их входом без отдельного `research.md`; влияние на системы распределяется между Proposal и Design; план проверки, поставки и Archive фиксируется в Design и Tasks. Project rules только добавляют multi-repo-требования и не заменяют встроенные prompts и templates. Поэтому обновление OpenSpec приносит актуальные правила `spec-driven` без ручной синхронизации локальной схемы.

Spec Root регистрируется как OpenSpec Store. Команды SDD, которые читают или изменяют specs и Changes, после разрешения root получают явный `--store <store-id>`. В Code Repository обычное разрешение без флага проверяет командный pointer и возвращает `source: declared`; явный флаг всё равно имеет приоритет и используется для критичных операций.

Store отвечает за постоянную идентичность и единое место хранения Master Specs, Changes, архитектурных решений и задач реализации. Project pointer `store:` связывает с ним Code Repositories. Глобальный `defaultStore`, `references` и worksets на этом этапе не используются. Получение свежего Git-состояния, точные ревизии, Baseline, границы записи и Composite Verification остаются ответственностью `sdd`.

### Конфигурация `sdd`

`sdd init` создаёт `sdd.yaml`, записывает закреплённую версию OpenSpec `1.7.0` и заполняет известные репозитории:

```yaml
version: 1

versions:
  process: draft
  openspec: "1.7.0"

agent:
  id: qwen
  openspec_adapter: qwen
  architecture: markdown-commands
  commands_directory: .qwen/commands
  instructions_file: QWEN.md

repositories:
  - id: payments-specs
    role: store
    url: "<canonical-git-url>"
    default_branch: main
  - id: ui
    role: code
    url: "<canonical-git-url>"
    default_branch: main
  - id: api-server
    role: code
    url: "<canonical-git-url>"
    default_branch: main
```

При `--agent gigacode` секция агента выглядит так:

```yaml
agent:
  id: gigacode
  openspec_adapter: qwen
  architecture: markdown-commands
  commands_directory: .gigacode/commands
  instructions_file: GIGACODE.md
```

Официальным источником Store ID остаётся `.openspec-store/store.yaml`. В `sdd.yaml` то же значение используется как `id` единственной записи `role: store`, чтобы центральный репозиторий участвовал в общем реестре без второго идентификатора. `sdd` всегда проверяет равенство значений и не выводит ID из имени локального каталога. Секция `agent` фиксирует выбранного агента и фактический адаптер OpenSpec. Для `gigacode` поле `openspec_adapter` равно `qwen`, `commands_directory` равно `.gigacode/commands`, а `instructions_file` — `GIGACODE.md`. Секция проверяется как единый набор, поэтому смена одного пути вручную считается ошибкой конфигурации. Записи `role: code` имеют собственные проектные `repository-id`; все ID внутри `repositories` уникальны.

Если сведения о репозитории ещё неизвестны, в `sdd.yaml` не создаётся фиктивная запись. Неизвестная система или Code Repository фиксируется адресным TODO в `system-map.yaml`, а связанный вопрос о границах или ответственности — в `03-architecture.md`; оба закрывает Technical Owner. Credential и путь локального Store checkout в конфигурацию не записываются.

Capabilities, Requirements, Scenarios и состояние Changes в `sdd.yaml` не хранятся.

### Подключение новой рабочей машины и миграция существующего проекта

На новой рабочей машине разработчик сначала клонирует уже инициализированный центральный репозиторий в `openspec/`, затем запускает из его корня `sdd connect`:

```bash
git clone <canonical-git-url> <workspace>/openspec/<store-id>
cd <workspace>/openspec/<store-id>
sdd connect
```

Команда читает ID из версионируемого `.openspec-store/store.yaml`, регистрирует текущий checkout, проверяет Store и загружает Code Repositories из принятого `sdd.yaml`. Существующий skeleton не меняется. Это автоматизированный эквивалент однократной настройки рабочего места из базовой инструкции.

Если тот же Store ID уже привязан на машине к другому checkout, пользователь сначала явно выбирает нужный клон и самостоятельно выполняет `openspec store unregister <store-id>`; `sdd` не делает этого автоматически. При каждом повторе `sdd connect` идемпотентно передаёт текущий путь в `openspec store register`, а затем заново проверяет workspace.

Для центрального проекта, созданного до принятия Store-контракта, `sdd init` остаётся однократной инициализацией проекта:

```bash
sdd init --store <store-id> --agent <agent-id>
```

Команда разрешена только для чистого Git checkout без Store metadata и конфликтующих SDD-путей; существующий исправный OpenSpec root допускается. Официальный `openspec store setup` создаёт `.openspec-store/store.yaml` сразу с Store ID и canonical remote, а `sdd` проверяет результат, но не редактирует metadata вручную. Новая Store identity проходит обычное ревью и коммитится отдельным Store adoption PR. Затем единый `sdd connect` загружает и проверяет все Code Repositories; отсутствующий pointer принимается отдельным setup PR соответствующего репозитория. Повторно выполнять первичное наполнение context pack для такой миграции не требуется.

### Как `/sdd-context` наполняет скелет

При каждом вызове порядок приоритетов фиксирован: **структура центрального Store → raw-материалы → роль пользователя → относящиеся к роли inline TODO**. Агент не начинает свободный опрос пользователя, пока найденные raw-файлы не обработаны или пользователь явно не отложил конкретный материал.

Агент:

1. рекурсивно и только для чтения сканирует `openspec/context/`, строит полный перечень находящихся внутри `.md`-файлов и отдельно проверяет обязательный `system-map.yaml`;
2. классифицирует найденные пути как нормативный context, ADR, служебный README или raw-материал и отмечает отсутствующие элементы skeleton;
3. до обработки `_raw/` читает `00-start-here.md`, существующий `system-map.yaml`, README специальных каталогов, `sdd.yaml`, CODEOWNERS, Store metadata и разрешённые источники только внутри центрального Store; отсутствие активного CODEOWNERS для целевого файла блокирует изменение контекста;
4. находит все `_raw/**/*.md`, кроме служебного `_raw/README.md`, и обрабатывает их по одному в устойчивом порядке путей;
5. для каждого raw-файла извлекает отдельные утверждения, предполагаемый целевой context-файл и недостающие подтверждения;
6. по каждому утверждению просит пользователя подтвердить, исправить, отклонить или отложить его и сверяет утверждение только с нормативным контекстом, Master Specs и принятыми ADR центрального Store;
7. после разбора каждого raw-файла формирует diff целевых файлов, показывает его пользователю и применяет подтверждённые изменения до перехода к следующему raw-файлу;
8. неподтверждённые утверждения не переносит из `_raw/` в нормативный контекст;
9. не переходит по записям `role: code`, не читает `<workspace>/src/`, не вызывает для Code Repositories Git-команды и не сверяет контекст с реализацией;
10. после обработки или явного откладывания raw-файлов отдельным сообщением задаёт только вопрос «Какую роль вы представляете?»;
11. после ответа читает относящиеся к роли context-файлы и Master Specs, затем задаёт ровно один открытый адресный вопрос в каждом следующем сообщении, не предлагая придуманные предметные варианты ответа;
12. обновляет `00-start-here.md` последним, приводит в соответствие inline TODO и индекс ADR, показывает оставшийся diff по каждому файлу и применяет только подтверждённые пользователем изменения.

Инвентаризация структуры всегда предшествует чтению содержания. Наличие файла определяется по файловой системе, а не по истории чата. Неожиданный Markdown-файл не игнорируется: агент показывает его путь и просит определить назначение до использования содержащихся в нём сведений.

При каждом новом вызове агент заново читает все raw-файлы и сравнивает утверждения с нормативным контекстом. Уже перенесённый факт повторно не добавляется, а новое, изменённое или противоречащее утверждение снова выносится на уточнение пользователю.

Правила маршрутизации:

| Полученная информация | Куда записывается |
|---|---|
| Устойчивый факт о продукте, домене, архитектуре, ИБ, качестве или поставке | Соответствующий нормативный файл `01-...md`–`08-...md` |
| Долговечное принятое техническое решение и его основания | Новый ADR и ссылка на него из архитектурного контекста |
| Неизвестная система или Code Repository | Inline TODO в `system-map.yaml`; связанный вопрос о границах или ответственности — в `03-architecture.md` |
| Другой неизвестный факт или вопрос | Inline TODO в целевом context-файле; только если цель действительно неизвестна — `Open questions` в `00-start-here.md` |
| Неподтверждённое утверждение или исходный материал | `_raw/`; нормативные README и context files на него как на факт не ссылаются |

Самоназванная роль определяет маршрут диалога, но не является доказательством полномочий. Право принять diff определяется CODEOWNERS и правилами проекта.

Команда возвращает `context_status: current`, если context pack центрального Store не изменился, обязательные файлы существуют и между разрешёнными источниками нет нерешённых противоречий. После принятого diff при тех же условиях возвращается `updated`. Неподтверждённое изменение, нерешённое противоречие или ожидающее владельца решение дают `needs_confirmation`. Эти статусы описывают только центральный context pack и не подтверждают актуальность реализации в Code Repositories.

### Правила `.gitignore` и владения

В Git попадает весь SDD skeleton и его дальнейшее содержимое, а также созданные OpenSpec Store identity и официальный agent pack: `.openspec-store/store.yaml`, project config, команды `sdd-*` и `opsx-*`, подтверждённый контекст, inline TODO, `_raw/`, ADR, Master Specs, Changes, progress и Evidence. Встроенная schema `spec-driven` и её templates остаются частью установленного пакета OpenSpec и в проект не копируются.

Игнорируются только кэши, логи и локальные credential внутри репозитория. Каталоги `<workspace>/openspec/` и `<workspace>/src/` находятся выше корней отдельных Git-репозиториев и не требуют правил в их `.gitignore`. Широкие правила, скрывающие provider-specific agent pack, `openspec/` или `.sdd/` целиком, запрещены.

CODEOWNERS покрывает как минимум:

- `openspec/specs/**` и `openspec/changes/**` — Spec Owner;
- `.openspec-store/**` — Spec Owner и Technical Owner;
- `openspec/config.yaml` — Spec Owner и Apply Owner;
- продуктовый и доменный контекст — Change Owner;
- архитектурный контекст и `system-map.yaml` — Technical Owner;
- контекст безопасности и compliance — Security Owner;
- provider-specific команды `sdd-*` и `sdd.yaml` — Apply Owner и Technical Owner;
- provider-specific команды `opsx-*` и skills `openspec-*` — Apply Owner; файлы принимаются только как результат штатного обновления OpenSpec и не редактируются вручную;
- файлы quality gates — QA;
- файлы поставки — Technical Owner;
- `00-start-here.md` и README специальных каталогов — Spec Owner.

### Действия

1. Technical Owner согласовывает уникальный Store ID и собирает известные параметры центрального и code repositories.
2. В подготовленном центральном репозитории один раз выполняется `sdd init --store <store-id> --agent <agent-id>`: создаются Store identity, официальный agent pack, SDD skeleton и `sdd.yaml`.
3. Technical Owner заменяет placeholder в CODEOWNERS реальными account handles и активирует правила для всех нормативных context-файлов.
4. Из того же checkout выполняется `sdd connect --workspace <workspace>`: Store подтверждается в локальном registry, все Code Repositories загружаются в `src/` и проверяются с `source: declared`.
5. Если `sdd connect` вернул `needs_setup_pr`, pointer принимается в соответствующем Code Repository, после слияния checkout обновляется и команда повторяется.
6. Выполняется первичный `/sdd-context`; `_raw/` и inline TODO заменяются доступным подтверждённым контекстом, после чего обновляются `00-start-here.md` и ADR index.
7. Store identity, skeleton, настроенный CODEOWNERS и первичный контекст фиксируются в initialization PR центрального репозитория, а новые pointers — в setup PR соответствующих Code Repositories.
8. Каждый разработчик клонирует принятый центральный репозиторий и выполняет только `sdd connect`; повторный `sdd init` для onboarding запрещён.

### Результат шага 00

На уровне проекта после шага:

- skeleton bundle создан и находится в Git;
- `.openspec-store/store.yaml` содержит согласованные Store ID и canonical remote;
- `openspec context --store <store-id> --json` разрешает ожидаемый Spec Root с `source: store`;
- все Code Repositories из `sdd.yaml` содержат принятый config-only pointer на тот же Store;
- `00-start-here.md` объясняет маршрутизацию и порядок чтения контекста;
- неизвестные сведения представлены конкретными inline TODO с владельцами и ожидаемыми источниками;
- CODEOWNERS содержит активные правила с реальными владельцами для всех нормативных context-файлов;
- первичный `/sdd-context` наполнил доступный подтверждённый контекст;
- `_raw/` отделён от нормативных фактов;
- ADR создаются только из подтверждённого контекста;
- Spec Owner просмотрел diff и разрешил переход к первому рабочему запросу;
- initialization PR слит в основную ветку; setup PR всех зарегистрированных Code Repositories также слиты.

На каждой рабочей машине готовность к шагу 01 подтверждается отдельным успешным `sdd connect`: локальный checkout Store зарегистрирован, а все Code Repositories из `sdd.yaml` загружены в `<workspace>/src/<repository-id>` и разрешают Store с `source: declared`. `sdd init` на этой машине не выполняется.

Новый Code Repository добавляется через изменение `sdd.yaml`, setup PR с pointer и повторный `sdd connect` на рабочих машинах. До успешной проверки он не участвует в Explore, Planning или реализации через общий Store. Оставшиеся TODO допустимы, если у каждого есть владелец и они не блокируют понимание первого запроса.
