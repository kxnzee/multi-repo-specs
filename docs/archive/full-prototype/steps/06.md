## 06. Реализация в Code Repository

> [!WARNING]
> Архивный шаг предыдущего полного прототипа; не используйте его для Alpha.

Шаг выполняется отдельно в каждом затронутом Code Repository.

### 1. Запустите Apply-сессию

Откройте новую агентскую сессию из корня Code Repository и вставьте `next_action`, полученный от `openspec-orch load`, целиком и без изменения параметров.

Пример:

```text
Сначала прочитай файл инструкций агента "<path>/<agent-instructions-file>".
Затем прочитай и выполни инструкцию "<path>/sdd-apply.md" с параметрами:
--store payments-specs
--repo payments-api
--change pay-412-payment-status
--baseline 0123456789abcdef0123456789abcdef01234567
--work-package "1"
--work-package "2"
```

`<agent-instructions-file>` — `QWEN.md` для Qwen или `.gigacode/GIGACODE.md` для GigaCode; `next_action` уже содержит точный абсолютный путь.

Перед началом правок проверьте, что агент подтвердил правильные Change, Baseline, репозиторий и Work Packages.

### 2. Выполните работу

Попросите агента реализовать только выбранные Work Packages и выполнить проверки текущего репозитория.

Если работа большая, используйте короткий checklist в Draft PR. Дополнительный OpenSpec Change или отдельная feature-subtask для следующего подхода не нужны.

Если в subtask остались Work Packages:

1. завершите текущую порцию;
2. зафиксируйте прогресс в той же ветке и Draft PR;
3. повторите [шаг 05](05.md) со следующими ID;
4. передайте новый `next_action` в новую Apply-сессию.

### 3. Показывайте прогресс

После первого законченного commit опубликуйте `feature/<change-id>` и откройте Draft PR. В subtask указывайте текущий статус, блокеры и ссылку на PR.

При передаче работы другой разработчик продолжает ту же subtask, ветку и Draft PR.

### 4. Выполните проверки

Запустите предусмотренные репозиторием проверки, например:

- lint и format checks;
- unit и компонентные тесты;
- contract-тесты;
- build или compile;
- проверку diff на случайные изменения.

Если проверка не запускалась, укажите `Not run` и причину. Упавшая обязательная проверка блокирует готовность PR.

### 5. Подготовьте implementation PR

Перед переводом Draft PR в готовый синхронизируйте ветку с основной веткой по правилам репозитория и повторите проверки.

Добавьте в PR:

```yaml
ticket: PAY-412
change_id: pay-412-payment-status
store_id: payments-specs
spec_baseline: 0123456789abcdef0123456789abcdef01234567
repository_id: payments-api
work_packages:
  - "1"
  - "2"
planning_pr: <planning-pr-reference>
implementation_subtask: <tracker-reference>
checks:
  - command: npm test
    result: passed
```

Не копируйте в описание PR тексты Specs и Tasks.

После устранения блокирующих замечаний и успешных проверок запишите в subtask полную SHA текущего HEAD как `code_revision`. Если после этого появился новый commit, повторите проверки и замените SHA.

Не сливайте implementation PR: сначала требуется общая проверка системы.

Если во время реализации изменился принятый Baseline, остановите работу и используйте
сценарий [возобновления реализации после correction](../reference/changes.md#реализация-уже-началась).

### Успешный результат

Шаг завершён для репозитория, когда:

- выполнены все Work Packages из subtask;
- обязательные проверки успешны;
- блокирующие замечания исправлены;
- implementation PR готов;
- `code_revision` совпадает с HEAD PR.

Первый пилот завершается, когда такой результат получен для всех затронутых Code Repositories. Дальнейшие Composite Verification, merge, rollout и Archive выполняются по отдельным инструкциям.
