# Backlog OpenSpec Orchestrator

> [!CAUTION]
> **Документ заменён и не является текущим планом реализации.**
>
> Он описывает предыдущую модель `init → connect → explore → change → load`.
> Актуальные границы задаёт
> [текущий продуктовый контракт](../../technical/product-contract.md), а порядок работ —
> [текущий план реализации](../../technical/implementation-plan.md).
> Задачи ниже не следует выполнять без новой записи в `docs/user/pilot-feedback.md` и
> отдельного решения после пилота.

## 0. Цель первой версии

Статус: `superseded`.

Первая версия готова, когда новая команда может без изменения исходного кода Core:

1. создать собственный каталог Project Template;
2. выбрать поддерживаемого OpenSpec-агента;
3. описать центральный Store и нужные Code Repositories;
4. пройти `init -> connect -> optional explore -> change -> load -> Apply handoff`;
5. диагностировать локальную конфигурацию и использовать команды интерактивно либо
   через машинный JSON-контракт.

Backlog основан на текущей реализации `src/`. Он не добавляет в Core правила
backend/frontend-команд, конкретную OpenSpec-схему или процесс согласования.

## 1. Обязательные задачи v1

### 1.1. ORCH-001 — выборочное подключение Code Repositories

**Проблема:** `connect` обрабатывает все `role: code`, а `explore` требует локальный
checkout каждого зарегистрированного репозитория. Это не масштабируется на команды с
большим количеством микросервисов.

**Нужно:**

- добавить повторяемый `openspec-orch connect --repo <repository-id>`;
- добавить явный `openspec-orch connect --all`;
- сохранить проверку repository ID по `openspec-orch.yaml`;
- разрешить `explore` работать с подключённым подмножеством репозиториев;
- не считать отсутствующий невыбранный checkout ошибкой;
- показывать зарегистрированные, подключённые и отсутствующие репозитории отдельно.

**Критерий готовности:** разработчик может подключить и исследовать два репозитория
из большого Store, не клонируя остальные.

### 1.2. ORCH-002 — декларативный контракт agent adapter

**Проблема:** Core принимает только `architecture: markdown-commands`, проверяет
`<commands_directory>/opsx-explore.md` и формирует жёстко заданный `/opsx-explore`.
Это ограничивает Project Template агентами с такой же файловой моделью.

**Нужно:**

- убрать фиксированную архитектуру `markdown-commands` из Core-контракта;
- хранить в agent mapping официальное имя OpenSpec adapter;
- декларативно задавать путь установленного Explore action и его invocation;
- сохранить декларативные generated/target paths, provider instructions и handoffs;
- проверять безопасность путей, но не интерпретировать семантику agent assets;
- не изменять встроенные `openspec-*` skills и `opsx-*` commands.

**Критерий готовности:** новый совместимый OpenSpec agent adapter добавляется через
Project Template и тестовый fixture без изменения production-кода Core.

### 1.3. ORCH-003 — неинтерактивный Explore

**Проблема:** `openspec-orch explore` требует TTY, поэтому его нельзя воспроизводимо
вызывать из agent command, CI или будущего Plugin.

**Нужно:**

- добавить повторяемый `--repo <repository-id>`;
- добавить `--intent <text>`;
- при наличии полного набора параметров не требовать TTY;
- сохранить текущий интерактивный сценарий по умолчанию;
- одинаково валидировать интерактивный и неинтерактивный ввод.

**Критерий готовности:** одна полностью заданная команда без TTY возвращает тот же
проверенный Explore scope и invocation, что и интерактивный сценарий.

### 1.4. ORCH-004 — единый JSON-контракт команд

**Проблема:** `change` всегда печатает JSON, `load` имеет `--json`, а `init`,
`connect` и `explore` возвращают только человекочитаемый вывод.

**Нужно:**

- поддержать `--json` у `init`, `connect`, `explore`, `change` и `load`;
- в JSON-режиме писать в stdout только один итоговый JSON-документ;
- отправлять progress и предупреждения в stderr;
- зафиксировать поля успешного результата и ненулевой exit code ошибки;
- сохранить удобный человекочитаемый вывод без `--json`.

**Критерий готовности:** каждая команда безопасно вызывается агентом или скриптом
без разбора произвольного терминального текста.

### 1.5. ORCH-005 — read-only команда `doctor`

**Проблема:** `connect` выполняет часть диагностики, но одновременно регистрирует
Store, создаёт workspace, клонирует репозитории и записывает pointers.

**Нужно:**

- добавить `openspec-orch doctor` и `openspec-orch doctor --json`;
- автоматически определять запуск из Store или Code Repository;
- проверять доступность требуемых OpenSpec capabilities;
- проверять Store metadata, `openspec-orch.yaml`, agent mapping и handoffs;
- проверять регистрацию Store, workspace, repository identity и pointers;
- в strict mode проверять Git-состояние без fetch, pull или других изменений;
- возвращать все найденные диагностики за один запуск, где это безопасно.

**Критерий готовности:** команда объясняет, что именно мешает `connect`, `explore`,
`change` или `load`, не изменяя файловую систему, Git и OpenSpec registry.

### 1.6. ORCH-006 — версия Core-конфигурации

**Проблема:** project-local `openspec-orch.yaml` переживает обновления Core, но не
содержит версии своего публичного контракта.

**Нужно:**

- добавить обязательное целое поле `version: 1` в `openspec-orch.yaml`;
- генерировать его при `init`;
- отклонять неизвестную major-версию с конкретной ошибкой;
- покрыть чтение и сериализацию contract tests;
- не связывать эту версию с версией Template или OpenSpec.

**Критерий готовности:** новый Core однозначно определяет, совместима ли сохранённая
конфигурация, без повторного `init` и перегенерации Project Template.

### 1.7. ORCH-007 — файл репозиториев для `init`

**Проблема:** большое количество повторяемых `--repo <id=url#branch>` неудобно для
Store с десятками Code Repositories.

**Нужно:**

- сохранить текущий повторяемый `--repo`;
- добавить альтернативный `--repositories <path>` с YAML-массивом;
- разрешить только `id`, `url` и `default_branch`;
- применять к обоим способам ввода одну нормализацию и валидацию;
- запретить неоднозначное одновременное использование двух способов ввода.

**Критерий готовности:** большой список репозиториев передаётся в `init` отдельным
файлом без появления domain-specific ролей или ключей в Core.

### 1.8. ORCH-008 — публичная поставка и hosted-пилот

**Нужно:**

- утвердить npm name/scope и стабильную CLI-поверхность v1;
- снять `private: true` перед публикацией;
- проверить содержимое `npm pack`;
- проверить установку tarball и запуск CLI в чистом окружении;
- повторить flow со встроенным и пользовательским Project Template;
- пройти hosted Git pilot с настоящими remotes, PR и branch protection;
- отдельно зафиксировать непроверенные agent runtimes и внешнюю инфраструктуру.

**Критерий готовности:** опубликованный пакет устанавливается независимо от checkout
Core и проходит заявленный v1 flow на поддерживаемом OpenSpec CLI.

## 2. Задачи после обязательного v1

### 2.1. ORCH-009 — безопасная синхронизация checkout

Добавить явную команду:

```bash
openspec-orch sync --repo <repository-id>
openspec-orch sync --all
```

Команда выполняет только проверяемый `fetch` и fast-forward default branch для
чистых checkout. Она не делает merge, rebase, принудительный checkout или
автоматическое разрешение конфликтов.

### 2.2. ORCH-010 — Orchestrator Plugins

После стабилизации публичного Core-контракта:

1. определить Plugin API, out-of-process host и contract test kit;
2. реализовать read-only Jira/SberTrack Plugin;
3. отдельно спроектировать explicit writes, idempotency и audit evidence;
4. подготовить SDK для Plugins других команд.

Plugins не изменяют OpenSpec и не получают неявных lifecycle hooks Core-команд.

## 3. Что не входит в v1

- отдельная команда `openspec-orch apply`;
- типы команд или репозиториев `backend`, `frontend`, `mobile`;
- наследование и автоматическое объединение Project Templates;
- registry или marketplace Project Templates;
- автоматическое обновление уже скопированного Template;
- отдельные `repo add/remove` до подтверждённой потребности;
- Jira/SberTrack-логика внутри Core;
- автоматический commit, push, PR, merge, rollout или Archive;
- Plugin marketplace и выполнение недоверенных Plugins;
- отдельные `template validate`, `config validate` и `status`, пока их задачи
  покрываются `init` и `doctor`.

## 4. Рекомендуемый порядок реализации

1. `ORCH-006` — зафиксировать версию сохраняемого Core-контракта.
2. `ORCH-002` — убрать agent-specific ограничения до объявления публичного API.
3. `ORCH-001` — поддержать выборочный multi-repo workspace.
4. `ORCH-003` и `ORCH-004` — сделать CLI воспроизводимым и машиночитаемым.
5. `ORCH-005` — собрать существующие read-only проверки в `doctor`.
6. `ORCH-007` — упростить первичную настройку большого Store.
7. `ORCH-008` — выполнить package и hosted release checks.
8. После v1 оценить `ORCH-009` и начать `ORCH-010`.

Каждая задача выполняется отдельным небольшим commit. После изменения публичного
контракта обязательны затронутые tests, полный `npm run check`, package dry-run и
`git diff --check`.
