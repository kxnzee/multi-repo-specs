### 0.1. Как читать технические термины

В документе сохранены английские имена тех сущностей, которые должны оставаться узнаваемыми в командной строке, конфигурации, JSON и коде. После определения в этом словаре их можно использовать в основном тексте без повторного перевода. Русский термин нужен для первого объяснения смысла, а не как обязательная замена каждого английского употребления. Английское имя в скобках означает не вторую сущность, а точное техническое название той же сущности.

| Техническое имя | Русский термин | Что именно означает |
|---|---|---|
| Orchestrator Core, Core | ядро оркестратора, ядро | Универсальная часть продукта. Она хранит технические связи и проверяет общие ограничения, но не определяет процесс конкретной команды. |
| Project Template, Template | шаблон проекта, шаблон | Набор принадлежащих проекту файлов, команд и правил, через которые команда настраивает свой процесс работы. |
| OpenSpec Change, Change | изменение OpenSpec, изменение | Один набор требований и проектных артефактов OpenSpec, который нужно провести через несколько репозиториев. |
| Store | хранилище OpenSpec | Единственный репозиторий или корень Git, где OpenSpec хранит изменения, спецификации и схемы. |
| Repository Reference | описание репозитория | Стабильная запись о репозитории в конфигурации оркестратора: идентификатор, роль, удалённый адрес и основная ветка. |
| Cycle / Cycle Record | принятый цикл изменения / его запись в Git | Cycle — единственная сквозная координационная идентичность Core: он связывает одну принятую версию планирования и согласованный состав репозиториев. Cycle Record — файл, которым это решение представлено в Git. Assignment, Receipts и Snapshot имеют собственную роль, но ссылаются на один `cycle_id` и не создают конкурирующую сквозную идентичность. |
| Assignment | задание на реализацию | Вычисляемое задание реализовать текущий Cycle в одном конкретном репозитории. Оно определяется парой `cycle_id + repository_id`, не хранится отдельно и не означает назначение человека или список задач. |
| Handoff Mapping / Handoff Envelope | описание передачи / пакет контекста | Mapping указывает проектную точку входа. Envelope содержит структурированные факты, которые Core передаёт проектной команде или агенту. |
| Result Receipt / Verification Receipt | подтверждение реализации / подтверждение проверки | Структурированные результаты внешней работы. Core проверяет их форму и связь с точным Assignment или Snapshot, но не повторяет проектные проверки. |
| Snapshot | снимок версий | Вычисляемый неизменяемый набор точных версий реализации текущего Cycle, собранный для общей проверки Change. |

Названия команд, аргументов, полей и машинных состояний приводятся в обратных кавычках, например `assign`, `change-id`, `planning_revision`, `pending`. Их нельзя переводить в реализации: это часть публичного машинного контракта.

## 1. Продукт

### 1.1. Исходная проблема

Продуктовый инженер регулярно реализует одно изменение OpenSpec в системе из нескольких Git-репозиториев и одного центрального хранилища OpenSpec. Обычно он заранее знает основной список репозиториев, но вынужден вручную:

- развернуть или восстановить локальное рабочее пространство;
- проверить удалённые адреса, ветки, незавершённые операции Git и состояние рабочих копий;
- связать изменение с участвующими репозиториями;
- зафиксировать, на какой версии хранилища принят план;
- переносить между командами и рабочими сессиями технические идентификаторы принятого цикла, репозитория и задания, а также пути к артефактам планирования;
- объяснять исполнителю границы текущего репозитория;
- восстанавливать контекст после смены репозитория или рабочей сессии;
- фиксировать результат реализации каждого репозитория на точном коммите;
- собирать единый набор версий реализации;
- доказывать, что сводная проверка относится именно к этому набору версий и к тому же Cycle.

Git, OpenSpec, AI-агент и CI по отдельности не решают эту задачу:

- Git знает коммиты, ветки и удалённые адреса, но не знает, какой набор репозиториев реализует одно изменение;
- OpenSpec владеет изменением, схемой и жизненным циклом артефактов, но не обязан координировать рабочие копии нескольких репозиториев;
- агент или человек может реализовать задачу, но без стабильного технического контекста легко теряет изменение, принятый Cycle или границы репозитория;
- CI проверяет конкретный коммит или запуск задания, но сам по себе не связывает несколько проверенных версий с одним принятым Cycle.

### 1.2. Первый пользователь

Первый пользователь — **один продуктовый инженер**, который один или несколько раз в день проводит изменение через два или три заранее известных Git-репозитория.

Для функционального v1 не требуется одновременная координация нескольких инженеров. Сначала продукт должен доказать ценность в локальном сценарии одного человека, где основное состояние хранится на его машине и в Git.

После проверки готовности к распространению одно и то же ядро смогут независимо использовать разные команды. У каждой команды могут быть свои шаблон проекта, схема OpenSpec, команды для агента и процесс проверки.

Необходимо различать:

- **несколько команд независимо используют продукт** — целевой сценарий после проверки готовности к распространению v1;
- **несколько инженеров обмениваются локальными подтверждениями результатов и совместно изменяют одно рабочее состояние** — следующий этап, не входящий в v1.

В одном проекте v1 используется один активный профиль агента. Разные проекты и команды могут выбирать разных агентов. Автоматическое переключение между несколькими средами выполнения агентов внутри одного проекта в v1 не требуется.

### 1.3. Определение продукта

OpenSpec Orchestrator — локальный координатор реализации одного изменения OpenSpec в нескольких репозиториях. Он опирается на Git и не зависит от конкретной схемы OpenSpec.

Короткая формулировка:

> Оркестратор связывает одно изменение OpenSpec с отслеживаемым в Git Cycle, заданиями на реализацию, подтверждениями их результатов и сводной проверкой воспроизводимого Snapshot.

Ядро координирует процесс, но не строит содержательный план, не ведёт задачи, не запускает тесты и не управляет средой агента. Оно понимает технические связи между Store, Change, Cycle, репозиторием, Assignment, подтверждением результата и Snapshot. Бизнесовый смысл требований и критерии приёмки ядро не интерпретирует.

### 1.4. Самостоятельная ценность v1

Функциональный v1 должен доказать один сценарий:

> Один инженер проводит одно принятое изменение OpenSpec через два или три заранее известных репозитория. После активации Cycle он передаёт ежедневным операциям только `change-id` и, когда это нужно, `repository-id`; `cycle_id`, идентичность Assignment и набор версий реализации ядро разрешает само.

Минимальный путь:

```text
(init | adopt) → connect → repository status
    ↓
OpenSpec/Template создаёт или обновляет Change
    ↓
[plan(change-id)] → фиксация состояния планирования в Git
    ↓
assign(change-id, repository IDs) → Cycle Record в состоянии pending
    ↓
обычный процесс Git/PR → этот Cycle Record оказывается по нормативному пути в точном состоянии основной ветки и становится active
    ↓
status(change-id)
    ↓
implement(change-id) → record assignment(change-id, receipt)
    ↓
повторить для каждого репозитория
    ↓
verify(change-id) → точный Snapshot + передача контекста проверки
    ↓
запись Verification Receipt
    ↓
status(change-id) = phase: completed, condition: ok для этого Snapshot
```

`plan` — необязательная точка входа. Команда может планировать через существующий процесс OpenSpec и шаблона, а затем перейти к `assign`, если состояние планирования уже подготовлено и зафиксировано в Git.

### 1.5. Измеримая продуктовая ценность пилота

Пилот считается доказавшим самостоятельную ценность, если одновременно выполнены условия:

1. После активации Cycle пользователь не вводит вручную `cycle_id`, идентификатор Store, идентичность Assignment или полный список версий в `implement`, `record`, `status` и `verify`.
2. После перезапуска процесса `status(change-id)` восстанавливает текущий Cycle и вычисляемые Assignment без редактирования локального состояния.
3. Подтверждение результата с неверным `cycle_id`, репозиторием или версией отклоняется с безопасным отказом: операция останавливается и не оставляет частично принятого результата.
4. Результат проверки нельзя записать для снимка версий, отличного от подготовленного ядром.
5. Одно и то же изменение проходит не менее чем через два репозитория с кодом.
6. Пользовательская схема OpenSpec не требует ветвления ядра по имени схемы или имени артефакта планирования.
7. Подключение существующего проекта не перезаписывает его схему, команды, навыки и инструкции без явного выбора пользователя.
8. Инженер может вернуться к изменению через несколько дней и понять следующее действие только по `status(change-id)`.

### 1.6. Чем продукт не является

Оркестратор не является:

- заменой OpenSpec;
- новым форматом спецификаций и изменений;
- системой содержательного планирования;
- системой учёта задач;
- CI/CD-системой;
- площадкой размещения Git-репозиториев;
- системой управления релизами;
- средой выполнения агента;
- обязательным агентским фреймворком;
- изолированной средой на уровне операционной системы для внешнего агента или человека;
- владельцем критериев приёмки;
- механизмом скрытого запуска произвольного кода из шаблона;
- системой, которая сама принимает архитектурные решения;
- владельцем архива OpenSpec;
- командным сервером или общим рабочим состоянием нескольких пользователей.

## 2. Зафиксированные границы v1

### 2.1. Функциональные границы v1

В функциональный v1 входят:

1. Одно авторитетное хранилище OpenSpec как корень оркестрации.
2. Один принадлежащий пользователю и отслеживаемый в Git файл `openspec-orch.yaml`.
3. Для каждого принятия Change существует Cycle. Он связывает точный `planning_revision` и согласованный набор репозиториев. В Git Cycle представлен одним Cycle Record; подробная модель приведена в [разделе 5.3](#53-cycle).
4. Один файл `.openspec-orch/state.json`, которым управляет ядро и который хранится только на конкретной машине.
5. Заранее известный реестр репозиториев.
6. Роли репозитория: `store`, `code` или одновременно `store+code`.
7. Операции уровня репозиториев: `init`, `adopt`, `connect`, `repository status`.
8. Явный `change-id` во всех операциях слоя общего изменения и слоя изменения конкретного репозитория.
9. Необязательная команда `plan(change-id)`, которая готовит не зависящий от схемы пакет контекста для планирования.
10. `assign(change-id, repository IDs)` как единственная поддерживаемая операция подготовки нового Cycle.
11. Cycle Record проходит состояния хранения `pending → committed_pending → active`. `pending` означает, что `assign` подготовил файл в рабочей копии, но пользователь ещё не зафиксировал его в Git. `committed_pending` означает, что файл уже входит в коммит, но точное содержимое по нормативному пути ещё не совпадает с файлом в точном состоянии настроенной основной ветки Store. `active` означает, что корректная запись по этому пути находится в точном дереве файлов разрешённой ссылки на основную ветку, а её `planning_revision` достижима из этой ссылки. Историческое содержимое этого же пути не может стать вторым текущим Cycle. Эти состояния описывают положение файла в Git, а не отдельный жизненный цикл продукта.
12. Не более одного текущего Assignment для пары `cycle_id + repository-id`. Ограничение не относится к пользователю целиком: он может переключаться между репозиториями, параллельно вести другие Change и возвращаться к ним позже. Оно лишь запрещает два конкурирующих текущих результата одного и того же вычисляемого задания.
13. `status(change-id)` как сводная операция только для чтения по текущему принятому циклу.
14. `implement(change-id, repository?)` как подготовка пакета контекста для реализации.
15. `record assignment` для записи Result Receipt — локального структурированного подтверждения, что Assignment для пары `cycle_id + repository-id` получил результат на конкретном чистом коммите Git. Команда не заявляет, что Core самостоятельно проверил качество кода. Подробности приведены в [разделе 4.4](#44-уровень-изменения-конкретного-репозитория) и [разделе 5.8](#58-подтверждение-результата-реализации-result-receipt).
16. Snapshot — вычисленный перечень точных коммитов реализации текущего Cycle. Он нужен, чтобы тестировщик проверял один однозначный набор версий, даже если ветки позднее продвинулись. Незакоммиченные версии в Snapshot не входят; подробности и пример приведены в [разделе 4.5](#45-сводная-проверка-в-слое-общего-изменения) и [разделе 5.9](#59-снимок-версий-snapshot).
17. `verify(change-id)` как подготовка и развёртывание Snapshot и пакета контекста для проверки. Команда собирает проверяемые версии, но не запускает проектные тесты.
18. `record verification` для записи Verification Receipt — результата внешней проверки, который обязан ссылаться на тот же Snapshot.
19. Работа через публичные структурированные возможности OpenSpec без зависимости от конкретной схемы.
20. Понятный человеку вывод и версионированный вывод JSON.
21. Явные правила для предупреждений, ошибок и подтверждений пользователя.
22. `adopt`, который в первую очередь сохраняет существующий процесс OpenSpec и агента, а не заменяет его.
23. Передача контекста по запросу без запуска внешнего процесса из ядра.
24. Внутренний пилот одного реального изменения на двух или трёх репозиториях.
25. Проверка готовности к распространению перед объявлением продукта готовым для независимого использования разными командами.

### 2.2. Не входит в функциональный v1

В функциональный v1 сознательно не входят:

- `repository sync` как автоматическое обновление существующих рабочих копий;
- `disconnect` как отдельная публичная команда;
- автоматическое обнаружение участвующих репозиториев;
- граф репозиториев и вычисление списка затронутых репозиториев (`affected`);
- автоматическое изменение привязки изменения;
- зависимости или порядок выполнения между заданиями как модель, принадлежащая ядру;
- отдельная сущность проекта над Store и репозиториями: собственный идентификатор проекта, отдельный жизненный цикл и ещё один уровень общей конфигурации. В v1 эта сущность не нужна, потому что границу одного проекта уже задают Store и расположенный в нём `openspec-orch.yaml`;
- оркестрация нескольких хранилищ OpenSpec;
- сборщик шаблонов, рецепты или автоматическое объединение шаблонов;
- среда выполнения расширений, комплект разработчика и каталог расширений;
- автоматическое чтение или запись Jira, GitHub, Bitbucket, CI и каталога сервисов;
- серверный центр управления, фоновая служба или индексатор;
- командная синхронизация подтверждений реализации и проверки;
- автоматическое определение смысла существующих команд и навыков при подключении проекта;
- автоматическое создание произвольных исполняемых связок;
- запуск проектных тестовых команд внутри ядра;
- рабочая копия с незакоммиченными изменениями как воспроизводимая версия реализации или проверки;
- собственное управление архивом OpenSpec.

Отсутствие этих функций не является дефектом v1.

### 2.3. Проверка функциональной готовности и готовности к распространению

После проверки функциональной готовности продукт может использовать первый инженер в поддерживаемом пилотном проекте.

Продукт нельзя объявлять готовым для распространения в разные команды, пока не проверены: установка в чистом окружении, совместимость версий, миграция, целостность пакета, минимум два разных шаблона или описания совместимости и внешний пилот.

Эта проверка не добавляет новую продуктовую модель. Она подтверждает переносимость и эксплуатационную готовность уже реализованных функций.

## 3. Границы ответственности

Практически разделение выглядит так:

| Вопрос | Кто отвечает |
|---|---|
| Что именно нужно изменить и по каким критериям принять результат? | Команда через OpenSpec, выбранную схему и проектные артефакты |
| Как аналитик, разработчик, тестировщик или агент выполняет свою часть процесса? | Template и правила конкретной команды |
| Какие репозитории участвуют, какая версия планирования принята и каких результатов ещё не хватает? | Core |
| Кто принимает решения, изменяет код и выполняет проверки? | Человек, агент или внешняя система вроде CI |

С точки зрения бизнеса Core не определяет требования, архитектурные решения, порядок разработки и критерии приёмки. С технической точки зрения он хранит связи между Change, репозиториями и точными версиями, не позволяя случайно смешать результаты разных циклов. Следующие подразделы подробно фиксируют эту границу для каждого владельца.

### 3.1. OpenSpec

OpenSpec остаётся единственным владельцем:

- спецификаций;
- изменений;
- схем;
- графа артефактов;
- артефактов, заданных схемой;
- инструкций по созданию и проверке артефактов;
- проверки и жизненного цикла OpenSpec;
- штатных команд и навыков OpenSpec;
- жизненного цикла синхронизации и архивирования.

Ядро вызывает только публичные, поддерживаемые и структурированные возможности OpenSpec. Оно не вычисляет пути к артефактам планирования по предполагаемому расположению файлов и не подменяет OpenSpec собственной реализацией графа артефактов.

OpenSpec не обязан предоставлять понятие принятого Cycle. В v1 это событие координации, которым управляет ядро через команду `assign` и Cycle Record, отслеживаемый в Git.

### 3.2. Ядро оркестратора

Ядро отвечает за универсальную техническую координацию:

- хранилище и идентичность репозиториев;
- разбором `openspec-orch.yaml`;
- контракт Cycle Record;
- чтение действующего Cycle Record по нормативному пути из точного состояния настроенной основной ветки Store;
- проверку целостности Cycle и вычисление Assignment для его репозиториев;
- выбор рабочего пространства и точного рабочего дерева Git;
- пакет передачи контекста;
- контракты подтверждения результата и подтверждения проверки;
- проверку согласованности;
- сводное состояние;
- точный снимок версий;
- универсальные контрольные условия оркестрации;
- смысловые отпечатки и правила признания данных неактуальными;
- наблюдаемое локальное состояние;
- диагностику для человека и в формате JSON.

Ядро не должно:

- понимать бизнесовую цель изменения;
- интерпретировать критерии приёмки;
- генерировать содержательный план реализации;
- требовать конкретные артефакты планирования;
- запускать произвольные команды или навыки, принадлежащие проекту;
- объявлять проектный набор тестов пройденным без внешнего подтверждения результата;
- считать разрешённые корневые каталоги технически обеспеченной изоляцией;
- определять командную методологию;
- блокировать архивирование OpenSpec.

### 3.3. Шаблон проекта и описание совместимости

Шаблон проекта определяет правила конкретной команды и точки входа для агента:

- начальную конфигурацию OpenSpec и локальные схемы нового проекта;
- команды, навыки, инструкции и вспомогательных агентов проекта;
- начальный общий `context`;
- декларативные описания передачи контекста;
- проектный процесс планирования, реализации и проверки;
- набор файлов, из которых вычисляется отпечаток договора проверки.

Шаблон — декларативный набор файлов. После `init` созданные из него материалы принадлежат проекту.

Описание совместимости для `adopt` минимально и декларативно описывает уже существующий процесс. Оно может указать существующие точки входа и входные файлы контракта, но не получает права владения этими файлами.

Ядро не исполняет шаблон или описание совместимости. Оно только:

1. проверяет описание и безопасные пути относительно корня проекта;
2. формирует версионированный пакет передачи контекста;
3. показывает или возвращает настроенную точку входа;
4. описывает ожидаемое подтверждение реализации или проверки.

### 3.4. Агент или человек

Агент или человек:

- создаёт и читает артефакты планирования через процесс OpenSpec и шаблона;
- строит локальный план реализации;
- определяет задачи и порядок работы;
- изменяет код;
- запускает проектные проверки;
- создаёт структурированное подтверждение результата;
- честно указывает источник и подтверждающие данные.

Ядро не хранит рассуждения агента, временный список задач или полную историю реализации.

### 3.5. Передача контекста по запросу

В v1 контекст передаётся по запросу со стороны проекта:

1. Принадлежащая проекту команда агента вызывает соответствующую операцию ядра. Прямой вызов человеком остаётся ручным диагностическим способом.
2. Ядро возвращает пакет контекста и настроенную точку входа.
3. Та же проектная команда передаёт пакет в существующий процесс агента, который самостоятельно продолжает работу.
4. По завершении внешний исполнитель вызывает `record assignment` или `record verification`.

Пакет контекста — это Handoff Envelope: структурированный объект одного вызова `plan`, `implement` или `verify`. В нём находятся вычисленные Core факты, пользовательский `context`, безопасные пути, настроенная точка входа и описание ожидаемого результата. Точная JSON-схема относится к плану реализации, но по смыслу пакет для реализации выглядит так:

```json
{
  "operation": "implement",
  "change_id": "checkout-flow",
  "repository_id": "frontend",
  "cycle_id": "cycle-7f2a...",
  "entrypoint": ".qwen/commands/project-implement.md",
  "allowed_read_roots": ["<точное рабочее дерево Store>"],
  "allowed_write_roots": ["<рабочая копия frontend>"],
  "expected_result": "Result Receipt"
}
```

Это поясняющий пример, а не зафиксированная JSON-схема. Для человека Core показывает те же сведения в читаемом виде и сообщает следующую команду или файл инструкции. Для команды Template предусмотрен машиночитаемый JSON, который она может добавить в текущий контекст агента. План реализации выбирает конкретный транспорт: стандартный вывод, стандартный ввод или временный файл. Независимо от транспорта Handoff Envelope остаётся данными, а не исполняемым сценарием.

Ядро не запускает дочерний процесс, не вызывает API агента и не воспринимает команду Markdown как исполняемый код.

Если ядро вызывает человек напрямую, вывод должен показать точную следующую точку входа и способ передать пакет контекста. Если ядро вызывает команда агента, вывод JSON служит машинным контрактом для текущей сессии агента.

Основной пользовательский сценарий не требует ручного копирования между ядром и агентом: проектная команда сама получает структурированный пакет и продолжает существующий процесс. Ядро по-прежнему не запускает агента.

`allowed_read_roots`, `allowed_write_roots` и границы безопасности входят в обязательный контракт и диагностику, но не считаются технически обеспеченной изоляцией на уровне операционной системы. Реальную изоляцию может предоставить среда выполнения агента или будущее расширение, но не ядро v1.

## 4. Три иерархических уровня оркестрации

### 4.1. Общая последовательность

```text
Уровень репозиториев
init | adopt → connect → repository status
                         │
                         ▼
Уровень общего изменения
[plan(change-id)] → assign(change-id, repositories) → status(change-id)
                         │
                         ▼
Уровень изменения конкретного репозитория
implement(change-id, repository) → record assignment(change-id, receipt)
                         │
                         └── повторить для каждого репозитория
                                      │
                                      ▼
Возврат на уровень общего изменения
verify(change-id) → record verification(change-id, receipt) → status(change-id)
```

Иерархия идёт сверху вниз: рабочее пространство объединяет репозитории, общий Change связывает одну принятую версию планирования с их составом, а для каждого репозитория вычисляется собственное Assignment. Команды `verify` и `record verification` не создают следующий уровень. Они собирают результаты дочерних Assignment и завершают общий Change, поэтому относятся ко второму уровню.

Канонические имена публичных операций зафиксированы в разделе 7. Точную грамматику командной строки, флаги и правила передачи данных через стандартный ввод или файл определяет план реализации.

### 4.2. Уровень репозиториев

#### Назначение

Уровень репозиториев создаёт и восстанавливает технически пригодное локальное рабочее пространство из авторитетного хранилища и заранее объявленных репозиториев.

Он отвечает на вопросы:

- какой репозиторий служит хранилищем OpenSpec;
- какие репозитории объявлены пользователем;
- где находятся локальные рабочие копии;
- совпадают ли идентификатор репозитория, канонический удалённый адрес и роль;
- отсутствует ли рабочая копия;
- чистая ли рабочая копия, есть ли в ней незакоммиченные изменения, расхождение веток или проблема доступа;
- есть ли незавершённая операция Git;
- можно ли продолжать работу с изменением;
- какое безопасное ручное действие требуется.

#### Публичные операции уровня репозиториев

| Операция | Когда вызывается | Результат | Чего не делает |
|---|---|---|---|
| `init` | Проекта OpenSpec ещё нет | Новый проект из одного начального шаблона, конфигурация и первое локальное подключение | Не подключает существующий проект OpenSpec |
| `adopt` | Корректный проект OpenSpec уже существует | Конфигурация оркестратора с сохранением существующего процесса, отчёт о совместимости и первое подключение | Не переустанавливает схему, пакет поставщика агента или командный процесс |
| `connect` | Проект уже создан или подключён | Восстановленные локальные пути и наблюдаемое состояние подключения | Не меняет существующие ветки и не переписывает желаемую конфигурацию |
| `repository status` | В любой момент после обнаружения конфигурации | Состояние хранилища и всех репозиториев только для чтения, включая диагностику | Не исправляет расхождения автоматически |

`repository sync` и `disconnect` не входят в публичный API v1. До их появления `repository status` обязан достаточно подробно объяснять следующее безопасное действие.

#### `init`

`init` предназначен только для создания нового проекта OpenSpec.

Нормативная последовательность:

1. Выполнить предварительную проверку только для чтения. Любая неоднозначность должна остановить операцию до первой записи.
2. Убедиться, что целевой каталог не является корнем уже существующего корректного проекта OpenSpec.
3. Полностью проверить один начальный шаблон до первой записи.
4. Инициализировать OpenSpec через публичную поддерживаемую возможность.
5. Создать файлы ровно из одного шаблона без автоматического смешивания нескольких шаблонов.
6. Создать начальный `openspec-orch.yaml` и реестр репозиториев.
7. Создать необходимую структуру метаданных оркестратора.
8. Выполнить первое локальное подключение.
9. Показать итоговый `repository status`.

Если шаблон не указан, можно использовать один встроенный базовый шаблон. Явно выбранный шаблон полностью заменяет базовый; шаблоны автоматически не объединяются.

После `init` созданные материалы принадлежат проекту. Обновление ядра не перезаписывает их автоматически.

`init` не создаёт коммит и не отправляет созданные проектные файлы в удалённый репозиторий. Пользователь проверяет и фиксирует их обычным процессом Git.

#### `adopt`

`adopt` предназначен только для существующего корректного проекта OpenSpec.

Нормативная последовательность:

```text
проверка без записи → явное описание точек входа → предварительный показ изменений
→ подтверждённое безопасное добавление → подключение → отчёт о совместимости
```

`adopt` обязан:

1. Найти точный корень целевого проекта через публичную структурированную диагностику OpenSpec.
2. Потребовать точного совпадения найденного корня и переданного целевого пути.
3. Проверить идентичность хранилища и репозитория Git.
4. Сохранить существующие конфигурацию, схемы, спецификации, изменения, команды, навыки и инструкции OpenSpec.
5. Создать только отсутствующий `openspec-orch.yaml`, принадлежащие оркестратору метаданные и основу локального состояния.
6. Получить описания передачи явно: из командной строки, интерактивных ответов или явно переданного описания совместимости.
7. Проверить, что указанные пути существуют, безопасны и не конфликтуют друг с другом.
8. Выполнить первое локальное подключение.
9. Вернуть отчёт о возможностях: какие уровни готовы, каких способов передачи контекста не хватает и какие операции пока завершатся отложенной ошибкой отсутствующей возможности.

`adopt` может показать найденные каталоги поставщиков агентов и файлы-кандидаты, но не может определять смысл команды только по имени файла или каталога. Наличие `.qwen/`, `.codex/`, `commands/` или `skills/` не доказывает, какая точка входа отвечает за планирование, реализацию или проверку.

`adopt` не создаёт исполняемую связку автоматически. Принадлежащую проекту связку можно добавить, только если:

- пользователь явно передал описание совместимости или шаблон совместимости;
- полный diff рассчитан до записи;
- целевой путь свободен;
- пользователь подтвердил добавление;
- связка остаётся собственностью проекта и не получает скрытых разрешений.

Отсутствие способов передачи контекста не блокирует уровень репозиториев. Оно приводит к отложенной ошибке только при вызове соответствующего `plan`, `implement` или `verify`.

#### Безопасный выбор между `init` и `adopt`

| Команда и состояние | Результат |
|---|---|
| `init`, корректного корня OpenSpec нет | Продолжить начальное развёртывание |
| `init`, корректный корень OpenSpec есть | Ошибка без записей: использовать `adopt` |
| `adopt`, корректный корень OpenSpec есть | Продолжить подключение с сохранением существующего процесса |
| `adopt`, корень OpenSpec отсутствует | Ошибка без записей: использовать `init` |
| Оркестратор уже полностью настроен | Идемпотентная проверка и подключение |
| Состояние повреждено, конфликтует или неоднозначно | Ошибка с отчётом о восстановлении, без скрытой перезаписи |

Ядро не переключает `init` на `adopt` или наоборот без ведома пользователя.

#### `connect`

`connect`:

- заново читает `openspec-orch.yaml`;
- проверяет идентичности хранилища и репозиториев;
- находит или создаёт локальное рабочее пространство на текущей машине;
- может клонировать отсутствующий репозиторий по объявленному удалённому адресу и основной ветке;
- не выполняет `pull`, `rebase`, `merge`, `reset` и не переключает ветку существующей рабочей копии;
- не переписывает конфигурацию;
- обновляет только наблюдаемое локальное состояние;
- не восстанавливает потерянные подтверждения результатов так, будто проверки уже выполнялись.

На новой машине `connect` восстанавливает долговечные записи координации и идентичности заданий из Git. Локальные подтверждения результатов, снимки версий и подтверждения проверок отсутствуют до повторного получения или появления будущего механизма переноса.

#### `repository status`

`repository status` ничего не изменяет и показывает как минимум:

- идентичность и путь хранилища;
- реестр репозиториев;
- локальный путь каждого репозитория;
- missing/connected;
- совпадение канонического удалённого адреса;
- совпадение роли;
- текущую ветку и `HEAD`;
- наличие незакоммиченных изменений;
- незавершённую операцию Git;
- расхождение веток или недоступность версии, если это можно определить безопасно;
- связанные предупреждения и ошибки;
- следующее безопасное действие.

Команда состояния не обязана автоматически определять последнюю версию в удалённом репозитории, если для этого нужен доступ к сети. Локальные факты и сведения об удалённом репозитории должны быть явно разделены.

#### Критерий готовности уровня репозиториев

Из чистого окружения можно:

- создать новый проект через `init`;
- подключить существующий проект через `adopt` без замены файлов его процесса;
- повторно открыть рабочее пространство через `connect`;
- получить полное состояние без изменения данных;
- понять, почему работа с изменением разрешена или заблокирована, без ручного анализа внутреннего состояния ядра.

### 4.3. Уровень общего изменения

#### Назначение

Уровень изменения превращает согласованное планирование OpenSpec в устойчивую техническую основу для работы нескольких репозиториев. Он не читает смысл плана, а отвечает на практический вопрос: «какую именно версию требований и какой состав репозиториев мы сейчас реализуем?»

На этом уровне есть одна главная сущность — Cycle. Она объединяет:

```yaml
cycle_id: cycle-7f2a...
change_id: checkout-flow
planning_revision: a1b2c3...
repositories:
  - repository_id: frontend
    repository_fingerprint: repo-fp-frontend...
  - repository_id: backend
    repository_fingerprint: repo-fp-backend...
```

Cycle Record — не вторая сущность, а представление Cycle в отслеживаемом Git файле. `planning_revision` — не отдельная базовая сущность, а поле Cycle. Согласованный состав репозиториев — не отдельная привязка, а поле `repositories`. Assignment также не хранится отдельно: для каждого репозитория он однозначно вычисляется из пары `cycle_id + repository_id`.

Например, для Change `checkout-flow` пользователь принял план из коммита Store `a1b2c3` и репозитории `frontend` и `backend`. Core подготавливает один Cycle Record. После его активации существуют один Cycle и два вычисляемых Assignment — по одному для `frontend` и `backend`.

Если после активации `HEAD` Store продвинулся с `a1b2c3` на `d4e5f6`, текущий Cycle продолжает ссылаться на `a1b2c3`, пока пользователь явно не подготовит новый Cycle через `assign`. Core не создаёт коммит планирования и не управляет историей Git команды.

Уровень изменения отвечает на вопросы:

- какое изменение рассматривается;
- существует ли активный Cycle;
- какие `planning_revision` и репозитории входят в Cycle;
- какие Assignment вычисляются из `cycle_id` и репозиториев;
- какие подтверждения результатов заданий отсутствуют, завершены или некорректны;
- готово ли изменение к проверке;
- какие Snapshot и Verification Receipt относятся к текущему Cycle.

#### Cycle и Cycle Record как единый источник истины

Для каждого Change может существовать последовательность Cycle. Один из них является текущим, а предыдущие остаются историческими. `cycle_id` — сквозной идентификатор одного принятия. Например, первое согласование может иметь `cycle_id: C1`, а повторное после изменения плана — `cycle_id: C2`. Result Receipt из `C1` нельзя принять как результат `C2`.

Предыдущие версии записи остаются в обычной истории Git, но Core не диктует структуру коммитов. Запись логически расположена по пути:

```text
.openspec-orch/changes/<change-key>.json
```

Точный безопасный способ кодирования `change-id` в имени файла определяет план реализации. Ядро не размещает Cycle Record внутри пути артефактов OpenSpec, заданного схемой, и не требует знания внутреннего расположения файлов изменения.

Cycle Record содержит как минимум:

| Поле | Что хранит | Зачем нужно |
|---|---|---|
| версия контракта | Версию формата записи | Позволяет Core безопасно читать старые записи и отклонять неподдерживаемые |
| `cycle_id` | Уникальный идентификатор Cycle | Отделяет повторные согласования одного Change друг от друга |
| `change_id` | Например `checkout-flow` | Не позволяет применить запись к другому изменению |
| `planning_revision` | Точный чистый коммит Store с принятым состоянием планирования | Позволяет позднее восстановить именно тот контекст, который был согласован |
| `repositories` | Пары `repository_id + repository_fingerprint` | Одновременно определяет состав работ и защищает от незаметной подмены репозитория под прежним ID |

Версия контракта относится к формату хранения. Время создания, автор и другие диагностические поля можно хранить рядом, но они не участвуют в идентичности Cycle. Коммит, в котором находится Cycle Record, также не входит в его идентичность: Git-коммит показывает, где запись была принята, но не создаёт второй сквозной ID.

Cycle Record не содержит:

- задач;
- пакетов работ;
- целей;
- критериев приёмки;
- копии проектного решения;
- порядка реализации;
- содержательного плана выполнения;
- правил управления Git, ветки, стратегии слияния или особых требований к коммиту.

Отслеживаемый в Git Cycle Record долговечно переносит принятое решение. Только активная корректная версия служит авторитетным источником текущего Cycle. `.openspec-orch/state.json` не является источником его идентичности.

Отпечатки репозиториев связывают идентификатор репозитория с каноническим удалённым адресом и другими стабильными идентифицирующими данными. Они не включают текущую ветку, текущий коммит, незакоммиченные изменения или ход реализации.

#### Подготовка и активация Cycle

`assign` — единственная поддерживаемая операция ядра, которая готовит новый Cycle.

Практический пример:

1. В Store существует Change `checkout-flow`, а согласованное планирование находится в чистом коммите `a1b2c3`.
2. Пользователь вызывает `assign(change-id, repository IDs)`, передавая `checkout-flow` как `change-id`, а `frontend` и `backend` как идентификаторы репозиториев.
3. Core показывает: в новый Cycle войдут `planning_revision: a1b2c3`, `frontend` и `backend`; из него будут вычисляться два Assignment.
4. После подтверждения Core создаёт только ожидающий Cycle Record. Текущий Cycle пока не меняется.
5. Пользователь проверяет файл, коммитит его и проводит через обычный Git/PR-процесс.
6. Когда корректная запись по нормативному пути оказывается в точном дереве файлов настроенной основной ветки Store, она становится `active`. После этого разработчикам достаточно передавать `change-id` и `repository-id`; `cycle_id` и Assignment Core находит сам. Старые версии файла в истории Git остаются историческими и не участвуют в выборе текущего Cycle.

Таким образом, идентификаторы нужны не для ручного ввода пользователем, а для защиты от смешивания старого плана, нового состава репозиториев и результатов другой попытки.

Для первого принятия ядро обязано:

1. Однозначно определить хранилище и изменение.
2. Проверить состояние OpenSpec через публичный структурированный контракт.
3. Потребовать чистый индекс и рабочее дерево без незавершённой операции Git.
4. Проверить все идентификаторы репозиториев по реестру.
5. Определить явно принимаемый точный чистый коммит хранилища как `planning_revision`; ядро не создаёт этот коммит.
6. Сформировать предлагаемый Cycle Record с новыми `cycle_id` и `planning_revision`.
7. До первой записи показать полный состав репозиториев Cycle и последствия принятия.
8. Получить явное подтверждение пользователя.
9. Подготовить Cycle Record в состоянии `pending` по нормативному пути относительно проекта.
10. Вернуть успешный результат только в смысле «ожидающая запись подготовлена» и показать, что обычный процесс Git/PR ещё должен зафиксировать её в коммите.

После подтверждения `assign` может записать только предложенный Cycle Record. Команда не выполняет `git add`, `git commit`, `git push`, не переключает ветку, не выполняет слияние или перебазирование и не создаёт PR. Пользователь проводит файл через обычный процесс Git своей команды.

Cycle Record в состоянии `pending` не разрешает `implement`. Запись, зафиксированная только в рабочей ветке, имеет состояние `committed_pending` и также ещё не действует. Cycle становится активным, когда содержимое Cycle Record по нормативному пути в точном дереве файлов настроенной основной ветки совпадает с корректной записью, а её `planning_revision` достижима из этой ссылки. Для выбора текущего Cycle Core не перебирает предыдущие версии файла в истории. Коммит можно объединить, перебазировать или слить по правилам команды, если итоговое содержимое по нормативному пути остаётся корректным; ядро не требует особой структуры родителей или состава изменений коммита.

#### Повторное принятие и идемпотентность

Если активный Cycle существует и переданы те же `planning_revision` и состав репозиториев:

- обычный повторный `assign` идемпотентно возвращает текущий Cycle;
- более новый `HEAD` Store сам по себе не создаёт новый Cycle;
- новая версия планирования принимается только при явно указанном намерении обновить или заменить текущее принятие;
- точную форму такого намерения в командной строке определяет план реализации;
- новый состав репозиториев всегда требует нового `cycle_id`, ожидающего Cycle Record и подтверждения;
- старый цикл остаётся в истории, но перестаёт быть текущим.

Ядро не переносит старые подтверждения реализации или проверки в новый Cycle.

Изменение артефактов планирования, схемы или состава репозиториев не принимается автоматически. Пока пользователь явно не повторит `assign`, текущий Cycle остаётся прежним. `status` может показать информационное расхождение между `HEAD` Store и `planning_revision`, не объявляя исторические подтверждения ложными.

#### `plan(change-id)`

`plan` — необязательная операция ядра только для чтения, которая передаёт управление принадлежащему проекту процессу планирования.

Ядро:

1. Определяет хранилище и идентификатор изменения.
2. Проверяет уровень репозиториев.
3. Формирует не зависящий от схемы пакет контекста для планирования.
4. Включает реестр репозиториев, текущую зафиксированную версию хранилища как возможный контекст и общий пользовательский контекст.
5. Возвращает настроенную точку входа планирования.
6. Не запускает точку входа.
7. Не читает, не интерпретирует и не переписывает артефакты планирования.
8. В завершение указывает, что состояние планирования нужно проверить и зафиксировать в Git до нового `assign`.

Если передача в процесс планирования не настроена, `plan` возвращает отложенную ошибку отсутствующей возможности. Это не блокирует прямой переход к `assign` после внешнего планирования.

#### Краткий контракт `assign(change-id, repository IDs)`

Предыдущий подраздел описывает полный процесс принятия. Здесь не вводится вторая команда: это краткое резюме ограничений той же публичной операции `assign`.

`assign`:

- не назначает людей;
- не создаёт задачи;
- не определяет порядок реализации;
- не выбирает репозитории автоматически;
- не принимает текущий `HEAD` хранилища без явного указания;
- не использует имена артефактов, характерные для конкретной схемы OpenSpec.

Результат `assign` — Cycle Record в состоянии `pending`. Новый Cycle и вычисляемые Assignment становятся текущими только после перехода той же корректной записи в состояние `active`.

#### `status(change-id)`

`status` ничего не меняет. Он каждый раз:

1. Определяет хранилище и изменение.
2. Читает Cycle Record по нормативному пути из точного дерева файлов настроенной основной ветки Store; только эта версия может быть текущей. Отдельно обнаруживает кандидата в состоянии `pending` или `committed_pending`, но не выдаёт его за действующий Cycle.
3. Восстанавливает текущий Cycle и проверяет его целостность.
4. Проверяет описания репозиториев.
5. Вычисляет Assignment для каждого репозитория Cycle.
6. Проверяет локальные подтверждения результатов.
7. Проверяет последний снимок версий и подтверждение проверки.
8. Показывает текущий репозиторий только как явный атрибут представления, а не как скрытый фильтр.

`status` не доверяет локальному состоянию без проверки идентичностей Git и OpenSpec.

#### Вычисляемое состояние изменения

Вместо длинного плоского списка состояний Core вычисляет три независимых поля:

```yaml
phase: planning | implementing | verifying | completed
condition: ok | pending | blocked | failed | inconsistent
reason_code: WAITING_GIT_ACTIVATION
```

`phase` отвечает на вопрос, на каком участке находится текущий Cycle. `condition` показывает, можно ли продолжать. `reason_code` объясняет конкретную причину и следующее действие. Примеры: `WAITING_GIT_ACTIVATION`, `MISSING_RECEIPT`, `REVISION_UNAVAILABLE`, `SNAPSHOT_OUTDATED`, `VERIFICATION_FAILED`.

Состояние хранения Cycle Record (`pending`, `committed_pending`, `active`) выводится отдельно и не подменяет вычисляемое состояние Change. Исторический Cycle или Snapshot помечается `current: false`, а не ошибкой: старое состояние может быть корректным, хотя больше не является текущим.

`phase: completed` вместе с `condition: ok` означает только следующее: универсальные контрольные условия Core выполнены, а для текущего Snapshot записан корректный Verification Receipt со статусом `pass`. Это не означает одобрение PR, безопасности или выпуска и не доказывает независимую проверку CI, если указанный источник этого не подтверждает. Состояние вычисляемое: замена Result Receipt или создание нового Cycle может вернуть Change на более раннюю фазу.

#### Критерий готовности уровня изменения

По одному `change-id` ядро находит текущий Cycle, выводит не более одного вычисляемого Assignment на репозиторий и показывает сводное состояние без ручной передачи `cycle_id` и идентификаторов заданий.

### 4.4. Уровень изменения конкретного репозитория

#### Назначение

Этот уровень связывает принятое планирование с результатом реализации в одном конкретном репозитории. Он нужен, чтобы Core мог отдельно ответить: какая часть Change относится к `frontend`, какая — к `backend`, на каком точном коммите завершена каждая часть и каких результатов ещё не хватает.

Например, Cycle с репозиториями `frontend` и `backend` определяет два независимых Assignment. Фронтенд-разработчик может закончить своё задание раньше, но Snapshot для общей проверки не будет готов, пока актуальный Result Receipt со статусом `completed` не появится и для бэкенда.

```text
Assignment = cycle_id + repository_id
```

Задание на реализацию не является задачей, пакетом работ, веткой Git или документом планирования.

#### `implement(change-id, repository?)`

`implement` подготавливает выполнение, но не запускает принадлежащий проекту процесс реализации.

Ядро обязано:

1. Перечитать конфигурацию и проверить уровень репозиториев.
2. Найти текущий Cycle.
3. Определить репозиторий по текущему рабочему каталогу или явному фильтру.
4. Проверить, что репозиторий входит в Cycle.
5. Вычислить Assignment из `cycle_id + repository_id`. При необходимости JSON может содержать производный `assignment_id`, но пользователь не передаёт его и Core не хранит его как источник истины.
6. Создать или переиспользовать доступное только для чтения рабочее дерево Store на `planning_revision` текущего Cycle.
7. Зафиксировать начальную версию кода.
8. Сформировать пакет передачи контекста для реализации.
9. Вернуть настроенную точку входа реализации и контракт ожидаемого подтверждения результата.
10. Не запускать точку входа и не изменять репозиторий с кодом.

Ядро не может проигнорировать уже существующие незакоммиченные изменения в рабочей копии кода. Оно возвращает предупреждение и точно объясняет риск: будет невозможно однозначно определить, какие изменения относятся к текущему заданию. В интерактивном режиме продолжение возможно только после подтверждения; в неинтерактивном нужен токен подтверждения. Пока результат не оформлен как чистый коммит, записать подтверждение результата нельзя.

Если хранилище одновременно имеет роль `code`, ядро использует отдельные рабочие деревья:

- рабочее дерево Store только для чтения на `planning_revision`, чтобы передать контекст планирования;
- изменяемую рабочую копию кода для реализации;
- точное рабочее дерево реализации на записанном коммите для проверки.

#### Пакет передачи контекста для реализации

Пакет содержит как минимум:

- версию контракта;
- operation `implement`;
- идентификатор изменения;
- `cycle_id`;
- идентификатор и отпечаток репозитория;
- необязательный производный `assignment_id` для диагностики;
- путь к рабочему дереву Store на `planning_revision`;
- путь к репозиторию с кодом и начальную версию;
- разрешённые корневые каталоги для чтения;
- разрешённые корневые каталоги для записи;
- описание границ безопасности;
- принадлежащий пользователю контекст;
- метаданные настроенной точки входа;
- требуемую версию контракта подтверждения результата.

Факты, вычисленные ядром во время выполнения, имеют приоритет над пользовательским контекстом. Пользовательский контекст не может переопределить идентичности, версии, пути или поля границ безопасности.

#### `record assignment`

`record assignment` принимает одно версионированное подтверждение результата.

Для локального v1 ядро обязано требовать:

1. Явный `change-id`.
2. Однозначно определённый текущий репозиторий или явный фильтр репозитория.
3. Совпадение `cycle_id`, репозитория и хеша Handoff Envelope с текущим Assignment.
4. Точный коммит Git как версию реализации.
5. Наличие коммита в ожидаемом репозитории.
6. Совпадение `HEAD` текущей рабочей копии с заявленной версией для локального источника.
7. Чистое рабочее дерево без незавершённой операции Git.
8. Корректные источник и структуру подтверждающих данных.

Рабочее дерево с незакоммиченными изменениями, `stash`, незакоммиченный патч или только разница файлов не считаются версией реализации, которую можно записать в v1.

Результат подтверждения имеет следующую продуктовую семантику:

- `completed` — исполнитель заявляет, что задание завершено на точном коммите;
- `failed` — попытка завершилась известной ошибкой и не проходит контрольное условие завершения;
- `blocked` — выполнение невозможно без внешнего решения и не проходит контрольное условие завершения.

Точное машинное написание значений определяет план реализации, но эти три смысла должны оставаться различимыми.

Только актуальное подтверждение со статусом `completed` допускает задание в снимок версий изменения.

Новое подтверждение не становится текущим только потому, что у него более поздняя отметка времени. Если текущее подтверждение уже существует, новое обязано явно указать его `receipt_id` в поле `supersedes`. Несовпадение считается ошибкой и защищает от результатов, пришедших не по порядку. После корректной замены новое подтверждение `completed|failed|blocked` становится текущим; предыдущее остаётся в истории и не участвует в текущем снимке.

Ядро проверяет структуру и согласованность, но не заявляет, что самостоятельно повторило проектные проверки. Источник и подтверждающие данные всегда показываются пользователю.

#### Подтверждение результата реализации (Result Receipt)

Минимальный контракт включает:

- версию контракта;
- уникальный идентификатор подтверждения;
- необязательное поле `supersedes` с точным идентификатором предыдущего текущего подтверждения;
- `cycle_id`;
- идентификатор репозитория;
- коммит реализации;
- результат;
- тип и идентичность источника;
- список подтверждающих данных;
- хеш пакета передачи контекста;
- время создания;
- диагностические метаданные, не участвующие в идентичности.

В v1 ядро хранит текущее подтверждение и минимальную цепочку замен: `receipt_id`, версию контракта, результат и `supersedes`. Полный журнал рассуждений и внешние журналы не входят в модель ядра.

#### Критерий готовности уровня изменения конкретного репозитория

В каждом репозитории пользователь передаёт `change-id` и, если текущий каталог не определяет репозиторий однозначно, `repository-id`. Ядро автоматически находит Cycle и вычисляет Assignment, предоставляет точный контекст планирования и принимает только подтверждение результата на чистом коммите, согласованное с этим Cycle.

### 4.5. Сводная проверка в слое общего изменения

#### Две фазы проверки

Проверка намеренно разделена на две операции:

1. `verify(change-id)` — ядро строит и развёртывает точный снимок версий, затем выдаёт пакет контекста для проверки.
2. `record verification(change-id, receipt)` — ядро принимает и сохраняет результат внешней проектной проверки.

Обе операции принадлежат слою общего изменения. Snapshot агрегирует результаты дочерних Assignment, а Verification Receipt подтверждает проверку общего Change. Ни один из них не образует отдельный уровень.

Это разделение обязательно: ядро не исполняет точку входа шаблона, а проверка может завершиться позже, в отдельной сессии человека, агента или CI.

#### `verify(change-id)`

Ядро обязано:

1. Найти текущий Cycle.
2. Потребовать актуальный Result Receipt со статусом `completed` для каждого репозитория Cycle.
3. Проверить точные коммиты и идентичности репозиториев.
4. Построить детерминированный снимок версий.
5. Рассчитать отпечаток договора проверки.
6. Проверить универсальные контрольные условия оркестрации.
7. Развернуть изолированное рабочее пространство проверки на точных коммитах.
8. Сформировать пакет передачи контекста для проверки.
9. Сохранить ожидающий снимок в локальном состоянии.
10. Вернуть настроенную точку входа проверки и требуемый контракт подтверждения проверки.
11. Не запускать проектные проверки.

Если хотя бы один коммит недоступен, подтверждение результата некорректно или точное рабочее дерево невозможно создать, `verify` завершается ошибкой и не создаёт корректное ожидающее состояние проверки.

#### Точный снимок версий (Snapshot)

Snapshot отвечает на вопрос: «какой именно совместный набор версий был передан на проверку?» Без него фраза «проверили frontend и backend» неоднозначна: ветки могли сдвинуться, а разработчики и тестировщик могли смотреть на разные коммиты.

Пример: Result Receipt фронтенда указывает на коммит `f111`, а Result Receipt бэкенда — на `b222`. `verify` создаёт Snapshot `S1`, который связывает текущий `cycle_id`, `f111`, `b222` и отпечаток договора проверки. Если позже ветка фронтенда продвинется до `f333`, результат проверки для `S1` останется честно связан с `f111` и не будет выдан за проверку `f333`. Для нового набора версий потребуется новый Snapshot.

Снимок включает:

- версию контракта снимка;
- детерминированный идентификатор снимка;
- `cycle_id`;
- пары `repository_id + implementation_revision` для всех репозиториев Cycle;
- отпечаток договора проверки;
- метаданные развёртывания рабочих деревьев;
- время создания и источник.

`Snapshot ID` вычисляется только из проекции идентичности, то есть из полей, которые действительно определяют проверяемое содержимое:

```text
Snapshot ID = hash(
  Snapshot contract version,
  cycle ID,
  canonical implementation entries:
    repository ID + implementation commit,
  verification contract fingerprint
)
```

Время создания, имя узла, идентификатор машины, временные пути, пути развёртывания, каталог рабочего дерева и другие диагностические метаданные можно хранить рядом со снимком, но они не входят в `Snapshot ID`.

Снимок состоит только из коммитов Git. Поле `dirty` не используется вместо точного определения содержимого.

Текущие изменяемые рабочие копии не служат средой проверки. Ядро создаёт точные рабочие деревья или эквивалентные неизменяемые копии на указанных коммитах.

#### Пакет передачи контекста для проверки

Этот Handoff Envelope нужен, чтобы тестировщик, агент или CI получил не только идентификатор Snapshot, но и готовые пути к точным рабочим деревьям, проектную инструкцию проверки и форму ожидаемого результата. Без пакета исполнитель вынужден вручную искать коммиты и инструкции и может проверить не тот набор версий.

Например, пакет для Snapshot `S1` сообщает: frontend развёрнут на `f111`, backend — на `b222`, инструкция находится в `.qwen/commands/project-verify.md`, а результат нужно вернуть как Verification Receipt именно для `S1`. Core передаёт эти сведения, но не запускает указанную инструкцию.

Пакет включает:

- точный снимок версий;
- пути к точным рабочим деревьям;
- границы чтения и записи в рабочем пространстве проверки;
- настроенную точку входа проверки;
- пользовательский контекст;
- отпечаток договора проверки;
- требуемую версию подтверждения проверки;
- указание, что результат должен относиться к тем же `cycle_id` и `Snapshot ID`.

#### `record verification`

Подтверждение проверки включает как минимум:

- версию контракта;
- уникальный `receipt_id`;
- необязательный `supersedes` с точным `receipt_id` предыдущего текущего подтверждения;
- `cycle_id`;
- идентификатор снимка;
- отпечаток договора проверки;
- хеш пакета передачи контекста для проверки;
- результат;
- тип и идентичность источника;
- список подтверждающих данных;
- время создания;
- диагностические метаданные.

Результат проверки имеет четыре разных смысла:

- `pass` — проектная проверка завершена успешно;
- `fail` — проверка была выполнена и обнаружила несоответствие;
- `error` — проверка не смогла корректно выполниться;
- `inconclusive` — подтверждающих данных недостаточно для `pass` или `fail`.

Ядро обязано отклонить подтверждение, если `cycle_id`, идентификатор снимка, отпечаток договора проверки или хеш пакета контекста не совпадают с подготовленной ожидающей проверкой.

Если для того же Snapshot уже существует текущий Verification Receipt, новый результат обязан явно сослаться на него через `supersedes`. Отметка времени не выбирает текущий результат. Это позволяет повторить проверку и одновременно защищает от результатов, пришедших не по порядку.

`pass` от агента или человека остаётся результатом с соответствующим источником. Ядро не выдаёт его за независимо подтверждённый результат. Пользовательский интерфейс и JSON обязаны показывать источник и подтверждающие данные рядом с результатом.

#### Критерий готовности сводной проверки

Для изменения с подтверждениями `completed` ядро воспроизводимо развёртывает точный снимок версий, выдаёт пакет контекста для проектной проверки и принимает только подтверждение, связанное с тем же снимком и отпечатком договора.

## 5. Доменная модель v1

Этот раздел — справочная карта данных оркестратора, а не ещё один уровень процесса и не новая схема OpenSpec. Проще всего читать модель как цепочку:

```text
OpenSpec владеет Change
    ↓
Cycle фиксирует planning_revision и репозитории
    ↓
по одному вычисляемому Assignment на каждый репозиторий Cycle
    ↓
Result Receipt связывает Assignment с точным коммитом
    ↓
Snapshot объединяет все точные коммиты
    ↓
Verification Receipt фиксирует результат проверки этого Snapshot
```

Handoff Mapping и Handoff Envelope обслуживают передачу контекста внешнему исполнителю. Подтверждающие данные, отпечатки и контрольные условия помогают Core проверять согласованность всей цепочки.

Практическая карта сущностей:

| Сущность | Зачем нужна | Короткий пример |
|---|---|---|
| Store | Даёт один авторитетный корень для Change и конфигурации оркестратора | Репозиторий `specs` содержит OpenSpec и `openspec-orch.yaml` |
| Repository Reference | Стабильно описывает один подключаемый репозиторий без локального пути конкретного человека | `frontend` → удалённый URL и основная ветка `main` |
| Cycle | Одним ID связывает принятую версию планирования и состав репозиториев | `C1` связывает `checkout-flow`, коммит `a1b2c3`, `frontend` и `backend` |
| Cycle Record | Переносит Cycle через обычную историю Git | `.openspec-orch/changes/checkout-flow.json` содержит данные `C1` |
| Assignment | Однозначно обозначает реализацию Cycle в одном репозитории и не требует отдельной записи | Пара `C1 + frontend` |
| Handoff Mapping | Указывает, где проект хранит свою инструкцию для планирования, реализации или проверки | `.qwen/commands/project-implement.md` |
| Handoff Envelope | Передаёт исполнителю вычисленный Core контекст одного вызова | Cycle, репозиторий, безопасные пути и ожидаемый Result Receipt |
| Result Receipt | Связывает результат одного Assignment с точным коммитом и источником | Frontend завершён на коммите `f111`, источник — агент или человек |
| Snapshot | Фиксирует единый набор версий для общей проверки | Cycle `C1` + frontend `f111` + backend `b222` |
| Verification Receipt | Связывает результат внешней проверки с конкретным Snapshot | Тестировщик записал `pass` для Snapshot `S1` |
| Подтверждающие данные | Объясняют, что именно выполнялось и откуда взялся результат | Название проверки, источник, результат и ссылка на запуск CI |
| Отпечаток | Обнаруживает смысловое изменение идентичности или договора | Изменение файла инструкции проверки даёт новый отпечаток договора |
| Контрольное условие | Разрешает или запрещает переход состояния на основании фактов Core | `verify` недоступен, пока хотя бы один Assignment не имеет `completed` Result Receipt |

Следующие подразделы уточняют состав и ограничения каждой сущности.

### 5.1. Хранилище OpenSpec (Store)

Хранилище — авторитетный репозиторий или корень Git, принадлежащий OpenSpec и содержащий изменения, спецификации и схемы. В v1 он одновременно служит корнем оркестрации.

Существует ровно одно описание репозитория с ролью `store`. Тот же репозиторий может дополнительно иметь роль `code`.

Хранилище не содержит и не определяет:

- локальные пути к рабочим копиям на конкретной машине;
- учётные данные;
- систему учёта задач;
- общий для организации граф зависимостей;
- локальные подтверждения результатов;
- жизненный цикл выпуска других репозиториев.

### 5.2. Описание репозитория (Repository Reference)

Описание репозитория — стабильная отслеживаемая в Git запись в `openspec-orch.yaml`:

- `repository_id`;
- `roles`: `store`, `code` или оба значения;
- канонический URL удалённого репозитория;
- основную ветку;
- необязательные принадлежащие проекту метаданные внутри явно выделенного раздела расширений.

Идентификатор репозитория задаёт его логическую идентичность внутри проекта оркестратора. Удалённый URL и роли входят в отпечаток этой идентичности.

Локальный путь на конкретной машине не хранится в отслеживаемой Git конфигурации.

Ядро не требует бизнесовых ролей `frontend`, `backend`, `analytics` или `infrastructure`.

### 5.3. Cycle

Cycle — главная сущность координации Core. Он фиксирует одно принятое решение:

```yaml
cycle_id: cycle-7f2a...
change_id: checkout-flow
planning_revision: a1b2c3...
repositories:
  - repository_id: frontend
    repository_fingerprint: repo-fp-frontend...
  - repository_id: backend
    repository_fingerprint: repo-fp-backend...
```

`cycle_id` — универсальный сквозной ID. Result Receipt и Verification Receipt обязаны ссылаться на него. Пользователь в ежедневных командах передаёт `change-id`; Core самостоятельно находит текущий Cycle.

`planning_revision` является точным чистым коммитом Store с принятым состоянием планирования OpenSpec. `repositories` одновременно задаёт состав реализации и защищает идентичность каждого репозитория его отпечатком. Эти данные не образуют отдельные доменные сущности или дополнительные пользовательские ID.

Изменение `planning_revision`, `change_id`, состава репозиториев или их отпечатков означает другой Cycle и требует нового `cycle_id`. Точный алгоритм создания и проверки `cycle_id` определяет план реализации. Диагностические поля, время, путь файла и Git-коммит с Cycle Record не входят в идентичность.

### 5.4. Cycle Record

Cycle Record — Git-представление Cycle по пути `.openspec-orch/changes/<change-key>.json`. Это не отдельная доменная сущность и не второй источник истины.

`assign` подготавливает запись в состоянии `pending`, но не выполняет `git add`, `commit`, `push`, `merge`, `rebase` и не создаёт PR. После коммита рабочей ветки запись имеет состояние `committed_pending`. Она становится `active`, когда корректное содержимое этого Cycle Record находится по нормативному пути в точном дереве файлов настроенной основной ветки Store и её `planning_revision` достижима из этой ссылки. Предыдущие версии Cycle Record в истории Git не рассматриваются как кандидаты на текущий Cycle.

Состояния Cycle Record описывают положение записи в Git. Они не входят в `cycle_id` и не создают дополнительный уровень оркестрации. Предыдущие Cycle сохраняются в истории Git и могут быть показаны как `current: false`.

### 5.5. Задание на реализацию (Assignment)

Assignment — вычисляемая пара:

```text
Assignment = cycle_id + repository_id
```

Core не хранит Assignment отдельным файлом. Для удобства машинного вывода он может вернуть детерминированный `assignment_id = hash(cycle_id + repository_id)`, но этот ID не является пользовательским входом или источником истины.

Один Cycle имеет ровно по одному Assignment на каждый входящий в него репозиторий. Новый Cycle создаёт новый набор Assignment; результаты предыдущего Cycle не переносятся автоматически.

### 5.6. Описание передачи контекста (Handoff Mapping)

Описание передачи контекста — декларативная принадлежащая проекту ссылка на точку входа для агента.

Описание содержит как минимум:

- тип;
- точку входа по пути относительно проекта;
- необязательный объявленный список входов контракта;
- необязательные принадлежащие проекту метаданные.

Описание не является разрешением на исполнение и не запускается ядром.

### 5.7. Пакет передачи контекста (Handoff Envelope)

Пакет передачи контекста — версионированный неизменяемый объект одного вызова `plan`, `implement` или `verify`.

Пакет объединяет:

- технические факты ядра;
- принадлежащий пользователю контекст;
- метаданные настроенной точки входа;
- контракт ожидаемого результата.

Пакет можно вывести в JSON, передать через стандартный ввод или файл либо предоставить текущей сессии агента. Точный способ передачи определяет план реализации.

### 5.8. Подтверждение результата реализации (Result Receipt)

Подтверждение результата — версионированное локальное свидетельство результата одного Assignment на точном коммите реализации. Его основная связь имеет вид:

```yaml
receipt_id: result-r1
cycle_id: cycle-7f2a...
repository_id: frontend
implementation_revision: f111...
status: completed
source: agent
evidence: []
supersedes: null
```

Версия контракта, хеш Handoff Envelope, время и диагностические метаданные могут дополнять запись, но не заменяют обязательную связь `cycle_id + repository_id + implementation_revision`.

Подтверждение доказывает только то, что в нём заявлено, и всегда сохраняет указанный источник. Оно не становится свидетельством CI или независимой проверкой без соответствующего источника.

После потери локального подтверждения нужно повторно получить результаты проверок, которые больше нечем доказать. Это не повреждает Store, Cycle Record или репозиторий с кодом.

### 5.9. Снимок версий (Snapshot)

Снимок версий — неизменяемый набор точных коммитов для сводной проверки.

Snapshot является производным представлением для проверки, а не новым источником истины:

```yaml
snapshot_id: snapshot-s1
cycle_id: cycle-7f2a...
implementations:
  frontend: f111...
  backend: b222...
verification_contract_fingerprint: verify-fp-1...
```

`snapshot_id` детерминированно зависит только от `cycle_id`, приведённых к каноническому виду пар `repository_id + implementation_revision` и отпечатка договора проверки. Время, локальные пути и идентификатор машины в него не входят.

Снимок не зависит от текущих изменяемых имён веток или состояния рабочих деревьев.

### 5.10. Подтверждение проверки (Verification Receipt)

Подтверждение проверки — версионированное локальное свидетельство проектной проверки одного точного Snapshot и одного подготовленного Handoff Envelope:

```yaml
receipt_id: verification-v1
cycle_id: cycle-7f2a...
snapshot_id: snapshot-s1
result: pass
source: tester
evidence: []
supersedes: null
```

Явный `cycle_id` не позволяет случайно принять Snapshot другого Cycle даже при ошибке локального состояния. Хеш Handoff Envelope и отпечаток договора проверки дополнительно связывают результат с точной операцией.

Подтверждение не заменяет снимок и не может ссылаться только на «текущие ветки».

После потери подтверждения проверки нужно повторить проверку или заново получить доказательство для того же снимка.

### 5.11. Вспомогательные контракты

Repository Reference, Handoff Mapping, Handoff Envelope, подтверждающие данные, отпечатки и контрольные условия поддерживают основные сущности, но не создают собственные оси жизненного цикла.

#### Подтверждающие данные

Подтверждающие данные — структурированное утверждение о выполненной проверке.

Как минимум они отвечают на вопросы:

- что проверялось;
- на каком коммите реализации или снимке версий;
- кем или какой системой;
- какая команда, задача или проверка выполнялась, если это известно;
- какой результат получен;
- где находится внешняя ссылка, если она есть.

Текст «тесты прошли» без идентичности проверенного объекта и источника не считается достаточным подтверждением.

Ядро не обязано проверять доступность внешнего URL в v1 и не выдаёт наличие ссылки за подтверждение её содержимого.

#### Отпечаток

Отпечаток — детерминированный хеш нормализованных данных, влияющих на идентичность.

В v1 различаются как минимум следующие отпечатки и хеши:

- отпечаток описания репозитория;
- правила целостности `cycle_id` и Cycle Record;
- хеш пакета передачи контекста;
- отпечаток договора проверки;
- идентификатор снимка версий.

Алгоритмы приведения к каноническому виду и хеширования выбираются в плане реализации. Они должны быть версионированы и одинаково пониматься в выводе для человека и JSON.

Отпечаток договора проверки обязательно включает:

- версию контракта и формата отпечатка;
- тип передачи проверки и идентичность точки входа;
- хеш содержимого самой точки входа, если она ссылается на файл;
- нормализованную конфигурацию проверки;
- хеши содержимого всех объявленных входов контракта;
- определения проектных контрольных условий, которые описание включает в контракт.

Точка входа всегда входит в отпечаток независимо от того, повторил ли автор её в `contract_inputs`.

#### Контрольное условие

Контрольное условие определяет допустимость перехода внутри жизненного цикла, которым владеет ядро.

Ядро может запретить считать задание завершённым или снимок проверенным оркестратором, но не может запрещать архивирование OpenSpec или внешний процесс выпуска.

## 6. Конфигурация, долговечные метаданные и локальное состояние

### 6.1. Четыре класса проектных данных

| Данные | Владелец | Хранение в Git | Назначение |
|---|---|---|---|
| `openspec/config.yaml` | Проект OpenSpec | отслеживается | Схема и конфигурация OpenSpec |
| `openspec-orch.yaml` | Пользователь | отслеживается | Желаемая конфигурация оркестратора |
| `.openspec-orch/changes/*` | Контракт Core | отслеживается | Cycle Records; текущий Cycle задаёт только корректная запись в состоянии `active` |
| `.openspec-orch/state.json` | Core | игнорируется, хранится локально | Подтверждения, снимки версий, локальные пути и наблюдаемое состояние |

Материалы Template и описания совместимости принадлежат проекту, отслеживаются в Git и не входят в состояние Core.

Это разделение входит в зафиксированные границы продукта. План реализации может уточнить имена файлов, каталоги и миграцию, но не может сделать Cycle доступным только на одной машине либо начать сохранять Receipts в Git в v1.

### 6.2. Целевой минимальный `openspec-orch.yaml`

В описании передачи есть два разных поля:

- `entrypoint` — одна главная инструкция или точка входа, которую Core должен показать исполнителю. Её содержимое всегда автоматически входит в отпечаток договора, поэтому повторять тот же путь в `contract_inputs` не нужно;
- `contract_inputs` — только дополнительные файлы, которые меняют смысл главной инструкции. Например, команда реализации находится в `project-implement.md`, а общие обязательные правила агента — в `QWEN.md`. Если главная инструкция самодостаточна, `contract_inputs` можно не задавать.

Хранить текст инструкции прямо внутри `openspec-orch.yaml` не следует: крупные проектные команды и навыки уже живут в принадлежащих Template файлах, могут переиспользоваться агентом напрямую и проверяются обычным Git diff. Конфигурация хранит стабильную ссылку на такую инструкцию и дополнительные входы её договора.

```yaml
version: 1
strict: true

context: |
  Общий контекст продукта и команды для агента.

agent:
  id: qwen
  openspec_adapter: qwen
  handoffs:
    plan:
      kind: markdown-command
      entrypoint: .qwen/commands/project-plan.md
    implement:
      kind: markdown-command
      entrypoint: .qwen/commands/project-implement.md
      contract_inputs:
        - QWEN.md
    verify:
      kind: markdown-command
      entrypoint: .qwen/commands/project-verify.md
      contract_inputs:
        - QWEN.md

repositories:
  - id: specs
    roles: [store]
    remote: ssh://git.example.org/product/specs.git
    default_branch: main

  - id: frontend
    roles: [code]
    remote: ssh://git.example.org/product/frontend.git
    default_branch: main

extensions: {}
```

`extensions` — изолированное место для необязательных метаданных Template или будущего расширения, смысл которых Core не обязан понимать. Практическая цель — позволить проекту добавить, например, собственную группу сервисов или настройку плагина без новых полей верхнего уровня и без отключения строгой проверки всей конфигурации. Если дополнительных метаданных нет, раздел остаётся пустым. Секреты и локальные абсолютные пути запрещены и внутри `extensions`.

Это продуктовая форма, а не окончательная схема JSON/YAML. План реализации может выбрать точные имена свойств, но обязан сохранить:

- строгий версионированный контракт;
- один действующий профиль агента;
- явно заданное описание передачи контекста;
- объявленные входы контракта;
- роли репозитория как множество значений;
- один Store;
- отсутствие локальных путей и секретов;
- отдельное пространство имён `extensions` для непрозрачных проектных метаданных.

### 6.3. Правила конфигурации

`openspec-orch.yaml`:

- принадлежит пользователю;
- проверяется через Git;
- перечитывается при каждой операции;
- имеет обязательную поддерживаемую версию;
- в строгом режиме отклоняет неизвестные поля вне `extensions`;
- не содержит секретов;
- не содержит локальных абсолютных путей;
- не хранит подтверждения, снимки версий или рабочее состояние отдельных Change;
- может быть создан командами `init` или `adopt`, но затем редактируется обычным процессом Git;
- не переписывается `connect`;
- его версия на `planning_revision` входит в принятый контекст планирования.

### 6.4. Правила описания передачи контекста

Поддерживаемые логические типы v1 должны включать как минимум три базовых варианта:

| Тип | Когда нужен | Что получает пользователь или агент |
|---|---|---|
| `markdown-command` | У проекта уже есть команда агента в Markdown, например команда Qwen или совместимый файл другого поставщика | Путь к файлу команды и Handoff Envelope для текущего вызова |
| `skill` | Процесс команды оформлен как переиспользуемый навык агента, а не как команда конкретного проекта | Идентификатор или безопасную ссылку на навык и тот же Handoff Envelope |
| `manual` | Проект подключается без агентской команды или нужный шаг выполняет человек | Читаемую инструкцию и структурированный контекст без попытки запуска агента |

Все три нужны не как отдельные среды выполнения, а как три способа честно описать уже существующий процесс команды. `markdown-command` сохраняет сценарий с командами, `skill` позволяет Template использовать навыки, а `manual` не блокирует `adopt` для проекта без агентской интеграции. Core во всех трёх случаях только проверяет описание и возвращает следующую точку входа.

Тип описывает способ представления и обнаружения точки входа, но не разрешает её исполнение.

Настроенная точка входа `entrypoint` и объявленные входы контракта `contract_inputs`:

- задаются относительно корня проекта;
- проходят проверку безопасности пути;
- не могут выходить за границы Store или проекта через `..` либо символическую ссылку;
- читаются только для проверки, формирования вывода и расчёта отпечатка;
- не исполняются ядром;
- могут отсутствовать только в режиме `manual`, если Handoff Mapping содержит достаточную ссылку на инструкцию для человека.

`contract_inputs` определяет дополнительные принадлежащие проекту файлы, изменение которых меняет смысловой контракт операции. Сама настроенная точка входа всегда входит в соответствующий отпечаток контракта независимо от этого списка.

Для проверки изменение любого объявленного входа создаёт новый отпечаток договора проверки и делает прежний Verification Receipt неактуальным.

Для реализации изменение контракта передачи не делает уже записанный Result Receipt ложным: Receipt остаётся подтверждением для своего точного коммита и хеша Handoff Envelope. Новые вызовы используют новый Handoff Envelope.

### 6.5. Объединение пользовательского контекста и вычисленных фактов

Core формирует Handoff Envelope из:

1. принадлежащего пользователю `context`;
2. фактов, вычисленных ядром во время выполнения;
3. метаданных настроенной передачи контекста.

Вычисленные факты имеют приоритет. Пользовательский контекст не может переопределить:

- Change ID;
- `cycle_id`;
- идентичность Store и репозитория;
- вычисляемую идентичность Assignment;
- версии;
- идентификатор Snapshot;
- настроенную точку входа;
- разрешённые корневые каталоги;
- описание границ безопасности;
- требуемую версию Receipt.

Изменение общего `context` само по себе не делает Cycle, Result Receipt или Verification Receipt недействительными. Если текст должен входить в договор проверки, проект обязан включить соответствующую проекцию файла или конфигурации в объявленные входы контракта. Точный способ построения проекции определяет план реализации.

### 6.6. Cycle Records

Cycle Records:

- версионированы;
- отслеживаются в Git;
- находятся в Store вне графа артефактов, заданного схемой;
- записываются только поддерживаемым процессом `assign`;
- не содержат секретов и локальных путей;
- валидируются при каждом чтении;
- получают новый `cycle_id` при изменении полей идентичности;
- позволяют восстановить Cycle и вычислить Assignment на другой машине при наличии истории Git.

Жизненный цикл записи:

```text
pending   = `assign` подготовил корректный файл в рабочем дереве
committed_pending = файл входит в коммит, но точное содержимое по нормативному пути ещё не находится в точном дереве основной ветки
active    = корректная запись по нормативному пути находится в точном дереве основной ветки Store,
            а её planning_revision достижима из этой ссылки
```

Core использует локально доступную ссылку на настроенную основную ветку и всегда показывает её точный коммит в машинном и понятном человеку выводе. Без `fetch` или других сетевых данных она не выдаётся за подтверждённое состояние удалённого репозитория. Cycle Record, закоммиченный только в рабочей ветке, остаётся `committed_pending`, пока точное содержимое нормативного пути в дереве основной ветки не совпадёт с ним. Правило не требует коммита с одним родителем, коммита только с одним изменённым файлом или определённой стратегии слияния.

Если Cycle Record существует в рабочем дереве, но ещё не зафиксирован в коммите, `status` показывает ожидающую активацию, а `implement` и `verify` останавливаются с безопасным отказом.

Если активный Cycle Record некорректен, его `planning_revision` недоступна или отпечатки репозиториев не совпадают с принятой идентичностью, Core возвращает `condition: inconsistent` и точный `reason_code`.

### 6.7. Наблюдаемое локальное состояние

Для v1 используется один файл под управлением Core:

```text
.openspec-orch/state.json
```

Он:

- версионирован;
- хранится локально на конкретной машине;
- исключён из Git;
- записывается атомарно;
- валидируется при каждом чтении;
- не служит источником истины для Cycle;
- может быть полностью удалён без повреждения репозиториев и Cycle Records.

Минимальное содержимое:

- идентичности локального рабочего пространства и подключения;
- локальные пути репозиториев;
- кешированные производные представления Assignment;
- Result Receipts;
- ожидающие и завершённые снимки версий;
- Verification Receipts;
- результаты контрольных условий;
- хеши Envelope;
- диагностические отметки времени.

После потери состояния Core восстанавливает из Git:

- Store;
- реестр репозиториев;
- активные и исторические Cycle Records;
- текущий Cycle;
- вычисляемые Assignment.

Core не восстанавливает как доказанные:

- проектные проверки;
- Result Receipts;
- Verification Receipts;
- ожидающее рабочее пространство проверки.

Они переходят в состояние `missing`, а не «предположительно пройдены».

### 6.8. Точные рабочие деревья и их развёртывание

Core может использовать рабочие деревья Git или эквивалентный безопасный механизм для:

- контекста Store только для чтения на `planning_revision` текущего Cycle;
- проверки точного коммита реализации;
- рабочего пространства сводной проверки.

План реализации определяет расположение в файловой системе, повторное использование, очистку и блокировки.

Неизменяемые требования продукта:

- текущая изменяемая рабочая копия не подменяет точное рабочее дерево;
- идентичность рабочего дерева проверяется до передачи контекста;
- Core не изменяет точные исходные рабочие деревья проверки;
- отсутствующий коммит считается ошибкой;
- рабочая копия с незакоммиченными изменениями не включается в Snapshot.

### 6.9. Изменение схемы и шаблона

Схема OpenSpec и принадлежащие проекту материалы Template меняются обычным процессом Git/PR без повторного `init` или `adopt`.

Изменение текущих файлов Store не меняет активный Cycle автоматически.

Для нового состояния планирования пользователь:

1. изменяет артефакты OpenSpec, схему или процесс Template;
2. проверяет и коммитит изменения;
3. явно повторяет `assign`;
4. проводит новый Cycle Record через обычный Git/PR-процесс до состояния `active`.

Изменение только передачи контекста реализации не требует нового Cycle.

Изменение передачи контекста проверки или объявленных входов договора проверки не требует нового Cycle, но прежний Verification Receipt не подтверждает новый отпечаток контракта.

Несовместимая миграция активного OpenSpec Change остаётся решением владельца процесса OpenSpec. Core только показывает, что текущий Cycle относится к прежней `planning_revision`.

## 7. Публичный API и управляющая семантика

### 7.1. Публичные операции

Канонические логические операции v1:

```text
Уровень репозиториев:
init(path, store identity, agent, template, repositories?)
adopt(path, store identity?, agent?, compatibility mapping?, repositories?)
connect(path?)
repository status(repository filter?)

Уровень общего изменения:
plan(change-id)
assign(change-id, repository IDs, expected-cycle?, explicit refresh/replace intent?)
status(change-id, repository filter?)
verify(change-id)
record verification(change-id, verification receipt)

Уровень изменения конкретного репозитория:
implement(change-id, optional repository filter/assertions)
record assignment(change-id, result receipt)
```

Идентичности публичных операций и их семантика входят в зафиксированные границы.

План реализации фиксирует:

- точную грамматику команд и подкоманд;
- позиционные аргументы и флаги;
- точные названия режима обновления или замены;
- точный формат Cycle Record, алгоритм его целостности и определение активации;
- передачу Receipt через стандартный ввод, файл или JSON;
- коды завершения;
- схему JSON.

План реализации не может объединить `assign` с `plan`, `implement` с `record`, `verify` с внешним выполнением или `repository status` со `status` уровня Change.

### 7.2. Почему операции разделены

| Операция | Единственная ответственность |
|---|---|
| `plan` | Подготовить не зависящую от схемы передачу контекста планирования; не принимать состав работ |
| `assign` | Подготовить Cycle Record; Core не проводит его через Git, а Cycle становится текущим только после обычного процесса Git/PR, когда корректная запись находится по нормативному пути в точном состоянии настроенной основной ветки |
| `implement` | Подготовить контекст Assignment и передачу в реализацию; не утверждать завершение |
| `record assignment` | Зафиксировать внешний результат одного Assignment на точном коммите |
| `status` | Показать сводное состояние без изменения данных; не принимать решения и не исправлять состояние |
| `verify` | Построить точный Snapshot и передать контекст проверки; не выдумывать результат |
| `record verification` | Зафиксировать внешний результат для точного Snapshot |

Это разделение исключает скрытые побочные изменения и позволяет внешнему процессу завершаться отдельно от вызова Core.

### 7.3. Явный Change ID

Каждая операция уровня Change, Assignment и Receipt получает явный `change-id`.

Core не использует:

- скрытый активный Change;
- «последний открытый Change»;
- историю предыдущих вызовов командной строки;
- имя ветки как единственный источник идентичности.

Текущий репозиторий можно определить по рабочему каталогу, но при неоднозначности нужен явный фильтр репозитория.

### 7.4. Проверочные ожидания не выбирают идентичность

`expected-cycle` и `expected-snapshot` задают проверочные ожидания для автоматизации. Отдельные ожидания для версии планирования и Assignment не нужны: первая входит в Cycle, а второй однозначно вычисляется из Cycle и репозитория.

Они защищают от ситуации, когда между чтением состояния и следующей командой другой процесс успел изменить текущий цикл или результат. Например:

1. Скрипт вызывает `status(change-id)` и получает ожидаемый Snapshot `S1`.
2. До следующего шага разработчик записывает новый Result Receipt, поэтому текущий набор версий меняется и Core строит Snapshot `S2`.
3. Скрипт вызывает следующую операцию с `expected-snapshot=S1`.
4. Core останавливает операцию с ошибкой вместо того, чтобы незаметно применить её к `S2`.

Проверочное ожидание — это предохранитель от изменившегося состояния, а не способ выбрать старую версию. Несовпадение всегда считается ошибкой. Пользователь не может передать `expected-cycle` или `expected-snapshot`, чтобы обойти текущий Cycle и продолжить работу с произвольной исторической версией.

### 7.5. Предупреждение, подтверждение и ошибка

`warning` означает, что операция технически может продолжиться, но существует явно описанный риск.

- по умолчанию интерактивный режим отменяет операцию;
- продолжение требует явного подтверждения;
- первый неинтерактивный вызов возвращает `needs_confirmation` без побочных изменений;
- повторный вызов подтверждает конкретный код предупреждения и неизменяемый отпечаток предварительно показанных изменений.

`error` означает, что Core не может сформировать корректную операцию.

- подтверждение не обходит ошибку;
- неоднозначная идентичность, некорректный контракт, недоступный коммит, изменённый целевой Cycle Record, небезопасный путь и неподдерживаемая возможность OpenSpec считаются ошибками;
- безопасный отказ не оставляет операцию в состоянии, которое Core выдаёт за успешное.

### 7.6. Предварительный показ изменений

Любая операция Core, изменяющая отслеживаемые в Git проектные файлы, обязана до первой записи показать или вернуть структурированный предварительный просмотр:

- целевые файлы;
- создаваемые или изменяемые пути;
- краткое описание разницы в полях идентичности;
- коды предупреждений;
- ожидаемый Git effect;
- явный факт, что Core не создаст локальный коммит;
- явный факт, что Core не изменит индекс Git, не выполнит `push`, не переключит ветку, не выполнит `merge` или `rebase` и не создаст PR.

К таким операциям относятся `init`, `adopt` и путь подготовки принятия через `assign`.

### 7.7. Вывод для человека и JSON

Вывод для человека обязан:

- показывать идентичности и точные версии;
- объяснять причины состояния;
- отделять долговечные факты от локальных подтверждающих данных;
- показывать источник подтверждающих данных;
- предлагать следующее допустимое действие;
- не использовать цвет как единственный носитель смысла.

Вывод JSON обязан:

- иметь версионированную оболочку;
- содержать те же идентичности и семантику жизненного цикла;
- различать успех, `warning`/`needs_confirmation` и `error`;
- включать стабильные машиночитаемые коды причин;
- быть достаточным для команды агента без разбора текста для человека;
- не скрывать источник или уровень надёжности Result Receipt и Verification Receipt.

## 8. Схема OpenSpec, граница публичных возможностей и контрольные условия

### 8.1. Схема остаётся произвольной

Ядро не должно содержать условия вида:

```text
if schema == "spec-driven"
if artifact == "proposal"
if artifact == "tasks"
if path == "openspec/changes/<id>/design.md"
```

Для Core идентификаторы схемы и артефактов, а также пути артефактов остаются непрозрачными значениями, полученными из публичного структурированного ответа OpenSpec.

Допустимы схемы:

- с предложением, проектным решением и задачами;
- без отдельных задач;
- с другими именами артефактов;
- с другим графом артефактов;
- с дополнительными контрольными условиями, заданными схемой;
- с процессом для всего Change без адресуемых рабочих пакетов.

Изменение способа чтения или создания артефактов агентом требует изменения Template или описания совместимости, а не отдельной ветки логики Core по имени схемы.

### 8.2. Требуемые публичные возможности OpenSpec

Концепция требует, чтобы поддерживаемая версия OpenSpec позволяла через публичный контракт:

- определить точный корень OpenSpec;
- подтвердить идентичность Store и Change;
- выполнить машиночитаемую проверку состояния;
- получить не зависящий от схемы контекст или ссылки, достаточные для Handoff Envelope;
- работать из точного рабочего дерева Store на `planning_revision` текущего Cycle;
- зарегистрировать или определить идентичность Store без чтения закрытой внутренней структуры файлов.

План реализации обязан проверить эти возможности на реально поддерживаемых версиях OpenSpec и зафиксировать матрицу совместимости.

Если требуемая возможность отсутствует, допустимы только два решения:

1. Ограничить поддерживаемые версии OpenSpec публично документированным диапазоном.
2. Согласовать отдельное изменение продуктовой концепции.

Недопустимо без явного решения читать закрытые файлы или копировать внутреннюю логику OpenSpec в Core.

### 8.3. Что проверяет ядро

Core проверяет только универсальные технические факты:

- ответ относится к ожидаемым Store и Change;
- корень и пути безопасны;
- идентичности однозначны;
- Cycle Record находится в состоянии `active` и корректен;
- `planning_revision` и коммиты реализации существуют;
- отпечатки репозиториев согласованы;
- Result Receipt относится к ожидаемой паре `cycle_id + repository_id`;
- Snapshot состоит из точных коммитов;
- Verification Receipt относится к точным Snapshot и отпечатку контракта;
- требуемый Handoff Mapping объявлен;
- версии конфигурации, состояния и контрактов поддерживаются.

### 8.4. Контрольные условия разных владельцев

| Контрольное условие | Пример | Владелец исполнения |
|---|---|---|
| Условие артефактов OpenSpec | Схема разрешает следующий артефакт | OpenSpec |
| Условие принятия Core | Cycle Record находится в состоянии `active`, а Cycle однозначен и целостен | Core |
| Условие Assignment | Receipt со статусом `completed` относится к точному коммиту Assignment | Core |
| Условие Snapshot | Все текущие задания имеют корректные Result Receipt со статусом `completed` | Core |
| Проектное условие | Интеграционные тесты прошли | Template, агент, человек или CI |
| Условие управления | PR одобрен | Человек или внешняя система |

Схема может требовать артефакт проверки или одобрение, но сама по себе не доказывает выполнение внешней команды.

Core не блокирует архивирование OpenSpec. Если архивирование выполнено вне процесса оркестрации, Core показывает последнее известное состояние координации, но не изменяет жизненный цикл OpenSpec.

### 8.5. Межрепозиторные зависимости

Core v1 не моделирует граф зависимостей и не вычисляет порядок заданий.

Универсальное условие завершения формулируется только так:

> Для каждого репозитория текущего Cycle существует текущий корректный Result Receipt со статусом `completed`.

Требования к зависимостям, заглушки, порядок выполнения и контрактные тесты остаются частью семантики планирования и проверки Template. Если повторяющаяся проблема потребует машиночитаемый граф зависимостей, его следует рассматривать как отдельное расширение после наблюдаемого триггера.

## 9. Жизненный цикл и признание данных неактуальными

### 9.1. Главный принцип

Подтверждающие данные не переносятся на новую идентичность автоматически.

При этом точные подтверждающие данные не становятся ложными только потому, что изменяемая рабочая копия или `HEAD` Store продвинулись. Они остаются связаны со своим `cycle_id`, коммитом реализации или `snapshot_id`. Историческое состояние обозначается `current: false`; оно не считается ошибкой само по себе.

### 9.2. Текущий принятый цикл

Для одного `change-id` текущий Cycle определяется активным Cycle Record и его `cycle_id`. Запись, существующая только в рабочем дереве или рабочей ветке, ещё не переключает текущий Cycle.

Новый `cycle_id`:

- фиксирует новые или повторно принятые `planning_revision` и состав репозиториев;
- создаёт новый вычисляемый набор Assignment;
- переводит предыдущий цикл в историю;
- не копирует подтверждения;
- делает предыдущий Snapshot нетекущим;
- требует новой сводной проверки.

Core может хранить ссылки на предыдущие локальные подтверждающие данные для диагностики, но текущий `status` не смешивает циклы.

### 9.3. Матрица признания данных неактуальными

| Событие | Cycle | Result Receipts | Snapshot | Verification Receipt |
|---|---|---|---|---|
| `HEAD` Store продвинулся, повторный `assign` не выполнен | Без изменений; показать информационное сообщение | Остаются корректными для своих коммитов | Остаётся корректным для своего Cycle | Остаётся корректным для своих Snapshot и контракта |
| Активирован новый `cycle_id` | Новый текущий Cycle | Предыдущие получают `current: false` | Предыдущий получает `current: false` | Предыдущее получает `current: false` |
| Изменились `planning_revision` или список репозиториев | Требуется новый Cycle | До его активации текущие данные не меняются | Без изменений до активации | Без изменений до активации |
| Изменился отпечаток идентичности репозитория внутри активного Cycle | `condition: inconsistent` до явного решения или нового `assign` | Result Receipt затронутого репозитория нельзя использовать как текущий | Новый Snapshot не строится | Проверка не считается текущей |
| Текущая рабочая копия кода продвинулась после Result Receipt | Cycle не меняется | Result Receipt остаётся корректным для записанного коммита; `status` показывает расхождение | Существующий Snapshot остаётся точным | Существующая проверка остаётся точной для Snapshot |
| Записан корректный Result Receipt, который через `supersedes` заменяет текущий результат той же пары `cycle_id + repository_id` | Без изменений | Новый Result Receipt становится текущим; предыдущий остаётся историческим | Предыдущий Snapshot получает `current: false` | Предыдущее подтверждение проверки получает `current: false` |
| Изменилась передача контекста реализации | Без изменений | Существующие Result Receipts остаются корректными; новый Handoff Envelope меняется | Без изменений, пока коммиты те же | Без изменений |
| Изменилась передача проверки или объявленный вход контракта | Без изменений | Без изменений | Для новой проверки нужен новый отпечаток контракта | Предыдущее подтверждение остаётся исторически точным, но получает `current: false` |
| Изменился общий `context` | Без изменений | Без автоматического признания неактуальными | Без автоматического признания неактуальным | Без автоматического признания неактуальным, если `context` не объявлен входом контракта |
| Потеряно локальное состояние | Восстанавливается из Git | Отсутствуют | Отсутствует | Отсутствует |
| Версия контракта подтверждения не поддерживается | Без изменений | Несогласован или не поддерживается | Не строится | Не строится |
| Коммит недоступен | Идентичность сохраняется, операция завершается ошибкой | Result Receipt нельзя подтвердить | Snapshot нельзя развернуть | Проверка не может считаться текущей |
| Коммит с Cycle Record объединён или перебазирован, а в точном дереве основной ветки по нормативному пути осталась та же корректная запись | Без изменений после повторной проверки | Без изменений | Без изменений | Без изменений |
| `planning_revision` после переписывания истории недоступна или недостижима | `condition: inconsistent`; требуется новый `assign` | Остаются историческими фактами, но не используются как текущие | Нельзя воспроизводимо материализовать | Не считается текущим, пока Snapshot нельзя воспроизвести |
| Cycle Record удалён или поля идентичности изменены без нового `cycle_id` | `condition: inconsistent` | Не используются как текущие | Не строится новый Snapshot | Не считается текущим подтверждением |

Модель обязана сохранять различие:

- подтверждающие данные относятся к историческому, но корректному Cycle (`current: false`);
- подтверждающие данные нарушают согласованность;
- подтверждающие данные физически отсутствуют;
- подтверждающие данные содержат отрицательный результат.

### 9.4. Производное состояние результатов репозиториев

Для каждого репозитория текущего Cycle Core вычисляет состояние по наличию и результату текущего Result Receipt:

```text
нет Receipt
  → подготовлен Handoff Envelope
  → записан Result Receipt: completed | failed | blocked
  → Receipt явно заменён через supersedes
```

Это производное представление, а не отдельно сохраняемый жизненный цикл Assignment. Подготовка Handoff Envelope — наблюдаемое событие, но не самостоятельная доменная фаза.

В Snapshot участвует только текущий Result Receipt со статусом `completed`.

### 9.5. Создание Snapshot и проверка

```text
не все Result Receipts имеют completed
  → все результаты готовы
  → создан Snapshot
  → записан Verification Receipt: pass | fail | error | inconclusive
```

Повторный `verify` с теми же входными данными обязан вернуть ту же детерминированную идентичность Snapshot или эквивалентный идемпотентный результат.

Новый текущий Result Receipt для репозитория или новый отпечаток договора проверки требует нового Snapshot. Старый Snapshot остаётся точным историческим объектом с `current: false`, а не превращается в ошибочный.

### 9.6. Восстановление после частичной записи

План реализации обязан обеспечить восстановимое поведение `init`, `adopt` и пути подготовки принятия через `assign`.

Неизменяемые требования продукта:

- предварительный просмотр рассчитывается до изменения данных;
- успешный результат не возвращается до проверки итоговых условий;
- частично записанный файл не выдаётся за активный Cycle Record;
- действующее принятие определяется точным содержимым нормативного пути в разрешённой ссылке на основную ветку и другими проверяемыми фактами Git, а не промежуточным локальным флагом и не поиском старой версии в истории;
- повторный вызов либо безопасно завершает операцию, либо возвращает отчёт о восстановлении;
- Core не выполняет широкий откат с удалением принадлежащих пользователю файлов;
- Core не добавляет Cycle Record в индекс Git, не создаёт коммит и не отправляет его в удалённый репозиторий.

## 10. Целевые сквозные сценарии

### 10.1. Новый проект

1. Инженер создаёт или выбирает Git-репозиторий для Store.
2. Запускает `openspec-orch init`.
3. Core с безопасным отказом подтверждает отсутствие корректного корня OpenSpec.
4. Пользователь выбирает один начальный Template и задаёт реестр репозиториев.
5. Template создаёт начальные файлы OpenSpec и материалы для агента.
6. Core создаёт `openspec-orch.yaml` и структуру метаданных оркестратора.
7. Core выполняет первое локальное подключение.
8. `repository status` показывает Store и репозитории.
9. Пользователь проверяет и коммитит проектные файлы обычным процессом Git.

### 10.2. Существующий проект OpenSpec

1. Инженер запускает `openspec-orch adopt` в точном корне Store.
2. Core через публичную диагностику OpenSpec подтверждает корректный целевой проект.
3. Core без изменения данных проверяет идентичность Store, конфигурацию и найденные материалы агента.
4. Пользователь явно задаёт или подтверждает описания передачи контекста.
5. Core предварительно показывает будущие записи.
6. Core создаёт только отсутствующие конфигурацию и метаданные оркестратора, а также явно выбранные файлы связки.
7. Существующие схемы, спецификации, изменения, команды, навыки и инструкции остаются неизменными.
8. Core выполняет `connect` и показывает отчёт о возможностях.
9. Проект может быть готов на уровне репозиториев, даже если часть способов передачи контекста отсутствует.

### 10.3. Планирование и принятие изменения

1. Change создаётся и планируется штатным процессом OpenSpec и Template.
2. При необходимости инженер вызывает `plan(change-id)` и получает Handoff Envelope для планирования.
3. Агент или человек завершает артефакты планирования.
4. Состояние планирования коммитится в Store.
5. Инженер вызывает `assign(change-id, repository IDs)`.
6. Core показывает предлагаемый Cycle: `planning_revision`, репозитории, их отпечатки и новый `cycle_id`.
7. Пользователь подтверждает.
8. `assign` атомарно записывает Cycle Record в состоянии `pending`, но не добавляет его в индекс и не создаёт коммит.
9. Core выводит `cycle_id`, вычисляемые Assignment и состояние записи `pending`; вычисляемое состояние Change имеет `phase: planning`, `condition: pending`, `reason_code: WAITING_GIT_ACTIVATION`.
10. Пользователь проверяет Cycle Record и проводит его через обычный процесс Git/PR команды.
11. Когда та же корректная версия Cycle Record оказывается по нормативному пути в точном дереве настроенной основной ветки Store, Core считает её действующей.
12. `planning_revision` и репозитории уже являются полями Cycle; коммит с Cycle Record не создаёт дополнительную идентичность.
13. `status(change-id)` показывает новый Cycle текущим только после перехода Cycle Record в `active`.

### 10.4. Реализация в репозитории с кодом

1. Инженер переходит в репозиторий с кодом.
2. Вызывает `implement(change-id)`.
3. Core определяет репозиторий и Assignment.
4. Core создаёт рабочее дерево Store только для чтения на `planning_revision` текущего Cycle.
5. Core возвращает Handoff Envelope реализации и настроенную точку входа.
6. Агент или человек строит локальный план и изменяет только разрешённый репозиторий.
7. Проектные проверки выполняются вне Core.
8. Изменения коммитятся; рабочее дерево становится чистым.
9. Исполнитель формирует Result Receipt.
10. Вызывается `record assignment(change-id, receipt)`.
11. Core проверяет Receipt и сохраняет его в локальном состоянии.
12. Цикл повторяется для остальных репозиториев.

### 10.5. Сводная проверка

1. `status(change-id)` показывает `phase: verifying`, `condition: pending` и причину, указывающую на необходимость `verify`.
2. Инженер вызывает `verify(change-id)`.
3. Core проверяет текущие Receipts со статусом `completed`.
4. Core строит детерминированный Snapshot.
5. Core создаёт точное рабочее пространство проверки.
6. Core возвращает Handoff Envelope проверки и настроенную точку входа.
7. Агент, человек или CI выполняет проектные проверки вне Core.
8. Исполнитель формирует Verification Receipt с тем же Snapshot ID.
9. Вызывается `record verification(change-id, receipt)`.
10. Core проверяет источник, подтверждающие данные, Snapshot и отпечаток контракта.
11. `status(change-id)` показывает результат и источник.
12. Архивирование OpenSpec остаётся отдельным действием.

### 10.6. Возврат через несколько дней

1. Инженер вызывает `status(change-id)`.
2. Core перечитывает конфигурацию, Cycle Records и локальное состояние.
3. Core заново читает Cycle Record по нормативному пути из точного дерева настроенной основной ветки и восстанавливает Cycle.
4. Core проверяет идентичности репозиториев и коммиты.
5. Core показывает текущие задания, подтверждения, Snapshot и следующее действие.
6. Инженер не вводит `cycle_id` и производные Assignment IDs вручную.

### 10.7. Новая машина или удалённое локальное состояние

1. Инженер клонирует Store и запускает `connect`.
2. Core читает `openspec-orch.yaml` и Cycle Records.
3. Core восстанавливает текущий Cycle и вычисляет Assignment.
4. Локальные Result Receipts и Verification Receipts отсутствуют.
5. `status(change-id)` честно показывает отсутствие подтверждающих данных, а не предполагаемый успех.
6. Инженер повторяет только локальные проверки, которые больше нечем доказать, либо использует будущий механизм переноса вне v1.

### 10.8. Хранилище одновременно содержит код

1. Repository Reference для Store имеет роли `[store, code]`.
2. Cycle явно включает идентификатор этого репозитория.
3. Для него вычисляется обычный Assignment.
4. `planning_revision` Cycle указывает на точный коммит Store с принятым планированием.
5. Коммит реализации может быть более поздним коммитом того же Git-репозитория.
6. Core использует разные точные рабочие деревья для контекста `planning_revision` и версии реализации.
7. Snapshot ссылается на `cycle_id` и отдельный коммит реализации, не смешивая их смысл.

### 10.9. Изменение состава планирования

1. Пользователь изменяет артефакты планирования и/или список репозиториев.
2. Изменения коммитятся в Store.
3. Пользователь вызывает `assign` с явным намерением обновить или заменить принятие.
4. Core показывает новый `cycle_id` и предупреждает, что после его активации предыдущие подтверждающие данные получат `current: false`.
5. `assign` записывает Cycle Record в состоянии `pending` и не изменяет текущий Cycle до активации.
6. Пользователь проводит Cycle Record через обычный процесс Git/PR; после попадания корректной версии в историю настроенной основной ветки она становится действующей.
7. Новый Cycle становится текущим, а Assignment вычисляются из него.
8. Старые Receipts и Verification остаются в истории, но не используются в текущем состоянии.

### 10.10. Распределение процесса между аналитиком, фронтенд-разработчиком, бэкенд-разработчиком и тестировщиком

Этот сценарий показывает, как путь одного продуктового инженера можно организационно разделить между несколькими людьми. В примере есть четыре логические роли, но один человек может совмещать несколько из них. Сценарий не вводит в Core учётные записи, роли или права доступа: названия ролей описывают ответственность людей, а не новые сущности оркестратора.

Фронтенд и бэкенд также не становятся новыми ролями репозитория в Core. Оба репозитория сохраняют универсальную роль `code`, а их назначение выражается через стабильные идентификаторы Repository Reference, содержание Change и правила Template. Поэтому это уточнение не добавляет новый уровень, команды или состояния оркестратора.

| Роль | Зона ответственности | Основные операции | Передаваемый результат |
|---|---|---|---|
| Аналитик | Подготовить и согласовать содержание Change, состав затрагиваемых репозиториев и принятую версию планирования | существующий процесс OpenSpec и Template, при необходимости `plan(change-id)`, затем `assign(change-id, repository IDs)` | зафиксированные в Git Change и активный Cycle Record |
| Фронтенд-разработчик | Реализовать пользовательский интерфейс и клиентскую интеграцию в назначенных репозиториях с ролью `code` | `status(change-id)`, `implement(change-id, repository-id)`, `record assignment(change-id, receipt)` | точные коммиты фронтенд-реализации и Result Receipt для соответствующих Assignment |
| Бэкенд-разработчик | Реализовать серверное поведение, API и интеграции в назначенных репозиториях с ролью `code` | `status(change-id)`, `implement(change-id, repository-id)`, `record assignment(change-id, receipt)` | точные коммиты бэкенд-реализации и Result Receipt для соответствующих Assignment |
| Тестировщик | Проверить единый набор версий, а не произвольные текущие рабочие копии | `status(change-id)`, `verify(change-id)`, проектные проверки, `record verification(change-id, receipt)` | точный Snapshot и связанный с ним Verification Receipt |

Пример последовательности:

1. Аналитик создаёт или уточняет Change штатными средствами OpenSpec и Template.
2. Аналитик фиксирует состояние планирования в Git, вызывает `assign(change-id, repository IDs)`, проверяет предлагаемый Cycle и проводит Cycle Record через обычный процесс Git/PR.
3. После перехода записи в состояние `active` фронтенд- и бэкенд-разработчики выполняют `connect`, если их локальные рабочие пространства ещё не подключены, а затем вызывают `status(change-id)`.
4. Core восстанавливает из Git Cycle Record и вычисляет Assignment. Разработчикам не требуется получать от аналитика `cycle_id` или идентификаторы заданий отдельным сообщением.
5. Каждый разработчик вызывает `implement(change-id, repository-id)` только для назначенных ему репозиториев, коммитит реализацию и записывает Result Receipt для каждого точного коммита. Core различает работу по идентификатору репозитория и Assignment, а не по названию специализации разработчика.
6. Фронтенд- и бэкенд-реализация могут выполняться параллельно либо в определённом порядке. Зависимости, временные заглушки и требуемый порядок задаются планированием и Template; Core v1 не вычисляет их самостоятельно.
7. Когда все задания завершены, тестировщик вызывает `status(change-id)` и получает следующее действие `verify`, а не собирает версии репозиториев вручную.
8. `verify(change-id)` формирует детерминированный Snapshot и точное рабочее пространство проверки из принятых результатов фронтенд- и бэкенд-реализации.
9. Тестировщик выполняет проверки, принадлежащие Template и процессу команды, после чего записывает Verification Receipt для того же `Snapshot ID`.
10. Аналитик, любой из разработчиков или тестировщик может вызвать `status(change-id)` и увидеть общий результат, точные версии и источник проверки. Смена человека не меняет идентичности Change, Cycle, Assignment или Snapshot.

Логические роли можно распределить между двумя, тремя или четырьмя людьми. Например, один разработчик может выполнить оба набора Assignment, аналитик может также выполнять проверку, а один из разработчиков — совмещать реализацию и тестирование. Core не закрепляет допустимые сочетания ролей; это определяет процесс команды и Template.

Граница v1 для такого сценария:

- если роли последовательно выполняются в одном локальном рабочем пространстве оркестратора, описанная последовательность использует уже определённую модель состояния;
- если аналитик, фронтенд-разработчик, бэкенд-разработчик и тестировщик работают на разных машинах, Git уже переносит конфигурацию и Cycle Record;
- Result Receipt, Verification Receipt и подготовленный Snapshot в v1 остаются локальными, поэтому тестировщик на другой машине не получит результаты фронтенд- и бэкенд-разработчиков автоматически;
- без механизма переноса подтверждений полностью автоматический переход от разработчиков к тестировщику на другой машине не является возможностью v1 и не должен быть заявлен как работающий;
- следующим расширением для командного сценария должен стать перенос подтверждений через Git с правилами идентичности, замены и разрешения конфликтов, а не сервер оркестратора;
- Template может уже сейчас описывать ответственность ролей, обязательные согласования и проектные проверки, но Core не интерпретирует эти правила и не вмешивается в схему OpenSpec.

## 11. Границы следующего плана реализации

### 11.1. Продуктовые решения, которые закрыты этим документом

План реализации не должен повторно обсуждать:

1. Первого пользователя: один продуктовый инженер.
2. Локальный характер v1 с опорой на Git.
3. Один авторитетный Store.
4. Заранее известный реестр репозиториев.
5. Три иерархических уровня: репозитории, общее изменение и изменение конкретного репозитория; сводная проверка завершает уровень общего изменения.
6. Явный `change-id`.
7. OpenSpec как владельца Change, схемы и жизненного цикла артефактов.
8. Core как владельца координационных идентичностей и универсальных контрольных условий.
9. Template как владельца проектного процесса.
10. Handoff по запросу без запуска внешнего процесса из Core.
11. Cycle как единственную сквозную координационную идентичность, объединяющую `cycle_id`, `change_id`, `planning_revision` и репозитории; Cycle Record является только её Git-представлением.
12. Assignment как вычисляемую пару `cycle_id + repository_id`, а не отдельный сохраняемый объект или пользовательский вход.
13. `assign` как единственную поддерживаемую операцию Core для подготовки нового Cycle: она пишет Cycle Record в состоянии `pending`, но не изменяет индекс Git, не создаёт и не отправляет коммит, не переключает ветку, не выполняет слияние или перебазирование и не создаёт PR.
14. Только точные чистые коммиты как версии реализации v1.
15. Раздельные `implement` и `record assignment`.
16. Раздельные `verify` и `record verification`.
17. Версионированный Verification Receipt с `pass|fail|error|inconclusive`.
18. Развёртывание точного Snapshot.
19. Роли репозитория `store`, `code`, `store+code`.
20. Локальные Receipts и Verification Receipts в v1.
21. Подключение существующего проекта с сохранением его процесса и явным Handoff Mapping.
22. Отсутствие `repository sync` и `disconnect` в v1.
23. Отсутствие графа зависимостей, среды выполнения расширений, нескольких Store и общего состояния команды.
24. Проверка функциональной готовности и отдельная проверка готовности к распространению.
25. Явная цепочка замены Result Receipt по идентификаторам, а не выбор результата по отметке времени.
26. Детерминированный Snapshot ID только из версии контракта, `cycle_id`, коммитов реализации и отпечатка проверки, без диагностических метаданных.
27. Отпечаток договора проверки с обязательными идентичностью и содержимым точки входа, а также объявленными входами контракта.
28. Выбор текущего Cycle Record только по содержимому нормативного пути в точном дереве настроенной основной ветки Store, без поиска альтернатив в истории и без требований к структуре коммитов или стратегии слияния.

### 11.2. Что обязан определить план реализации

План реализации обязан определить технические контракты без изменения продуктовой модели:

- точную грамматику командной строки и псевдонимы команд;
- точную схему конфигурации JSON/YAML;
- миграцию старой конфигурации;
- точную схему Cycle Record;
- безопасное кодирование `change-id` в имени файла;
- алгоритм определения состояний Cycle Record: `pending`, `committed_pending`, `active`;
- алгоритм чтения и валидации единственного текущего Cycle Record по нормативному пути из точного дерева настроенной основной ветки Store;
- проверку достижимости `planning_revision` из той же ссылки;
- атомарную запись ожидающего Cycle Record и восстановление без управления структурой коммитов Git;
- алгоритм создания и проверки `cycle_id`, включая отказ при изменении полей идентичности без нового Cycle;
- необязательный алгоритм производного Assignment ID для JSON;
- схемы Handoff Envelope;
- передачу Envelope и Receipts через стандартный вывод, стандартный ввод или файл;
- схемы Result Receipt и Verification Receipt;
- схему Snapshot и его детерминированный идентификатор;
- приведение отпечатков к каноническому виду и версии хеширования;
- точную схему вычисляемых `phase`, `condition`, `reason_code` и признака `current`;
- коды предупреждений, ошибок и причин;
- формат токена подтверждения и отпечаток предварительного просмотра;
- коды завершения;
- схему и миграцию локального состояния;
- атомарную запись и файловые блокировки;
- расположение рабочих пространств и рабочих деревьев;
- повторное использование и очистку рабочих деревьев;
- приведение URL репозитория к каноническому виду;
- правила безопасности символических ссылок и путей;
- точную схему Mapping для `adopt`;
- представление поддерживаемых типов Handoff;
- структуру вывода для человека;
- структуру пакета и автоматизацию выпуска;
- матрицу характеризационных, контрактных, интеграционных и сквозных тестов;
- миграцию или удаление текущих прототипных команд.

### 11.3. Что можно решить только после проверки кода и зависимостей

План реализации обязан начаться с аудита кода и зависимостей и не принимать предыдущую опись реализации на веру.

Только по коду и установленным зависимостям можно подтвердить:

- какие обработчики командной строки реально существуют;
- какие текущие команды и контракты можно перенести;
- текущую безопасность путей и операций Git;
- наличие средств работы с точными рабочими деревьями;
- текущее поведение при создании файлов из Template;
- поведение анализатора `openspec-orch.yaml`;
- видимость пакета и готовность к публикации;
- наличие и семантику публичных структурированных команд OpenSpec;
- поддержку точного определения корня;
- возможность работать с OpenSpec из отсоединённого точного рабочего дерева;
- способ регистрации Store;
- стабильность JSON-контрактов OpenSpec;
- поддерживаемые версии Node.js и OpenSpec;
- возможность переиспользовать существующий код Receipt и контекста;
- риски обратной совместимости.

Если аудит кода показывает, что публичной возможности OpenSpec из раздела 8.2 нет, план реализации не должен подменять её закрытым API. Нужно зафиксировать ограничение совместимости или отдельным решением изменить концепцию.

### 11.4. Ненормативная опись текущей реализации

Описание текущей реализации не входит в зафиксированные продуктовые границы. Оно должно существовать как отдельный датированный документ, привязанный к версии репозитория.

Причина проста: продуктовая концепция должна оставаться стабильной, а опись кода меняется при каждом коммите. Смешивание этих двух типов данных создаёт ложные противоречия и быстро устаревающий документ.

## 12. Рекомендуемая структура плана реализации

Следующий документ должен быть планом реализации, разбитым на вертикально проверяемые этапы.

### Этап 0. Аудит кода, контракты и миграция

1. Зафиксировать проверяемую версию репозитория.
2. Построить опись текущих команд, конфигурации, состояния, Template и средств Git.
3. Проверить публичные возможности OpenSpec и матрицу версий.
4. Определить миграцию или удаление прототипных команд.
5. Определить версионированные схемы конфигурации, Cycle Record, локального состояния, Handoff Envelope и подтверждений.
6. Определить идентификаторы, правила приведения к каноническому виду, отпечатки и коды причин.
7. Определить контракт записи ожидающего Cycle Record, обнаружения активации и восстановления.
8. Написать контрактные тесты до функциональной реализации.

Критерий выхода: разработчик может реализовать контракты, не выбирая заново продуктовые идентичности или владельцев.

### Этап 1. Уровень репозиториев

1. Характеризационные тесты существующих путей `init` и `connect`.
2. Безопасное разделение `init` и `adopt` с остановкой при неоднозначности.
3. Строгая версионированная конфигурация.
4. Роли репозиториев и отпечатки идентичности.
5. Подключение с сохранением существующего процесса и явным Mapping.
6. Первое локальное подключение после `init` или `adopt`.
7. `repository status` только для чтения.
8. Основа локального состояния.
9. Тесты восстановления после частичной записи.

Критерий выхода: новый и существующий проекты безопасно достигают готовности уровня репозиториев без автоматической замены процесса.

### Этап 2. Cycle Record и уровень изменения

1. Схема Cycle Record и стратегия путей.
2. Предварительный просмотр и подтверждение `assign`.
3. Процесс ожидающего Cycle Record без изменения Git со стороны Core.
4. Активация через историю настроенной основной ветки и проверка достижимости `planning_revision`.
5. Создание и проверка единого `cycle_id` для `change_id`, `planning_revision` и репозиториев.
6. Вычисление Assignment из `cycle_id + repository_id`.
7. Сводный `status(change-id)` с `phase`, `condition`, `reason_code`, `current` и отдельным состоянием Cycle Record.
8. Повторный `assign` и семантика текущего и исторических циклов.
9. Тесты обычного коммита, слияния, объединения и перебазирования Cycle Record без требований к структуре истории.
10. Отрицательные тесты согласованности, включая недоступную `planning_revision`.

Критерий выхода: Cycle восстанавливается из Git по одному `change-id`, а Assignment вычисляются без дополнительных пользовательских ID.

### Этап 3. Передача контекста и результат задания

1. Handoff Envelope планирования и необязательный `plan`.
2. Handoff Envelope реализации.
3. Точное рабочее дерево Store на `planning_revision` Cycle.
4. Однозначное определение одного репозитория.
5. `record assignment` и Result Receipt.
6. Явная замена Receipt и защита от результатов, пришедших не по порядку.
7. Обязательный чистый коммит.
8. Локальное восстановление и признание данных неактуальными.
9. Тест структуры `store+code`.

Критерий выхода: для каждого репозитория пользователь вызывает `implement(change-id)` и записывает корректный результат без ручного ввода `cycle_id` или Assignment ID.

### Этап 4. Сводная проверка

1. Схема Snapshot и детерминированный идентификатор.
2. Точное развёртывание нескольких репозиториев.
3. Отпечаток договора проверки с обязательным хешем настроенной точки входа, нормализованной конфигурацией, объявленными входами и определениями контрольных условий.
4. Универсальные контрольные условия.
5. `verify` Handoff Envelope.
6. `record verification` и модель четырёх результатов.
7. Интеграция со `status`.
8. Тесты `current: false`, `SNAPSHOT_OUTDATED` и других причин при новом Receipt и изменении контракта.

Критерий выхода: один Change получает честный сводный результат на точном воспроизводимом Snapshot.

### Этап 5. Функциональный пилот

Провести реальный Change через два или три репозитория:

```text
connect → [plan] → assign → Cycle Record pending
→ обычный процесс Git/PR → active → status
→ implement → record assignment
→ implement → record assignment
→ verify → record verification → status
```

Пилот обязан проверить успешные сценарии и сценарии с ошибками:

- пользовательскую схему;
- перезапуск между операциями;
- Receipt с неверными `cycle_id`, репозиторием или коммитом;
- попытку записать Cycle Record при незакоммиченных изменениях;
- принятие в состояниях `pending` и `committed_pending`;
- обычное слияние, объединение и перебазирование Cycle Record без признания данных неактуальными, если корректное содержимое сохраняется;
- недоступная или недостижимая `planning_revision`;
- повторный `assign`;
- Result Receipt, пришедший не по порядку, и его явную замену;
- изменённый договор проверки;
- потерю локального состояния;
- подключение существующего процесса;
- `store+code` либо отдельное явно задокументированное решение о структуре пилота.

### Этап 6. Проверка готовности к распространению

До распространения в разные команды необходимо:

- определить имя пакета, его видимость и процесс выпуска;
- проверить установку в чистом окружении;
- проверить содержимое пакета;
- зафиксировать поддерживаемые версии Node.js и OpenSpec;
- описать миграции конфигурации, состояния и Cycle Record;
- предоставить минимальный начальный Template;
- проверить минимум два разных Template или Mapping совместимости;
- проверить подключение активного Change без замены схемы;
- проверить пользовательскую схему без стандартных задач;
- описать установку, обновление, диагностику и удаление;
- исключить секреты и локальные пути из отслеживаемых артефактов;
- провести внешний пилот силами другого инженера;
- подтвердить продуктовые метрики раздела 1.5.

После проверки готовности к распространению разные команды могут независимо использовать один Core. Перенос общих Receipts между участниками остаётся отдельным будущим этапом.

## 13. Расширение только по наблюдаемому триггеру

| Наблюдаемая повторяющаяся проблема | Допустимое следующее расширение |
|---|---|
| Пользователи регулярно вручную исправляют безопасные расхождения репозитория | `repository sync` с отдельным контрактом безопасности |
| Локальное рабочее пространство требуется явно удалять или отвязывать | `disconnect` |
| Пользователь регулярно не знает участвующие репозитории | Граф или обнаружение репозиториев |
| Нужен машиночитаемый порядок заданий | Модель зависимостей после отдельного продуктового аудита |
| Одного Handoff по запросу недостаточно для нескольких сред выполнения | Контракт доверенного адаптера среды выполнения |
| Команды постоянно объединяют несколько шаблонов | Рецепт или сборщик Template |
| Состояние CI/PR приходится постоянно переносить вручную | Одно расширение только для чтения |
| Receipts необходимо передавать между инженерами | Перенос через Git с моделью идентичности, замены и разрешения конфликтов |
| Один Store перестал описывать границу оркестрации | Модель проекта или нескольких Store |
| Локальные вычисления не справляются с общим состоянием | Оценка необходимости индексатора или центра управления |
| Нужна изоляция внешнего исполнителя на уровне ОС | Явная возможность изолированной среды выполнения |

До появления измеримой повторяющейся проблемы расширение не входит в список работ v1.

Если появится граф репозиториев, его нельзя смешивать с графом артефактов OpenSpec: первый описывает связи между репозиториями, второй — заданные схемой артефакты одного Change.

## 14. Основные риски и защиты

### 14.1. Ядро начинает владеть семантикой планирования OpenSpec

Риск: Core снова начинает ожидать предложение, проектное решение, задачи или конкретные пути.

Защита: артефакты OpenSpec остаются непрозрачными для Core; используется публичная структурированная возможность; контрактные тесты покрывают пользовательскую схему и режим всего Change.

### 14.2. Неоднозначный Cycle

Риск: Core использует текущий `HEAD`, локальный флаг, переписанный коммит или произвольную версию.

Защита: Cycle Record хранит единый `cycle_id`, точную `planning_revision` и репозитории с отпечатками. Запись становится действующей только если она находится по нормативному пути в точном дереве настроенной основной ветки, а `planning_revision` достижима из этой ссылки. Старые версии по тому же пути не могут стать параллельно текущими. Структура коммитов и способ слияния не входят в идентичность Cycle.

### 14.3. Подготовка принятия повреждает хранилище

Риск: `assign` оставляет частично записанный Cycle Record, незаметно меняет текущий Cycle или вмешивается в процесс Git команды.

Защита: чистое исходное состояние, неизменяемый предварительный просмотр, явное подтверждение, узкая атомарная запись и проверка итоговых условий. Результат всегда остаётся `pending`; Core не изменяет индекс Git, не создаёт и не отправляет коммит, не переключает ветку, не выполняет слияние или перебазирование и не создаёт PR.

### 14.4. Cycle Record превращается во второй план

Риск: в Cycle Record начинают добавлять задачи, цели и порядок выполнения.

Защита: минимальная схема; только `cycle_id`, `change_id`, `planning_revision` и репозитории с отпечатками идентичности.

### 14.5. Передачу контекста ошибочно принимают за выполнение

Риск: документация утверждает, что Core «запустил агента» или обеспечил изолированную среду.

Защита: контракт Handoff по запросу; Core только формирует Envelope и Mapping; границы безопасности носят информационный характер без внешней изолированной среды.

### 14.6. Ложные подтверждающие данные

Риск: `pass` от агента или человека показывается как независимое доказательство CI.

Защита: обязательны источник, идентичность объекта и подтверждающие данные; сочетание `phase: completed` и `condition: ok` имеет узкое определение; источник всегда видим.

### 14.7. Незакоммиченная версия попадает в снимок

Риск: SHA из `HEAD` не описывает фактически проверенный код.

Защита: Result Receipt и Snapshot принимают только точные коммиты; результат с незакоммиченными изменениями отклоняется с безопасным отказом.

### 14.8. Результат проверки относится к другому снимку

Риск: проверки выполняются после изменения коммитов или контракта.

Защита: Verification Receipt обязан совпадать по `cycle_id`, `snapshot_id` и отпечатку договора проверки.

### 14.9. Хеш конфигурации делает всё неактуальным без причины

Риск: форматирование или нерелевантное изменение конфигурации делает все подтверждающие данные устаревшими.

Защита: смысловые отпечатки только по проекциям, влияющим на идентичность; явная матрица актуальности; общий `context` не делает подтверждающие данные неактуальными автоматически.

### 14.10. Подключение проекта незаметно заменяет процесс команды

Риск: Core угадывает смысл команды, повторно устанавливает пакет поставщика агента или переписывает схему.

Защита: отдельная команда `adopt`, точный корень, явный Mapping, предварительный просмотр, сохранение существующих файлов и отложенные ошибки отсутствующих возможностей.

### 14.11. Локальное состояние путают с общим состоянием команды

Риск: потеря локального состояния или переход на другую машину воспринимается как потеря принятого состава работ либо продукт ошибочно объявляется многопользовательским.

Защита: Cycle Record отслеживается в Git; Receipts остаются локальными; правила восстановления описаны; общий перенос не входит в v1.

### 14.12. Роль `store+code` смешивает `planning_revision` и коммит реализации

Риск: один SHA используется сразу в двух ролях.

Защита: разные поля и назначения `planning_revision` Cycle и `implementation_revision` Result Receipt, отдельные точные рабочие деревья.

### 14.13. Закрытый API OpenSpec становится скрытой зависимостью

Риск: Core читает внутреннее расположение файлов, потому что публичная возможность неудобна.

Защита: матрица совместимости, безопасный отказ для неподдерживаемой версии, изменение концепции вместо скрытого обхода.

### 14.14. Границы v1 снова разрастаются

Риск: синхронизация, граф, расширения, адаптеры и общее состояние добавляются до доказательства основного цикла.

Защита: функциональные границы раздела 2 и таблица наблюдаемых причин из раздела 13 служат обязательными ограничителями состава работ.

## 15. Источники идей и границы заимствования

Концепция использует общие идеи существующих инструментов, не копируя их целиком:

- OpenSpec — Change, схема, жизненный цикл артефактов и локальная настройка проекта;
- коммиты и рабочие деревья Git — точные версии планирования и реализации, воспроизводимое развёртывание Snapshot;
- матрицы CI — объединение нескольких версий компонентов;
- воспроизводимые системы сборки — идентичность входов без превращения Core в систему сборки;
- описания рабочих пространств — восстановление локального окружения;
- архитектуры расширений — будущая явная граница возможностей вместо скрытых обработчиков;
- команды и навыки агента — заменяемая методология поверх стабильного контракта Core.

Главный архитектурный принцип: OpenSpec владеет содержанием Change, Template — способом работы команды, а Core — только универсальной технической координацией репозиториев и подтверждающих данных.

## 16. Окончательно зафиксированные границы v1

OpenSpec Orchestrator v1 концептуально определён следующим образом:

1. Первый пользователь — один продуктовый инженер.
2. Основной сценарий — один Change через два или три заранее известных репозитория.
3. Один авторитетный Store служит корнем оркестрации.
4. Один репозиторий может иметь роли `store`, `code` или `store+code`.
5. OpenSpec владеет Change, схемой, артефактами и архивированием.
6. Core не интерпретирует критерии приёмки и не создаёт содержательный план.
7. Template или описание совместимости владеет проектным процессом и точками входа.
8. Core не запускает код Template, среду агента или проектные команды.
9. Передача контекста состоит из версионированного Handoff Envelope и декларативного Handoff Mapping, которые запрашивает проектная сторона.
10. Разрешённые корневые каталоги не выдаются за изолированную среду на уровне операционной системы.
11. Существуют три иерархических уровня: репозитории, общее изменение и изменение конкретного репозитория. Сводная проверка относится к слою общего изменения.
12. Операции уровня репозиториев в v1: `init`, `adopt`, `connect`, `repository status`.
13. `repository sync` и `disconnect` не входят в v1.
14. Операции слоя общего изменения в v1: необязательный `plan`, а также `assign`, `status`, `verify` и `record verification`.
15. Операции слоя изменения конкретного репозитория в v1: `implement` и `record assignment`.
16. Каждая операция уровня изменения, Assignment или Receipt получает явный `change-id`.
17. Cycle — единственная сквозная координационная идентичность Core, которая связывает `cycle_id`, `change_id`, `planning_revision` и репозитории с их отпечатками. Assignment, Receipts и Snapshot остаются отдельными сущностями своего назначения, но все ссылаются на `cycle_id`.
18. Cycle Record — Git-представление Cycle; он не содержит задачи или проектные решения и не создаёт второй источник истины.
19. `planning_revision` и состав репозиториев являются полями Cycle, а не самостоятельными доменными идентичностями.
20. `assign` — единственная поддерживаемая операция Core для подготовки нового Cycle; после подтверждения она записывает Cycle Record в состоянии `pending`, но не изменяет индекс Git, не создаёт и не отправляет коммит и не управляет ветками или PR.
21. Cycle Record проходит состояния хранения `pending → committed_pending → active`; только активная запись переключает текущий Cycle.
22. Движение `HEAD` Store не меняет текущий Cycle автоматически.
23. Для каждой пары `cycle_id + repository_id` существует один вычисляемый Assignment.
24. Assignment не хранится отдельно, не требует пользовательского ID и не зависит от задач, рабочих пакетов или имени ветки.
25. `implement` только подготавливает контекст и Handoff Envelope.
26. `record assignment` принимает только точный чистый коммит реализации.
27. Результат с незакоммиченными изменениями не входит в v1.
28. Result Receipt хранится локально на конкретной машине и явно сохраняет источник данных.
29. `verify` строит и развёртывает точный Snapshot, но не запускает тесты.
30. `record verification` принимает отдельный Verification Receipt.
31. Результат проверки различает `pass`, `fail`, `error`, `inconclusive`.
32. `phase: completed` и `condition: ok` не означают управленческое одобрение или разрешение выпуска.
33. Verification Receipt явно связан с `cycle_id`, `snapshot_id` и отпечатком договора проверки.
34. Cycle восстанавливается из Git; подтверждения после потери локального состояния становятся `missing`.
35. `openspec-orch.yaml` — желаемая конфигурация, принадлежащая пользователю.
36. `.openspec-orch/state.json` — наблюдаемое локальное состояние и подтверждающие данные конкретной машины.
37. Core работает через публичные возможности OpenSpec без зависимости от схемы.
38. Отсутствующую публичную возможность OpenSpec нельзя заменять чтением закрытой структуры файлов.
39. `adopt` сохраняет существующий процесс и использует явный Handoff Mapping; автоматическое определение смысла файлов не входит в v1.
40. Предупреждение требует явного подтверждения; подтверждение не обходит ошибку.
41. Core не изменяет индекс Git, не создаёт и не отправляет коммит с Cycle Record, не управляет ветками, слиянием, перебазированием или PR команды.
42. Функциональный v1 подтверждается реальным пилотным Change.
43. Независимое использование разными командами разрешается только после проверки готовности к распространению.
44. Общие между пользователями Receipts, граф зависимостей, расширения, несколько Store, сборщик Template, автоматическая интеграция CI и центр управления не входят в v1.
45. План реализации может определить технические схемы и алгоритмы, но не переоткрывает перечисленные продуктовые решения.
46. Новый Result Receipt или Verification Receipt заменяет текущее подтверждение того же объекта только по явно указанному `supersedes`; отметка времени не выбирает текущий результат.
47. Идентификатор Snapshot детерминированно зависит от `cycle_id`, коммитов реализации и отпечатка договора проверки; он не включает отметку времени, имя узла, идентификатор машины или пути развёртывания.
48. Отпечаток договора проверки всегда включает идентичность настроенной точки входа и хеш её содержимого для ссылки на файл, даже если точка входа не указана в `contract_inputs`.
49. Объединение или перебазирование коммита с Cycle Record не делает Cycle неактуальным, если в итоговом точном дереве основной ветки по нормативному пути осталась та же корректная запись; переписывание или недостижимость `planning_revision` требует нового `assign`.
