# Работа с subagents при планировании Change

Это руководство описывает Repository Context Passes шага 03: когда основной planning-agent делегирует чтение Code Repositories subagents, какие данные им передаёт и как превращает их ответы в стандартные артефакты OpenSpec.

Subagents являются возможностью agent runtime, а не отдельной командой `sdd` или OpenSpec. Harness не запускает их самостоятельно, не определяет поддержку provider и не хранит ответы между сессиями. Правила из `openspec/config.yaml` инструктируют основной агент использовать native subagents, когда выбранный runtime их поддерживает.

## Зачем нужны Repository Context Passes

Одна бизнесовая фича может затрагивать несколько крупных репозиториев. Если основной агент последовательно загрузит их документацию и код в один planning-context, технические детали вытеснят Proposal, Business Specs и межсистемные решения.

Repository Context Pass изолирует техническое чтение:

```text
центральный Change
        ↓ бизнесовые границы и один вопрос
основной planning-agent
        ├─→ backend subagent ──→ краткий результат
        ├─→ frontend subagent ─→ краткий результат
        └─→ config subagent ───→ краткий результат
        ↓ синтез без сырого кода
Delta Specs / design.md / tasks.md
```

Единицей бизнесового планирования остаётся один OpenSpec Change. Subagents разделяют только техническое исследование и не создают отдельные фичи, Changes, planning-ветки или человеческие гейты.

## Роли

### Основной planning-agent

Основной агент:

- ведёт текущую planning-сессию и читает Proposal, Master Specs и межсистемный контекст;
- решает, какие репозиторные вопросы требуют изоляции;
- создаёт subagents средствами выбранного agent runtime;
- проверяет принадлежность каждого ответа ожидаемым `repository-id`, ревизии и вопросу;
- сопоставляет и разрешает противоречия между ответами;
- единолично создаёт и изменяет Proposal, Delta Specs, `design.md` и `tasks.md`;
- переносит в центральный Store только бизнесовый и межсистемный результат.

### Repository subagent

Subagent:

- отвечает только за один `repository-id` и один ограниченный вопрос;
- работает read-only на переданной точной Git-ревизии;
- сначала исследует provider-specific каталог агента и Repository Knowledge Pack;
- при недостатке документации адресно читает только относящийся к вопросу код;
- отделяет подтверждённые факты от выводов и открытых вопросов;
- возвращает короткий структурированный ответ основному агенту;
- не изменяет Code Repository, центральный Store или артефакты Change.

## Когда использовать subagent

Repository Context Pass нужен, когда выполняется хотя бы одно условие:

- Change затрагивает несколько Code Repositories и для решения требуется читать их технический контекст;
- один репозиторий настолько велик, что его документация и адресное чтение кода заметно сокращают контекст, необходимый для синтеза;
- репозитории требуют независимых вопросов к разным владельцам технической ответственности;
- один pass обнаружил дополнительный зарегистрированный репозиторий в пределах прежнего бизнесового scope;
- вывод одного репозитория нужно независимо проверить по другому репозиторию;
- ответы репозиториев противоречат друг другу и нужен адресный повторный pass.

Фиксированный порог токенов не используется. Основной критерий: основной planning-context не должен получать совокупный сырой код нескольких репозиториев и должен сохранять достаточный резерв для создания целостных Specs, Design и Tasks.

Subagent обычно не нужен, если:

- вопрос полностью разрешается Proposal, Master Specs и business context pack без чтения кода;
- небольшой Knowledge Pack даёт достаточный и непротиворечивый ответ;
- вопрос относится к бизнесовому решению, которое нельзя делегировать техническому исследователю;
- требуется написать или изменить центральный OpenSpec-артефакт;
- делегирование используется только ради формального параллелизма и не уменьшает контекст основного агента.

## Место в `/opsx-continue`

Отдельного пользовательского вызова для subagents нет. Они используются внутри работы агента над очередным стандартным артефактом:

```text
/opsx-continue <change-id>
        ↓
OpenSpec определяет следующий artifactId
        ↓
основной агент читает dependencies, context и rules
        ↓
формулирует только необходимые репозиторные вопросы
        ↓
запускает Repository Context Passes
        ↓
синтезирует и создаёт один стандартный артефакт
        ↓
/opsx-continue возвращает управление
```

Типичное применение по артефактам:

| Артефакт | Когда нужны subagents |
|---|---|
| Delta Specs | Только если без кода нельзя достоверно определить уже существующее наблюдаемое поведение или границу совместимости |
| `design.md` | Основное место применения: ответственность систем, интеграции, данные, совместимость, rollout и rollback |
| `tasks.md` | Только для проверки принадлежности Work Packages, зависимостей и способов проверки; не для создания файлового implementation plan |

Результаты предыдущего вызова можно использовать в следующем артефакте, пока основная planning-сессия и точные ревизии сохранены. Не нужно повторно запускать все passes перед каждым `/opsx-continue`: новый pass создаётся только для нового или неразрешённого вопроса.

## Подготовка pass

Перед созданием subagent основной агент:

1. определяет следующий OpenSpec-артефакт и читает его официальные `instructions`;
2. формулирует один вопрос, ответ на который действительно влияет на этот артефакт;
3. проверяет, что `repository-id` зарегистрирован с `role: code` в `sdd.yaml`;
4. использует уже подключённый чистый checkout того же Store;
5. фиксирует точный 40-символьный Git commit ID;
6. передаёт только относящиеся к вопросу бизнесовые границы и межсистемный контекст;
7. явно запрещает любые записи и загрузку репозитория целиком;
8. задаёт требуемый структурированный формат ответа.

Один pass не получает:

- полную историю planning-чата;
- полные результаты других репозиториев, если они не нужны для вопроса;
- право создавать или редактировать OpenSpec-артефакты;
- задачу «изучи весь репозиторий»;
- заранее выбранный технический ответ, который требуется лишь подтвердить.

## Шаблон задания subagent

Основной агент может использовать следующий шаблон, адаптируя только содержимое полей:

```text
Роль: Repository Context Pass шага 03 SDD.

Change: <change-id>
Целевой артефакт: <specs|design|tasks>
Repository: <repository-id>
Checkout: <absolute-path>
Revision: <40-char-commit>

Вопрос:
<один конкретный вопрос текущей фичи>

Бизнесовые границы:
- <подтверждённая capability или поведение>
- <scope и out of scope, относящиеся к вопросу>

Нужный межсистемный контекст:
- <минимально необходимый контракт или зависимость>

Порядок чтения:
1. Проверь repository-id, checkout и revision.
2. Сначала найди релевантные Markdown/YAML-знания в provider-specific каталоге агента.
3. Не считай generated commands и openspec skills технической документацией репозитория.
4. Если знаний недостаточно, адресно исследуй только относящиеся к вопросу участки кода.

Ограничения:
- Работай read-only.
- Не изменяй Code Repository или центральный Store.
- Не загружай и не пересказывай репозиторий целиком.
- Не проектируй локальный implementation plan.
- Отделяй факты, выводы и неизвестное.
- Не возвращай большие фрагменты кода.

Верни результат строго по контракту Repository Context Pass.
```

## Порядок исследования внутри subagent

Subagent действует от общего к адресному:

1. подтверждает, что работает с ожидаемым checkout и revision;
2. определяет provider-specific каталог агента: например, `.qwen/` или `.gigacode/`;
3. ограниченно инвентаризирует Markdown- и YAML-файлы Knowledge Pack;
4. читает только документы, относящиеся к вопросу;
5. формулирует, чего именно не хватает для ответа;
6. использует поиск по коду для нахождения точек входа;
7. читает минимально достаточные связанные фрагменты;
8. проверяет вывод вторым независимым источником, когда от него зависит контракт или совместимость;
9. прекращает чтение, когда вопрос разрешён либо сформулирован конкретный открытый факт;
10. возвращает структурированный результат без изменения файлов.

Отсутствие Knowledge Pack не является ошибкой. Оно только переводит pass к адресному чтению кода. Блокирующим является конкретный неразрешённый факт, без которого нельзя достоверно определить межсистемный контракт, совместимость или безопасную поставку.

## Контракт результата

Ответ должен быть коротким и содержать только сведения, влияющие на текущий вопрос:

```yaml
repository_id: payments-backend
revision: 0123456789abcdef0123456789abcdef01234567
question: Как репозиторий участвует в поставке нового статуса платежа?
status: complete # complete | needs_followup | blocked

facts:
  - Публичный контракт уже передаёт стабильный идентификатор платежа.

system_impact:
  responsibilities:
    - Репозиторий является владельцем переходов состояния платежа.
  integrations:
    - Новое состояние передаётся потребителям через существующую границу API.
  compatibility:
    - Клиенты, не знающие новое состояние, должны сохранить прежнее поведение.
  rollout:
    - Поставку можно выполнить до обновления UI при сохранении fallback.
  rollback:
    - Откат UI не требует отката владельца состояния.

verification_implications:
  - Нужна контрактная проверка известного и неизвестного состояния.

confidence: high # high | medium | low
open_questions: []

evidence:
  - reference: path/to/file:line
    supports: Краткое указание, какой факт подтверждается.

knowledge_pack_update_candidate: false
```

Правила результата:

- `facts` содержит подтверждённые сведения, а не предположения;
- `system_impact` заполняется только относящимися к вопросу разделами;
- `evidence` содержит короткие `file:line` ссылки для проверки основным агентом, но не большие цитаты;
- локальные имена файлов, классов и функций допустимы только в transient evidence и не копируются в Business Specs или центральный System Design;
- `needs_followup` означает, что нужен ещё один адресный вопрос;
- `blocked` требует назвать один конкретный неразрешённый факт и объяснить, какой planning-вывод без него недостоверен;
- низкая уверенность сама по себе не заменяет открытый вопрос и не является автоматическим блокером.

## Синтез результатов основным агентом

После получения ответа основной агент:

1. сверяет `repository_id`, revision и исходный вопрос;
2. отклоняет результат другого checkout или ревизии;
3. отделяет подтверждённые факты от выводов subagent;
4. сравнивает ответственность, контракты, данные и порядок поставки между репозиториями;
5. при конфликте формулирует узкий follow-up и запускает повторный pass только для затронутого репозитория;
6. определяет, изменился ли бизнесовый scope;
7. переносит бизнесовое поведение в Delta Specs, межсистемное решение в Design, а ожидаемые результаты по `repository-id` — в Tasks;
8. не копирует transient evidence и локальное устройство кода в центральные артефакты.

Соответствие результата артефактам:

| Результат pass | Куда переносится |
|---|---|
| Наблюдаемое бизнесовое поведение | Delta Specs |
| Ответственность систем, интеграции, данные, совместимость, rollout и rollback | `design.md` |
| Ожидаемый результат репозитория, зависимость и способ проверки | `tasks.md` как Work Package |
| Файлы, классы, функции, хуки и локальные шаги | Не переносятся; остаются для implementation PR |
| Устойчивое новое техническое знание | Work Package на обновление Repository Knowledge Pack |
| Сырой код и большие цитаты | Не переносятся |

## Параллельность

Независимые passes разных репозиториев можно запускать параллельно. Основной агент не должен создавать больше subagents, чем требуется для текущих вопросов.

Последовательно выполняются:

- два вопроса к одному репозиторию, если второй зависит от первого;
- follow-up после противоречия;
- исследование нового репозитория, обнаруженного предыдущим pass;
- повторный pass после ошибки scope или revision.

Параллельные subagents не изменяют общие файлы, поэтому не должны конфликтовать на записи. Единственная точка синтеза и записи — основной planning-agent.

## Обработка отклонений

| Ситуация | Действие |
|---|---|
| Knowledge Pack отсутствует или неполон | Адресно читать код; само отсутствие документации не блокирует |
| Checkout грязный, имеет другой Store pointer или не совпадает revision | Не исследовать; вернуть конкретное нарушение предусловия |
| Subagent вернул слишком общий обзор | Повторить pass с одним более узким вопросом |
| Ответы репозиториев противоречат друг другу | Запустить targeted follow-up, не создавать второй Change |
| Обнаружен зарегистрированный дополнительный репозиторий | Проверить условия шага 03 и создать отдельный pass |
| Обнаружен незарегистрированный репозиторий | Сохранить Change; не исследовать до появления поддержанного setup-перехода `BL-009` |
| Обнаружена новая capability, внешняя система или изменение бизнесового scope | Вернуть процесс в Explore |
| Основная сессия потеряна до синтеза | Повторить только незасинтезированный pass; долговечный handoff относится к `BL-006` |
| Agent runtime не поддерживает subagents | Не объявлять контекст изолированным; выполнить один ограниченный pass в основном контексте только если это безопасно для его размера |

## Пример

Change меняет отображение статуса платежа и затрагивает `payments-backend`, `payments-frontend` и `payments-config`.

Основной агент не просит три subagents «изучить репозиторий». Он задаёт разные вопросы:

```text
payments-backend:
Кто владеет состоянием и какой наблюдаемый контракт доступен потребителям?

payments-frontend:
Как потребитель различает известное, новое и неизвестное состояние без изменения бизнесового смысла?

payments-config:
Какая межсистемная возможность нужна для независимого rollout и rollback компонентов?
```

После ответов основной агент:

- описывает состояния и пользовательские сценарии в Delta Specs;
- фиксирует владельца состояния, границы API и порядок rollout в `design.md`;
- создаёт по одному outcome-based Work Package для backend, frontend и config в `tasks.md`;
- не переносит в Store контроллеры, Java-классы, React hooks, имена конфигурационных файлов или локальную последовательность правок.

## Проверка перед созданием артефакта

Основной агент может завершить работу с Repository Context Passes, когда:

- каждый использованный результат относится к ожидаемому `repository-id`, revision и вопросу;
- открытые вопросы классифицированы как блокирующие или неблокирующие;
- противоречия между репозиториями разрешены либо явно признаны блокирующими;
- итоговый бизнесовый scope остаётся одним Change;
- основной контекст получил краткие выводы, а не совокупный сырой код;
- центральный артефакт не содержит repo-local implementation details;
- следующий `/opsx-continue` может использовать созданный артефакт без отдельного человеческого подтверждения.
