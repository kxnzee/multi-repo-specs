# OpenSpec для команды: единый flow для нескольких репозиториев

Этот гайд объясняет, как использовать отдельный репозиторий sdd-specs в качестве единого источника технических требований для нескольких сервисов, синхронно реализовывать изменение в backend и frontend и архивировать change только после проверки всей цепочки.

## Весь процесс в четырех действиях

1. Настроить store

   ```bash
   openspec store register .
   ```

   Один раз на рабочем компьютере.

2. Создать change

   ```bash
   openspec new change PAY-412-team-update
   ```

   Один идентификатор для Jira, веток, PR.

3. Проверить

   ```bash
   openspec validate --all --store sdd-specs --strict
   ```

   До начала разработки и перед push.

4. Архивировать

   ```bash
   openspec archive PAY-412-team-update --yes
   ```

   Только после завершения всех сервисов.

## Жизненный цикл

```text
Jira Story (PAY-412) -> OpenSpec change (proposal, specs, design, tasks) -> Реализация (api-server + web-app ...) -> Composite verification (контракт + система целиком) -> Мастер-спека (фактическое состояние)
```

В гайде используются:

- sdd-specs — требования, контракты и история изменений;
- api-server — backend;
- web-app — frontend.

Все названия организаций и GitHub-репозиториев в документе тестовые. Перед использованием замените acme-example и URL репозиториев на значения вашего проекта.

## 1. Как устроена схема

В проекте есть три репозитория:

```text
sdd-specs
├── openspec/specs/ ← действующие мастер-спеки
└── openspec/changes/ ← проектируемые и реализуемые изменения
api-server ← реализация backend
web-app ← реализация frontend
```

Главный принцип. Требование описывается один раз в sdd-specs, а затем реализуется во всех затронутых сервисах

Репозитории api-server и web-app не должны хранить собственные независимые версии общего контракта. Оба сервиса используют спецификации из одного OpenSpec store.

Это помогает избежать ситуации, когда:

- backend возвращает одно поле;
- frontend ожидает другое;
- документация описывает третий вариант;
- команды считают правильными разные версии контракта

## 2. Что такое store, change и мастер-спека

### Store

sdd-specs — центральный репозиторий OpenSpec, или store.

В нём хранятся:

- действующие требования;
- проектируемые изменения;
- архитектурные решения;
- задачи по реализации;
- история завершённых изменений.

### Change

Change — отдельное изменение поведения системы.

Например:

```text
pay-412-team-update
```

Change описывает:

- зачем нужно изменение;
- какое поведение системы меняется;
- какие сервисы затронуты;
- какой контракт должен получиться;
- какие задачи необходимо выполнить.

### Мастер-спека

Мастер-спека описывает уже действующее поведение системы.

Она находится в:

```text
openspec/specs/
```

Пока изменение проектируется или реализуется, оно находится в:

```text
openspec/changes/
```

После завершения change архивируется, а его требования переносятся в мастерспеку.

## 3. Общий жизненный цикл изменения

```text
Идея или Jira Story
↓
Создание OpenSpec change
↓
Proposal, design, specs и tasks
↓
Проверка OpenSpec
↓
Реализация в api-server и web-app
↓
Проверка общего контракта
↓
Merge связанных PR
↓
Archive change
↓
Обновлённая мастер-спека
```

Главное правило. Сначала команда согласует изменение поведения системы, затем меняет код.

# Часть I. Однократная настройка рабочего места

## 5. Что нужно установить

На компьютере разработчика должны быть установлены:

- Git;
- Node.js 20 или новее;
- OpenSpec CLI;
- доступ к GitHub или внутреннему Git-серверу через SSH либо HTTPS

## 6. Рекомендуемая структура локальных папок

Создадим две отдельные директории:

```text
work/
├── openspec/ ← центральные store-репозитории
└── src/ ← репозитории с кодом
```

## 7. Клонирование и регистрация store

Зарегистрируйте репозиторий как OpenSpec store:

```bash
openspec store register .
openspec store list
```

### Что делает регистрация

Команда (выполняется в терминале):

```bash
openspec store register .
```

Сообщает OpenSpec CLI:

Текущий локальный репозиторий содержит общие спецификации, которые могут использовать другие репозитории проекта.

Регистрация выполняется один раз на каждом рабочем компьютере

## 8. Проверка контекста OpenSpec

Находясь в каталоге sdd-specs, выполните (в терминале):

```bash
openspec doctor --json
openspec context --json
```

Проверьте, что:

- store найден;
- структура OpenSpec корректна;
- активным является sdd-specs;
- CLI видит каталоги specs и changes;
- путь указывает на ожидаемый локальный репозиторий.

## 9. Клонирование кодовых репозиториев

В src клонируем все репозитории web-api, api-server и тд

## 10. Проверка подключения сервисов к общему store

Заходим в каждый кодовый репозиторий

```bash
openspec doctor --json
openspec context --json
openspec status --change team-update
```

# Часть II. Как команда работает с изменением

## 11. Пример. Изменение общей авторизации

Допустим, нужно изменить механизм авторизации. Изменение затрагивает:

- API;
- frontend;
- общий контракт;
- интеграционные тесты;
- порядок развёртывания компонентов.

Для него создаётся единый change:

```text
pay-412-team-update
```

Один change объединяет общее понимание изменения, но каждый сервис реализует собственную часть.

## 12. Шаг 1. Зафиксировать change-id

Change-id должен быть:

- коротким;
- понятным;
- уникальным;
- одинаковым во всех связанных задачах, ветках и PR.

Рекомендуемый формат:

```text
<JIRA>-<краткое-название>
```

Пример:

```text
pay-412-team-update
```

Это позволяет построить сквозную связь:

```text
Jira/SberTrack Story PAY-412
↕
OpenSpec change pay-412-team-update
↕
PR в sdd-specs
↕
PR в api-server
↕
PR в web-app
↕
код и тесты
```

Создание change:

```bash
cd "$src/api-server"
openspec new change PAY-412-team-update
```

Через настроенную привязку change должен появиться в центральном store:

```text
sdd-specs/
└── openspec/
    └── changes/
        └── PAY-412-team-update/
```

После выполнения команды проверьте фактическое расположение файлов:

```bash
openspec status --change PAY-412-team-update
```

## 13. Шаг 2. Описать изменение

В change должны появиться следующие артефакты:

```text
openspec/changes/pay-412-team-update/
├── proposal.md
├── design.md
├── specs/
│   └── shared-update/
│       └── spec.md
└── tasks.md
```

### proposal.md

Отвечает на вопросы:

- какую проблему решаем;
- зачем изменение нужно бизнесу или пользователю;
- какие сервисы затронуты;
- что входит и не входит в scope;
- существуют ли риски совместимости;
- как change связан с Jira Story.

Пример:

```markdown
# Proposal

## Jira

PAY-412

## Problem

Backend и frontend используют разные версии контракта авторизации.

## Proposed change

Ввести единый контракт `shared-update`, используемый обоими сервисами.

## Affected components

- api-server
- web-app
- integration tests

## Out of scope

- замена поставщика идентификации;
- изменение механизма хранения пользовательских сессий.
```

### design.md

Описывает техническое решение:

- API endpoints;
- структуру данных;
- взаимодействие сервисов;
- обработку ошибок;
- миграцию;
- обратную совместимость;
- порядок rollout;
- механизм отката;
- затронутые репозитории и компоненты.

### specs/shared-update/spec.md

Описывает проверяемое поведение системы.

Это главный контракт change.

### tasks.md

Разделяет реализацию по компонентам:

```markdown
## OpenSpec store

- [ ] Согласовать proposal.
- [ ] Согласовать общий контракт.
- [ ] Описать порядок rollout.

## API server

- [ ] Обновить модель ответа.
- [ ] Обновить endpoint `/features/shared-update`.
- [ ] Добавить unit-тесты.
- [ ] Добавить contract-тесты.

## Web app

- [ ] Обновить API client.
- [ ] Добавить обработку новых полей.
- [ ] Обновить интерфейс.
- [ ] Добавить frontend-тесты.

## Integration

- [ ] Проверить совместимость API и Web.
- [ ] Проверить обратную совместимость.
- [ ] Проверить порядок rollout.
- [ ] Выполнить составной пользовательский сценарий.
```

## 14. Шаг 3. Проверить change до начала разработки

Команды одинаковы для Windows PowerShell и Linux/macOS Bash, выполняются в терминале.

Проверка конкретного change:

```bash
openspec status --change pay-412-team-update --json
```

Общая валидация store:

```bash
openspec validate --all --store sdd-specs
```

Строгая проверка:

```bash
openspec validate --all --store sdd-specs --strict
```

Валидация должна выполняться до начала разработки.

Она помогает заранее найти:

- отсутствующие обязательные секции;
- некорректную структуру требований;
- требования без MUST или SHALL;
- сценарии без WHEN и THEN;
- неполное описание поведения;
- ошибки в структуре change;
- конфликты с действующей спецификацией.

## 15. Шаг 4. Создать связанные ветки

Рекомендуется использовать одинаковый change-id в названиях веток

В sdd-specs:

```powershell
Set-Location $storePath
git checkout main
git pull
git checkout -b feature/pay-412-team-update
```

В api-server:

```powershell
Set-Location (Join-Path $src 'api-server')
git checkout main
git pull
git checkout -b feature/pay-412-team-update
```

В web-app:

```powershell
Set-Location (Join-Path $src 'web-app')
git checkout main
git pull
git checkout -b feature/pay-412-team-update
```

В описании каждого PR должны быть ссылки на:

- Jira Story;
- OpenSpec change;
- связанные PR в других репозиториях.

Пример описания PR:

```markdown
## Change

OpenSpec change: `pay-412-team-update`

## Related work

- Jira/SberTrack: PAY-412
- sdd-specs: PR #15
- api-server: PR #42
- web-app: PR #73

## Verification

- [ ] OpenSpec validation passed
- [ ] Unit tests passed
- [ ] Contract tests passed
- [ ] Composite verification passed
```

## 16. Шаг 5. Реализовать изменение

### Backend

В api-server реализуется серверная часть:

- модели данных;
- бизнес-логика;
- API;
- валидация;
- обработка ошибок;
- unit-тесты;
- contract-тесты.

Проверяемый endpoint:

```http
GET /features/shared-update
```

### Frontend

В web-app реализуется клиентская часть:

- API client;
- типы данных;
- обработка новых полей;
- отображение;
- состояния загрузки и ошибок;
- frontend-тесты.

Frontend должен использовать контракт, описанный в shared-update, а не собственное неформальное представление требований.

## 17. Что значит «контракт согласован»

Недостаточно проверить, что endpoint отвечает с кодом 200

Необходимо проверить:

- одинаковые имена полей;
- одинаковые типы данных;
- одинаковую обязательность полей;
- одинаковые значения enum;
- одинаковую трактовку null;
- одинаковые коды ошибок;
- одинаковую версию контракта;
- совместимость при поэтапном rollout.

Frontend не должен ожидать поля, которого ещё нет в развёрнутом backend.

Backend не должен удалять поле, которое продолжает использовать frontend.

## 18. Шаг 6. Выполнить составную проверку

Поскольку изменение затрагивает несколько репозиториев, проверки одного сервиса недостаточно. Нужны три уровня проверки.

### Уровень 1. OpenSpec validation

Проверяется корректность требований (выполняется в терминале):

```bash
openspec validate --all --store sdd-specs --strict
```

### Уровень 2. Проверки отдельных компонентов

Для каждого репозитория запускаются:

- unit-тесты;
- статический анализ;
- сборка;
- компонентные тесты;
- contract-тесты.

Пример общей последовательности (выполняется в терминале):

```bash
npm ci
npm run lint
npm test
npm run build
```

Конкретные команды зависят от проекта.

### Уровень 3. Composite verification

Проверяется вся цепочка:

```text
OpenSpec contract
↓
api-server
↓
HTTP API
↓
web-app
↓
пользовательский сценарий
```

Composite verification подтверждает, что:

- backend реализовал контракт;
- frontend правильно использует контракт;
- версии компонентов совместимы;
- интеграционный сценарий работает целиком;
- порядок rollout не создаёт несовместимого состояния.

Это шире обычного контрактного тестирования. Контрактный тест проверяет границу между компонентами, а composite verification — итоговое поведение всей затронутой цепочки.

## 19. Шаг 7. Завершить связанные задачи

Перед архивированием change убедитесь, что:

- OpenSpec change согласован;
- PR в sdd-specs принят;
- backend реализован и проверен;
- frontend реализован и проверен;
- связанные PR смержены;
- интеграционные тесты проходят;
- rollout выполнен или подтверждён;
- все пункты tasks.md завершены.

Пример завершённого tasks.md:

```markdown
## OpenSpec store

- [x] Согласовать proposal.
- [x] Согласовать общий контракт.
- [x] Описать порядок rollout.

## API server

- [x] Обновить модель ответа.
- [x] Обновить endpoint.
- [x] Добавить unit-тесты.
- [x] Добавить contract-тесты.

## Web app

- [x] Обновить API client.
- [x] Добавить обработку новых полей.
- [x] Обновить интерфейс.
- [x] Добавить frontend-тесты.

## Integration

- [x] Проверить совместимость.
- [x] Проверить обратную совместимость.
- [x] Проверить rollout.
- [x] Выполнить composite verification.
```

## 20. Шаг 8. Архивировать change

Команда одинакова для Windows PowerShell и Linux/macOS Bash (выполняется в терминале):

```bash
openspec archive pay-412-team-update --yes
```

При архивировании:

- change перестаёт считаться активным;
- его требования применяются к мастер-спеке;
- обновляется действующее описание системы;
- change сохраняется в истории.

После этого мастер-спека становится источником текущего состояния системы.

Change следует архивировать только после завершения всех затронутых компонентов. Архивирование не должно происходить сразу после завершения одного из сервисов.

## 21. Шаг 9. Проверить мастер-спеку

Получите список действующих спецификаций (выполняется в терминале):

```bash
openspec list --specs --json
```

Просмотрите конкретную спецификацию (выполняется в терминале):

```bash
openspec show shared-update --type spec --json
```

Проверьте, что:

- shared-update присутствует в мастер-спеках;
- требования из change перенесены;
- версия контракта обновлена;
- backend и frontend реализуют эту версию;
- мастер-спека описывает фактически работающую систему.

Например

```yaml
version: 1.2.0
```

# Часть III. Командные правила

## 25. Что хранится в sdd-specs

- общее поведение продукта;
- межсервисные контракты;
- архитектурные решения;
- требования к совместимости;
- правила rollout;
- OpenSpec changes;
- мастер-спеки;
- история изменений

## 26. Что хранится в кодовых репозиториях

В api-server и web-app находятся:

- исходный код;
- компонентные тесты;
- локальные технические детали;
- конфигурация сборки;
- реализация общего контракта.

Общий контракт не должен вручную копироваться в несколько репозиториев как независимый источник требований.

Допустимы производные или сгенерированные артефакты:

- TypeScript-типы;
- Java DTO;
- API clients;
- JSON Schema;
- OpenAPI-файлы;
- тестовые fixtures

Но они должны создаваться или проверяться относительно центрального контракта.

## 28. Рекомендуемый порядок merge и rollout

Для изменений, затрагивающих несколько репозиториев:

1. Согласовать OpenSpec change.
2. Подготовить реализацию backend.
3. Подготовить реализацию frontend.
4. Проверить совместимость компонентов.
5. Смержить изменения в безопасном порядке.
6. Выполнить rollout.
7. Выполнить composite verification.
8. Архивировать OpenSpec change.

Порядок rollout зависит от совместимости. Например, при добавлении нового необязательного поля:

1. Backend начинает возвращать новое необязательное поле.
2. Frontend начинает использовать новое поле.
3. Старое поведение удаляется отдельным change.

Нельзя удалять старое поле до того, как все клиенты перестали его использовать.

# Часть IV. Ежедневная работа

## 29. Что делать в начале работы

Обновить store:

```powershell
Set-Location $storePath
git checkout main
git pull
```

Обновить backend:

```powershell
Set-Location (Join-Path $src 'api-server')
git checkout main
git pull
```

Проверить окружение:

```bash
openspec doctor --json
openspec context --json
openspec list
```

## 30. Что делать перед push

1. Проверьте конкретный change:

   ```bash
   openspec status --change pay-412-team-update --json
   ```

2. Запустите строгую валидацию:

   ```bash
   openspec validate --all --store sdd-specs --strict
   ```

3. Выполните проверки кодового репозитория:

   ```bash
   npm run lint
   npm test
   npm run build
   ```

4. Если в проекте есть отдельные contract-тесты:

   ```bash
   npm run test:contract
   ```

Конкретные команды должны быть зафиксированы в README соответствующего репозитория.

## 31. Что делать перед archive

## Главные правила команды

1. Один общий контракт хранится в одном месте — sdd-specs.
2. Один change описывает одно законченное изменение поведения системы.
3. Сначала change, затем реализация.
4. Все связанные репозитории используют одинаковый change-id.
5. Change нельзя архивировать, пока не завершены все затронутые сервисы.
6. OpenSpec validation проверяет требования, но не заменяет тестирование кода.
7. Для мультирепозиторного изменения обязательна проверка системы целиком.
8. Мастер-спека должна описывать фактически работающую систему, а не планы на будущее.
9. Порядок merge и rollout должен быть явно описан в design.md.
10. Все URL и названия из этого гайда являются тестовыми и должны быть заменены на значения проекта.

## Тестовый статус PoC

Центральная мастер-спека:

```text
openspec/specs/shared-update/spec.md
```

Проверяемый backend endpoint:

```text
api-server: GET /features/shared-update
```

Frontend использует этот endpoint для получения общего контракта:

```text
web-app → api-server → GET /features/shared-update
```

Тестовая версия контракта:

```text
1.2.0
```

Целевой результат PoC. Backend и frontend реализуют один контракт из общего OpenSpec store, а завершённые изменения последовательно переносятся в мастер-спеку.
