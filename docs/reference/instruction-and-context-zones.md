# Зоны хранения контекста и инструкций

Этот документ помогает выбрать место для нового правила, контекста или механизма. Он описывает установленные файлы в рабочем проекте. Каталоги `harness/init/` содержат их шаблоны и не образуют отдельные runtime-зоны.

## Основные зоны

### Файл инструкций выбранного агента

Путь задаётся полем `agent.instructions_file` в `sdd.yaml`:

- Qwen Code: `QWEN.md`;
- GigaCode: `.gigacode/GIGACODE.md`.

Здесь хранится постоянный контекст текущего репозитория, который должен быть доступен агенту с начала сессии.

В центральном Store файл создаётся Harness и описывает:

- назначение Store и его границы относительно Code Repositories;
- структуру `openspec/` и владельцев машинной конфигурации;
- устойчивые ограничения на Changes, встроенные команды и Archive;
- минимальную межсессионную маршрутизацию, которая нужна до выполнения отдельной команды.

В Code Repository файл поддерживает команда этого репозитория и описывает:

- назначение и границы репозитория;
- структура исходного кода;
- основной технологический стек;
- команды сборки, тестирования и локальной разработки;
- устойчивые инженерные соглашения и ограничения;
- особенности работы агента в этом репозитории.

Содержимое файла Code Repository относится только к этому репозиторию и не переносится в центральный Store. При Repository Context Pass основной агент передаёт subagent точный путь к нему через `repository_instructions_path`.

В файле инструкций не должны находиться:

- алгоритмы отдельных проектных команд;
- правила формирования Proposal, Specs, Design и Tasks;
- продуктовый контекст нескольких репозиториев;
- параметры конкретного Change, ревизии и временное состояние выполнения.

Исключение допустимо для короткого правила, которое необходимо агенту в любой сессии и нельзя надёжно передать через конкретную команду. Причина такого размещения должна быть указана рядом с правилом.

### Каталог команд агента

Путь задаётся полем `agent.commands_directory` в `sdd.yaml`:

- Qwen Code: `.qwen/commands/`;
- GigaCode: `.gigacode/commands/`.

Здесь находятся инструкции для конкретных инженерных процессов:

- последовательность действий;
- обязательные проверки и условия остановки;
- разрешённые чтение и изменения;
- формат результата;
- переход к следующему шагу.

Файлы `opsx-*` принадлежат OpenSpec и не изменяются проектом. Файлы `sdd-*` принадлежат Harness и описывают проектные процессы. `sdd-apply.md` используется как runtime-инструкция по точному пути из `next_action`, а не как обычная slash-команда. Перед ней тот же `next_action` загружает точный `agent.instructions_file` из immutable runtime Store.

Команды не заменяют файл инструкций агента и не должны дублировать постоянное описание репозитория.

### `openspec/context/`

Здесь описывается проект в целом без локального устройства кода отдельных репозиториев:

- продуктовый контекст;
- доменный глоссарий и модель;
- архитектура и границы систем;
- безопасность и compliance;
- межсистемные инварианты;
- общие quality gates и release process;
- принятые ADR.

`00-start-here.md` служит индексом и помогает выбрать нужную часть контекста.

В `openspec/context/` не размещаются определения subagents, алгоритмы команд, структура классов и модулей конкретного Code Repository, временные результаты исследования и инструкции по реализации.

### `openspec/config.yaml`

Здесь настраивается использование OpenSpec в spec-driven процессе команды:

- schema;
- общий контекст, который OpenSpec передаёт при подготовке артефактов;
- правила формирования Proposal, Specs, Design и Tasks;
- условия применения проектных механизмов во время planning.

Конфигурация может определить, когда нужен Repository Context Pass и какой общий результат от него требуется. Полный prompt subagent и его набор инструментов принадлежат определению subagent, а технический алгоритм команды — каталогу `commands/`.

В Code Repository файл `openspec/config.yaml` имеет другое назначение: это только pointer `store: <store-id>`. Правила spec-driven процесса хранятся в конфигурации центрального Store.

## Дополнительные существующие зоны

Эти зоны уже используются проектом. Они дополняют четыре основные зоны, но не заменяют их.

### Невызваемые проектные инструкции

`.sdd/instructions/` хранит стабильные контракты, которые Harness передаёт агенту по точному пути, но которые не должны регистрироваться как slash-команды. Общий `.sdd/instructions/explore.md` дополняет штатный `/opsx-explore`; пользователь запускает только CLI-команду `sdd explore`, а отдельной `/sdd-explore` нет.

В этом каталоге не хранят runtime-параметры, локальные данные или инструкции конкретного Code Repository.

### Каталог native subagents

Provider-specific каталог `agents/` содержит определения subagents:

- условие выбора в `description`;
- разрешённые инструменты;
- специализированный системный prompt;
- вход и формат результата;
- ограничения делегированной работы.

Обязательный общий профиль — `repository-context-pass`. Остальные профили являются optional-специализациями и выбираются runtime по `description`.

### Машинная конфигурация и управление

`sdd.yaml`, `.openspec-store/` и `CODEOWNERS` содержат версии, ID, репозитории, provider-specific пути, Store metadata и владельцев. В этих файлах не размещаются развёрнутые инструкции агенту. Все поля `sdd.yaml` описаны в [справочнике конфигурации](sdd-yaml.md).

### OpenSpec-артефакты

`openspec/specs/` содержит принятое поведение системы. `openspec/changes/` содержит Proposal, Delta Specs, Design и Tasks планируемого изменения. Это требования и решения Change, а не настройка агента.

### Runtime-передача

`next_action`, `.sdd/runtime/.../context.json` и prompt конкретного subagent передают проверенные параметры одного запуска. Runtime не хранит постоянные правила и не становится новым источником процесса.

### Пользовательская документация

`docs/` и `harness/README.md` объясняют процесс человеку. Агент не обязан читать их для выполнения команды. Обязательное правило должно находиться в предназначенной для него runtime-зоне, а документация только объясняет это правило.

## Как выбрать зону

1. Если это устойчивое знание о текущем Store или одном Code Repository, используйте `agent.instructions_file` этого репозитория.
2. Если это вызываемый пользователем порядок выполнения конкретной задачи, используйте проектную команду `sdd-*`.
3. Если это продуктовый, доменный или межсистемный контекст проекта, используйте `openspec/context/`.
4. Если правило влияет на формирование OpenSpec-артефактов, используйте `openspec/config.yaml`.
5. Если описывается делегированная роль, её инструменты и ответ, используйте каталог `agents/`.
6. Если это ID, путь, версия, владелец или Store metadata, используйте машинную конфигурацию.
7. Если значение относится только к одному запуску, передавайте его через runtime.
8. Если стабильный контракт передаётся только по точному runtime-пути и не должен становиться slash-командой, используйте `.sdd/instructions/`.
9. Если текст нужен только участнику команды, разместите его в `docs/`.

При пересечении зон выберите одного владельца правила. В остальных местах оставьте короткую ссылку или необходимое локальное ограничение, но не копию полного алгоритма.

## Итоговая матрица ответственности

| Правило или контракт | Единственный владелец | Допустимая передача или fallback |
|---|---|---|
| Постоянные инструкции центрального Store | `<store>/<agent.instructions_file>` | автоматически загружаются агентом из корня Store и передаются первыми в Apply-сессию из runtime Store |
| Постоянные инструкции Code Repository | `<checkout>/<agent.instructions_file>` | Repository Context Pass адресно читает код и тесты, если файла нет или сведений недостаточно |
| Repository Context Pass | provider-specific каталог `agents/` | `openspec/config.yaml` задаёт только условие применения и ожидаемый результат |
| Explore | `.sdd/instructions/explore.md` | Harness передаёт runtime-параметры и точный путь штатному `/opsx-explore` |
| Формирование OpenSpec-артефактов | `openspec/config.yaml` | агент использует принятый проектный контекст и стандартные инструкции OpenSpec |
| Контекст проекта | `openspec/context/` | `00-start-here.md` служит индексом, а не отдельным владельцем правил агента |
| Реализация Work Packages | provider-specific `commands/sdd-apply.md` | `next_action` и `context.json` передают только проверенные параметры запуска |

## Проверка при расширении

Перед добавлением нового файла или правила проверьте:

- кто читает его автоматически;
- относится ли информация к одному репозиторию или ко всему проекту;
- действует ли правило всегда или только в одной команде;
- является ли содержимое постоянным или runtime-вводом;
- где находится единственный источник правила;
- не появляется ли второй список профилей, путей или этапов, который придётся синхронизировать вручную.
