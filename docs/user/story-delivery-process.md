# Единый процесс работы над Jira Story

Этот документ задаёт единый процесс от требования потребителя до выпуска и заменяет
отдельные командный и одиночный потоки. Он разделяет Jira, OpenSpec SDD и Git Flow:
Jira управляет работой людей, OpenSpec — требованиями и подтверждениями, Git Flow —
поставкой кода.

Термины `Jira Story`, `Store Story branch`, `Code PR`, `Subtask Store PR` и
`Story Store PR` определены в [конце этого документа](#термины).

## Единые правила Git Flow

Этот процесс применяется в проектах, явно выбравших Jira Story и Git Flow.
Универсальный шаблон проекта не устанавливает его автоматически. Команда должна
явно принять этот документ или передать эквивалентные правила агенту; наличие Store
само по себе не включает Git Flow.

Git Flow обязателен для центрального Store и всех репозиториев кода одного
проекта только после такого принятия. Все репозитории следуют явно заданным ролям
веток и направлениям PR. Конкретные имена и префиксы задаёт команда, а не Orchestrator.

| Логическая роль | Создаётся от | PR направляется в | Назначение |
|---|---|---|---|
| Production branch | — | — | Состояние, выпущенное в промышленную среду |
| Integration branch | Production branch при создании репозитория | — | Интеграция следующих изменений и источник выпуска |
| Code work branch | Integration branch | Integration branch | Реализация подзадачи в Code Repository |
| Store Story branch | Integration branch Store | Integration branch Store | Интеграция Planning, Tasks, подтверждений и Archive одной Jira Story |
| Store subtask branch | Store Story branch | Store Story branch | Изменение Store в рамках отдельной подзадачи |
| Release branch | Integration branch | Production branch, затем обратно в Integration branch | Стабилизация и публикация выпуска |
| Hotfix branch | Production branch | Production branch, затем обратно в Integration branch | Срочное исправление выпущенной версии |

Например, команда может выбрать `main`/`develop`/`feature/*` или
`master`/`dev`/`work/*`. Это примеры, а не встроенные разрешённые имена.

Во всех репозиториях действуют одинаковые ограничения:

- прямые коммиты и отправка изменений в Production и Integration branches запрещены;
- изменение попадает в целевую ветку только через PR, проверку и обязательные проверки проекта;
- Production и Integration branches защищены от принудительной перезаписи и удаления;
- рабочая ветка удаляется после слияния;
- Release и Hotfix получают тег Git после слияния в Production branch;
- отклонение от конвенции оформляется как временное исключение с владельцем, сроком
  и планом возврата, а не как локальное правило репозитория.

SDD и Git Flow не смешиваются: SDD определяет требуемое поведение и подтверждения, а Git
Flow — ветки и продвижение одного и того же изменения. Git Flow действует на всех
этапах: рабочие ветки используются во время Planning и Apply, Release branch — только
после успешного UAT и контрольной точки 3.

## Роли

| Роль | Ответственность |
|---|---|
| Владелец продукта | Решение брать требование или нет, область продукта, UAT и решение о выпуске |
| Аналитик | Discovery, все Planning-артефакты, Jira-декомпозиция, Store Story branch и Archive |
| Разработчик | Проверка Planning, реализация назначенной подзадачи, Code PR и Subtask Store PR |
| Тестировщик | Проверка Planning, ИФТ, проверка Scenarios, подтверждения Zephyr, Verify и решение человека |
| Лид разработки | Проверка Planning и рисков реализации, разрешение технических блокирующих проблем |

«Три амиго» — аналитик, разработчик и тестировщик. Лид разработки подключается к
Planning PR дополнительно и не заменяет ни одну из этих ролей.

Роли обозначают ответственность, а не учётные записи или ACL Orchestrator. В
небольшой команде один человек может совмещать несколько ролей, включая все роли в
одиночном процессе. При этом Planning, Apply, Verify, Archive, UAT и выпуск остаются
разными решениями с отдельными подтверждениями. Неизвестный владелец решения,
бессрочное исключение или решение о приёмке, принятое только агентом, считаются
блокирующей проблемой.

## 1. Приём требования

1. Потребитель создаёт задачу в Jira.
2. Владелец продукта решает, брать требование в работу или нет.
3. Если требование принято, владелец продукта создаёт Jira Story с исходными
   требованиями и создаёт в ней подзадачу аналитика.

## 2. Исследование требований

1. Jira Story находится в статусе `Discovery`.
2. Аналитик собирает и уточняет требования у потребителей.
3. Когда требований достаточно для начала SDD, аналитик переводит свою подзадачу в
   работу и создаёт связанный OpenSpec Change.
4. От Integration branch Store создаётся Store Story branch по принятому в проекте
   шаблону имени. Прямые изменения этой ветки запрещены: она обновляется
   только через PR подзадач.

Аналитик выбирает схему и создаёт Change по
[сценариям Change](../templates/default.md#выбор-процесса-и-старт). Схему
существующего Change не переключают.

## 3. Планирование

1. Аналитик готовит Planning по правилам выбранной схемы. Состав артефактов,
   переходы между ними и правила контрольной точки 1 описаны в
   [сценариях Change](../templates/default.md#сценарии-работы-с-change).
2. Аналитик создаёт от Store Story branch ветку по принятому шаблону имени для
   Store subtask branch и открывает Planning PR обратно в Store Story
   branch.
3. Весь PR проверяют разработчик, тестировщик и лид разработки. Аналитик устраняет
   замечания и сохраняет согласованность всех Planning-артефактов.
4. После одобрений, строгой проверки OpenSpec и контрольной точки 1 Planning PR сливается в Store
   Story branch.

Контрольная точка 1 относится к точной ревизии Planning PR. Изменение принятого
поведения, Repository Impact, Design или Tasks требует нового Planning PR и нового
прохождения контрольной точки 1.
Git-процесс не заменяет проверок схемы и человеческого решения по Planning.

## 4. Декомпозиция в Jira

1. После слияния Planning PR аналитик создаёт подзадачи разработки согласно
   `tasks.md`.
2. Обычно работа каждого репозитория кода оформляется отдельной подзадачей. Если в
   одном репозитории нужно несколько подзадач, их связь с пунктами `tasks.md` должна
   оставаться однозначной.
3. Исполнители назначаются из участников Jira Story.
4. Для ИФТ и Verify создаётся подзадача тестировщика.

Jira-подзадачи управляют назначением и статусом работы, а `tasks.md` остаётся
каноническим планом реализации OpenSpec Change.

## 5. Начало разработки

Каждый разработчик берёт назначенную подзадачу в работу и выполняет её только в
указанном репозитории кода. От Integration branch создаётся Code work branch
по принятому шаблону имени. Один OpenSpec `change-id` указывается в Jira,
ветках и PR вместе с ключом Jira, если это не нарушает ограничение Git-сервера на длину
имени.

Назначение, Repository Impact и соответствующая секция Tasks должны совпадать.
Если во время Apply обнаружен новый репозиторий, capability или изменение принятой
области, разработка останавливается до обновления Planning и повторного прохождения
контрольной точки 1.

## 6. План реализации объёмной подзадачи

Разработчик до Apply готовит отдельный план реализации, если выполняется хотя бы одно
условие:

- в одном репозитории кода затронуто более 10 Scenarios;
- меняются несколько модулей или публичный контракт;
- требуются миграция данных, решение по безопасности или нетривиальный откат;
- план потребовал лид разработки во время проверки Planning.

План размещается в описании Code PR или в закреплённом комментарии. Для небольшой
подзадачи достаточно шагов и проверок из `tasks.md`. Порог в 10 Scenarios является
стартовым правилом и пересматривается по фактической сложности завершённых задач.

## 7. Apply и PR подзадачи

1. Разработчик завершает Agent-сессию Store, переходит в назначенный репозиторий
   кода и открывает из его корня новую Agent-сессию. В ней запускается штатный
   OpenSpec Apply. Расширять доступ Store-сессии к соседнему checkout для обхода
   файловой защиты нельзя. Для нескольких репозиториев используются отдельные
   сессии Apply.
2. Разработчик реализует задачу, выполняет проверки репозитория, создаёт коммит и
   отмечает задачу выполненной.
3. Разработчик создаёт Code PR в Integration branch соответствующего репозитория
   кода. В описании
   указываются Jira Story, подзадача, `change-id`, план реализации и результаты
   проверок.
4. После проверки Code PR сливается в Integration branch. Точный коммит реализации
   и идентификатор собранного артефакта сохраняются как подтверждение.
5. После слияния кода разработчик создаёт от Store Story branch ветку
   по принятому шаблону имени для Store subtask branch и открывает Subtask Store PR
   обратно в Store Story branch с обновлёнными Tasks и подтверждением реализации.
   Прямое изменение
   Store Story branch запрещено.

Разработчик создаёт два разных PR: один с кодом в репозитории кода, второй с
OpenSpec-изменениями своей подзадачи в Store. Разработка подзадачи считается
завершённой после слияния Code PR и создания Subtask Store PR.

В описании Code PR фиксируются Change, Jira Story и подзадача, репозиторий и его
задачи OpenSpec, связанные PR других репозиториев, план реализации, результаты
проверок репозитория и известные блокирующие проблемы. Для кандидата используются
полные SHA коммитов и идентификатор собранной версии или развёртывания: имени ветки,
номера задачи или последнего коммита в PR недостаточно.

Завершение Tasks одного репозитория означает только завершение работы в нём. Весь
Change готов к ИФТ после сведения всех запланированных результатов в единый кандидат.
Производные DTO, клиенты API, OpenAPI/JSON Schema и тестовые данные не становятся отдельным
источником требований. Межрепозиторная проверка покрывает типы и обязательность
полей, `null`, enum, error contracts, совместимость версий, миграцию и сквозные
Scenarios между поставщиком и потребителями данных.

В `superspec-multirepo` независимые области репозиториев выполняются параллельно,
только когда зависимости в `tasks.md` явно это разрешают и между ними нет общего
состояния, порядка выполнения или пересекающихся файлов. Развёртывание не должно
создавать несовместимое состояние поставщика и потребителей данных.

## 8. ИФТ, Verify и дефекты

1. После объединения реализаций формируется один кандидат реализации с точными
   ревизиями и идентификатором артефакта. Это контрольная точка 2: Code PR прошли
   проверку, проверки репозиториев выполнены, зависимости сведены, кандидат развёрнут
   на ИФТ.
2. Тестировщик берёт подзадачу в работу и проверяет кандидата на ИФТ.
3. Каждый применимый Scenario из Delta Specs проверяется на этом кандидате. При
   использовании Zephyr запуск связывается с ID Scenario и идентификатором кандидата.
4. Результаты заносятся в `verify.md` через Subtask Store PR.
5. Тестировщик явно устанавливает решение человека `PASS` или `FAIL`. Агент может
   собрать подтверждения, но не принимает это решение.
6. Подзадача тестирования закрывается только после успешного Verify, `PASS` и слияния
   относящегося к ней Store PR.

Контрольная точка 2 фиксирует кандидата, но не подтверждает результат ИФТ. Новый
коммит, сборка или развёртывание создаёт нового кандидата и требует повторного
прохождения контрольной точки 2, проверки и решения человека. Для
`superspec-multirepo` Verify завершается только при Feature Acceptance `PASS` и
Process Compliance `PASS` либо `PASS_WITH_WARNINGS`; предупреждения
записываются явно.

### Классификация найденного дефекта

| Ситуация | Действие |
|---|---|
| Реализация не выполняет существующий Scenario | Создать дефект, вернуть работу в Apply, собрать нового кандидата и повторить Verify |
| Scenario отсутствует, но следует из уже принятого требования | Считать это расхождением Planning, дополнить Delta Specs через PR, повторить контрольную точку 1, Apply и Verify |
| Обнаружено новое требование | Владелец продукта решает включить его в текущую Jira Story или создать отдельные Jira Story и OpenSpec Change |

Причина дефекта — ошибка человека, агента или проверки — фиксируется отдельно и не
заменяет классификацию относительно принятой спецификации.

## 9. Archive и готовность к UAT

1. Все Code PR слиты, подзадачные Store PR объединены в Store Story branch, Verify
   завершён с `PASS`; открытой остаётся подзадача аналитика.
2. Аналитик запускает штатный OpenSpec Archive в Store subtask branch
   от Store Story branch и создаёт Subtask Store PR с результатом Archive
   обратно в Store Story branch.
3. После слияния Archive PR аналитик создаёт Story Store PR из Store Story branch в
   Integration branch Store.
4. После проверки и слияния Story Store PR аналитик закрывает свою подзадачу.
5. Когда все подзадачи закрыты, Jira Story переводится в `Ready to UAT`.

Archive фиксирует принятую после ИФТ нормативную версию требований, но не выполняет
UAT и не разрешает выпуск автоматически. Если UAT обнаружил несоответствие уже
архивированному Scenario, создаётся связанный корректирующий OpenSpec Change, а
выпуск блокируется до его прохождения. Master Specs напрямую не редактируются.

Если подключён OpenSpec Graph, команда
`openspec-orch plugin exec openspec-graph inspect --json` выполняется из Store до и
после Archive. Зависимые Changes архивируются в порядке зависимостей. Необходимая
зависимому Change ранняя синхронизация оформляется отдельным проверяемым PR; она не
доказывает реализацию или развёртывание и не заменяет Archive.

## 10. UAT и выпуск по Git Flow

1. Потребители выполняют UAT для Jira Story.
2. После успешного UAT команда проходит контрольную точку 3, а владелец продукта
   принимает решение о выпуске. Контрольная точка 3 подтверждает отсутствие
   блокирующих дефектов, готовность развёртывания, наблюдения и отката, необходимые
   меры безопасности, миграции, SLO и эксплуатационные одобрения, а также точный
   идентификатор проверенного артефакта.
3. В Store и каждом выпускаемом репозитории кода из Integration branch создаётся
   Release branch по единому принятому шаблону имени.
4. Кандидат на выпуск проходит обязательные проверки проекта.
5. Release branch сливается в Production branch и обратно в Integration branch,
   затем версия фиксируется Git-тегом.
6. Выпускается тот же артефакт, который прошёл итоговые проверки. Замена коммита,
   сборки или образа создаёт нового кандидата и требует повторного решения.

Git Flow выполняется средствами Store, Code Repositories и CI/CD. OpenSpec
Orchestrator не создаёт ветки, PR, теги, Jira-подзадачи, запуски Zephyr и Release.

Hotfix начинается от Production branch, проходит отдельный PR и обязательные проверки,
получает тег в Production branch, затем обязательно сливается обратно в
Integration branch. Если Hotfix меняет
наблюдаемое поведение, связанный OpenSpec Change и обновление Store обязательны:
срочность не отменяет трассировку требований.

## Применение процесса одним человеком

Для одиночной работы не используется сокращённый жизненный цикл: выполняются те же
10 этапов и те же проверки. Один человек может последовательно выступать владельцем
продукта, аналитиком, разработчиком и тестировщиком, но должен отдельно зафиксировать
ревизию Planning, кандидата реализации, результаты Verify, решение человека, Archive,
UAT и решение о выпуске. Совмещение ролей не превращает технические подтверждения в
автоматическое человеческое одобрение.

## Обязательные связи

Для одной поставки должна восстанавливаться цепочка:

```text
Jira Story
→ OpenSpec Change
→ подзадача Jira
→ задача OpenSpec
→ репозиторий кода и Code PR
→ ревизия реализации и артефакт
→ подтверждения Scenario и Verify
→ ревизия Archive
→ UAT
→ тег выпуска
```

## Термины

| Термин | Значение |
|---|---|
| Jira Story | Принятая владельцем продукта единица поставки, объединяющая требования, участников и подзадачи. |
| OpenSpec Change | Нормативный набор Planning-артефактов и Delta Specs, связанный с Jira Story. |
| Store | Git-репозиторий с OpenSpec Changes, Master Specs и проектным контекстом. |
| Specs Repository | Store другой команды, подключённый как источник спецификаций и контекста. |
| Code Repository | Git-репозиторий с реализацией компонента без локальной копии нормативного OpenSpec Change. |
| Store Story branch | Временная интеграционная ветка Jira Story в Store; Planning, обновления подзадач и Archive попадают в неё через PR. |
| Subtask Store PR | PR из ветки подзадачи в Store Story branch с Planning, Tasks или подтверждениями этой подзадачи. |
| Code PR | PR с реализацией подзадачи в Integration branch соответствующего Code Repository. |
| Story Store PR | Финальный PR из Store Story branch в Integration branch Store после Verify и Archive. |
| Git Flow | Единая для Store и Code Repositories модель веток Production, Integration, work, Release и Hotfix. Конкретные имена задаёт команда. |
| Кандидат реализации | Точный набор ревизий и собранных артефактов, переданный на ИФТ как единое целое. |
| Archive | Операция OpenSpec, применяющая Delta Specs к Master Specs до передачи Jira Story на UAT. |
