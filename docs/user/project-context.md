# Бизнес-контекст

`openspec/context/` в Store — единое описание продукта для всех репозиториев:
назначение, термины, участники, процессы и ограничения. Агент читает его перед
работой с Change. Контекст помогает понимать требования, но не заменяет
Requirements и Scenarios из Master Specs.

Каталог создаётся Template `default` и `initiative`. Наполняет его Extension
`project-context`.

## Структура

| Файл | Содержание |
|---|---|
| `00-start-here.md` | Короткая навигация |
| `01-product-context.md` | Назначение, участники и их цели |
| `02-domain.md` | Термины и связи между ними |
| `03-architecture.md` | Границы продукта, ответственность сторон, обмен информацией |
| `04-business-processes.md` | Начало, исполнители, крупные действия и результат процессов |
| `05-constraints.md` | Все условия: бизнес-ограничения, данные, доступ, безопасность |
| `ADR/` | Принятые значимые решения с причинами и альтернативами |
| `_raw/` | Исходные материалы для наполнения |

Каждый факт записывается в одном месте: участники — в 01, термины — в 02,
условия — в 05. Новая редакция заменяет старую, закрытые вопросы удаляются.
Разделы ссылаются друг на друга, но не на файлы из `_raw/`. Роли команды и правила
поставки в бизнес-контекст не входят.

## Заполнение и обновление

Откройте сессию агента из корня Store и вызовите команду:

| Агент | Первое заполнение | Обновление |
|---|---|---|
| Claude | `/project-context:project-context initialize` | `/project-context:project-context update` |
| Qwen, GigaCode | `/project-context initialize` | `/project-context update` |

Без указания режима агент выберет `initialize` для пустого шаблона и `update`,
если сведения уже есть. Проверка согласованности входит в оба режима.

Источники можно ограничить: `--change <change-id>`, `--spec <capability-path>`,
`--domain <domain-path>`; параметры можно повторять. Change и Specs для первого
заполнения не нужны.

Как идёт работа:

1. Агент читает текущий контекст и материалы, сообщает, что нашёл.
2. Задаёт по одному вопросу о пробелах; любой вопрос можно пропустить.
3. Показывает фрагмент «до» и полный текст «после».
4. После вашего подтверждения записывает только эти замены и проверяет ссылки и
   повторы.
5. Итог: сохранённые разделы, ADR, оставшиеся вопросы и непрочитанные источники.

Неподтверждённые сведения записываются как TODO: что выяснить, у кого и по какому
источнику. Файл в `_raw/` не означает, что сведения приняты.

В метаданных разделов `owner` — владелец раздела (`unassigned`, если неизвестен),
`updated` — дата фактического изменения. Это не подтверждение того, что все
сведения приняты.

## ADR

Один файл — одно принятое решение о границах продукта, ответственности,
взаимодействиях или ограничениях. Имя — `NNNN-short-title.md`, шаблон — в
`context/ADR/README.md`. Change для ADR не нужен. Текущее состояние остаётся в
тематическом разделе, ADR объясняет выбор. Непринятое предложение остаётся вопросом.

## Store, созданный до появления project-context

Подключите Extension из корня Store и перезапустите агента:

```bash
openspec-orch extension init project-context
openspec-orch extension connect project-context
```

Прежняя команда `spec-driven-extended-context` больше не поставляется. Перенос
уже заполненного контекста в новую структуру — отдельное согласованное изменение
Store: сохраните существующие знания, проверьте входящие ссылки и не переименовывайте
файлы молча. Обновление файлов Template — по [миграции Store](maintenance.md#миграция-store).
