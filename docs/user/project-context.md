# Бизнес-контекст приложения

Контекст объясняет бизнес приложения и не зависит от количества репозиториев.
Реализация из frontend, gateway и backend или из множества отдельных микросервисов
может использовать один и тот же бизнес-контекст. Каталог репозиториев, компонентов
и внутренние технические схемы в него не входят.

## Основные разделы

Пути относительны к `openspec/context/` центрального Store.

| Раздел | Единственный предмет раздела |
|---|---|
| `01-product-context.md` | Проблема, ценность, участники и их цели |
| `02-domain.md` | Бизнес-термины и смысловые отношения |
| `03-architecture.md` | Ответственность приложения среди внешних участников и систем |
| `04-business-processes.md` | Крупные шаги достижения бизнес-результата |
| `05-constraints.md` | Применимые бизнес-условия, данные, доступ и кибербезопасность |

`00-start-here.md` задаёт навигацию и общие правила; нумерация контекста — `00–05`.
Контекст содержит описание бизнеса и правила его оформления. Вызовы команд и
порядок работы агента принадлежат Extension; навигация к ним находится в `STORE.md`.
Согласования и поставка находятся отдельно: `openspec/process/quality-gates.md` и
`openspec/process/release-process.md`. Принятые правила существующего проекта сохраняются. `ADR/` используется
для причин принятых решений о бизнес-границах и ограничениях, `_raw/` — для
ещё не подтверждённых материалов. Технические ADR ведутся вне бизнес-контекста.

Словарь и смысловая модель объединены в `02`. Вместо отдельной модели с нормативными
переходами появился обзор бизнес-процессов `04`. Старый `06-cross-system-invariants.md`
убран: проверяемые обязательства приложения принадлежат Master Specs.

## Где архитектура и кибербезопасность

В `03-architecture.md` добавляйте бизнес-архитектуру: где заканчивается ответственность
приложения, что делает внешний участник и какая бизнес-информация между ними передаётся.
Например, приложение координирует услугу, исполнитель выполняет работу, платёжный
оператор проводит платёж. Диаграмма размещается прямо в контексте. Реестр микросервисов,
API, очереди, таблицы БД и сетевые настройки здесь не описываются.

В `05-constraints.md` добавляйте применимые ограничения, включая кибербезопасность,
на уровне данных, доступа, целей использования и разрешённых действий. Сохраняйте
условие целиком, его применимость, текстовые реквизиты происхождения и подтверждение
уполномоченного владельца. Технический способ выполнения условия не становится
частью бизнес-контекста.

## Разделение без дублирования

Участник определяется в `01`, термин — в `02`, внешняя граница — в `03`, последовательность
действий — в `04`, ограничение — в `05`. В остальных местах используются только
внутренние ссылки. Например, процесс ссылается на ограничение данных, но не повторяет его.

Контекст объясняет смысл; Master Specs задают проверяемые обязательства. Обзор процесса
не копирует Scenarios, формулы, ветвления ошибок и критерии приёмки. Изменение требования
проходит через Change. Отсутствие Spec не отменяет внешнюю политику; конфликт или пробел
требует решения владельца.

## Самодостаточность

Все ссылки, изображения и включения ведут только внутрь `openspec/context/`.
Ссылки на Specs, Changes, код, внешние документы и URL не допускаются. Внешний материал
можно прочитать при сборе знаний, но нужное подтверждённое содержание переносится
внутрь. Название, пункт, версия/дата и подтверждение сохраняются текстом, без URL и пути.
Если материал недоступен для переноса — явный TODO, а не видимость заполненного раздела.

Большую бизнес-тему можно разделить на документы внутри `architecture/`, `processes/`
или `constraints/`, оставив в основном разделе только навигацию. Количество документов
определяется сложностью бизнеса, а не количеством репозиториев.

## Наполнение и проверка

Команда `/spec-driven-extended-context` поддерживает initialize, audit и update.
Initialize начинает с бизнес-разделов; ADR требует соответствующей цели.
Документы процесса команды эта команда не изменяет. Наличие Specs не является
условием описания нового приложения. Selectors задают
источники чтения, но не разрешают сохранять ссылки наружу.

Неизвестное — TODO с `question`, `owner`, `expected_source`; неприменимость обоснуйте.
Audit не пишет файлы, initialize/update показывают diff перед подтверждением.
Изменение числа репозиториев без изменения бизнеса не требует обновления контекста.
Это инструкции агенту, а не программный запрет произвольного редактирования Store.

Без указанного режима команда выбирает initialize для незаполненного шаблона:
заголовки, инструкции и TODO не считаются фактами проекта. Если уже есть описание
бизнеса, выбирается audit. Явный режим имеет приоритет.

Перед интервью агент просматривает состав `_raw/`, читает материалы в выбранной
области и сопоставляет утверждения с текущим контекстом. Исходники сохраняются;
непрочитанные файлы и причины пропуска попадают в отчёт. Наличие текста в `_raw/`
не делает его подтверждённым фактом. Затем initialize/update задаёт по одному вопросу
о недостающих сведениях, не повторяя вопросы, на которые уже есть подтверждённый ответ.
Audit возвращает вопросы и замечания без обязательного интервью.

Отчёт содержит `coverage` для каждого из пяти разделов: подтверждено для выбранной
цели (`confirmed`), есть пробелы (`gaps`), обоснованно неприменимо (`not_applicable`)
или вне области проверки (`out_of_scope`). `findings` перечисляет нарушения ссылок,
дублирование и сведения, требующие отдельного Change. Неразрешённые вопросы не
позволяют объявить контекст актуальным; согласованная запись TODO также не означает,
что все знания собраны.

## Перенос существующего Store

Template копируется при первом init; повторный init и connect не мигрируют context.
Существующие Store этим изменением не затрагиваются. Перенос выполняется отдельным
проверяемым Store PR с сохранением принятых правил.

1. Учтите факты и входящие ссылки. Не заменяйте заполненные документы пустыми шаблонами.
2. Объедините определения и смысловые отношения старых `02-domain-glossary.md` и
   `04-domain-model.md` в `02-domain.md`; общий ход работы бизнеса поместите в новый `04`.
3. Из `03` оставьте бизнес-границы и внешние взаимодействия. Не удаляйте единственные
   технические знания молча: согласуйте их сохранение вне бизнес-контекста, включая
   технические ADR.
4. Из старых `05-security-and-compliance.md` и `06` перенесите применимые бизнес-условия
   в `05-constraints.md`. Нормативные продуктовые правила требуют проверки принятой
   Spec или отдельного Change; команда context сама их не принимает.
5. Замените внешние ссылки перенесённым допустимым содержанием и внутренними ссылками;
   недоступное отметьте как пробел. Перенесите старые `07-quality-gates.md` и
   `08-release-process.md` в `openspec/process/quality-gates.md` и
   `openspec/process/release-process.md`, сохранив реальные роли, Gate и Git Flow.
   Обновите пути в установленной конфигурации, schemas и инструкциях Store.
6. Обновите навигацию. Удаляйте старые файлы после проверки каждой записи и входящих
   ссылок. Обновите установленный Extension и выполните audit. Отчёт read_sources
   с внешними источниками не копируйте в context.
