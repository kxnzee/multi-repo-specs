Этот файл заполняется наблюдаемыми фактами после каждого реального Change пилота.
До ревизии пилота здесь не проектируются решения и не расширяется scope пилота.

Если на одном из трёх вопросов проблем не было, явно напишите «не наблюдалось».

До ревизии пилота изменение Core допустимо только для подтверждённого нарушения
текущего контракта или блокирующего кейса. Новые возможности записываются в
`BACKLOG.md`, но не реализуются.

## Подтверждённые дефекты до пилота

### 2026-08-23 — candidate Plugin commands нарушали два сохранённых CLI-контракта

- Шаг runbook: повторный аудит переноса Change Tracking в Plugin API.
- Наблюдаемый факт: повтор scalar option завершался обычным `Error`, а `status` после
  отключения Plugin от Store блокировался до чтения сохранённой истории.
- Нарушает ли факт текущий контракт: да — формат CLI-ошибок и read-only status должны
  сохраняться при архитектурной миграции.
- Блокирует ли факт продолжение пилота: да — candidate нельзя сравнивать с legacy.
- Где пришлось руками переносить контекст: не наблюдалось.
- Где пользователь сомневался или боялся ошибиться: зелёные unit tests скрывали оба
  расхождения.
- Решение в Core: parser errors нормализуются Commander, а read-only command явно
  запрашивает context без обязательного Repository binding.

### 2026-08-22 — CodeGraph Plugin не был доступен агенту через MCP

- Шаг runbook: запуск агента после `plugin init codegraph` и подключения Code
  Repository.
- Наблюдаемый факт: Package умел индексировать Repository через свой CLI, но не
  регистрировал bundled MCP server и не добавлял агенту правило использования графа.
- Нарушает ли факт текущий контракт: да — установленный CodeGraph Plugin должен быть
  нативно доступен выбранному при `init` агенту без отдельной ручной установки.
- Блокирует ли факт продолжение пилота: да — агент не видел `codegraph_explore` и
  неизбежно возвращался к полному чтению Repository.
- Где пришлось руками переносить контекст: Agent ID и provider-specific MCP config
  приходилось повторно определять вне Orchestrator.
- Где пользователь сомневался в следующем действии: должен ли MCP настраиваться
  вручную после каждого `plugin init`.
- Где пользователь боялся ошибиться: глобальный launcher мог использовать другую
  версию Node.js или исчезнуть после переключения runtime.
- Решение в Core: `init` сохраняет Agent ID, а generic Plugin lifecycle вызывает
  необязательные `agent.install`/`agent.remove` hooks для зарегистрированных агентов.
- Решение в Plugin: CodeGraph Package сам владеет adapters, project-local MCP config,
  инструкциями и абсолютным bundled launcher; Core и Template не знают его форматов.
- Регрессия: тесты проверяют несколько агентов, сохранение чужих настроек,
  идемпотентность, удаление и отказ до установки при пустом списке `agents`.

### 2026-08-22 — новый Plugin требовал ручной сборки файлов и правок рядом с Core

- Шаг runbook: добавление второго самостоятельного Plugin Package после CodeGraph.
- Наблюдаемый факт: контракт Package был описан только документацией; автору нужно
  было вручную создать согласованные `package.json`, `plugin.yaml`, entrypoint и
  каталог, а базовый Template всё ещё содержал интеграцию конкретного Plugin.
- Нарушает ли факт текущий контракт: да — Plugins и Template должны быть независимы,
  а новый Plugin не должен требовать ветки или файла по его ID в Core.
- Блокирует ли факт продолжение пилота: да — следующий Plugin нельзя было добавить
  через единый воспроизводимый интерфейс.
- Где пришлось руками переносить контекст: автору приходилось сверять структуру с
  существующим Plugin и общей документацией Core.
- Где пользователь сомневался в следующем действии: какие файлы обязательны и где
  должна находиться точка входа.
- Где пользователь боялся ошибиться: случайно добавить Plugin-specific код в `src/`
  или связать Plugin с Project Template.
- Решение: универсальный `plugin register` создаёт отдельный готовый Package;
  специализированные документация и тесты находятся внутри Package, а Core и
  Template защищены boundary-тестами от упоминаний конкретного Plugin.

### 2026-08-22 — встроенный CodeGraph зависел от глобального PATH

- Шаг runbook: реальный Plugin E2E после переключения на поддерживаемую версию Node.js.
- Наблюдаемый факт: `plugin connect codegraph` завершился `spawn codegraph ENOENT`,
  хотя CodeGraph был установлен для предыдущей NVM-версии Node.js; повторный запуск
  работал только после ручного добавления старого npm bin в `PATH`.
- Нарушает ли факт текущий контракт: да — встроенный Plugin поставлялся Orchestrator,
  но требовал отдельной глобальной установки и настройки окружения пользователя.
- Блокирует ли факт продолжение пилота: да — чистая установка Orchestrator не могла
  выполнить первый `connect` встроенного CodeGraph.
- Где пришлось руками переносить контекст: пришлось искать установку CodeGraph другой
  версии Node.js и вручную подменять `PATH` для Plugin E2E.
- Где пользователь сомневался в следующем действии: нужно ли отдельно устанавливать
  CodeGraph каждому участнику команды.
- Где пользователь боялся ошибиться: смена активной версии Node.js незаметно ломала
  уже подключённый Plugin.
- Решение: вынести CodeGraph в самостоятельный `@openspec-orch/plugin-codegraph`,
  передать ему runtime dependency и launcher, а Core оставить generic; descriptor и
  CLI пользовательских Plugins не менять.
- Регрессия: интеграционный тест подтверждает запуск Package entrypoint через
  `process.execPath`, а не executable `codegraph` из `PATH`.

### 2026-08-22 — ревью первого Plugin demo выявило ложный lifecycle и небезопасный cache path

- Шаг runbook: ревью незакоммиченной реализации Plugin lifecycle и CodeGraph package.
- Наблюдаемый факт: descriptor без `connect`/`status` считался рабочим, `help` можно
  было зарегистрировать как Plugin ID, а symlink внутри Store-local cache path позволял
  направить установку за пределы Store.
- Нарушает ли факт текущий контракт: да — binding должен записываться только после
  успешного setup, публичный CLI должен сохраняться, cache остаётся локальным Store.
- Блокирует ли факт продолжение пилота: да — дефекты затрагивают первый Plugin demo.
- Где пришлось руками переносить контекст: фильтры status и интерактивный выбор
  repositories обходили общий `ProjectModel` и повторно читали структуру config.
- Где пользователь сомневался в следующем действии: ревью потребовало определить,
  считать ли отсутствующий lifecycle успешной операцией или неподдерживаемой.
- Где пользователь боялся ошибиться: установка пользовательского Plugin могла записать
  данные не в заявленный Store-local cache.
- Решение в Core: обязательные `connect`/`status`, безопасный cache path, единый registry
  CLI tokens и полный routing Repository/Plugin operations через `ProjectModel`.

### 2026-08-18 — штатный `/opsx:apply` не получает repository scope текущего Cycle

- Проверка: первый реальный multi-repository Change
  `jit-002-moderated-visitor-promotion` после принятия Planning и создания Cycle.
- Наблюдаемый факт: `openspec instructions apply --json` из подключённого Code
  Repository возвращает общий список Tasks Change, а существующий
  `openspec-orch status` не работает из Code Repository и не имеет JSON-контракта,
  по которому агент мог бы подтвердить текущий repository-id и его участие в Cycle.
- Нарушает текущий контракт: да — Code Repository подключён официальным OpenSpec
  pointer, но штатный `/opsx:apply` нельзя безопасно ограничить его частью Tasks.
- Блокирует продолжение пилота: да — разработчик либо должен обходить штатный Apply,
  либо рискует выполнить задачи другого репозитория.
- Решение: не добавлять новую операцию и не изменять штатный `/opsx:apply`; расширить
  существующий `status` опцией `--json`, разрешать Store через pointer Code Repository
  и передавать repository-scoped правила через Project Template skill.
- Регрессия: CLI-тест JSON-опции, тест identity текущего checkout и Template-тест
  repository-scoped Apply-контракта.

### 2026-08-16 — повторный `init` после ошибки Store registry

- Проверка: smoke-test базового Template с выбранным `--agent`.
- Наблюдаемый факт: `openspec store setup` завершился ошибкой
  `store_registry_busy`, но официальный agent pack и `openspec/config.yaml`
  остались в целевом репозитории.
- Нарушает текущий контракт: да — повторный `openspec-orch init` блокировался
  собственными частичными артефактами первого запуска.
- Блокирует продолжение пилота: да, если Store metadata ещё не создана.
- Решение: при ошибке до появления Store metadata удалять только agent-pack paths
  и `openspec/config.yaml`, созданные текущим запуском; существовавшие до запуска
  файлы не удалять. Состояние с уже созданной metadata по-прежнему переводить в
  явный `needs_recovery` без автоматического ремонта.
- Регрессия: интеграционный тест воспроизводит ошибку, проверяет очистку и
  успешный повторный запуск.

## Подтверждённые наблюдения до пилота

### 2026-08-18 — runtime Orchestrator был ниже требования OpenSpec

- Шаг runbook: подготовка комплекта для переноса в закрытый контур.
- Наблюдаемый факт: Orchestrator объявлял Node.js `20.5+`, а рекомендуемый и
  проверенный OpenSpec `1.7.0` требует Node.js `20.19.0+`. На Node.js `20.13.1`
  внутренние тесты и основные команды запускались, хотя связка находилась вне
  поддерживаемого runtime OpenSpec.
- Нарушает ли факт текущий контракт: да — заявленная нижняя граница не учитывала
  обязательную внешнюю CLI-зависимость.
- Блокирует ли факт продолжение пилота: да для воспроизводимого переноса в закрытый
  контур; runtime комплект нельзя считать поддерживаемым.
- Где пришлось руками переносить контекст: требование OpenSpec пришлось отдельно
  сопоставить с `package.json`, README и фактической версией Node.js.
- Где пользователь сомневался в следующем действии: какую версию Node.js переносить
  вместе с Orchestrator.
- Где пользователь боялся ошибиться: зелёные тесты могли быть ошибочно приняты за
  подтверждение поддерживаемой runtime-комбинации.
- Решение в Core: единая граница `20.19.0+` в package metadata и README, ранний
  отказ binary и regression test для Node.js `20.18.0`.

### 2026-08-18 — обязательный Cycle блокирует упрощённый OpenSpec flow

- Шаг runbook: повторное использование Project Template после первого полного
  multi-repository Change.
- Наблюдаемый факт: `openspec-orch init` и `connect` полезны для установки Project
  Template и подключения репозиториев, но Apply skill блокировал любой Change без
  Cycle, даже когда пользователь осознанно хотел обычный OpenSpec flow.
- Нарушает ли факт текущий контракт: нет — строгий Cycle соответствовал пилотному
  flow, но делал Orchestrator обязательным для каждого Change.
- Блокирует ли факт продолжение пилота: нет.
- Где пришлось руками переносить контекст: не наблюдалось.
- Где пользователь сомневался в следующем действии: можно ли после `init` и `connect`
  не использовать `assign`, Receipts и Snapshot.
- Где пользователь боялся ошибиться: стандартный `/opsx:apply` мог оказаться жёстко
  заблокированным добавленным Template.
- Повторяется ли наблюдение из предыдущих Changes: пока неизвестно.
- Решение в Template: только `CYCLE_NOT_FOUND` открывает выбор standard/orchestrated;
  существующий или неисправный Cycle сохраняет строгие guardrails.

- Нарушает ли факт текущий контракт: да — project Apply skill разрешал checkbox
  только после evidence, но не задавал проверяемую форму evidence и финальный audit.
- Блокирует ли факт продолжение пилота: нет — Verification Receipt честно записан как
  `fail`, но happy path требует исправления.
- Где пришлось руками переносить контекст: пользователь вручную сопоставил finding
  Verify с checkbox Tasks и Result Receipt.
- Где пользователь сомневался в следующем действии: было неясно, должен ли Verify сам
  снимать checkbox и нужно ли запускать его после каждой задачи.
- Где пользователь боялся ошибиться: при выборе между повторным Verify и возвратом

- Повторяется ли наблюдение из предыдущих Changes: пока неизвестно.
- Решение в Template: task-level `task_evidence`, обязательная проверка test-файла и
