## Подтверждённые дефекты до пилота

### 2026-08-18 — штатный `/opsx:apply` не получает repository scope текущего Cycle

- Проверка: первый реальный multi-repository Change
  `jit-002-moderated-visitor-promotion` после принятия Planning и создания Cycle.
- Наблюдаемый факт: `openspec instructions apply --json` из подключённого Code
  Repository возвращает общий список Tasks Change, а существующий
  `openspec-orch status` не работает из Code Repository и не имеет JSON-контракта,
  по которому агент мог бы подтвердить текущий repository-id и его участие в Cycle.
- Нарушает текущий контракт: да — Code Repository подключён официальным OpenSpec
  pointer, но штатный `/opsx:apply` нельзя безопасно ограничить его частью Tasks.
- Блокирует продолжение пилота: да — разработчик либо должен обходить штатный Apply,
  либо рискует выполнить задачи другого репозитория.
- Решение: не добавлять новую операцию и не изменять штатный `/opsx:apply`; расширить
  существующий `status` опцией `--json`, разрешать Store через pointer Code Repository
  и передавать repository-scoped правила через Project Template skill.
- Регрессия: CLI-тест JSON-опции, тест identity текущего checkout и Template-тест
  repository-scoped Apply-контракта.

### 2026-08-16 — повторный `init` после ошибки Store registry

- Проверка: smoke-test базового Template с выбранным `--agent`.
- Наблюдаемый факт: `openspec store setup` завершился ошибкой
  `store_registry_busy`, но официальный agent pack и `openspec/config.yaml`
  остались в целевом репозитории.
- Нарушает текущий контракт: да — повторный `openspec-orch init` блокировался
  собственными частичными артефактами первого запуска.
- Блокирует продолжение пилота: да, если Store metadata ещё не создана.
- Решение: при ошибке до появления Store metadata удалять только agent-pack paths
  и `openspec/config.yaml`, созданные текущим запуском; существовавшие до запуска
  файлы не удалять. Состояние с уже созданной metadata по-прежнему переводить в
  явный `needs_recovery` без автоматического ремонта.
- Регрессия: интеграционный тест воспроизводит ошибку, проверяет очистку и
  успешный повторный запуск.

## Подтверждённые наблюдения до пилота

### 2026-08-18 — runtime Orchestrator был ниже требования OpenSpec

- Шаг runbook: подготовка комплекта для переноса в закрытый контур.
- Наблюдаемый факт: Orchestrator объявлял Node.js `20.5+`, а рекомендуемый и
  проверенный OpenSpec `1.7.0` требует Node.js `20.19.0+`. На Node.js `20.13.1`
  внутренние тесты и основные команды запускались, хотя связка находилась вне
  поддерживаемого runtime OpenSpec.
- Нарушает ли факт текущий контракт: да — заявленная нижняя граница не учитывала
  обязательную внешнюю CLI-зависимость.
- Блокирует ли факт продолжение пилота: да для воспроизводимого переноса в закрытый
  контур; runtime комплект нельзя считать поддерживаемым.
- Где пришлось руками переносить контекст: требование OpenSpec пришлось отдельно
  сопоставить с `package.json`, README и фактической версией Node.js.
- Где пользователь сомневался в следующем действии: какую версию Node.js переносить
  вместе с Orchestrator.
- Где пользователь боялся ошибиться: зелёные тесты могли быть ошибочно приняты за
  подтверждение поддерживаемой runtime-комбинации.
- Решение в Core: единая граница `20.19.0+` в package metadata и README, ранний
  отказ binary и regression test для Node.js `20.18.0`.

### 2026-08-18 — обязательный Cycle блокирует упрощённый OpenSpec flow

- Шаг runbook: повторное использование Project Template после первого полного
  multi-repository Change.
- Наблюдаемый факт: `openspec-orch init` и `connect` полезны для установки Project
  Template и подключения репозиториев, но Apply skill блокировал любой Change без
  Cycle, даже когда пользователь осознанно хотел обычный OpenSpec flow.
- Нарушает ли факт текущий контракт: нет — строгий Cycle соответствовал пилотному
  flow, но делал Orchestrator обязательным для каждого Change.
- Блокирует ли факт продолжение пилота: нет.
- Где пришлось руками переносить контекст: не наблюдалось.
- Где пользователь сомневался в следующем действии: можно ли после `init` и `connect`
  не использовать `assign`, Receipts и Snapshot.
- Где пользователь боялся ошибиться: стандартный `/opsx:apply` мог оказаться жёстко
  заблокированным добавленным Template.
- Повторяется ли наблюдение из предыдущих Changes: пока неизвестно.
- Решение в Template: только `CYCLE_NOT_FOUND` открывает выбор standard/orchestrated;
  существующий или неисправный Cycle сохраняет строгие guardrails.

### 2026-08-18 — Apply отметил test-задачу выполненной без test-артефакта

- Шаг runbook: Development и последующий штатный `/opsx:verify` для
  `jit-002-moderated-visitor-promotion`.
- Наблюдаемый факт: Apply переключил task 6.1 в `[x]`, хотя diff `jitsi-web` не
  содержал требуемого unit test; Verify корректно обнаружил несоответствие как
  critical finding.
- Нарушает ли факт текущий контракт: да — project Apply skill разрешал checkbox
  только после evidence, но не задавал проверяемую форму evidence и финальный audit.
- Блокирует ли факт продолжение пилота: нет — Verification Receipt честно записан как
  `fail`, но happy path требует исправления.
- Где пришлось руками переносить контекст: пользователь вручную сопоставил finding
  Verify с checkbox Tasks и Result Receipt.
- Где пользователь сомневался в следующем действии: было неясно, должен ли Verify сам
  снимать checkbox и нужно ли запускать его после каждой задачи.
- Где пользователь боялся ошибиться: при выборе между повторным Verify и возвратом
  конкретной задачи в Apply.
- Повторяется ли наблюдение из предыдущих Changes: пока неизвестно.
- Решение в Template: task-level `task_evidence`, обязательная проверка test-файла и
  успешного запуска, финальный `repository_completion`; встроенный Verify не изменён.

### 2026-08-17 — ожидание создания Store по `--store`

- Шаг runbook: подготовка Store перед подключением workspace.
- Наблюдаемый факт: пользователь выполнил из корня workspace
  `openspec-orch init --agent claude --store specs`, ожидая, что `--store specs`
  создаст одноимённый каталог Store. CLI использовал текущий каталог как target и
  безопасно отказал из-за пересечения target root со встроенным Template root.
- Нарушает ли факт текущий контракт: нет — `--store` задаёт Store ID, а target
  передаётся отдельным позиционным аргументом и должен быть существующим Git checkout.
- Блокирует ли факт продолжение пилота: нет — Store можно заранее подготовить и
  передать его путь в `init`.
- Где пришлось руками переносить контекст: пришлось отдельно сопоставить Store ID,
  target path и требование существующего Git checkout.
- Где пользователь сомневался в следующем действии: было неясно, создаёт ли `init`
  каталог Store и можно ли разместить OpenSpec в checkout Orchestrator.
- Где пользователь боялся ошибиться: не наблюдалось.
- Повторяется ли наблюдение из предыдущих Changes: пока неизвестно.

### 2026-08-17 — информационный баннер OpenSpec показан как предупреждение

- Шаг runbook: подключение Store и Code Repositories.
- Наблюдаемый факт: успешный `openspec-orch connect` трижды пометил строку
  `Using OpenSpec root: specs (...)` как «Предупреждение OpenSpec» — для Store и
  двух Code Repositories. OpenSpec выводит этот штатный информационный баннер в
  `stderr`; Doctor сообщил `metadata ok`, а итоговый `connect_status` был `ready`.
- Нарушает ли факт текущий контракт: нет — Core сейчас показывает любой успешный
  `stderr` как предупреждение.
- Блокирует ли факт продолжение пилота: нет.
- Где пришлось руками переносить контекст: пришлось сопоставить баннер OpenSpec,
  успешный exit и итоговую диагностику Orchestrator.
- Где пользователь сомневался в следующем действии: пользователь отдельно уточнил,
  означает ли предупреждение проблему подключения.
- Где пользователь боялся ошибиться: не наблюдалось.
- Повторяется ли наблюдение из предыдущих Changes: пока неизвестно.
