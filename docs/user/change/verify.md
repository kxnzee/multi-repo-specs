# 3. Verify

Verify подтверждает, что собранный кандидат выполняет каждый Scenario из принятых
Delta Specs. На выходе получаются `verify.md` и решение человека. Выполняется в Store-сессии.

[← Apply](apply.md) · [Дальше: Archive →](archive.md)

## Перед началом

- Apply завершён во всех назначенных репозиториях: все задачи отмечены, проверки
  выполнены.
- Есть кандидат реализации с точными ревизиями и идентификатором сборки или
  развёртывания.
- Кандидат развёрнут в среде, где его можно проверить.

Пустой `verify.md` до завершения Apply не создаётся.

## Запуск

Из Store-сессии вызовите `/opsx:verify <change-id>` (Claude) или
`/opsx-verify <change-id>` (Qwen, GigaCode). Агент:

1. превращает каждый Scenario в воспроизводимые ручные шаги и ожидаемый результат;
2. собирает итоги автоматических проверок (тип, количество, общий статус);
3. запускает `openspec validate <change-id> --strict --no-interactive`;
4. оставляет решение человека в `PENDING`.

`verify.md` пишется для человека: без путей, коммитов, ссылок на CI и журналов агента.

## Решение человека

Проверяющий проходит сценарии на кандидате и выставляет `PASS` или `FAIL`.

- `PASS`: есть выполненное подтверждение ожидаемого поведения.
- `FAIL`: поведение нарушено.
- `PENDING`: подтверждения нет или оно устарело.
- `N/A`: только с обоснованием неприменимости.

Агент может собрать подтверждения, но не принимает решение. Для
`superspec-multirepo` Verify завершается только при Feature Acceptance `PASS` и
Process Compliance `PASS` или `PASS_WITH_WARNINGS`; предупреждения записываются.

## Если что-то не так

| Ситуация | Что делать |
|---|---|
| Кандидат не собран | Сначала завершить [Apply](apply.md) |
| Код не выполняет существующий Scenario | Дефект: вернуться в Apply, собрать нового кандидата, повторить Verify |
| Scenario отсутствует, но следует из принятого требования | Дополнить Delta Specs в [Planning](planning.md), заново принять план, затем Apply и Verify |
| Найдено новое требование вне scope | Владелец продукта решает: расширить текущую задачу или создать новый Change |
| Артефакты Planning разошлись с результатом | Вернуться к артефакту, где принято решение, и повторить зависимые этапы |
| После проверки появился новый коммит, сборка или развёртывание | Это новый кандидат: подтверждения устарели, Verify повторяется |

Причина дефекта (ошибка человека, агента или проверки) записывается отдельно и не
заменяет эту классификацию.
