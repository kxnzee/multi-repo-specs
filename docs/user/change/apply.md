# 2. Apply

На этапе Apply принятый план реализуется в репозиториях кода. Для каждого назначенного
репозитория открывается своя сессия агента, и она меняет код только этого репозитория.

**Кто:** разработчик, которому назначена подзадача по этому репозиторию ([роли](../story-delivery-process.md#роли)).

[← Planning](planning.md) · [Дальше: Verify →](verify.md)

## Перед началом

- Planning принят: Delta Specs, Repository Impact и Tasks согласованы.
- Репозиторий, в котором вы работаете, указан в Repository Impact и имеет свою
  секцию в `tasks.md`.
- Если Planning не закоммичен в Store, сделайте это: так ссылка на план будет
  воспроизводимой.

## Запуск

Закройте Store-сессию. Перейдите в назначенный репозиторий и откройте новую сессию
агента из его корня:

```bash
cd /absolute/path/to/workspace/src/frontend
gigacode
```

В сессии вызовите `/opsx-apply <change-id>`. Агент выполнит только задачи секции текущего репозитория.

Если Change затрагивает несколько репозиториев, повторите запуск в каждом из них
отдельной сессией.

## По ходу работы

| Ситуация | Что делать |
|---|---|
| Задача выполнена, проверки прошли | Отметить задачу и сохранить конкретное подтверждение |
| Задача заблокирована или проверка не прошла | Оставить задачу открытой и записать причину |
| Найден новый репозиторий, capability или изменение scope | Остановить Apply, вернуться в [Planning](planning.md) и принять его заново |
| Текущий репозиторий не совпадает с Repository Impact или Tasks | Не продолжать: исправить Planning или открыть сессию в нужном репозитории |
| Apply запущен из Store, и защита запретила запись в код | Не расширять права; открыть сессию в репозитории кода и повторить |
| Области репозиториев независимы | В `superspec-multirepo` можно работать параллельно, если это разрешают зависимости в Tasks |
| Есть зависимость или общие файлы | Работать последовательно в порядке Tasks |
| CodeGraph недоступен или устарел | Искать адресно в текущем репозитории; `sync` не запускать автоматически |

Отмеченные галочки сами по себе не доказывают готовность: нужны выполненные
проверки репозитория.

## Результат

- Код в каждом назначенном репозитории закоммичен, проверки репозитория пройдены.
- Задачи в `tasks.md` отмечены, у каждой есть подтверждение.
- Собран один кандидат реализации: точные ревизии всех репозиториев и
  идентификатор сборки или развёртывания. Имени ветки или «последнего коммита»
  недостаточно.

Межрепозиторная проверка охватывает общие контракты: типы и обязательность полей,
`null`, enum, ошибки, совместимость версий, миграции и сквозные сценарии между
поставщиком и потребителями данных.

## Связь задач с коммитами

Если подключён плагин [Change Tracking](../../plugins/change-tracking.md), он
связывает задачу OpenSpec с коммитом реализации:

```bash
openspec-orch plugin exec --repo specs change-tracking start <change-id> <task-id>
# работа и обычный commit
openspec-orch plugin exec --repo specs change-tracking complete <change-id> <task-id>
```

Плагин не отмечает задачи и не меняет OpenSpec: состояние задачи по-прежнему
определяет галочка в `tasks.md`.
