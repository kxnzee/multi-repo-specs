# 1. Planning

Planning отвечает на вопросы: что меняется, почему, какие требования затронуты,
какие репозитории нужно менять и как проверить результат. Все шаги выполняются в
сессии агента, открытой из корня Store. Код на этом этапе не меняется.

[← Обзор этапов](README.md) · [Дальше: Apply →](apply.md)

## Перед началом

1. В `openspec/context/` есть достаточный для задачи
   [бизнес-контекст](../project-context.md).
2. Есть принятый запрос: Jira Story или согласованный Intent. Понятны наблюдаемый
   результат, границы доработки и то, что должно сохраниться.
3. Найдены затронутые Master Specs: `openspec/specs/<capability>/spec.md`.

| Ситуация | Что делать |
|---|---|
| Затронутое поведение описано в актуальной Master Spec | Создать Change и описать дельту относительно неё |
| Поведение уже работает, но Master Spec нет | Сначала принять [baseline](#baseline-для-уже-работающего-поведения), затем Planning |
| Добавляется новая capability | Создать Change с `ADDED Requirements`; baseline не нужен |
| Новая возможность расширяет существующую capability | Использовать её текущий путь, добавить и изменить нужные Requirements |
| Код расходится с принятым Requirement | Завести дефект или получить решение об изменении контракта; Master Spec под код не переписывать |
| В Master Spec отсутствует или устарел `Purpose` | Исправить отдельной операцией в Store, не попутно в Delta Specs |

## Создание Change

```bash
openspec new change add-sms-recovery --schema spec-driven-extended
openspec status --change add-sms-recovery
```

Дальше агент готовит артефакты по одному: `/opsx-continue add-sms-recovery`. Перед каждым
артефактом он читает `openspec instructions`, а после проверяет статус.

| Статус | Что делать |
|---|---|
| Доступен один артефакт | Подготовить его по инструкциям |
| Доступны несколько | Человек выбирает один; порядок не угадывается |
| Артефакт `blocked` | Устранить причину или получить решение владельца |

## Что куда записывается

| Файл | Содержание |
|---|---|
| `intake.md` | Источник запроса, аналитический контекст, подтверждённые уточнения. Остаётся актуальным на всех этапах |
| `proposal.md` | Зачем нужно изменение, целевое поведение, scope, Non-Goals, Repository Impact |
| `specs/<capability>/spec.md` | Delta Specs: новые, изменённые, удалённые или переименованные Requirements |
| `design.md` | Архитектура, публичные контракты, решения, риски, совместимость |
| `tasks.md` | Задачи по репозиториям кода и способ проверки каждой |

Proposal и Specs готовятся только в Store. В Repository Impact попадают только
зарегистрированные репозитории кода, в которых планируются изменения.

### Intake

| Состояние в Intake | Что делать |
|---|---|
| `readiness: ready`, `next_stage: proposal` | Перейти к Proposal |
| `readiness: not_ready`, есть исследовательские вопросы | Выполнить только указанный Explore и вернуть результаты в `intake.md` |
| `readiness: not_ready`, есть блокирующие вопросы | Остановиться и получить решение владельца продукта |
| Intake уточнён на следующем этапе | Обновить `next_stage`, `readiness` и `reconciled_after` |

Если Intent не согласован, Intake не начинают. Если Intent уже принят, его не
создают повторно.

### Delta Specs

- `ADDED Requirements`: новое обязательство, в том числе в существующей capability.
- `MODIFIED Requirements`: **полный** изменяемый Requirement со всеми сохраняемыми
  Scenarios в целевом виде. Частичный текст потеряет детали при Archive.
- `REMOVED Requirements`: удаление с Reason и Migration.
- `RENAMED Requirements`: только переименование, FROM и TO.

Незатронутые Requirements не копируются. ID существующих Scenarios сохраняются;
новым даётся суффикс `<change-id>-<NNN>`. `Purpose` пишется только для новой
capability. Если меняются только refactor, tooling или документация, укажите
`skip_specs: true` вместо фиктивного Requirement.

Пример: Master Spec описывает восстановление доступа по email. Change добавляет SMS
как `ADDED`. Если меняется общее правило числа попыток, весь существующий Requirement
с его сценариями переносится в `MODIFIED`. Объяснение «зачем SMS» остаётся в Proposal.

### Design

В `spec-driven-extended` Design обязателен перед Tasks. Для простого изменения
достаточно краткого решения и карты репозиториев. Design описывает архитектуру и
изменяемые публичные контракты: для HTTP это метод и URL, для событий канал, а
также поля, доступ, ошибки и совместимость по применимости. Внутренние пути и
номера строк остаются в рабочих заметках агента. Правила лежат в шаблоне
`templates/design.md` schema.

Design нужен до Tasks всегда, когда есть зависимости, миграция, безопасность,
производительность или заметный эксплуатационный риск. В `superspec-multirepo`
Design не создаётся только потому, что он доступен.

### Сверка артефактов

Перед завершением каждого этапа агент сверяет его с Intake и уже готовыми
артефактами и обновляет устаревшие разделы. Статус `done` не подтверждает, что
текст актуален. Это обязанность процесса агента (навык
`spec-driven-extended-reconcile`); Orchestrator смысл документов не проверяет.

## Принятие Planning

```bash
openspec validate add-sms-recovery --type change --strict --no-interactive
```

Валидация проверяет формат, но не заменяет ревью. Получите решение людей, которое
требуют schema и правила проекта. Только после этого переходите к
[Apply](apply.md).

Если во время следующих этапов меняется принятый scope, Repository Impact, Design
или Tasks, Change возвращается в Planning и принимается заново.

## Baseline для уже работающего поведения

Baseline: первичное описание поведения, которое уже работает и которое владелец
продукта принимает как обязательство системы. Это отдельная ручная операция в
Store, а не команда Orchestrator. Достаточно описать затронутую capability, а не
всю систему.

1. **Договоритесь о границах.** Кто принимает baseline, кто ревьюит, что агенту
   можно исследовать, как идёт PR в Store. Запишите capability, цель, что вне
   покрытия, версию продукта и выбранные checkout.
2. **Соберите факты.** Начните с договорённостей, API-контрактов, документации,
   демонстрации и тестов; к коду задавайте адресные вопросы. Разделяйте «система
   сейчас так делает» и «система должна так делать». По каждому расхождению владелец
   решает: контракт, дефект или неизвестно. Технические подробности (пути, символы,
   вывод тестов) храните вне Store.
3. **Напишите Master Spec** в `openspec/specs/<capability>/spec.md`: `Purpose` и
   `Requirements`, у каждого Requirement хотя бы один проверяемый Scenario.
   Заголовки `ADDED`/`MODIFIED` здесь не используются. Для ID сценариев согласуйте
   префикс операции, например `baseline-account-recovery-001`.
4. **Проверьте и примите:**

   ```bash
   openspec validate account-recovery --type spec --strict --no-interactive
   ```

   В PR укажите покрытые Requirements, проверенную версию системы, принятые
   расхождения и открытые вопросы. Решение ответственного фиксируется в ревью.
   Фиктивные Change, Apply, Verify и Archive для baseline не создаются.
5. **Вернитесь к Planning.** В Intake или Proposal сошлитесь на baseline PR и
   принятый SHA Store.

Пример Master Spec:

```markdown
# Восстановление доступа

## Purpose
Позволяет пользователю восстановить доступ к учётной записи
через подтверждённый адрес электронной почты.

## Requirements

### Requirement: Однократное использование ссылки
Система SHALL отклонять повторное использование ссылки восстановления.

#### Scenario: Повторное использование ссылки — baseline-account-recovery-001
- **WHEN** пользователь открывает уже использованную ссылку
- **THEN** система отклоняет запрос и предлагает запросить новую ссылку
```

Неподтверждённые предположения не превращаются в SHALL: они остаются открытыми
вопросами с ответственным.
