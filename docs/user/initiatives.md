# Профиль инициатив

Профиль `initiative` предназначен для общего планирования и приёмки результата
с участием нескольких команд. Он поставляется как Template со схемой OpenSpec
и Extension с навыком `initiative-workflow`. Основной Store может подключать
командные Store в роли `specs`; кодовые checkout для планирования не обязательны.

## Новый Store

Из подготовленного Git-репозитория с настроенным origin:

```bash
openspec-orch init . --store management --agent qwen --template initiative
```

Вместо `qwen` можно выбрать поддерживаемый `claude` или `gigacode`.
Template выбирает Extension `initiative`; настройка агента выполняется обычным
процессом Orchestrator. Профиль не требует `spec-driven-extended`, `superpowers`
или Change Tracking. Для визуального обзора подключите OpenSpec Graph обычными
командами Plugin и добавьте командные `specs` по [руководству конфигурации](configuration.md).

## Существующий Store

Не переинициализируйте Store и не заменяйте его текущие схемы. Скопируйте каталог
`templates/initiative/openspec/schemas/initiative` из этой поставки в
`openspec/schemas/initiative` своего Store, только если целевого каталога ещё нет.
Сначала проверьте и сохраните любые существующие локальные изменения.

Из основного Store:

```bash
openspec-orch extension init initiative
openspec-orch extension connect initiative
openspec schema validate initiative
openspec new change launch-shared-outcome --schema initiative
```

После подключения Extension перезапустите агент. Явный `--schema initiative`
выбирает процесс только для нового Change. При желании задайте
`schema: initiative` в `openspec/config.yaml` для будущих Changes; существующие
Changes сохраняют свою выбранную schema. Extension сам схемы не копирует.

## Работа руководителя

Попросите агента использовать навык `initiative-workflow`, например:

> Подготовь инициативу единого возврата денег. Участвуют payments и platform.
> Используй существующие общие спеки и профиль initiative. Уточни существенные пробелы.

Базовый граф артефактов:

1. `proposal.md`: проблема, ожидаемый результат, границы и Repository Impact.
2. `specs/**/spec.md`: Delta Specs с требованиями и наблюдаемыми сценариями.
3. `verify.md`: сопоставление требований со свидетельствами и открытыми вопросами.

При подготовке proposal агент не обещает согласие команд или сроки без источника.
Repository Impact перечисляет ID из реестра основного Store. Capabilities относятся
к Delta Specs текущего Change, а не к каталогам командных Store.

Критерии приёмки задаются в Specs при планировании. Verify может зафиксировать
проверку качества планирования, но без свидетельств реализации поставленный
результат остаётся непроверенным. Статус OpenSpec `isComplete` говорит о наличии
артефактов; существование verify.md не является подтверждением успешной приёмки.
Профиль не имеет кодового Apply, обязательного design или tasks. Совместимость
с командой OpenSpec `instructions apply` обеспечена инструкцией без реализации кода.

Профиль не создаёт командные Changes, не отправляет задания и не собирает
автоматически их статусы. Это база для планирования и проверки доступных свидетельств.

## Настройка под организацию

После установки файлы схемы принадлежат Store. Меняйте шаблоны и зависимости в
`openspec/schemas/initiative/`, добавляйте артефакты, например оценку рисков или
бюджета. Новые артефакты не становятся обязательными для других проектов.

В `openspec/config.yaml` можно добавить стандартные настройки OpenSpec:

```yaml
schema: initiative
context: |
  Инициативы планируются для нескольких продуктовых команд.
rules:
  proposal:
    - Укажи ожидаемый эффект и ограничения бюджета, если они известны.
  verify:
    - Отдельно укажи результаты проверки совместного сценария команд.
```

Дополнительные навыки подключайте своими Extensions обычным механизмом агента
или Orchestrator. Не изменяйте установленные bundled-пакеты: обновление runtime
и настройка проекта — разные операции. Повторная установка Template отклоняет
конфликтующие локальные файлы, а не перезаписывает их.

После изменения схемы выполните `openspec schema validate initiative` и проверьте
`openspec status --change <id> --json`. Изменение графа артефактов может повлиять
на активные Changes с этой schema; для независимого варианта создайте отдельную
локальную schema через `openspec schema fork initiative <new-name>`. Проверьте
и адаптируйте инструкции дополнительных навыков под её новое имя.

Сохраняйте стандартный формат Delta Specs и Repository Impact для совместимости
с OpenSpec и Graph. Правила согласования, роль владельца и процесс публикации
задаются организацией, а не этим стартовым профилем.
