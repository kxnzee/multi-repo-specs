# Доработка существующей системы и brownfield baseline

Когда в работающем продукте появляется задача на доработку, сначала определите,
какой принятый контракт она меняет. Master Spec хранит этот контракт, а Change —
обоснование и дельту будущего изменения. Всю спецификацию системы заново собирать
не нужно.

Brownfield baseline — первичное описание уже работающего поведения, которое
владелец продукта принимает как обязательство системы. Код помогает установить
факты; он сам по себе не делает каждую особенность реализации требованием.

## С чего начать

| Ситуация | Порядок действий |
|---|---|
| Затрагиваемое поведение описано в актуальной Master Spec | Создать Change и подготовить Delta Specs относительно неё |
| Поведение уже работает, но Master Spec или нужных Requirements нет | Принять baseline затрагиваемого поведения, затем завершить Planning доработки |
| Добавляется действительно новая capability | Создать Change с `ADDED Requirements`; baseline несуществующего поведения не нужен |
| Новая возможность расширяет существующую capability | Использовать её текущий путь; добавить новые Requirements и изменить затронутые существующие |
| Реализация расходится с принятым Requirement | Зафиксировать дефект или получить решение об изменении контракта; не переписывать Master Spec под код |
| В существующей Master Spec отсутствует или устарел `Purpose` | Согласовать отдельную Store-операцию исправления; не менять его попутно в Delta Specs |

Capability — связная возможность продукта, например восстановление доступа.
Она может затрагивать несколько Code Repositories. Отдельный репозиторий,
экран или Jira Story не обязательно требует отдельной Master Spec.

Если Store ещё не создан, сначала выполните [подключение проекта](getting-started.md).
Наполните достаточный для задачи [бизнес-контекст](project-context.md): назначение,
термины, участники, процесс и ограничения. Он помогает понимать требования, но
не заменяет Requirements и Scenarios.

## Маршрут 1. Добавить изменение в работающую систему

### 1. Определить цель и затронутые capabilities

Возьмите принятую Jira Story или Intent. Уточните наблюдаемый результат, границы
доработки и то, что должно сохраниться. Найдите соответствующие файлы
`openspec/specs/<capability-path>/spec.md` в центральном Store.

Если контракт затрагиваемого существующего поведения отсутствует, выполните
маршрут 2 ниже. Собрать пожелания или зарегистрировать задачу можно заранее,
но окончательные Delta Specs и принятие Planning должны опираться на принятый
baseline. Не требуется описывать остальные возможности продукта.

### 2. Создать Change в Store

Пример для доработки восстановления доступа. Все shell-команды этого руководства
выполняются из корня центрального Store; имя Change выбирается для вашей задачи.

```bash
openspec new change add-sms-recovery --schema spec-driven-extended
openspec status --change add-sms-recovery
openspec instructions intake --change add-sms-recovery
```

Подготовьте Intake по возвращённым instructions. Затем снова получите status и
instructions следующего разрешённого artifact. Дальнейший порядок задаёт schema:
Intake → Proposal/Specs/опциональный Design → Tasks → Apply → Verify.
Если доступны несколько artifacts, выберите один явно. Для
`superspec-multirepo` используйте её собственный порядок, начиная с Brainstorm;
не переносите туда стадии другой schema.

### 3. Разложить информацию по артефактам

| Где записать | Что записать |
|---|---|
| Master Spec | Принятые Requirements и Scenarios capability до этой доработки |
| `intake.md` | Источник запроса, аналитический контекст и подтверждённые уточнения |
| `proposal.md` | Зачем нужно изменение, целевое поведение, scope, Non-Goals и Repository Impact |
| `specs/<capability-path>/spec.md` внутри Change | Новые, изменённые, удалённые или переименованные Requirements |
| `design.md`, если требуется | Решения и обоснования реализации по правилам schema |
| `tasks.md` | Реализация по назначенным Repository IDs и способы проверки |

В Delta Specs используйте:

- `ADDED Requirements` — новое обязательство, в том числе в существующей capability;
- `MODIFIED Requirements` — **полный** изменяемый Requirement со всеми сохраняемыми
  Scenarios, отредактированный до целевого состояния;
- `REMOVED Requirements` — удаление с Reason и Migration;
- `RENAMED Requirements` — только переименование с FROM и TO.

Незатронутые Requirements не копируйте. При `MODIFIED` сохраняйте IDs существующих
Scenarios; новым дайте стабильный суффикс `<change-id>-<three-digit-index>`.
Для новой capability добавьте содержательный `Purpose`; для существующей её
Purpose в дельту не включается. Сохраняйте принятый capability path.

Например, Master Spec восстановления доступа описывает email-ссылку. Change
добавляет SMS как `ADDED Requirement`. Если при этом меняется общее правило числа
попыток, весь существующий Requirement об этом правиле переносится в `MODIFIED`
вместе со всеми его сценариями. Контекст «зачем нужен SMS» остаётся в Proposal.

### 4. Принять Planning и выполнить доработку

Проверьте согласованность уже созданных artifacts и выполните:

```bash
openspec validate add-sms-recovery --type change --strict --no-interactive
```

Валидация формата не заменяет review и решения людей. Примите Planning по
`openspec/process/quality-gates.md`, затем выполняйте Apply в назначенных Code
Repositories. Verify оформляется после фактического завершения Apply и проверок.
При изменении принятого scope вернитесь в Planning.

После Verify и необходимых решений выполните Archive по актуальным instructions
и процессу проекта. Archive переносит принятую дельту в Master Specs. Не добавляйте
будущее поведение в Master Spec вручную во время Planning. Публикация, UAT и Release
следуют `openspec/process/release-process.md`; Archive не подтверждает deployment.
Подробный пример поставки — в [процессе Jira Story](story-delivery-process.md).

## Маршрут 2. Добавить brownfield baseline

Это отдельная ручная Store-операция, а не встроенная команда или новая schema
Orchestrator. Описанный порядок нужно принять в конкретном проекте перед записью
Master Specs. Он не меняет правила обычного Change: Proposal и Specs в
`spec-driven-extended` остаются Store-only стадиями, а repository evidence scout
сохраняет свой scope и ограничения.

### 1. Согласовать операцию и её границы

В `openspec/process/quality-gates.md` определите ответственного за принятие
baseline, reviewers, необходимые подтверждения и полномочия агента. В
`openspec/process/release-process.md` определите маршрут Store PR для baseline.
Если действующие инструкции запрещают нужное исследование или запись, сначала
согласуйте их уточнение; само это руководство не разрешает обходить запреты.

В задаче на baseline запишите:

- capability и конкретные затрагиваемые правила;
- цель: первичное описание текущего принятого поведения;
- что остаётся вне покрытия;
- среду и версию продукта, выбранный checkout каждого исследуемого Repository;
- владельца решения и способ проверки результата.

При доработке одной фичи достаточно её затрагиваемого контракта, включая зависимые
правила, которые новая реализация обязана сохранить. Для постепенного описания
всего brownfield повторяйте этот маршрут по capabilities. Частичный baseline
не означает, что все возможности системы уже описаны.

### 2. Собрать факты о текущем поведении

Начните с действующих договорённостей, публичных API-контрактов, документации,
демонстрации системы и тестов. При необходимости сформулируйте адресные вопросы
к текущим исходникам выбранных checkout. Такое исследование проводится в рамках
согласованной baseline-операции; обычную генерацию Specs не используйте как
команду reverse engineering.

Разделяйте наблюдение и решение: «система сейчас допускает это» и «система должна
это допускать». Для каждого расхождения владелец определяет, принимается ли
поведение как контракт, считается ли дефектом или остаётся неизвестным.
Желаемое улучшение относится к будущему Change. Не найденный в коде сценарий
не считается доказательством отсутствия поведения.

Техническое evidence с paths, symbols и test output храните в согласованном
техническом месте, например в отчёте Code Repository или вложении задачи трекера.
В Store фиксируйте принятый смысл; не переносите туда code inventory.

### 3. Подготовить Master Spec

В ветке Store, выбранной по процессу проекта, создайте
`openspec/specs/<capability-path>/spec.md`. Если файл уже есть, дополняйте только
согласованный пробел в описании существующего поведения. Изменение ранее принятого
требования ради новой логики выполняется через обычный Change.

Master Spec содержит `Purpose` и `Requirements`, а не заголовки Delta Specs
`ADDED`/`MODIFIED`. У каждого Requirement должен быть хотя бы один проверяемый
Scenario. Для новых baseline-сценариев согласуйте стабильный префикс операции,
например `baseline-account-recovery`; это идентификатор первичного описания,
создавать фиктивный Change с таким именем не требуется.

Пример допустим только если это поведение проверено и принято владельцем:

```markdown
# Восстановление доступа

## Purpose
Позволяет пользователю восстановить доступ к своей учётной записи
через подтверждённый адрес электронной почты.

## Requirements

### Requirement: Однократное использование ссылки
Система SHALL отклонять повторное использование ссылки восстановления.

#### Scenario: Повторное использование ссылки — baseline-account-recovery-001
- **WHEN** пользователь открывает уже использованную ссылку
- **THEN** система отклоняет запрос и предлагает запросить новую ссылку
```

Не превращайте неподтверждённые предположения в SHALL. Открытые вопросы и границы
покрытия оставьте в задаче baseline и описании PR, с ответственным и необходимым
подтверждением. Если неизвестность влияет на доработку, разрешите её до принятия
соответствующего Planning.

### 4. Проверить и принять baseline

Для примера с capability `account-recovery`:

```bash
openspec validate account-recovery --type spec --strict --no-interactive
```

В Store PR укажите покрытые Requirements/Scenarios, проверенную версию системы,
способы подтверждения, принятые расхождения, границы покрытия и оставшиеся вопросы.
Зафиксируйте решение ответственного в review PR, а итоговый полный Store SHA и
ссылку на PR — в задаче baseline. Проверка синтаксиса и вывод агента сами по себе
не означают принятия контракта.

Завершите Store PR по согласованному маршруту. Для первичного описания уже
работающей системы не создавайте фиктивные Apply, Verify или Release и не
архивируйте фиктивный продуктовый Change. Принятие baseline подтверждает контракт
проверенной версии; оно не утверждает, что была выполнена новая поставка.

### 5. Перейти к изменению

Вернитесь к маршруту 1. Укажите в Intake или Proposal ссылку на baseline PR и
полный принятый Store SHA. Используйте принятую Master Spec для Delta Specs;
результаты технического исследования не подменяют этот контракт.

Если baseline изменился во время Planning, заново проверьте затронутые дельты
и их согласования. Для принятия очередного baseline не требуется ждать полного
описания остальных capabilities.

## Что должно получиться

Для доработки существующей capability последовательность такая:

**Достаточный бизнес-контекст → принятый baseline затрагиваемого поведения
(если его не было) → Change с дельтой → принятое Planning → Apply → Verify →
Archive по правилам проекта.**

Baseline PR и PR доработки могут относиться к одной Jira Story, но должны
оставаться отдельно проверяемыми результатами. Уже принятый baseline повторно
не переписывается при каждой новой задаче.
