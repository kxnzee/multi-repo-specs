# План исправлений по аудиту контекста и инструкций

Статус: план для поэтапного согласования. Выполненные пункты отмечены отдельно; остальные изменения не начаты.

План опирается на [карту зон хранения контекста и инструкций](instruction-and-context-zones.md). Четыре основные зоны и их назначение не пересматриваются:

- файл инструкций выбранного агента хранит постоянный контекст текущего репозитория;
- каталог `commands/` описывает конкретные инженерные процессы;
- `openspec/context/` хранит продуктовый, доменный и межсистемный контекст проекта без локального устройства кода;
- `openspec/config.yaml` настраивает spec-driven процесс и формирование OpenSpec-артефактов.

## Общие ограничения

Во всех этапах сохраняются следующие правила:

- не изменять built-in `opsx-*` команды и `openspec-*` skills;
- не создавать единый файл со всеми инструкциями;
- не переносить кодовый контекст отдельных репозиториев в центральный Store;
- не превращать `sdd.yaml`, `.openspec-store/`, `CODEOWNERS` и runtime-файлы в хранилища текстовых правил;
- не делать пользовательскую документацию обязательным входом агента;
- не добавлять в `openspec/config.yaml` список optional subagents;
- не связывать обязательные проверки `sdd init` и `sdd connect` с optional-профилями;
- не тестировать формулировки пользовательской документации.

## Этап 0. Native subagents

Статус: выполнено в commit `8e40359`.

Выполненные изменения:

- Repository Context Pass удалён из `openspec/context/`;
- определения перенесены в provider-specific каталог `agents/`;
- добавлен обязательный общий `repository-context-pass`;
- frontend и backend оставлены optional-примерами расширения;
- основной агент выбирает специализацию по `description`;
- `openspec/config.yaml` не содержит список optional-профилей;
- `sdd init`, `sdd connect` и recovery требуют только общий профиль;
- тесты фиксируют только обязательный профиль.

Дополнительных исправлений этого этапа не требуется. Следующие этапы не должны возвращать контракт subagents в `openspec/context/` или в пользовательскую документацию.

## Этап 1. Однозначный Repository Knowledge Pack

### Проблема

Repository Context Pass получает `agent_context_root`, вычисленный как родитель `agent.commands_directory`, и ищет внутри него Markdown/YAML-файлы.

Контракт работает по-разному:

- для GigaCode родитель `.gigacode/commands/` содержит `.gigacode/GIGACODE.md`;
- для Qwen родитель `.qwen/commands/` не содержит корневой `QWEN.md`;
- команды, skills и определения других агентов могут быть ошибочно приняты за контекст репозитория;
- добавление нового файла меняет результат поиска без изменения контракта.

Точный путь уже задаётся полем `agent.instructions_file` в `sdd.yaml`. Для Code Repository содержимое этого файла является Repository Knowledge Pack.

### Требуемые изменения

1. Определять точный путь:

   ```text
   knowledge_pack_path = <checkout>/<agent.instructions_file>
   ```

2. Передавать subagent абсолютный `knowledge_pack_path` вместо `agent_context_root`.
3. Проверять, что путь находится внутри `checkout` и указывает на обычный файл без symlink последнего сегмента.
4. Не искать альтернативный Knowledge Pack в `commands/`, `skills/` или `agents/`.
5. Считать отсутствие или неполноту файла допустимым состоянием и переходить к минимальному адресному чтению кода и тестов.
6. Обновить общий subagent и привести optional-профили к тому же входному контракту.
7. В `docs/subagents.md` объяснить точный путь без копирования полного prompt subagent.

### Предлагаемое решение по проверке пути

Для текущей архитектуры путь формирует и проверяет основной агент перед делегированием внутри `/opsx-continue`. Новая CLI-команда не добавляется. Harness не готовит planning-контекст шага 03 и не должен расширяться только ради передачи одного пути.

### Проверки

- обязательный контракт проверяется только для `repository-context-pass`;
- Qwen разрешает `<checkout>/QWEN.md`;
- GigaCode разрешает `<checkout>/.gigacode/GIGACODE.md`;
- отсутствие файла не блокирует pass;
- выход за пределы `checkout` и symlink отклоняются;
- тесты не перечисляют optional-профили и не читают их каталог динамически.

## Этап 2. Explore как явная проектная инструкция

### Проблема

`harness/explore/invocation.js` содержит не только проверенные runtime-параметры, но и полный агентский процесс Explore:

- границы чтения;
- порядок исследования;
- правила работы с фактами и гипотезами;
- формат результата;
- условия остановки и переход к Change.

JS-код стал скрытым источником постоянных инструкций, хотя алгоритм конкретной задачи относится к зоне `commands/`.

### Требуемые изменения

1. Добавить проектную инструкцию `sdd-explore.md` в каталог команд выбранного агента.
2. Перенести в неё стабильный процессный контракт Explore из `invocation.js`.
3. Оставить в JS только проверенные значения конкретного запуска:

   - ticket и исходное намерение;
   - Store ID и Spec Root;
   - workspace;
   - выбранные repository-id, checkout, branch и revision;
   - разрешённые корни чтения;
   - точный путь к `sdd-explore.md`.

4. Сохранить оригинальный OpenSpec `/opsx-explore` без изменений.
5. До реализации выбрать и проверить один способ запуска:

   - `/opsx-explore` получает runtime-параметры и точный путь к `sdd-explore.md`;
   - либо `sdd-explore.md` становится проектной wrapper-командой, которая использует штатный Explore OpenSpec.

6. Не копировать стабильный контракт обратно в generated prompt после переноса.
7. Добавить `sdd-explore.md` в обязательные файлы init/connect/recovery только если без него `sdd explore` больше не может выполнить свой контракт.

### Проверки

- JS формирует только параметры и ссылку на инструкцию;
- built-in `opsx-explore.md` не изменяется;
- Qwen и GigaCode получают provider-specific путь;
- отсутствие обязательной проектной инструкции блокирует запуск до исследования;
- тестируется структура runtime-вызова, а не русский текст документации.

## Этап 3. Разгрузка `QWEN.md` и `GIGACODE.md`

### Проблема

Файлы инструкций выбранного агента содержат большой процессный блок о Planning PR, Spec Baseline, implementation subtasks, `sdd load` и Apply. Часть правил нужна агенту в любой сессии, но пошаговые алгоритмы отдельных этапов относятся к командам или пользовательской документации.

### Требуемые изменения

1. Составить построчную таблицу текущих правил с одним владельцем каждого правила.
2. Оставить в файле инструкций агента:

   - постоянный контекст текущего репозитория;
   - общий язык общения;
   - короткие межсессионные ограничения, необходимые до выполнения любой команды;
   - минимальный routing override для ветки `isComplete: true`, поскольку built-in `/opsx-continue` в этой ветке не получает правила из `openspec/config.yaml`.

3. Удалить из файла инструкций подробности, уже полностью принадлежащие:

   - `sdd-apply.md` и runtime `next_action`;
   - пользовательским шагам Planning PR и создания subtasks;
   - правилам формирования OpenSpec-артефактов в `openspec/config.yaml`.

4. Не переносить ручной процесс Planning PR в `openspec/config.yaml`: конфигурация отвечает за OpenSpec-артефакты, а не за Git-provider workflow.
5. Если агенту действительно нужна автоматизация Planning PR, проектировать отдельную команду только после отдельного согласования. Документация сама по себе не является основанием создавать такую команду.
6. Сохранить смысловую эквивалентность Qwen и GigaCode без копирования provider-specific путей друг из друга.

### Проверки

- файл инструкций остаётся достаточным для начала новой сессии;
- завершение `/opsx-continue` ведёт на шаг 04, а не на Apply или Archive;
- Apply-сессия получает полный контракт из `sdd-apply.md`, а не из памяти основной сессии;
- Qwen и GigaCode различаются только необходимыми provider-specific деталями;
- тесты проверяют машинно значимый routing, а не весь текст файлов построчно.

## Этап 4. Устранение необоснованных повторов языка

### Проблема

Правила русского языка повторяются в файле инструкций агента, `sdd-context.md`, `sdd-change.md`, `sdd-apply.md`, `openspec/config.yaml` и `openspec/context/00-start-here.md`.

Часть повторов имеет разную область действия, но сейчас владельцы не определены.

### Целевое распределение

- файл инструкций агента — язык общения в обычной сессии текущего репозитория;
- `openspec/config.yaml` — язык новых OpenSpec-артефактов и planning-ответов;
- standalone runtime-инструкция `sdd-apply.md` — минимальный языковой fallback для новой Apply-сессии, если в Code Repository отсутствует файл инструкций агента;
- `sdd-context.md` и `sdd-change.md` — не повторяют общий контракт, если они всегда выполняются в Store-сессии с загруженным файлом инструкций;
- `openspec/context/00-start-here.md` — не задаёт поведение агента и хранит только сведения, относящиеся к содержимому context pack.

### Требуемые изменения

1. Проверить фактический способ загрузки файла инструкций для каждой команды и runtime-сессии.
2. Удалить повторы только там, где владелец гарантированно загружается до команды.
3. Сохранить локальный fallback в изолированной Apply-сессии.
4. Не переносить язык общения в `docs/` или машинную конфигурацию.
5. Не считать повтор ошибкой, если он необходим для автономного запуска команды; такую причину зафиксировать рядом с правилом.

### Проверки

- новая Store-сессия начинает общение на русском;
- OpenSpec создаёт русскоязычные текстовые артефакты;
- Apply-сессия сохраняет русский язык даже без Knowledge Pack;
- код, команды, пути, идентификаторы и машинные значения не переводятся.

## Этап 5. Финальная фиксация границ

После выполнения этапов 1–4:

1. Обновить `docs/instruction-and-context-zones.md` только если фактическая ответственность зоны изменилась.
2. Обновить `docs/subagents.md` и пользовательские шаги только в части наблюдаемого способа запуска.
3. Проверить, что `harness/README.md` описывает реализацию, но не становится источником обязательных правил агента.
4. Проверить отсутствие старых путей, скрытых копий контрактов и конфликтующих списков.
5. Сформировать итоговую матрицу:

   | Правило | Единственный владелец | Допустимые ссылки или fallback |
   |---|---|---|
   | Knowledge Pack | `agent.instructions_file` Code Repository | адресное чтение кода при отсутствии |
   | Repository Context Pass | provider-specific `agents/` | условие применения в `openspec/config.yaml` |
   | Explore | проектная инструкция в `commands/` | runtime-параметры из Harness |
   | OpenSpec-артефакты | `openspec/config.yaml` | принятый проектный контекст |
   | Контекст проекта | `openspec/context/` | `00-start-here.md` как индекс |
   | Реализация Work Packages | `sdd-apply.md` | `next_action` и `context.json` как параметры |
   | Язык обычной сессии | файл инструкций агента | standalone fallback в `sdd-apply.md` |

## Общая проверка после каждого этапа

- просмотреть полный diff и убедиться, что этап не захватил следующий блок аудита;
- выполнить `npm --prefix harness run check` для изменений Harness;
- выполнить `npm --prefix harness pack --dry-run --cache /private/tmp/multi-repo-specs-npm-cache`, если меняется публикуемый пакет;
- выполнить `git diff --check`;
- проверить Qwen и GigaCode отдельно;
- не добавлять тесты на формулировки файлов из `docs/`;
- не утверждать runtime-совместимость без отдельного запуска `/agents` и соответствующей команды в установленном тестовом Store.

## Порядок согласования и реализации

Этапы выполняются последовательно:

1. Repository Knowledge Pack;
2. Explore-контракт;
3. файл инструкций агента;
4. язык;
5. итоговая карта зон.

Каждый этап сначала обсуждается отдельно. Исправления следующего этапа не включаются в предыдущий коммит.
