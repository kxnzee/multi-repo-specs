# sdd — утилиты обвязки

Реализует часть Слоя E из `harness/SPEC.md` (копия Части III регламента), в объёме, нужном пилоту Pilot Core. Реестр соответствий (III.7, версии инструментов и что наш слой добавляет поверх них) — `harness/registry.yaml`.

| Команда | Статус | Покрывает |
|---|---|---|
| `sdd setup` | реализовано | III.12 «sdd setup» — через реальный `openspec` CLI (версия, `store register`, `list`), не собственный подсчёт |
| `sdd fetch-repos --change <id>` | реализовано | III.12 + раздел 7 профиля Pilot Core (восемь гарантий, включая исключение `configuration` и защиту от path traversal) |
| `sdd load <change-id> --repo <name>` | реализовано | III.12 «sdd load» — читает `tasks.md`/`specs/` на ревизии Baseline через `git show`, печатает полный текст сценариев, не только ID |
| `sdd check --change <id>` | реализовано | правило 1 (структура + содержимое Delta Specs: MUST, формат Scenario ID, наличие сценариев, уникальность в пределах изменения) |
| `sdd check --code --path <repo> --central <path>` | реализовано | правило 4 (карточка, тег, достижимость, соответствие ревизии — всё сверяется с `--central`, не с самим кодовым репозиторием) и правило 5 |
| `sdd conflicts`, `preview`, `status`, `baseline`, `cancel`, `finalize`, `smoke`, `metrics` | не реализовано | по III.17 — не раньше первой недели пилота / появления второго изменения |

Область `sdd check` задаётся флагом, не подкомандой (`--change`/`--code`) — дословно по III.12: «область задаётся явно, а не угадывается по каталогу». `--change` и `--code` взаимоисключающие.

**Правило 3** (регистрация Work Packages) в коде — предупреждение, не блокировка: по разделу 4 профиля Pilot Core это чек-лист Spec Owner до недели 1–2 пилота, машинная блокировка появится по III.17 позже.

## Формат `tasks.md`

Work Packages задаются одним YAML-блоком с явным `id` на пакет — см. `templates/tasks.schema.md`. Таблица в `templates/planning-pr-template.md` — читаемое резюме для ревью, не источник данных.

## `--central` обязателен для `sdd check --code`

Baseline-тег создаётся `sdd baseline` в центральном репозитории (III.12), не в `ui`/`backend`. Без `--central <путь к project-specs>` команда не может проверить ни существование тега, ни его достижимость, ни совпадение `spec_revision` в карточке с фактической ревизией — и по правилу fail closed (III.16) блокирует, а не пропускает молча. `--central-branch` нужен, только если в central-репозитории не настроен `origin/HEAD` (тогда используется первая найденная из `main`/`master`).

## Установка

```bash
cd harness
npm install
```

Требует Node `>=20.19` (как и сам OpenSpec CLI). На более старой 20.x `npm install` выдаст `EBADENGINE` — известное ограничение, см. трекер.

Локально можно вызывать через `node harness/bin/sdd.js <команда>` или добавить `harness/node_modules/.bin` в `PATH` после `npm link`.

`sdd setup` дополнительно требует установленный `openspec` (`npm install -g @fission-ai/openspec@1.7.0`) в `PATH` — версия сверяется с `PINNED_OPENSPEC_VERSION` в `setup.js`.

## Пре-коммит-хук

```bash
harness/scripts/install-hooks.sh
```

Копирует `harness/hooks/pre-commit` в `.git/hooks/pre-commit` (последний не версионируется git). Если там уже есть отличающийся хук — скрипт спрашивает подтверждение перед перезаписью. Хук запускает `sdd check --change <id>` для каждого изменения, чьи файлы попали в коммит.

## `harness/repos.yaml`

Адреса read-only remote для `sdd fetch-repos`. Только зарегистрированные здесь имена репозиториев принимаются — незарегистрированное имя из `candidate_repositories` не читается. `configuration` в список не входит и не читается никогда — раздел 7 профиля Pilot Core.

## Тесты

```bash
npm test
```

45 тестов. Обязательно включают негативные случаи (III.12, требование к `sdd smoke`, распространено и на `check`): невалидная фикстура `pilot-004` проверяет, что правило 1 действительно ловит нарушение, а не молча проходит. Отдельные группы — регрессии на находки двух раундов код-ревью (внутреннего и внешнего): пустой-но-существующий файл, detached HEAD в central, Baseline-тег не в том репозитории, расхождение ревизии в карточке, дублирование `.gitignore`, path traversal в именах репозиториев, фабрикация evidence в `fetch-repos`, чтение `tasks.md` из рабочего дерева вместо Baseline, лексикографическая сортировка версий тега, SHA тега вместо SHA коммита, YAML-парсинг карточки вместо substring-проверки.

## Что не сделано осознанно

- **Реестр хранилищ sdd** (`~/.sdd/registry.json`, путь настраивается через `--registry-path` для тестов) — машинное состояние, не в git, как того требует III.12. Отдельно от `harness/registry.yaml` (версионируемый реестр соответствий, III.7) и от Store-регистрации в самом `openspec` (`openspec store list`).
- **`sdd fetch-repos`** не может реально клонировать `ui`/`backend` в этой сессии — адресов read-only remote (В-04) в `harness/repos.yaml` нет. Команда работает и явно отказывает с понятным сообщением (fail closed, III.16), а не притворяется, что прочитала. Найденные при чтении ограничения инструмент не фабрикует — фиксирует только факт клонирования и ревизию, содержательный вывод оставляет как `TODO` для человека/агента.
- **Правило 2** (регистрация репозиториев с владельцем) не автоматизировано вовсе — по чек-листу `templates/planning-pr-template.md`, как и предписано профилем.
- **Сквозная уникальность Scenario ID** (по Master Specs и другим активным изменениям, не только внутри проверяемого) требует реестра области (I.7.4), которого в Pilot Core пока нет как отдельного артефакта — проверяется только уникальность в пределах одного изменения.
- **`sdd fetch-repos`** ограничивает объём выжимки числом файлов и байтами (порог — `EXCERPT_FILE_LIMIT`/`EXCERPT_BYTE_LIMIT` в `fetch-repos.js`), но сам клон на диске остаётся полным деревом — «выжимка» здесь означает «bounded и явно помеченный превышением», а не «усечённый физически». Более строгая реализация (например, sparse-checkout нужных путей) — за пределами MVP.
- **Полнота `MODIFIED Requirements`** (I.7.5: блок обязан содержать требование целиком со всеми сценариями) не проверяется — требует сравнения с текущей Master Spec той же capability на актуальной ревизии, вне объёма MVP.
