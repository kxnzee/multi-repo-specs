# `/openspec-orch-context`

Собери или актуализируй подтверждённый контекст центрального OpenSpec Store в `openspec/context/`. Команда вызывается как `/openspec-orch-context` без аргументов и всегда выполняет один процесс. Она не исследует код и не проверяет Code Repositories: для этого используются `openspec-orch explore` и оригинальный `/opsx-explore`.

## Границы

- Работай только внутри текущего центрального репозитория с `role: store` в `openspec-orch.yaml`.
- Для чтения используй только `openspec/context/`, `openspec/specs/`, `openspec-orch.yaml`, `CODEOWNERS`, `openspec/config.yaml`, `.openspec-store/store.yaml` и Git-состояние самого Store.
- Вноси изменения только в `openspec/context/`.
- Не обращайся к Code Repositories из `openspec-orch.yaml`, их URL и локальным checkout. Не читай `<workspace>/src/` и любые другие каталоги за пределами текущего Store.
- Не выполняй для Code Repositories `git ls-remote`, `git clone`, `git fetch`, `git checkout` и не создавай временные Git-копии.
- Не создавай и не изменяй `openspec/specs/`, `openspec/changes/`, OpenSpec Requirements, OpenSpec Scenarios, Delta Specs и код. Высокоуровневые бизнес-сценарии в `01-product-context.md` описывают назначение продукта и не заменяют нормативные Scenarios из Specs.
- Не записывай в общий контекст команды сборки, команды тестов и инструкции реализации конкретной функциональности.
- Никогда не записывай в контекст секреты, токены, приватные ключи и другие credential; фиксируй только подтверждённые правила их хранения и использования.
- Не принимай продуктовые, архитектурные, ИБ- и релизные решения вместо владельцев.
- Не вызывай `openspec-orch ...`, `/opsx-...`, другие пользовательские команды, скрипты и skills. Используй чтение и запись разрешённых файлов, Git только для текущего Store и адресные вопросы пользователю.

Успешный `openspec-orch connect` является внешней предпосылкой команды и отвечает за Store registry, workspace и Code Repositories. Не повторяй его проверки. Если текущий каталог не позволяет однозначно найти `openspec/config.yaml`, `openspec/context/`, `.openspec-store/store.yaml` и `openspec-orch.yaml` одного центрального репозитория, остановись и попроси пользователя открыть Store Repository. Не угадывай корневой каталог.

## Порядок работы

### 1. Проведи инвентаризацию структуры

1. Рекурсивно собери отсортированный список всех путей `*.md` внутри `openspec/context/`.
2. Классифицируй каждый путь как нормативный контекст, ADR, служебный README или raw-материал.
3. Сверь найденные пути с принятой структурой: `00-start-here.md`, файлы от `01-...md` до `08-...md`, `system-map.yaml`, `ADR/README.md` и `_raw/README.md`.
4. Покажи отсутствующие обязательные файлы и неожиданные пути. Уточни назначение неожиданного файла до использования его содержимого.
5. Не делай вывод о наличии файлов на основании истории диалога.

### 2. Прочитай правила и источники центрального Store

После инвентаризации прочитай `openspec/context/00-start-here.md`, существующий `openspec/context/system-map.yaml`, служебные README, `openspec-orch.yaml`, `CODEOWNERS`, `openspec/config.yaml` и `.openspec-store/store.yaml`. `system-map.yaml` прочитай до обработки `_raw/` и интервью, даже если он пока содержит только каркас и TODO. Используй запись `role: store` только для подтверждения текущего центрального репозитория; не переходи по записям `role: code`.

До первого изменения контекста проверь, что для каждого целевого нормативного файла существует активное, не закомментированное правило CODEOWNERS с реальными владельцами вместо placeholder из skeleton. Если правила отсутствуют, остаются закомментированными или содержат placeholder-владельцев, ничего не изменяй, верни `context_status: needs_confirmation` и попроси Technical Owner настроить CODEOWNERS.

Действующие Master Specs из `openspec/specs/`, принятые ADR и существующий нормативный контекст являются разрешёнными источниками только внутри текущего Store. Во всех OpenSpec-командах чтения Master Specs явно передавай `--store <store-id>`; не используй nearest root или глобальный `defaultStore`. Ошибку официальной команды покажи пользователю и остановись, не пытаясь исправлять registry.

Используй `00-start-here.md` для выбора релевантного контекста, а `CODEOWNERS` — для определения подтверждающего владельца. При расхождении разрешённых источников не выбирай победителя молча: покажи утверждение и конфликтующие источники, затем запроси решение соответствующего владельца. До решения оставь адресный TODO с `question`, `owner` и `expected_source`.

### 3. Обработай `_raw/`

1. На каждом вызове заново найди все `_raw/**/*.md`, кроме служебного `_raw/README.md`, и обрабатывай их по одному в устойчивом порядке путей.
2. Для каждого файла перечисли извлечённые атомарные утверждения, предполагаемые целевые файлы и недостающие подтверждения.
3. Сравни утверждения только с нормативным контекстом, существующим `system-map.yaml`, подходящими Master Specs и принятыми ADR центрального Store.
4. Попроси пользователя подтвердить, исправить, отклонить или отложить каждое новое, изменённое или противоречащее утверждение.
5. После каждого raw-файла покажи отдельный diff целевых файлов и примени только подтверждённые изменения до перехода к следующему raw-файлу.
6. Не переноси неподтверждённое утверждение в нормативный контекст и не считай raw-файл нормативным источником.

Не создавай индекс, статусы или список обработанных raw-файлов. Следующий вызов должен снова просканировать `_raw/` и определить изменения по текущему содержимому файлов и нормативного контекста.

### 4. Собери оставшееся у владельцев

Переходи к интервью только после обработки или явного откладывания raw-файлов.

1. Если роль пользователя ещё не названа, первым и единственным вопросом сообщения спроси: «Какую роль вы представляете?» Не добавляй к нему вопрос о raw-материалах, проекте или файлах.
2. После ответа кратко перечисли относящиеся к роли блоки и примерное число вопросов, затем задай один первый содержательный вопрос.
3. В каждом следующем сообщении также задавай ровно один вопрос и жди ответа. Не объединяй вопросы через «и», список или подпункты.
4. Содержательные вопросы задавай открытым текстом без готовых предметных вариантов ответа. Не придумывай за пользователя возможное назначение продукта, пользователей, правила, технологии или другие ответы. Нормативный выбор роли и служебные ответы «не знаю», «пропустить» и «позже» допустимы.
5. Разрешай ответить «не знаю», «пропустить» или «позже».
6. Используй inline TODO из относящихся к роли файлов как маршрут, а не показывай общую анкету целиком.
7. После завершения смыслового блока покажи предлагаемый текст и запиши только подтверждённое.
8. Вопросы другим ролям оставь как адресные TODO. Следующий вызов должен дополнять контекст, а не начинать сбор заново.

Самоназванная роль определяет маршрут диалога, но не доказывает полномочия на принятие diff. Право принять изменение определяется CODEOWNERS и правилами проекта.

### 5. Заполни и обнови файлы

- Направляй устойчивые факты в файлы от `01-...md` до `08-...md` согласно их назначению.
- Используй в `system-map.yaml` только подтверждённые системы, связи и `repository-id`, существующие в `openspec-orch.yaml`. Запись в реестре подтверждает только идентификатор, а не состояние кода.
- Неизвестную систему или Code Repository фиксируй адресным TODO в `system-map.yaml`; связанный вопрос о границах или ответственности системы — в `03-architecture.md`. `Open questions` в `00-start-here.md` используй только тогда, когда целевой context-файл действительно невозможно определить.
- Не создавай ADR из одного ответа интервью. Зафиксируй кандидата как TODO в `03-architecture.md`; создавай ADR только после явного подтверждения долговечного решения владельцем.
- Не переноси стенограмму интервью в нормативные файлы. Ответ «не знаю», отложенный или неполный ответ превращай в адресный TODO, а не в догадку.
- Сохраняй существующий подтверждённый текст. Перед удалением или смысловой заменой покажи изменение пользователю.
- Пиши короткими нормативными утверждениями: факт или правило, затем проверяемая причина либо источник.
- Обновляй `00-start-here.md` последним и не добавляй в него новое знание: только маршрутизацию, правила чтения и ссылки на реально существующие файлы.
- Не создавай новые верхнеуровневые файлы контекста вне принятой структуры.

### 6. Выполни самопроверку

Перед завершением проверь:

1. обязательные пути context pack существуют, а ссылки из `00-start-here.md` разрешаются;
2. `system-map.yaml` синтаксически корректен и использует только `repository-id` из `openspec-orch.yaml`;
3. нормативные файлы не ссылаются на `_raw/` как на источник факта;
4. контекст не содержит OpenSpec Requirements, OpenSpec Scenarios, Delta Specs и инструкций реализации конкретной функциональности;
5. контекст не содержит секретов, токенов, приватных ключей и других credential;
6. неподтверждённые утверждения не стали нормативными, а каждый оставшийся TODO имеет владельца и ожидаемый источник;
7. существующее подтверждённое содержание не потеряно;
8. итоговый diff затрагивает только `openspec/context/`;
9. каждый изменённый нормативный файл покрыт активным правилом CODEOWNERS с настроенным владельцем;
10. во время процесса не читались и не изменялись Code Repositories.

## Завершение

Сообщи:

- `context_status: current`, если подтверждённый контекст центрального Store не изменился, обязательные файлы существуют и между разрешёнными источниками нет нерешённых противоречий;
- `context_status: updated`, если пользователь принял diff и после обновления выполнены те же условия;
- `context_status: needs_confirmation`, если остались неподтверждённые изменения, противоречия или вопросы, требующие решения владельца;
- список прочитанных источников центрального Store;
- созданные и изменённые файлы;
- оставшиеся TODO, сгруппированные по владельцам;
- нерешённые расхождения источников и кандидаты в ADR.

Статус описывает только соответствие центрального context pack подтверждённым материалам Store. Он не подтверждает актуальность реализации в Code Repositories. Не перечисляй Code Repositories как проверенные и не объявляй их состояние актуальным.
