# Architecture Decision Records

ADR создаётся только для долговечного принятого технического решения. Один файл описывает одно решение.

После `sdd init` в каталоге `ADR/` существует только этот `README.md`: правила, минимальный шаблон и все демонстрационные примеры находятся в нём. Демонстрационные примеры не создаются отдельными файлами. Отдельный файл вида `NNNN-short-title.md` добавляется только для реального принятого решения.

## Формат имени

`NNNN-short-title.md`

## Обязательные разделы

- Status
- Context
- Decision
- Alternatives considered
- Consequences
- Related context and Changes

## Index

Пока ADR отсутствуют.

## Минимальный шаблон

```md
# ADR-NNNN: Название решения

## Status

Accepted

## Context

Почему потребовалось решение.

## Decision

Что решили.

## Alternatives considered

Какие варианты рассматривали и почему их не выбрали.

## Consequences

Какие положительные и отрицательные последствия приняли.

## Related context and Changes

Связанные context-файлы, Specs и Changes.
```

## Примеры заполнения

Все примеры ниже находятся только в этом `README.md`. Они показывают ожидаемую конкретность формулировок, не являются нормативным контекстом проекта и не должны добавляться в индекс как реальные ADR.

### Пример 1. Асинхронная передача статуса заказа

```md
# ADR-0001: Передавать изменения статуса заказа через события

## Status

Accepted

## Context

После изменения статуса заказа несколько систем должны обновить собственное состояние. Последовательные синхронные вызовы связывают их доступность и увеличивают время ответа пользователю.

## Decision

Система заказов публикует событие `OrderStatusChanged`. Подписчики обрабатывают его независимо и идемпотентно. Доставка события выполняется как минимум один раз.

## Alternatives considered

- Последовательные REST-вызовы отклонены из-за зависимости от доступности всех получателей.
- Периодический опрос отклонён из-за задержки обновления и лишней нагрузки.

## Consequences

Системы можно развивать и восстанавливать независимо. Получатели обязаны учитывать дубли событий, а пользователь некоторое время может видеть рассинхронизированное состояние.

## Related context and Changes

- `03-architecture.md`
- `06-cross-system-invariants.md`
```

### Пример 2. Идемпотентность платёжной команды

```md
# ADR-0002: Требовать ключ идемпотентности для создания платежа

## Status

Accepted

## Context

Клиент может повторить запрос после сетевого тайм-аута, не зная, был ли платёж создан. Повторная обработка команды способна создать два платежа.

## Decision

Команда создания платежа принимает обязательный `idempotency-key`. Платёжная система сохраняет результат первой обработки и возвращает его для повторного запроса с тем же ключом.

## Alternatives considered

- Запрет повторных запросов отклонён: клиент не может отличить тайм-аут от ошибки обработки.
- Сравнение только суммы и получателя отклонено: разные платежи могут иметь одинаковые реквизиты.

## Consequences

Повтор запроса становится безопасным. Потребуются хранение ключей, срок их действия и дополнительная проверка конфликтующего содержимого команды.

## Related context and Changes

- `04-domain-model.md`
- `05-security-and-compliance.md`
```

### Пример 3. Единый источник статуса клиента

```md
# ADR-0003: Считать Customer Service источником статуса клиента

## Status

Accepted

## Context

Статус клиента хранится в нескольких системах и может различаться. Из-за этого разные сервисы принимают несовместимые решения о доступности операций.

## Decision

Нормативный статус хранится и изменяется только в Customer Service. Остальные системы используют его API или локальную проекцию событий и не изменяют статус самостоятельно.

## Alternatives considered

- Синхронное изменение статуса во всех базах отклонено из-за отсутствия общей транзакции.
- Выбор статуса по времени последнего обновления отклонён: время не определяет полномочия источника.

## Consequences

Правило владения данными становится однозначным. Недоступность Customer Service влияет на синхронное чтение, а локальные проекции могут обновляться с задержкой.

## Related context and Changes

- `03-architecture.md`
- `04-domain-model.md`
- `06-cross-system-invariants.md`
```
