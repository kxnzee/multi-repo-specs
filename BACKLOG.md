# Backlog SDD-процесса

Этот файл содержит открытые решения и дефекты процесса, которые можно исправлять отдельно от проектирования следующих шагов.

Статусы:

- `decision_needed` — сначала требуется процессное решение владельца;
- `ready` — решение принято, пункт можно реализовывать;
- `done` — изменение реализовано и проверено.

Приоритеты:

- `P1` — процессный тупик или невозможность безопасно завершить поддержанный сценарий;
- `P2` — расхождение контракта или неполная проверка, не блокирующая основной happy path.

## BL-001 — Возврат из шага 02 в Explore и восстановление сессии

- **Приоритет:** P1
- **Статус:** `decision_needed`
- **Затронутые шаги:** 01, 02

### Проблема

После создания активного Change нельзя выполнить заявленный возврат `02 → 01` и нельзя нормативно продолжить шаг 02 после потери агентской сессии:

- `docs/steps/02.md:144` и `docs/steps/02.md:264` направляют в Explore, если нужен новый репозиторий, новая ревизия или дополнительное исследование;
- `harness/init/commands/sdd-change.md:18` требует полный структурированный итог Explore именно в текущей сессии;
- `harness/explore/validation.js:121`–`127` блокирует новый Explore при активном Change того же ticket;
- `docs/steps/02.md:286` обещает продолжение после потери сессии, но не задаёт достижимый путь восстановления.

Тупик возникает как минимум после потери сессии, после прерывания между созданием Change и Proposal и при изменении scope во время согласования Proposal.

### Требуется решить

Определить нормативную модель возобновления: какие сведения сохраняются после Explore и как существующий Change временно возвращается в исследовательский режим без удаления пользовательского состояния.

### Критерии закрытия

- определён достижимый переход `02 → 01 → 02` для того же ticket и Change;
- новая агентская сессия может безопасно продолжить состояния «Change без Proposal» и «Proposal ожидает подтверждения»;
- восстановление не требует автоматических `reset`, `stash` или удаления Change;
- сценарные тесты покрывают потерю сессии и расширение области исследования после создания Change;
- документация, `/sdd-change` и `sdd explore` описывают один и тот же переход.

## BL-002 — Восстановление частично выполненного `sdd init`

- **Приоритет:** P1
- **Статус:** `decision_needed`
- **Затронутый шаг:** 00

### Проблема

`harness/init/skeleton.js:361` создаёт Store metadata до установки всего skeleton. После сбоя повторный запуск на `harness/init/skeleton.js:320`–`333` считает одного наличия metadata достаточным признаком завершённой инициализации и возвращает `alreadyInitialized`.

В результате проект может остаться без `sdd.yaml`, agent commands или context pack. `sdd connect` такое состояние не исправляет, а точная ручная процедура восстановления не определена.

### Требуется решить

Выбрать один контракт: безопасное продолжение `sdd init` по структурно проверенному частичному состоянию либо явный `needs_recovery` с детерминированной инструкцией Technical Owner.

### Критерии закрытия

- завершённость определяется по полному минимальному набору инвариантов, а не только по Store metadata;
- повторный запуск не перезаписывает существующее пользовательское содержимое;
- для каждого нераспознаваемого состояния возвращается точная причина и безопасная процедура восстановления;
- тесты моделируют сбой после Store setup, после установки OpenSpec pack и во время установки skeleton;
- после разрешённого восстановления `sdd connect` может достичь `connect_status: ready`.

## BL-003 — Повторная работа по архивному ticket

- **Приоритет:** P1
- **Статус:** `decision_needed`
- **Затронутые шаги:** 01, 02

### Проблема

Шаг 01 разрешает интерактивно подтвердить новый Explore для архивного ticket, но решение не передаётся дальше. На шаге 02 `/sdd-change` запускает `sdd change` из агентской среды. При non-TTY запуске `harness/cli/change.js:36`–`49` не может запросить подтверждение, а `harness/change/index.js:73`–`76` блокирует создание Change.

Таким образом, объявленный поддержанным сценарий проходит Explore, но останавливается при создании Change.

### Требуется решить

Определить, допускается ли вообще повторная работа с одним Jira key после Archive.

### Критерии закрытия

- если повторное использование запрещено, шаги 01 и 02 одинаково и окончательно блокируют архивное совпадение;
- если оно разрешено, подтверждение передаётся в шаг 02 проверяемым способом, не зависящим от TTY агентского запуска;
- решение не выводится автоматически только из прежнего подтверждения в другой сессии или на другой машине;
- end-to-end тест покрывает полный маршрут от `sdd explore` до созданного Change для выбранной политики;
- пользовательская документация не предлагает недостижимый сценарий.

## BL-004 — Полнота проверки agent pack в `sdd connect`

- **Приоритет:** P2
- **Статус:** `done`
- **Затронутые шаги:** 00, 02, 03

### Проблема

`harness/connect/index.js:17` проверяет только `opsx-explore.md` и `sdd-context.md`. Команда может вернуть `connect_status: ready`, хотя обязательный для шага 02 файл `sdd-change.md` отсутствует.

### Принятое направление

Готовность шагов 00–02 должна включать наличие всех agent commands, необходимых для перехода до шага 03. Проверка подтверждает обычные файлы в ожидаемом `commands_directory`, но не редактирует встроенные `opsx-*` команды и skills.

### Критерии закрытия

- `sdd connect` проверяет как минимум `opsx-explore.md`, `opsx-continue.md`, `sdd-context.md` и `sdd-change.md`;
- отсутствующая команда блокирует `ready` с точным путём и инструкцией восстановления;
- проверки одинаково работают для Qwen и GigaCode adapters;
- тесты покрывают отсутствие каждой обязательной команды.

### Решение

`sdd connect` требует `opsx-explore.md`, `opsx-continue.md`, `sdd-context.md` и `sdd-change.md` как обычные файлы внутри настроенного `commands_directory`. Новая инициализация устанавливает официальный expanded agent pack OpenSpec; отсутствие любой обязательной команды блокирует `ready` до изменения registry или workspace.

## BL-005 — Роль Spec Owner в гейте шага 02

- **Приоритет:** P2
- **Статус:** `decision_needed`
- **Затронутый шаг:** 02

### Проблема

`docs/steps/02.md:119`–`128` возлагает на Spec Owner подтверждение Store, структуры Change и соблюдения процесса. Однако пользовательская инструкция, `/sdd-change` и итоговый гейт требуют только явного подтверждения Proposal от Change Owner. Непонятно, является ли участие Spec Owner человеческим гейтом, автоматизированной проверкой CLI или консультационной ответственностью.

### Требуется решить

Выбрать одно значение роли Spec Owner на шаге 02 и одинаково отразить его в таблице владельцев, команде и гейте перехода.

### Критерии закрытия

- у роли есть однозначное действие и момент выполнения либо она удалена из гейта шага;
- если достаточно автоматической проверки, документация прямо отделяет её от человеческого подтверждения;
- если требуется человек, результат шага содержит проверяемый статус его решения;
- пользовательская инструкция, техническая спецификация и `/sdd-change` не расходятся.

## BL-006 — Устойчивый handoff результатов Repository Context Pass

- **Приоритет:** P2
- **Статус:** `decision_needed`
- **Затронутый шаг:** 03

### Текущий поддержанный сценарий

Один OpenSpec Change может затрагивать несколько крупных Code Repositories, не разделяя бизнесовую фичу. Основной planning-agent остаётся единственным писателем Delta Specs, `design.md` и `tasks.md`, а read-only исследование каждого `repository-id` делегирует отдельному subagent. Subagent читает сначала Repository Knowledge Pack в provider-specific каталоге агента, затем при необходимости адресно исследует код на точной ревизии и возвращает в живую planning-сессию только краткий структурированный результат.

Стандартные артефакты OpenSpec являются долговечными контрольными точками. Результат subagent до его синтеза в очередной артефакт хранится только в контексте текущей агентской сессии. Если эта сессия потеряна, повторяется соответствующий ограниченный Repository Context Pass; новый Change, возврат в Explore и отдельное человеческое подтверждение не требуются. Такое повторение считается допустимой стоимостью текущей версии процесса и не блокирует шаг 03.

### Ограничение

OpenSpec 1.7.0 не предоставляет временное хранилище результатов агентского исследования. `workset` сохраняет и повторно открывает набор папок, `context` и `references` разрешают OpenSpec Stores, а стандартные артефакты сохраняют уже синтезированное состояние Change. Ни один из этих механизмов не восстанавливает вопрос Repository Context Pass, его доказательства, открытые вопросы и ответ subagent.

Проблема станет существенной, если пилот покажет, что повторные проходы после потери сессии заметно увеличивают время планирования, стоимость чтения крупных репозиториев или риск получить разные выводы на одной ревизии. Сам размер репозитория и отсутствие межсессионного handoff без такого наблюдаемого ущерба не являются блокером.

### Требуется решить

Спроектировать provider-neutral способ безопасно возобновлять незавершённый Repository Context Pass и передавать его ограниченный результат новой planning-сессии. При выборе решения сравнить как минимум:

- локальный невключаемый в Git runtime cache, привязанный к Change, `repository-id`, точной ревизии и исследованному вопросу;
- штатное долговечное состояние или session handoff конкретного agent provider, если оно имеет проверяемый общий контракт;
- расширение OpenSpec schema отдельным артефактом только в случае, если оно не переносит локальные технические детали в центральный Store и не дублирует `design.md`.

Решение должно определить формат результата, место хранения, срок жизни, правила инвалидирования при смене ревизии или вопроса, границы чувствительных данных и поведение при частично записанном состоянии.

### Ограничения решения

- Business Specs остаются описанием наблюдаемого поведения и не содержат файлов, классов, функций, хуков и внутренних модулей;
- устойчивые технические знания остаются в Repository Knowledge Pack соответствующего Code Repository;
- центральный Store сохраняет только бизнесовый и межсистемный результат, но не сырой код и не локальные доказательства Repository Context Pass;
- основной planning-agent остаётся единственным писателем артефактов Change;
- отсутствие cache или handoff не создаёт нового человеческого гейта и само по себе не блокирует `/opsx-continue`;
- решение не требует `knowledge_path` в `sdd.yaml` и не создаёт отдельные Changes по числу репозиториев;
- встроенные команды и skills OpenSpec не модифицируются.

### Критерии закрытия

- новая planning-сессия может проверить принадлежность результата конкретным Change, `repository-id`, ревизии и вопросу до его использования;
- основной агент загружает ограниченные структурированные выводы, а не совокупный сырой код нескольких репозиториев;
- устаревший, неполный или противоречивый результат адресно инвалидируется и приводит к повтору только соответствующего pass;
- потеря сессии между завершением subagent и созданием OpenSpec-артефакта не требует повторного чтения репозитория при наличии валидного handoff;
- техническое содержание не попадает в Business Specs или центральный System Design;
- happy path `/opsx-continue` и единый Planning PR шага 03 сохраняются без промежуточного подтверждения;
- сценарные тесты покрывают восстановление, смену ревизии, частично записанный результат и несколько репозиториев.

## BL-007 — Адресное обновление Git-ревизии во время планирования

- **Приоритет:** P2
- **Статус:** `decision_needed`
- **Затронутый шаг:** 03

### Текущий поддержанный сценарий

Каждый Repository Context Pass работает read-only на точной Git-ревизии, зафиксированной для текущего Change. Движение удалённой основной ветки само по себе не меняет входы шага 03: агент не выполняет автоматический `pull`, не переключает checkout и продолжает планирование по уже исследованной ревизии.

Если владелец намеренно выбирает новую ревизию до Planning PR, текущий процесс возвращает Change в Explore. Это безопасный, хотя и более дорогой путь. Обычный happy path не требует обновлять ревизии внутри шага 03, поэтому отсутствие более короткого перехода не считается блокером.

### Возможное улучшение

Если пилот покажет, что намеренное обновление ревизий во время планирования является частым и стоимость повторного Explore существенна, оценить targeted revision delta-pass для диапазона `old..new`. Такой pass должен исследовать только влияние новых коммитов на уже подтверждённые выводы и не перечитывать репозиторий целиком.

Технический результат delta-pass мог бы актуализировать `design.md` и `tasks.md` без возврата в Explore. Изменение capabilities, наблюдаемого поведения, внешних систем либо бизнесовых scope и out of scope по-прежнему должно возвращать процесс в Explore.

### Ограничения решения

- обновление ревизии выполняется только явно и никогда не выводится из движения remote branch;
- исходная и новая ревизии должны быть точными Git commit ID одного зарегистрированного `repository-id`;
- Code Repository остаётся read-only, а основной planning-agent — единственным писателем Change;
- delta-pass не создаёт новый OpenSpec Change, отдельный человеческий гейт или локальный implementation plan;
- отсутствие механизма не блокирует текущий flow шага 03;
- механизм не реализуется до появления измеряемого кейса на пилоте.

### Критерии закрытия

- определён явный инициатор и момент обновления revision baseline;
- агент проверяет достижимость обеих ревизий и исследует только `old..new` для одного `repository-id`;
- результат однозначно классифицирует изменение как техническое либо затрагивающее бизнесовый scope;
- техническое изменение адресно актуализирует зависимые Design и Tasks без переписывания неизменных Specs;
- бизнесовое изменение использует нормативный возврат в Explore;
- тесты покрывают отсутствие diff, технический diff, бизнесовый impact и недостижимую ревизию.

## BL-008 — Проверка частично созданного planning-артефакта

- **Приоритет:** P2
- **Статус:** `decision_needed`
- **Затронутый шаг:** 03

### Текущий поддержанный сценарий

`/opsx-continue` создаёт один стандартный артефакт и останавливается. Перед следующим вызовом основной агент выполняет рабочую самопроверку только что созданных Specs, Design или Tasks и завершает явно неполный файл напрямую либо через `/opsx-update`. Отдельная строгая валидация и человеческое подтверждение между артефактами не выполняются; весь Change валидируется и рассматривается один раз в Planning PR шага 04.

### Ограничение

OpenSpec определяет статус артефакта прежде всего по наличию ожидаемого файла. После прерывания записи частичный файл может получить статус `done`, а следующий артефакт — `ready`. Текущая защита зависит от содержательной самопроверки planning-agent и не имеет отдельного машинного результата.

Это не блокирует обычный flow: агент уже обязан перечитать созданный файл до следующего `/opsx-continue`, а строгая проверка всего Change остаётся в шаге 04. Дополнительный механизм следует рассматривать только при подтверждённых случаях каскадного создания Tasks или Design из частичных зависимостей.

### Возможное улучшение

Оценить лёгкую структурную completeness-проверку без человеческого гейта и без полной строгой валидации после каждого артефакта. Проверка может сопоставлять созданные файлы с `resolvedOutputPath`, dependency-файлами и минимальными обязательными секциями официальной инструкции установленной версии OpenSpec.

### Ограничения решения

- `/opsx-continue` и встроенные OpenSpec skills не модифицируются;
- успешная completeness-проверка не означает содержательного одобрения;
- проверка не прерывает последовательное создание артефактов ради человеческого подтверждения;
- официальная строгая валидация и единое ревью сохраняются в Planning PR шага 04;
- механизм не реализуется до появления измеряемого дефекта на пилоте.

### Критерии закрытия

- частичный, пустой или оборванный артефакт не используется как зависимость следующего `/opsx-continue`;
- проверка следует `instructions` и путям установленной версии OpenSpec, не копируя schema templates в SDD;
- ошибку можно исправить в том же Change без удаления файлов и повторного человеческого гейта;
- тесты покрывают пустой файл, отсутствующую обязательную секцию, несколько Delta Specs и успешное продолжение.

## BL-009 — Добавление Code Repository в registry при активном Change

- **Приоритет:** P2
- **Статус:** `decision_needed`
- **Затронутые шаги:** 00, 03

### Текущий поддержанный сценарий

Шаг 03 может расширить технический impact одной бизнесовой фичи без возврата в Explore, если дополнительный `repository-id` уже зарегистрирован с `role: code` в центральном `sdd.yaml`, checkout подключён к тому же Store и находится на проверяемой точной ревизии. Для репозитория запускается отдельный Repository Context Pass, после чего основной агент актуализирует Design и Tasks.

Репозиторий, отсутствующий в `sdd.yaml`, не входит в текущий happy path. Агент сохраняет существующий Change и не редактирует registry, Store metadata или planning-артефакты по догадке.

### Ограничение

После первичного `sdd init` проект не имеет отдельной поддержанной команды добавления Code Repository в registry. Ручное изменение `sdd.yaml` на planning-ветке смешивает setup проекта с Change, а отдельный setup PR требует определить безопасное возобновление уже активной planning-ветки после merge.

Сценарий не блокирует обычное планирование по полному зарегистрированному набору репозиториев. Улучшение требуется, только если пилот подтвердит регулярное обнаружение ранее неизвестных Code Repositories во время активного Change.

### Требуется решить

Определить отдельный setup-переход для добавления Code Repository без создания новой бизнесовой фичи. Решение должно установить владельца изменения registry, ветку и PR, проверку URL и `default_branch`, создание project pointer, обновление workspace и безопасное возобновление исходного Change.

Следует сравнить расширение существующего setup-процесса шага 00 и отдельную команду уровня `sdd`, не изменяя встроенные OpenSpec commands и skills.

### Ограничения решения

- новый репозиторий добавляется только явным решением владельца, а не автоматически из вывода subagent;
- изменение `sdd.yaml` и project pointer проходит отдельное ревью setup, не маскируется внутри Planning PR фичи;
- активный Change, его ветка и созданные артефакты не удаляются и не перезаписываются;
- после setup репозиторий разрешает тот же центральный Store через официальный `openspec context --json`;
- возобновление не требует создавать второй OpenSpec Change для той же бизнесовой фичи;
- отсутствие механизма не меняет happy path шага 03 для уже зарегистрированных репозиториев.

### Критерии закрытия

- документирован достижимый переход `03 → setup → 03` для того же Change;
- registry и workspace обновляются детерминированно и идемпотентно;
- конфликтующий URL, ветка, Store pointer или грязный checkout блокируются до изменения пользовательских файлов;
- исходная planning-ветка безопасно получает принятый setup без потери Change;
- Repository Context Pass начинается только после проверки регистрации, checkout и точной ревизии;
- сценарные тесты покрывают новый репозиторий, уже зарегистрированный репозиторий, конфликт и возобновление активного Change.

## BL-010 — Безопасная очистка runtime и Store worktrees

- **Приоритет:** P2
- **Статус:** `decision_needed`
- **Затронутые шаги:** 05, 06, 09

### Проблема

Шаг 05 создаёт воспроизводимый runtime и отдельный detached Store worktree для каждой пары `change-id + repository-id`. Они не являются источником истины и не блокируют основной процесс, но без поддержанного lifecycle со временем накапливают локальные файлы и записи Git worktree metadata зарегистрированного Store.

Автоматическое удаление в первой реализации опаснее накопления: harness пока не может надёжно доказать, что implementation-сессия, PR или последующая проверка больше не используют конкретный runtime. Поэтому очистка не включается в `sdd load` и не становится гейтом шагов 05–09.

### Требуется решить

Определить безопасный локальный cleanup-механизм, который находит только неактивные runtime-контексты, удаляет принадлежащие им Store worktrees штатным Git API и не затрагивает Code Repositories, активные ветки, central Store checkout или нормативные OpenSpec-артефакты.

Следует сравнить явную пользовательскую команду, best-effort cleanup после финализации и ограниченную автоматическую очистку при обслуживании workspace. Решение не должно зависеть от tracker API как единственного способа определить активность.

### Ограничения решения

- cleanup не выполняется скрытно во время обычного `sdd load` или активной Apply-сессии;
- runtime активной implementation-ветки не удаляется;
- перед удалением проверяются Store ID, Change ID, repository-id, Baseline и фактическая Git worktree relationship;
- рабочие файлы Code Repository, ветки, commit и credential никогда не являются целью cleanup;
- частичная ошибка сохраняет оставшиеся runtime и возвращает точный список удалённых и неудалённых путей;
- повторный запуск идемпотентен и не требует ручного редактирования Store `.git` metadata.

### Критерии закрытия

- определён проверяемый признак неактивного runtime;
- доступен dry-run со списком точных путей и связанных worktrees;
- удаление использует штатные `git worktree remove` и `git worktree prune`, а не широкое рекурсивное удаление;
- активные, грязные, неизвестные и неоднозначные worktrees блокируются fail-closed;
- после cleanup тот же контекст можно воспроизвести обычным `sdd load`;
- тесты покрывают активный runtime, завершённый runtime, отсутствующий каталог, повреждённую metadata и повторный запуск.

## BL-011 — Долговечная привязка implementation-ветки к параметрам subtask

- **Приоритет:** P2
- **Статус:** `decision_needed`
- **Затронутые шаги:** 05, 06

### Текущий поддержанный сценарий

Каждый запуск `sdd load` использует явные параметры актуальной implementation subtask и после проверки заменяет ими локальный `context.json`. При потере runtime или переносе работы на другую машину Apply Owner воспроизводит его той же командой. Loader заново валидирует Store, Baseline и Tasks и показывает descriptions, но намеренно не сравнивает текущие параметры с прежней привязкой Git-ветки.

Это не блокирует основной процесс: implementation subtask является долговечным источником назначения, а существующая чистая ветка может быть возобновлена без дополнительного локального state. Ограничение состоит в том, что ошибочное изменение subtask не обнаруживается по истории ветки автоматически.

### Возможное улучшение

Если пилот подтвердит реальные ошибки восстановления, спроектировать проверяемую долговечную привязку implementation-ветки к `change-id`, `spec_baseline`, `repository-id` и Work Packages. Сравнить metadata в Git-провайдере или tracker с минимальным версионируемым маркером; локальный Git config и новый runtime-файл не решают перенос между машинами.

### Ограничения решения

- отсутствие механизма не блокирует восстановление из актуальной implementation subtask;
- `sdd load` не создаёт служебный commit, tag или push только ради metadata;
- параметры не дублируют descriptions Tasks и нормативные OpenSpec-артефакты;
- решение не требует автоматической Jira/SberTrack-интеграции без отдельного процессного решения;
- встроенные команды и skills OpenSpec не модифицируются.

### Критерии закрытия

- новая машина может проверить прежнюю привязку ветки без старого runtime;
- расхождение Baseline или Work Packages обнаруживается до изменения кода;
- обычное восстановление с совпадающими параметрами остаётся неблокирующим;
- correction/amendment имеет явный способ обновить привязку;
- тесты покрывают потерю runtime, перенос на другую машину, совпадение и конфликт параметров.

## BL-012 — Composite Verification точных ревизий несмерженных PR

- **Приоритет:** P1
- **Статус:** `decision_needed`
- **Затронутые шаги:** 07, 08

### Текущий процесс

Шаг 06 заканчивается готовыми, но ещё не слитыми implementation PR. Каждый репозиторий передаёт шагу 07 точную `code_revision`, а Composite Verification должна проверить совместную работу этих ревизий до merge и rollout шага 08. Требования читаются только с принятого `spec_baseline`.

Этот порядок безопасен только если тестовая инфраструктура умеет собрать и развернуть одну согласованную комбинацию несмерженных commit из нескольких Code Repositories. Такая возможность пока не подтверждена и не должна молча предполагаться документацией шага 07.

Проверка инфраструктуры не блокирует реализацию шага 06: репозитории по-прежнему могут подготовить implementation PR, выполнить свои компонентные и контрактные проверки и зафиксировать точные SHA.

### Требуется решить

До фиксации шага 07 провести ограниченный инфраструктурный pilot и ответить на один вопрос: можно ли воспроизводимо собрать, развернуть и повторно проверить набор точных `code_revision` всех затронутых несмерженных PR.

Если возможность уже существует, документировать только штатный способ передачи ревизий, запуска окружения и получения evidence. Если её нет, отдельно сравнить минимальные варианты изменения порядка merge и проверки. Не вводить integration branch, дополнительный Store, временные Changes или новый оркестратор заранее.

### Ограничения решения

- одна бизнесовая фича остаётся одним OpenSpec Change;
- нормативный вход проверки содержит точный `spec_baseline`;
- вход проверки содержит точную полную SHA каждого Code Repository, а не плавающий HEAD PR или branch name;
- повторный запуск той же комбинации ревизий должен быть воспроизводим;
- инфраструктурный механизм не копирует Specs, Tasks или implementation plan в Code Repositories;
- fallback не выбирается до подтверждения, что штатная проверка несмерженных ревизий недоступна;
- отсутствие решения не расширяет шаг 06 и не добавляет в него новую CLI-команду;
- успешные компонентные проверки отдельных PR не выдаются за Composite Verification всей системы.

### Критерии закрытия

- зафиксировано, поддерживает ли инфраструктура сборку и развёртывание нескольких точных несмерженных ревизий;
- pilot воспроизводит одну и ту же комбинацию SHA без неявного перехода на новые HEAD веток;
- определены минимальные входы, команда или штатное действие запуска и проверяемое evidence;
- evidence однозначно указывает `spec_baseline` и весь набор `repository_id + code_revision`;
- при отсутствии поддержки принято отдельное решение о порядке merge и Composite Verification;
- документация шагов 07–08 не содержит скрытой зависимости от несуществующего integration environment;
- тестовый сценарий покрывает несовместимые ревизии и не позволяет случайно проверить другую комбинацию commit.

## BL-013 — Общая видимость технического плана и частичного прогресса

- **Приоритет:** P1
- **Статус:** `pilot_needed`
- **Затронутый шаг:** 06

### Проблема

Один Work Package может выполняться несколько сессий, передаваться между разработчиками или долго оставаться частично готовым. Внутренний план агента живёт только в текущем контексте, центральный `tasks.md` фиксирует принятый общий план на immutable Baseline, а обычный статус implementation subtask показывает лишь крупный этап работы.

Из-за этого команда может не видеть:

- какие технические части Work Package уже выполнены;
- что осталось и почему работа остановилась;
- какие решения были приняты внутри Code Repository;
- насколько локальный план соответствует фактическому diff и проверкам;
- с какого места другой разработчик или новая агентская сессия должны продолжить работу.

Необязательный implementation design/plan Code Repository способен дать дополнительный контекст, но пока не подтверждено, как часто он действительно нужен, кто поддерживает его актуальность и достаточно ли существующих subtask и Draft PR для наблюдаемости работы.

### Что наблюдать на пилоте

- сколько Work Packages переживают смену агентской сессии или исполнителя;
- как часто команда запрашивает отдельное пояснение текущего состояния;
- теряются ли технические решения и следующие действия после передачи работы;
- расходится ли описанный план с фактическими commit, diff и CI;
- создаёт ли ручное обновление прогресса заметную нагрузку;
- достаточно ли текущих возможностей tracker и Git-провайдера без дополнительного механизма.

### Решение отложено

До получения данных пилота не фиксируются:

- новая команда или метод обновления плана;
- обязательный файл, schema или расположение implementation plan;
- автоматическая синхронизация с tracker или Git-провайдером;
- новый runtime-state, progress manifest или отдельная subtask;
- обязательный дополнительный гейт шага 06.

Backlog-пункт не блокирует текущий простой flow: технический design/plan остаётся необязательным, а необходимость отдельного механизма будет оценена по фактическим передачам и потерям контекста.

## BL-014 — Перепривязка Work Packages после изменения Baseline без ручной работы

- **Приоритет:** P1
- **Статус:** `production_blocker`
- **Затронутые шаги:** 04, 05, 06

### Проблема

OpenSpec формирует `task.id` по текущему порядку checkbox в `tasks.md`. После correction/amendment добавление, удаление или перестановка Tasks может изменить ID даже у семантически прежнего Work Package.

Для безопасного продолжения требуется сопоставить все прежние назначения с новым Baseline и обновить все implementation subtasks активного Change до Archive, включая уже завершённые. Ручное выполнение этой операции каждым Apply Owner создаёт риск пропуска, ошибочного соответствия и различий между репозиториями.

### Граница пилота

На пилоте допускается ручная перепривязка под контролем Change Owner: команда явно сравнивает старый и новый Baseline и обновляет все назначения implementation subtasks. Это временное допущение для сбора фактических сценариев correction/amendment.

Ручная перепривязка не считается production-ready процессом и не допускается как штатное условие запуска.

### Что наблюдать на пилоте

- какие изменения `tasks.md` действительно меняют `task.id`;
- сколько subtasks и уже отмеченных Work Packages приходится перепроверять;
- возникают ли неоднозначные соответствия старых и новых Tasks;
- какие данные нужны для проверки обновлённого назначения;
- как correction/amendment влияет на уже готовые implementation PR;
- сколько времени и ошибок создаёт ручная операция.

### Решение отложено

До результатов пилота не фиксируются команда, алгоритм сопоставления, формат metadata, tracker-интеграция или новый стабильный идентификатор. Решение должно быть выбрано по наблюдаемым случаям, а не добавляться заранее в шаг 06.

### Критерий production readiness

До запуска процесс должен исключить необходимость ручного сопоставления каждым разработчиком. Любая смена Baseline обязана детерминированно обнаруживать изменившиеся назначения и выдавать проверяемый единый результат для всех implementation subtasks активного Change.
