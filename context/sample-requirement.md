# Образец требования (для Delta Specs)

Формат по I.7 регламента 3.5.4: стабильный ID, полнота, одна из четырёх операций (ADD / MODIFY / REMOVE / RENAME).

```markdown
## ADD Requirement: PILOT-003 — Отображение статуса релизного флага

**Scenario ID:** PILOT-003.1

### Сценарий

**Given** релизный флаг пилотной фичи выключен
**When** пользователь с ролью, не входящей в whitelist пилота, открывает экран
**Then** система показывает прежнее поведение (флаг не влияет на UI)

**Given** релизный флаг пилотной фичи включён для пользователя
**When** пользователь открывает экран
**Then** система показывает новое поведение фичи

### Acceptance Criteria (для Work Package `enables`, репозиторий `configuration`)

**AC-PILOT-003.1** — флаг создаётся новым (не переиспользует существующий), значение по умолчанию `false`, защитный критерий (I.16.2) описан и получил `Verified` до включения в production.
```

## Что делает этот образец правильным

- ID стабилен и не переиспользуется при правках — правки меняют содержимое, не ID.
- Сценарий сформулирован в Given/When/Then, проверяем разработчиком до утверждения (I.13).
- `AC-*` привязан к Work Package `enables`, а не к сценарию — `configuration` сценариев не имеет и иметь не может (I.16.1).
- Полнота: описано поведение и при выключенном, и при включённом флаге — не только «новый» случай.
