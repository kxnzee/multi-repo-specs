# Образец требования (для Delta Specs)

Формат по I.7 регламента 3.5.4 — дословно, не парафраз: нормативное слово `MUST` в теле требования, идентификатор сценария `<ПРЕФИКС>-<NNN>` в заголовке `#### Scenario:`, операция дельты `## ADDED Requirements`.

```markdown
## ADDED Requirements

### Requirement: Отображение статуса роли
Система MUST отображать текущую роль сотрудника в карточке профиля.

#### Scenario: PILOT-003 Роль назначена
- GIVEN сотрудник с назначенной ролью «Оператор»
- WHEN открывается карточка профиля
- THEN в поле «Роль» отображается «Оператор»

#### Scenario: PILOT-004 Роль не назначена
- GIVEN сотруднику роль не назначена
- WHEN открывается карточка профиля
- THEN в поле «Роль» отображается «Не назначена», а не пустое значение
```

## Что делает этот образец правильным

- `## ADDED Requirements` — точное имя секции дельты (I.7.5), не `## ADD Requirement`.
- `### Requirement: <название>` — есть, `MUST` стоит в теле требования строкой сразу после заголовка (I.7.3), не в заголовке.
- `#### Scenario: <ПРЕФИКС>-<NNN> <название>` — идентификатор перед названием, формат `<ПРЕФИКС>-<NNN>` (латиница верхнего регистра + три цифры), не `PILOT-003.1` (I.7.4).
- Каждый сценарий — `GIVEN`/`WHEN`/`THEN` на латинице, содержание по-русски (решение команды, раздел I.7.3).
- Требование содержит минимум два сценария — полнота (I.7.3: «хотя бы один», но positive/negative — норма команды по I.27).

## Что в требование не попадает (I.7.7)

Поведение при выключенном релизном флаге в требование **не пишется** — оно живёт как технический критерий (`AC-*`) в Work Package типа `enables`, не в Scenario:

```markdown
## ADD Work Package (configuration, enables)

AC-PILOT-003.1: пока релизный флаг выключен, поведение роли не меняется
для пользователей вне whitelist пилота; включение — по решению Release
Owner, критерий подтверждён статусом `Verified` до раскатки в production.
```

Имена классов, таблиц, компонентов, отступы, палитра — тоже не в требование (I.7.7): это код и макет, а не наблюдаемое поведение.
