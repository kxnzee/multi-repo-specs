# Временный backlog: зависимые Changes одного релиза

> Статус документа: `implementation_complete`.
>
> `DEP-001` и `SPEC-001` реализованы и проверены. `DEP-LATER` отложен до появления
> подтверждённой потребности.
>
> Нормативные правила уже перенесены в `AGENTS.md`, `docs/steps/`, reference и
> OpenSpec project context. Файл временно сохранён для review реализации и после него
> может быть удалён.

## 1. Проблема

В одном релизе могут существовать два самостоятельных OpenSpec Change:

- Change B зависит от поведения, которое вводит Change A;
- Change A уже принят и реализуется либо реализован, но ещё не архивирован;
- Archive обоих Changes выполняется только после завершения всего релиза;
- Delta Specs Change A до Archive отсутствуют в Master Specs;
- стандартное создание Delta Specs Change B использует Master Specs и не строит
  автоматически эффективную спецификацию из других активных Changes.

Из-за этого Change B нельзя надёжно описать как `MODIFIED` относительно требования,
которое пока существует только в Delta Specs Change A. Простая ссылка на Change A
не делает его Delta Specs базой OpenSpec-валидации Change B.

## 2. Принятое направление

Для последовательных зависимых Changes использовать стандартный `/opsx-sync`.

После принятия Planning PR Change A его Delta Specs при необходимости применяются к
Master Specs через отдельный reviewed Sync PR. Change A остаётся активным и не
архивируется. Change B после merge Sync PR планируется относительно обновлённых
Master Specs и явно указывает зависимость от Change A.

Собственный механизм Effective Specs на первом этапе не создаётся. Встроенные
OpenSpec skills и `opsx-*` commands не изменяются.

```text
Master Specs N
    │
    ├── Change A: Planning PR
    │              └── /opsx-sync A
    │                         │
    ▼                         ▼
Master Specs N+A ← merge отдельного Sync PR; Change A остаётся активным
    │
    └── Change B: Explore → Planning PR → implementation
                                      │
                                      ▼
                    Composite Verification A + B
                                      │
                         rollout и manual verification
                                      │
                              Archive A → Archive B
```

## 3. Новое значение Master Specs

После введения раннего Sync Master Specs центрального Store означают:

> принятое целевое поведение системы, доступное как нормативная база для
> последующих Changes, включая синхронизированные, но ещё не архивированные Changes.

Master Specs после Sync не являются самостоятельным доказательством того, что
поведение уже развёрнуто в production. Фактическое состояние поставки определяется
действующим release-процессом и его проверками.

Archive остаётся операцией финализации Change и разрешён только после выполнения
проектных условий для всех затронутых репозиториев и ручной проверки.

## 4. Термины и состояния

### 4.1. `spec_baseline`

Точная Git SHA Store, на которой реализация конкретного Change получила принятые
Proposal, Delta Specs, Design и Tasks.

У Change A и Change B могут быть разные `spec_baseline`. Все Code Repositories
одного Change продолжают использовать один принятый Baseline этого Change.

### 4.2. Sync PR

Обычный Git PR центрального Store, в котором стандартный `/opsx-sync <change-a>`
переносит Delta Specs A в Master Specs. Отдельный статус, manifest или runtime-state
для раннего Sync не создаётся.

История Git и ссылка на Sync PR достаточны для первой версии. Полная SHA merge Sync
PR может использоваться для аудита, но не вводится как новый обязательный параметр
Orchestrator Core или implementation subtask.

## 5. Пользовательский процесс

### 5.1. Подготовить Change A

Change A проходит обычное планирование:

```text
Explore → Change и Proposal → Specs, Design и Tasks
→ Planning PR → spec_baseline A
```

Change B не использует Delta Specs A как Master Specs, пока отдельный Sync PR A не
слит. Завершение реализации A не является дополнительным гейтом раннего Sync:
решение синхронизировать принятую дельту принимает Change Owner для подготовки
зависимого Change B.

### 5.2. Создать отдельный Sync PR

Из актуальной основной ветки центрального Store создаётся отдельная ветка:

```text
sync/<change-a>
```

В ней выполняется стандартная команда:

```text
/opsx-sync <change-a>
```

Перед публикацией Change Owner просматривает результат стандартного OpenSpec
workflow и diff Master Specs, затем создаёт commit и открывает отдельный Sync PR.
Специальная строгая валидация Orchestrator Core и собственный автоматический поиск конфликтов
не добавляются. Согласование дельты выполняют стандартный OpenSpec workflow, агент и
обычный review PR.

Ожидаемый diff Sync PR ограничен:

```text
openspec/specs/**
```

Если стандартный `/opsx-sync` требует допустимого служебного изменения вне этой
области, оно должно быть отдельно исследовано и явно добавлено в нормативный список;
молчаливое расширение diff запрещено.

В описании Sync PR достаточно указать Change A и зависимый Change или ticket B.
Обязательная собственная YAML-schema, evidence manifest и список `code_revision` не
вводятся. После merge Change A остаётся в `openspec/changes/<change-a>/`.

### 5.3. Создать зависимый Change B

Explore Change B запускается только после merge Sync PR A и читает актуальные
Master Specs. Зависимость фиксируется человекочитаемой ссылкой в стандартных
planning-артефактах, без новой OpenSpec schema:

- Proposal B объясняет функциональную зависимость и её границы;
- Delta Specs B описывают только поведение B относительно обновлённых Master Specs;
- Design B фиксирует интеграционный контракт, совместимость, порядок поставки и
  поведение при недоступности A;
- Tasks B включают проверку зависимости и совместную Composite Verification;
- Planning PR B содержит ссылку на Change A и его Sync PR.

После merge Planning PR B его собственная merge SHA становится `spec_baseline B`.
Именно Baseline B передаётся в `openspec-orch load` для реализации Change B.

### 5.4. Реализовать Change B

Apply-сессия Change B должна получать необходимый контекст зависимости из принятой
ревизии Store:

- применимые Master Specs, уже содержащие Delta Specs A;
- Proposal, Delta Specs, Design и назначенные Tasks Change B;
- человекочитаемую зависимость от Change A;
- межсистемный контракт A, необходимый для реализации B;
- актуальные planning-артефакты Change B.

### 5.5. Завершить релиз

Перед Archive должны быть выполнены:

1. все Work Packages A и B;
2. проверки каждого Code Repository;
3. действующие проектные проверки релиза;
4. manual verification зависимого сценария;
5. выполнение действующих проектных Archive gates.

Archive выполняется в известном команде порядке: сначала Change A, затем Change B:

```text
/opsx-archive <change-a>
/opsx-archive <change-b>
```

Archive A должен распознать, что его Delta Specs уже синхронизированы, не создать
повторные Requirements и переместить Change A в архив. Затем Archive B применяет
свою дельту поверх состояния, включающего A.

Для первой версии используется последовательный Archive. Специальная автоматическая
проверка порядка и собственная обёртка над `/opsx-bulk-archive` не создаются.

## 6. Изменение Change A после Sync

### 6.1. Change B ещё не начал Planning

1. остановить создание B;
2. провести correction planning-артефактов A;
3. выполнить `/opsx-sync <change-a>` в новом Sync PR;
4. только после этого начинать B.

### 6.2. Planning PR Change B открыт, реализация не началась

1. заблокировать merge Planning PR B;
2. провести correction и повторный Sync A;
3. обновить ветку B относительно основной ветки Store;
4. выполнить `/opsx-update <change-b>`;
5. просмотреть изменения B и обновить ссылку на Sync PR A;
6. продолжить обычный review Planning PR B.

### 6.3. Реализация Change B уже началась

1. остановить затронутые Work Packages и implementation PR B;
2. провести correction и повторный Sync A;
3. определить влияние на Delta Specs, Design, Tasks и код B;
4. провести correction Planning PR B;
5. продолжить обычный correction flow Change B и повторить необходимые действия
   текущего процесса.

Автоматическая инвалидация, сравнение Baselines и перепривязка Work Packages в первой
версии не реализуются. Если пилот покажет повторяемую проблему, она будет оформлена
как отдельное улучшение на основании фактического сценария.

## 7. Отмена и откат зависимости

Если после Sync Change A отменён:

1. остановить известный зависимый Change B;
2. не удалять Change A и не редактировать Master Specs напрямую;
3. открыть отдельный revert/correction PR, возвращающий Master Specs в согласованное
   состояние;
4. сохранить связь с Sync PR A и причиной отмены;
5. решить для B: отменить, перепланировать или перевести на другую зависимость;
6. не использовать Archive как замену откату.

## 8. Несколько зависимостей

В первой версии зависимости остаются явными человекочитаемыми ссылками между
Changes:

```text
A ──► B ──► D
└───► C ──► D
```

Собственный dependency graph, поиск циклов, транзитивная инвалидация и
автоматический порядок Archive не реализуются. Агент учитывает указанные связи при
подготовке Change, а участники проверяют их в обычных PR. Эти механизмы добавляются
только при подтверждённой потребности по результатам реальной работы.

## 9. Что требуется реализовать

### DEP-001 — Нормативная модель раннего Sync

- **Приоритет:** P1
- **Статус:** `implemented`

Обновить проектные правила так, чтобы Master Specs могли изменяться стандартным
`/opsx-sync` до Archive только для принятой зависимости между Changes и через reviewed
Sync PR.

Первая версия является документационным и agent-context изменением. Она не добавляет
новую команду `openspec-orch`, schema, manifest, runtime-state или проектный валидатор.

Затронутые места:

- `AGENTS.md`;
- `templates/base/skeleton/openspec/config.yaml`;
- `docs/reference/changes.md`;
- `docs/steps/README.md`;
- `docs/steps/03.md` и `docs/steps/04.md` в части подготовки зависимого Change и Sync
  PR.

Реализуемый пользовательский маршрут:

1. Planning PR Change A слит;
2. Change Owner создаёт `sync/<change-a>` от актуальной основной ветки Store;
3. агент выполняет стандартный `/opsx-sync <change-a>`;
4. Change Owner просматривает diff, создаёт commit и отдельный Sync PR;
5. после merge Change B создаётся относительно обновлённых Master Specs;
6. Proposal/Design B человекочитаемо ссылаются на Change A и Sync PR;
7. в конце релиза команда последовательно архивирует A, затем B.

Минимальные критерии готовности:

- документация и OpenSpec project context разрешают этот маршрут и не противоречат
  друг другу;
- обычный ранний Sync без зависимого Change не объявляется штатным действием;
- Change A после Sync остаётся активным;
- Sync PR изменяет Master Specs стандартным OpenSpec workflow;
- зависимость B от A видна людям в стандартных planning-артефактах и PR;
- Archive остаётся финализацией после действующих проектных проверок;
- встроенные OpenSpec skills и `opsx-*` commands не изменены;
- существующие тесты и `git diff --check` проходят.

Результат реализации:

- правила раннего Sync добавлены в `AGENTS.md` и OpenSpec project context;
- маршрут Change A → Sync PR → Change B, работа с существующими Master Specs и
  correction-кейсы объединены в справочнике `docs/reference/changes.md`; шаги 01–04
  содержат только условные ссылки на нужные разделы;
- отмена Change после Sync и несколько человекочитаемых зависимостей описаны в том же
  справочнике без отдельной schema или dependency graph;
- отдельная команда, schema, runtime-state, строгая валидация и поиск конфликтов не
  добавлялись;
- встроенные OpenSpec skills и `opsx-*` commands не изменялись;
- функциональные тесты Orchestrator Core не зависят от текста пользовательской документации.

### DEP-LATER — Возможные улучшения только по фактической потребности

- **Приоритет:** не назначен
- **Статус:** `deferred_until_observed`

В первую версию намеренно не входят:

- собственная строгая валидация Sync или зависимого Change;
- автоматический поиск конфликтов активных Delta Specs;
- schema/manifest статуса `dependency_ready`;
- обязательный `dependency_spec_revision` как новый параметр Orchestrator Core;
- dependency graph, поиск циклов и транзитивная инвалидация;
- автоматическая перепривязка Work Packages;
- собственная оркестрация Composite Verification или Archive;
- автоматизированный revert раннего Sync;
- обёртка над `/opsx-sync`, `/opsx-archive` или `/opsx-bulk-archive`.

В первой версии используются стандартные проверки и поведение OpenSpec, анализ
агента и обычный review PR. Любой механизм из списка выше возвращается в backlog
только после зафиксированного реального сбоя, повторяемой ручной ошибки или измеримой
стоимости текущего процесса.

### SPEC-001 — Изменение одной или нескольких capabilities без дублирования Master Specs

- **Приоритет:** P1
- **Статус:** `implemented`

Явно описать и проверить процесс, в котором новый Change изменяет или создаёт одну
либо несколько связанных capabilities, а Archive применяет каждую Delta Spec по её
исходному иерархическому пути без конкурирующих Master Specs.

Принятое распределение ответственности:

- Change Owner определяет и подтверждает целевое наблюдаемое поведение и границы
  Change, но не обязан вручную выбирать синтаксическую Delta operation;
- агент на точном planning Baseline читает подтверждённый intent, Proposal и
  фактическую Master Spec, после чего предлагает `ADDED`, `MODIFIED`, `REMOVED` или
  `RENAMED` с указанием целевых capability и Requirement;
- Spec Owner в Planning PR подтверждает, что выбранная операция корректно изменяет
  существующий нормативный контракт и не создаёт дублирование;
- `openspec validate --strict` является структурной защитой, но не заменяет решение
  Change Owner о поведении и содержательное подтверждение Spec Owner;
- при неоднозначности агент не выбирает операцию молча, не создаёт новую capability
  «на всякий случай» и не продолжает Specs: он показывает найденную Master Spec,
  варианты результата и запрашивает решение Change Owner.

Правило определения Delta operation:

| Фактическое состояние Master Spec | Подтверждённое намерение | Операция |
|---|---|---|
| Requirement отсутствует | Добавить самостоятельное наблюдаемое поведение | `ADDED` |
| Requirement существует | Изменить правило, условие или его Scenarios | `MODIFIED` |
| Requirement существует | Полностью прекратить поддержку поведения | `REMOVED` |
| Меняется только имя Requirement | Сохранить прежнее поведение | `RENAMED` |
| Наблюдаемое поведение не меняется | Рефакторинг, tooling или документация | Delta Spec не создаётся |

Intent сам по себе не является достаточным основанием для выбора операции. Решение
строится как сравнение подтверждённого целевого поведения с Master Spec на точном
planning Baseline. Если переименование одновременно меняет поведение, агент должен
явно представить составное изменение для review, а не маскировать смысловое изменение
одной операцией `RENAMED`.

Нормативный процесс:

1. До создания Delta Spec агент на точном planning Baseline проверяет каталог
   `openspec/specs/` и находит существующую capability и Requirement.
2. Proposal относит точное существующее имя capability к `Modified Capabilities`,
   а не к `New Capabilities`.
3. Delta Spec создаётся по тому же относительному capability path:

   ```text
   Master: openspec/specs/<capability>/spec.md
   Delta:  openspec/changes/<change-id>/specs/<capability>/spec.md
   ```

4. Для изменения существующего Requirement без переименования используется
   `## MODIFIED Requirements`. Заголовок `### Requirement: <name>` должен совпадать с
   Master Spec, а блок должен содержать полную новую версию Requirement и все
   сохраняемые Scenarios.
5. Для самостоятельного нового Requirement внутри уже существующей capability
   используется `## ADDED Requirements` в Delta Spec того же capability path.
6. Для удаления и переименования применяются соответственно `REMOVED` и `RENAMED`;
   новая capability не создаётся как обход существующего контракта.
7. Planning PR явно подтверждает ожидаемый результат Archive: какой существующий
   файл и Requirement будут изменены, добавлены, удалены или переименованы.
8. Стандартная OpenSpec-валидация проверяет структуру дельты, а агент и содержательное
   ревью блокируют неправильный тип операции, несовпадающий capability path,
   частичный `MODIFIED` и дублирующее Requirement.
9. Archive применяет Delta Spec к исходной Master Spec и не создаёт каталог вида
   `<capability>-v2`, второе Requirement с тем же смыслом или другой параллельный
   источник истины.
10. Если одна бизнес-цель затрагивает несколько capabilities, Change содержит по одной
    Delta Spec на каждый точный путь; существующие Master Specs обновляются, а новые
    создаются только из `New Capabilities` с `Purpose` и `ADDED Requirements`.

Не считать дублированием:

- новый Change и его Delta Spec — это история предлагаемого изменения;
- архивная копия Change — это audit trail;
- `ADDED Requirement` в существующей capability — это расширение исходной Spec,
  если поведение действительно является отдельным Requirement.

Считать ошибкой:

- существующая capability объявлена как `New Capabilities` без явного решения о
  создании самостоятельного контракта;
- вместо `MODIFIED` прежнее поведение повторено как новое `ADDED Requirement`;
- для той же бизнесовой возможности создано новое имя capability только ради новой
  версии;
- `MODIFIED` не содержит всех сохраняемых Scenarios;
- заголовок Requirement не совпадает с Master Spec и поэтому старый блок не может
  быть однозначно заменён;
- после Archive одновременно остаются старое и новое противоречащие Requirements.

Требуемые изменения:

- дополнить пользовательский шаг подготовки Specs практическим выбором
  `New Capabilities` / `Modified Capabilities`;
- закрепить правила capability path и полного `MODIFIED` в OpenSpec project context;
- добавить проверку Planning PR существующей Master Spec и ожидаемого результата
  Archive;
- закрепить, что структура проверяется штатным `openspec validate --strict`, а
  содержательный выбор операции — агентом и обязательным review;
- обязать planning-agent показывать обоснование выбранной Delta operation через
  ссылку на существующий capability path и Requirement либо через подтверждённое
  отсутствие такого Requirement;
- закрепить блокирующий вопрос Change Owner при неоднозначной классификации и
  обязательное подтверждение Spec Owner в Planning PR;
- не изменять встроенные OpenSpec skills и `opsx-*` commands.

Приёмочные сценарии процесса:

1. существующий Requirement успешно изменяется через полный `MODIFIED`;
2. новое Requirement добавляется в существующую capability через `ADDED`;
3. существующая capability ошибочно объявлена новой;
4. `MODIFIED` использует неправильное имя Requirement;
5. `MODIFIED` теряет сохраняемый Scenario;
6. Change пытается создать `<capability>-v2` для прежнего поведения;
7. Archive обновляет один исходный Master Spec без дублирования;
8. после rebase Delta Spec повторно сравнивается с актуальной Master Spec и при
   необходимости обновляется;
9. неоднозначный intent останавливает создание Specs до решения Change Owner;
10. неверно предложенная агентом операция блокируется review Spec Owner.

Критерий готовности: участник может по существующей Master Spec создать новый Change,
а Planning PR и проверки однозначно доказывают, что Archive изменит именно выбранную
capability и не создаст конкурирующий нормативный контракт.

Результат реализации:

- работа с существующей Master Spec и коррекция активного Change объединены в
  `docs/reference/changes.md`;
- там же описан один Change с несколькими Delta Specs и вложенными capability paths;
- шаги 02–04 содержат только действия пользователя и ссылки на общий справочник;
- `AGENTS.md` запрещает replacement capability и версионированные дубликаты;
- `openspec/config.yaml` требует сравнить intent с Master Spec, сохранить capability
  path и полный `MODIFIED`, а при неоднозначности запросить решение Change Owner;
- Planning PR фиксирует ожидаемый результат Archive, который подтверждает Spec Owner;
- собственный валидатор Orchestrator Core и тесты формулировок документации не добавлялись.

## 10. Критерии завершения backlog

Backlog можно закрыть и удалить, когда:

- нормативный процесс перенесён в проектную документацию и agent context;
- ранний Sync выполняется стандартным `/opsx-sync` через отдельный Sync PR;
- зависимость A → B видна в стандартных planning-артефактах и PR;
- процесс не вводит собственную строгую валидацию, поиск конфликтов или dependency
  graph;
- Archive A и B выполняется последовательно стандартными командами OpenSpec;
- изменение существующей capability использует тот же capability path и корректную
  Delta operation без дублирования Master Specs;
- существующие функциональные тесты и `git diff --check` пройдены;
- встроенные OpenSpec skills и `opsx-*` commands не изменены;
- временные решения и открытые ограничения перенесены либо закрыты.

## 11. Зафиксированные упрощения первой версии

1. Отдельный статус `dependency_ready` и evidence manifest не создаются.
2. Sync разрешён после принятия Planning PR A; готовность к production этим не
   утверждается.
3. Для Sync PR используются обычные правила review центрального Store без нового
   набора обязательных ролей.
4. OpenSpec и агент выполняют анализ дельты; Orchestrator Core не дублирует их строгой
   валидацией и поиском конфликтов.
5. Зависимость B от A фиксируется обычным текстом и ссылками, без schema и graph.
6. Изменение A после Sync обрабатывается новым Sync PR и обычным `/opsx-update B`.
7. Archive выполняется последовательно: сначала A, затем B. Автоматизация порядка и
   `bulk-archive` не входят в первую версию.
8. Дополнительные механизмы проектируются только после появления измеримой проблемы.
