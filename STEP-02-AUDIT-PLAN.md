# План по результатам аудита шагов 00–02

Документ объединяет все замечания, найденные во время ревью шага 02, его соответствия шагам 00 и 01, общей архитектуре SDD/OpenSpec и структуре `openspec/context/`.

- `[x]` — пункт уже выполнен в текущем рабочем дереве.
- `[ ]` — замечание только зафиксировано; исправление ещё не применялось.
- `P1` — блокирует согласование контракта до реализации.
- `P2` — требует исправления, но может выполняться после выбора основного решения.
- `P3` — редакционная или оформительская правка.

## 1. Переходы между шагами и контракт `sdd change`

- [x] **Объединить создание Change и Proposal.** Шаг 02 теперь продолжает подтверждённый Explore в той же агентской сессии, создаёт Change и сразу формирует `proposal.md`. Отдельный handoff-файл не вводится: существенные выводы Explore сохраняются в стандартном Proposal, а при потере сессии Explore повторяется.

- [x] **Унифицировать поиск Changes по ticket в документации.** Шаги 01 и 02 теперь считают совпадением точное имя `pay-412` и префикс `pay-412-*` для активных и архивных Changes. Реализацию этого контракта нужно покрыть тестами при добавлении команды.

- [x] **Принять процессную сериализацию планирования до Planning PR.** Один назначенный Change Owner ведёт ticket на одной рабочей машине, создаёт Change и готовит Proposal, Delta Specs, Design и Tasks в единственной planning-ветке. Техническая межмашинная резервация не требуется. После открытия Planning PR владельцы соответствующих блоков проводят ревью, а Change Owner вносит согласованные исправления в ту же ветку; параллельные версии planning-артефактов не создаются.

- [x] **Разделить Git-проверки первого и повторного запуска в контракте.** Первый запуск требует чистую актуальную основную ветку, а продолжение допускает ожидаемую planning-ветку и изменения только внутри текущего Change. Реализацию нужно подтвердить сценарными тестами.

- [x] **Описать продолжение объединённого шага и последующие состояния.** Change без Proposal и неподтверждённый Proposal являются возобновляемыми состояниями. Наличие Delta Specs, `design.md` или `tasks.md` запрещает возвращать процесс к шагу 02.

- [x] **Определить проверку remote-ветки.** В контракте первого запуска зафиксирован адресный `git ls-remote --heads origin refs/heads/feature/<change-id>`.

- [x] **Устранить противоречие проверки Code Repositories.** Шаг 02 не читает и не проверяет Code Repositories заново, а гарантирует только отсутствие обращений и записи. Ревизии берутся из принятого Explore.

- [x] **Исправить переход после Explore.** Шаг 01 теперь явно передаёт подтверждённые выводы объединённому шагу 02, который создаёт Change и Proposal.

## 2. Соответствие общей архитектуре

- [x] **Добавить создание Change в архитектурную таблицу шага 00.** Архитектурный обзор теперь включает `new change`, `status` и `instructions`, а также ticket, planning-ветку и процессные гейты SDD.

- [x] **Исключить `docs/OpenSpec для команды.md` из локальной нормализации.** Это read-only рекомендация с места работы: она задаёт общий ориентир flow, но не обязана совпадать с кастомными командами, шагами и гейтами этого репозитория. Расхождения с локальной реализацией сами по себе не являются дефектами; менять файл можно только по прямому запросу пользователя.

- [x] **Унифицировать каноническую запись Change ID в roadmap.** Roadmap больше не показывает двусмысленный uppercase-шаблон; точная машинная форма `<ticket-lowercase>-<name>` определена в шаге 02 отдельно от исходного Jira key.

## 3. Маршрутизация и размещение контекста

- [x] **Добавить архитектурный и security-контекст в маршрут Explore.** `00-start-here.md` теперь направляет Explore, Proposal и Delta Specs также в `03-architecture.md`, `05-security-and-compliance.md`, `system-map.yaml` и релевантные ADR.

- [x] **Обязать `/sdd-context` читать существующий `system-map.yaml`.** Команда теперь проверяет обязательный YAML и читает его до обработки `_raw/` и интервью, даже если файл содержит только каркас и TODO.

- [x] **Развести продуктовые и технические ограничения.** В `01-product-context.md` остались только бизнес-ограничения Change Owner. Технические ограничения перенесены в отдельный раздел `03-architecture.md` под ответственность Technical Owner; долговечное принятое решение при необходимости оформляется ADR.

- [x] **Уточнить место вопроса о неизвестном репозитории.** Неизвестная система или Code Repository теперь фиксируется в `system-map.yaml`, связанный вопрос о границах и ответственности — в `03-architecture.md`. `Open questions` в `00-start-here.md` используется только при действительно неизвестном целевом файле.

## 4. Владение и подтверждение контекста
- [x] **Настроить действующий CODEOWNERS до первого `/sdd-context`.** Шаг 00 теперь требует заменить placeholder реальными account handles и активировать правила до первичного наполнения контекста. `/sdd-context` не изменяет нормативные файлы без активного правила для каждого целевого пути.

- [x] **Закрепить release-контекст за Technical Owner.** `08-release-process.md`, документация и CODEOWNERS используют постоянную роль Technical Owner. Отдельная роль Release Owner пока исключена и может быть добавлена позже после практической проверки процесса.

- [x] **Унифицировать имя Security Owner.** Все содержательные TODO используют каноническую роль `Security Owner`. Запись вида `@security-owner` в шаблоне CODEOWNERS является заменяемым account handle, а не альтернативным названием роли.

- [x] **Исправить редакционные дефекты `docs/steps/02.md`.** Документ переписан с корректными формулировками и завершающим переводом строки.

## 6. Финальная проверка после выполнения плана

- [ ] После реализации `sdd change` и `/sdd-change` подтвердить кодом и тестами, что команда использует текущий Explore, создаёт Change официальным OpenSpec CLI и формирует Proposal по официальным instructions.
- [ ] Повторно сопоставить вход, результат и гейт каждого шага 00 → 01 → 02 → 03.
- [ ] Проверить одинаковые алгоритмы ticket/Change ID на активных и архивных Changes.
- [ ] Проверить сценарии первого запуска, безопасного повтора и частичного состояния; отдельно подтвердить, что параллельное планирование одного ticket с другой машины запрещено процессом и не заявляется как гарантия CLI.
- [ ] Проверить, что каждый тип контекста имеет одно нормативное место и одного канонического владельца.
- [ ] Проверить согласованность локальных контрактов `docs/steps/*.md`, skeleton, `sdd-context.md`, CODEOWNERS и CLI help; `docs/OpenSpec для команды.md` использовать только для сверки общего flow без требования совпадения реализации.
- [ ] Добавить или обновить тесты для принятых контрактов, затем выполнить `npm run check`, `npm test` и `git diff --check`.
