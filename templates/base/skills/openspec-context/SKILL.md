# Контекст OpenSpec-проекта

Поддерживать краткие подтверждённые знания о проекте, необходимые для понимания Specs,
Changes и межсистемного влияния. Не превращать context pack в документацию каждого
репозитория.

## Основные принципы

- Описывать общую концепцию проекта, продукт, домен, системы, межсистемные контракты и
  общие правила. Детали локальной реализации читать из Code Repository по мере
  необходимости.
- Хранить каждый факт в одном каноническом месте и ссылаться на него, а не копировать.
- Заполнять только файлы, для которых найдены относящиеся к ним долговечные факты.
  Пустой scaffold или незаполненный раздел допустимы. Заголовки и пример структуры
  Template не считать чек-листом обязательного заполнения.
- Не обновлять тематический файл только потому, что зарегистрирован новый Repository.
  Repository, не меняющий соответствующую общую концепцию или правило, не должен
  появляться в этом файле.
- Не стремиться описать проект полностью за один запуск. Исследовать только сведения,
  необходимые для устойчивого project-level контекста.

## Границы записи

- Определить OpenSpec root по `openspec/config.yaml`. Не требовать Orchestrator metadata, Store registry,
  конкретную структуру репозиториев или provider-specific команды. Если существует
  `openspec-orch.yaml`, использовать его только как authoritative registry identity:
  `repository-id`, roles, remotes и default branches.
- Сначала прочитать инструкции проекта, существующий context pack, принятые ADR и
  относящиеся к запросу Specs.
- Без отдельной просьбы писать только в `openspec/context/`. Не изменять
  `openspec/specs/`, `openspec/changes/`, прикладной код, встроенные OpenSpec skills и
  `opsx-*` commands.
- Не сохранять секреты, credentials, приватные ключи, access tokens и лишние
  персональные данные.
- Не переносить в долговечный контекст текущее состояние машины, сессии, ветки,
  checkout, незакоммиченный diff, количество commits, ограничения исследования и
  другую transient-информацию. Git revision использовать только как evidence.
- Передавать термины, лицензии, security-классификации, сроки и границы с точным
  смыслом источника. Не усиливать источник и не записывать предположение как факт.

## Единственный владелец информации

- `openspec-orch.yaml` — identity и регистрация Repository.
- `system-map.yaml` — единственная карта Repository, систем и отношений между
  системами: направление, тип и краткий смысл контракта. Держать карту компактной.
- `repositories/<repository-id>.md` — только уникальная долговечная ответственность,
  смысловая граница, внешний контракт или обязательное ограничение конкретного
  Repository, нужные для планирования Change. Не повторять карту систем и не создавать
  файл только потому, что Repository присутствует в реестре.
- `00-start-here.md` — только навигация и общие правила чтения. Не перечислять в нём
  конкретные Repository и не дублировать TODO из остальных файлов.
- Тематические файлы `01`–`08` — project-level знания по своей теме. Не перечислять в
  них все Repository и не вести сквозное описание одного Repository через весь pack.
- `06-cross-system-invariants.md` — смысл общих инвариантов нескольких систем.
  Существование и направление связей остаются в `system-map.yaml`; здесь использовать
  system-id и не повторять repository topology.

Добавление Repository в обычном случае должно требовать только изменения реестра,
`system-map.yaml` и, если есть уникальный подтверждённый контекст, одного
`repositories/<repository-id>.md`. Изменять тематический файл только при появлении
нового общего project-level факта.

## Порядок работы

1. Определить режим:
   - `initialize`: context pack отсутствует либо содержит только Template scaffold;
   - `audit`: сравнить существующий контекст с источниками без записи;
   - `update`: применить подтверждённые добавления, исправления или удаления.
   Если намерение записи неясно, задать один вопрос до изменения файлов.
2. До исследования составить краткий список предполагаемых целевых файлов. Не
   включать все файлы автоматически.
3. Классифицировать каждый кандидат:
   - project-level факт → соответствующий тематический файл;
   - система, Repository или отношение → `system-map.yaml`;
   - уникальная repository boundary → `repositories/<repository-id>.md`;
   - межсистемный поведенческий инвариант → `06-cross-system-invariants.md`;
   - решение конкретного Change → Specs, Design или Tasks, но не context pack;
   - локальная реализация или transient evidence → не записывать.
4. Адресно прочитать минимально необходимые источники. Вывод read-only subagent
   считать только навигацией; перед записью самостоятельно открыть evidence и
   проверить полный смысл утверждения.
5. Разложить составное утверждение на атомарные факты. Записывать только то, что
   подтверждено целиком.
6. Изменять только выбранные целевые файлы. Несвязанные scaffold-файлы и разделы
   оставлять без изменений.
7. Не создавать TODO ради полноты шаблона. Добавлять только один конкретный вопрос,
   если без ответа нельзя корректно записать важный долговечный факт. Указывать
   реального `owner` и `expected_source`; не использовать `unassigned`.
8. При конфликте источников вернуть `needs_confirmation`, показать обе версии и не
   выбирать трактовку самостоятельно. Конфликт registry role с документацией о
   deprecated, archived или moved Repository не разрешать изменением контекста.
9. Создавать ADR только для явно принятого долговечного решения.
10. Обновлять `00-start-here.md` последним и только при изменении маршрутизации или
    общих правил чтения.

## Фильтр содержания

Сохранять:

- назначение продукта, пользователей, ценность и устойчивые границы scope;
- предметные термины, сущности, отношения, состояния и бизнес-правила;
- концептуальные системы, их ответственность и межсистемные контракты;
- общие security, compliance, quality-gate и release-правила проекта;
- устойчивые repository boundaries, реально влияющие на planning нескольких Changes.

Не сохранять без отдельного доказанного project-level основания:

- списки каталогов, файлов, классов, функций, пакетов и внутренних API;
- версии toolchain, framework и зависимостей;
- перечни CI workflows, test suites и локальных команд запуска;
- build tags, feature flags и миграционные файлы как инвентарь реализации;
- upstream release facts, не являющиеся политикой текущего проекта;
- полные списки Repository в каждом тематическом файле;
- требования, Scenarios, Tasks и проверки конкретного Change.

Техническую деталь сохранять только когда она является подтверждённым внешним
контрактом, общим межсистемным ограничением или обязательной project-level политикой.

## Маршрутизация

- `01-product-context.md`: продукт, пользователи, ценность, scope; без списка Repository.
- `02-domain-glossary.md`: предметные и неоднозначные термины; не индекс символов кода.
- `03-architecture.md`: концептуальные компоненты и архитектурные принципы; без
  каталогов, классов и покомпонентного inventory.
- `04-domain-model.md`: смысл сущностей, отношения, состояния и жизненные циклы; код
  может быть evidence, но не заменяет модель.
- `05-security-and-compliance.md`: общие правила данных, доступа, privacy и compliance;
  без перечня handlers и security-пакетов.
- `06-cross-system-invariants.md`: только правила, одновременно обязательные для двух
  или более систем.
- `07-quality-gates.md`: стабильная project-level политика Gate и evidence; без
  матрицы CI и тестовых команд каждого Repository.
- `08-release-process.md`: процесс поставки, наблюдения и rollback текущего проекта;
  без инвентаря upstream release и repository implementation.
- `system-map.yaml`: компактная карта Repository, систем и отношений.
- `repositories/<repository-id>.md`: минимальные уникальные repository boundaries.
- `ADR/`: принятые архитектурные решения.
- `_raw/`: ненормативные исходные материалы.

## Evidence и проверка

1. Для каждого изменённого факта иметь точное evidence `path:line`, но не копировать
   технический evidence во все context-файлы. В результате запуска перечислить
   evidence отдельно; в context сохранять ссылку только когда она нужна для проверки
   важного или неоднозначного правила.
2. Не выводить назначение компонента из имени, зависимости или соседнего сервиса. Не
   записывать формулировки «вероятно», «возможно» и «по-видимому» как факты.
3. Разобрать `system-map.yaml` как YAML, проверить уникальность system-id и
   repository-id, затем сопоставить Repository с role `code` реестра.
4. Проверить single ownership: Repository topology не должна дублироваться в
   `00`–`08`, а repository-specific detail — повторяться в нескольких файлах.
5. Проверить change isolation: мысленно добавить ещё один Repository. Если это требует
   правки нескольких тематических файлов без нового project-level факта, структура
   сформирована неверно.
6. Проверить итоговый diff: изменены только файлы с подтверждёнными относящимися к ним
   знаниями; пустые и нерелевантные файлы не заполнены.
7. Убедиться, что context pack не содержит Requirements, Scenarios, Delta operations,
   прогресс Tasks, секреты и неподтверждённые выводы.

Вернуть `context_status: current`, `updated` или `needs_confirmation`, затем перечислить
прочитанные источники, изменённые файлы, evidence `path:line` и оставшиеся вопросы.
