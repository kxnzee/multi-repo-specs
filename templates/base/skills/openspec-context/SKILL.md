# Контекст OpenSpec-проекта

Поддерживать краткие и подтверждённые знания проекта в `openspec/context/`.

## Границы

- Определить корень проекта из текущего workspace и потребовать
  `openspec/config.yaml`. Не требовать Orchestrator metadata, Store registry,
  конкретную структуру репозиториев или provider-specific команды. Если в проекте
  существует `openspec-orch.yaml`, использовать его только как authoritative registry
  `repository-id`, roles, remotes и default branches.
- Сначала прочитать инструкции проекта. Считать возможными источниками явные решения
  пользователя, принятые ADR, текущие Specs, код, конфигурацию, тесты, CI и
  поддерживаемую документацию; учитывать их фактический приоритет в проекте.
- Без отдельной просьбы писать только в `openspec/context/`. Не изменять
  `openspec/specs/`, `openspec/changes/`, прикладной код, встроенные OpenSpec skills
  и `opsx-*` commands.
- Не сохранять секреты, credentials, приватные ключи, access tokens и лишние
  персональные данные.
- Не переносить в долговечный контекст временные детали реализации, если они не
  определяют устойчивое ограничение или контракт проекта.

## Порядок работы

1. Определить режим по запросу:
   - `initialize`: context pack отсутствует или почти пуст;
   - `audit`: существующий контекст нужно сравнить с актуальными источниками без
     автоматического переписывания;
   - `update`: нужно применить подтверждённые добавления, исправления или удаления.
2. Просмотреть `openspec/context/`. Если context pack отсутствует, создавать только
   файлы, необходимые для относящихся к запросу знаний, и не заполнять шаблоны
   вымышленными фактами.
3. Прочитать `00-start-here.md`, `system-map.yaml`, существующие ADR и относящиеся к
   запросу тематические файлы. При наличии `openspec-orch.yaml` прочитать из него
   список Code Repositories и сопоставить точные id с `system-map.yaml` и
   `repositories/<repository-id>.md`.
4. Рассматривать `_raw/` как ненормативные исходные материалы. Выделять атомарные
   утверждения, находить для них целевой context-файл и подтверждающий источник.
5. Адресно исследовать минимально необходимые источники проекта. Если доступен
   подходящий project subagent, делегировать ему один ограниченный read-only вопрос;
   отсутствие subagents не должно блокировать работу.
6. Классифицировать кандидатов как подтверждённые факты, выводы, конфликты или
   открытые вопросы. Записывать только подтверждённые факты. Неизвестное оформлять
   как TODO с `question`, `owner` и `expected_source`, используя реальную модель
   владения проекта.
7. Сохранять подтверждённый существующий контекст. Перед удалением или существенным
   изменением показать конфликт и подтверждающее изменение evidence. Когда требуется
   решение человека, задавать по одному конкретному вопросу.
8. Создавать ADR только для явно принятого долговечного решения. Кандидат на решение
   оставлять TODO до подтверждения.
9. Обновлять `00-start-here.md` последним и сохранять его навигационным индексом, а не
   дубликатом остальных файлов.

## Маршрутизация

- `01-product-context.md`: назначение, пользователи, ценность, scope и бизнес-ограничения.
- `02-domain-glossary.md`: специфичные термины и их подтверждённые значения.
- `03-architecture.md`: компоненты, границы, интеграции и технические ограничения.
- `04-domain-model.md`: сущности, отношения, состояния и жизненные циклы.
- `05-security-and-compliance.md`: данные, доступ, приватность и запреты.
- `06-cross-system-invariants.md`: правила нескольких компонентов или репозиториев.
- `07-quality-gates.md`: стабильные проверки, критичные сценарии и evidence.
- `08-release-process.md`: среды, миграции, rollout, наблюдение и rollback.
- `system-map.yaml`: компактная машиночитаемая карта репозиториев, систем и связей.
- `repositories/<repository-id>.md`: ответственность, границы, контракты и устойчивые
  ограничения конкретного Code Repository; файл создаётся только для подтверждённого id.
- `ADR/`: принятые архитектурные решения.
- `_raw/`: исходные материалы, не являющиеся нормативным контекстом.

Не создавать новый файл верхнего уровня, если знание помещается в существующий.

## Проверка результата

1. Проверить изменённые ссылки и пути.
2. Разобрать `system-map.yaml` как YAML, проверить уникальность ID и, при наличии
   `openspec-orch.yaml`, убедиться, что repository ids существуют в его role `code`.
3. Убедиться, что контекст не содержит Requirements, Scenarios, Delta operations,
   прогресс задач, секреты и неподтверждённые выводы под видом фактов.
4. Проверить итоговый diff и ограничить изменения запрошенным контекстом.
5. Сообщить о конфликтах и TODO, не объявляя контекст полным при наличии неизвестного.

Вернуть `context_status: current`, `updated` или `needs_confirmation`, затем перечислить
прочитанные источники, изменённые файлы и оставшиеся вопросы по владельцам.
