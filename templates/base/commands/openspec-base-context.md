# /openspec-base-context

## Цель

Команда запускает сбор, проверку или актуализацию устойчивого project context, который
используется в OpenSpec workflow для понимания проекта и влияния изменений.

## Когда запускать

- Инициализировать context pack в новом Store.
- Аудитировать и сверить текущее состояние `openspec/context/` с источниками.
- Актуализировать конкретные долгоживущие факты после подтверждения изменений в
  документации или governance.

## Нефункциональные ограничения

- Не создавать и не изменять `openspec/specs/`, `openspec/changes/`, прикладной код и
  `.openspec-store`.
- Не изменять встроенные OpenSpec `openspec-*` навыки и `opsx-*` команды.
- Не переносить transient-данные, CI-конфигурации, текущие ветки, незакоммиченные
  diff-ы, секреты и персональные данные.

## Виды режима

1. `initialize`
   - `openspec/context/` отсутствует или содержит только шаблонный scaffold.
   - Заполнять только подтверждённые project-level факты.
2. `audit`
   - Проверить соответствие текущего context pack источникам без записи.
   - Вернуть расхождения и отсутствующие доказательства.
3. `update`
   - Применить подтверждённые добавления и корректировки после явного подтверждения
     намерения записи пользователем или надёжного evidence.

## Обязательные источники

- `openspec/config.yaml` и `openspec-orch.yaml` для понимания scope проекта.
- `openspec/context/` и `openspec/context/_raw/` для текущих файлов.
- `openspec/context/system-map.yaml` и `openspec/context/repositories/<repository-id>.md`.
- `openspec/context/ADR/README.md`, `openspec/context/00-start-here.md` и
  тематические файлы `01`–`08`.

## Ограничения авторства

- Каждый факт должен иметь evidence с точным `path:line`.
- Не считать предположения и transient-данные фактами контекста.
- Не копировать детали локальной реализации в `01`–`08`, если это не устойчивый
  project-level контракт.
- `repositories/<repository-id>.md` используются только для уникальной долговечной
  ответственности конкретного репозитория.
- Изменять темы `01`–`08` только при появлении новых устойчивых project-level фактов.

## Процедура

1. Определить ожидаемый режим (`initialize` / `audit` / `update`).
2. Классифицировать кандидатов в факты:
   - project-level → файлы `01`–`08`;
   - система/relationship → `system-map.yaml`;
   - уникальная ответственность репозитория → `repositories/<repository-id>.md`;
   - неизбыточный transient → без записи.
3. Написать только выбранные файлы; не редактировать неподтверждённые.
4. Перед записью вернуть `needs_confirmation`, если намерение неоднозначно.
5. Проверить итоговую трассируемость `path:line` и отсутствие регрессий правил.

## Формат ответа

- `context_status: current` — изменений не требуется.
- `context_status: updated` — изменён контекст после подтверждённого `update`.
- `context_status: needs_confirmation` — требуется подтверждение пользователя из-за
  конфликтующих или неполных источников.
- Перечислить `changed_files`, `evidence`, `read_sources`, `open_questions`.

## Запреты

- Не перечислять в context pack все репозитории по умолчанию.
- Не создавать отдельные workflow-файлы Changes/Specs/Tasks из этой команды.
- Не изменять поведение штатных OpenSpec команд и workflow.
