# /openspec-base-context

## Цель

Команда запускает сбор, проверку или актуализацию устойчивого контекста проекта,
который используется в OpenSpec workflow для понимания продукта, предметной области,
границ систем и влияния изменений.

## Когда запускать

- Инициализировать context pack в новом Store.
- Аудитировать и сверить текущее состояние `openspec/context/` с разрешёнными
  источниками без записи.
- Актуализировать конкретные долгоживущие факты после подтверждения изменений в
  документации или governance.

## Инвариантные точки входа

Команда опирается на инвариантные точки входа проекта:

- `openspec/config.yaml` — стандартная конфигурация OpenSpec и scope проекта;
- `openspec-orch.yaml` — реестр репозиториев, если проект использует Orchestrator;
- `openspec/context/00-start-here.md` — единственная точка входа в структуру
  контекста. Состав тематических файлов, их назначение и порядок чтения определяются
  им, а не этой командой;
- `openspec/context/system-map.yaml` — машиночитаемая карта систем и репозиториев;
- `openspec/context/_raw/` — ненормативные исходные материалы.

Не предполагать конкретный набор тематических файлов: Template может меняться. Если
`00-start-here.md` отсутствует или не описывает структуру, вернуть
`context_status: needs_confirmation` и не изобретать структуру самостоятельно.

## Виды режима

1. `initialize`
   - `openspec/context/` отсутствует или содержит только шаблонный scaffold;
   - подготовить первоначальное заполнение только из подтверждённых project-level
     фактов; недостающее собирать интервью у владельцев.
2. `audit`
   - проверить соответствие текущего context pack источникам без записи;
   - вернуть расхождения и отсутствующие подтверждения.
3. `update`
   - подготовить подтверждённые добавления и корректировки для существующего context
     pack.

Если пользователь не выбрал режим явно, запросить ровно один режим. `audit` всегда
остаётся read-only. В `initialize` и `update` сначала показать конкретные
`proposed_changes`, затем отдельно получить явное подтверждение пользователя на их
запись. Сам вызов команды, выбранный режим или наличие evidence не считаются таким
подтверждением.

## Нефункциональные ограничения

- Вносить изменения только в `openspec/context/`. Не создавать и не изменять
  `openspec/specs/`, `openspec/changes/`, прикладной код и `.openspec-store`.
- Не изменять встроенные OpenSpec `openspec-*` навыки и `opsx-*` команды.
- Эта пользовательская команда — единственное исключение из meta-only orchestration:
  она может вызывать только `openspec-base-project-context-researcher` и
  `openspec-base-repository-evidence-scout`, но не project skills или другие
  subagents.
- Не переносить временные данные, CI-конфигурации, текущие ветки, незакоммиченные
  diff-ы и персональные данные.
- Не записывать секреты, токены и приватные ключи. Фиксировать можно только
  подтверждённые правила их хранения и использования.
- Файлы Code Repositories использовать только как read-only evidence, без
  `git clone` / `git fetch` и без копирования локальных деталей в центральный Store.

## Сбор evidence

1. Сначала использовать центральные источники, доступные через точки входа и
   навигацию `00-start-here.md`.
2. Для одного спорного факта в центральном Store использовать
   `openspec-base-project-context-researcher`. Передать один вопрос, точный Change
   либо явно указать, что Change отсутствует, абсолютный Planning Home и разрешённые
   context/spec/ADR paths.
3. Обращаться к Code Repository только для одного факта, который нельзя подтвердить
   центральными источниками. Перед вызовом полностью прочитать профиль
   `openspec-base-repository-evidence-scout` и сформировать его обязательный вход.
4. Для нескольких репозиториев выполнять отдельный ограниченный проход scout по
   каждому; subagent не формирует межрепозиторный вывод.
5. Не поручать subagent изменение контекста. Основной агент сопоставляет результаты,
   отделяет факт от вывода и определяет место только для уже подтверждённого
   project-level факта.
6. Если обязательные id, path, revision или подтверждение checkout отсутствуют,
   вернуть `context_status: blocked` или адресный `open_question`, а не исследовать
   случайный текущий checkout.

## Ограничения авторства

- Каждый факт должен иметь evidence: точный `path:line` в разрешённом постоянном
  источнике, Requirement/Scenario либо явный ответ владельца с ролью и датой. Для
  repository-specific evidence дополнительно указывать `repository-id` и полный Git
  commit SHA.
- Не считать предположения и временные данные фактами контекста. Ответ «не знаю» или
  «позже» превращать в адресный TODO с `question`, `owner`, `expected_source`, а не в
  догадку.
- В тематические файлы записывать только продуктовый, доменный и межсистемный
  контекст уровня проекта: короткое нормативное утверждение и проверяемая причина
  либо источник, без стенограммы диалога.
- Не копировать в Store структуру модулей и классов, версии технологий, локальные
  endpoints и config-параметры, команды build/test/lint, CI, упаковку и инструкции
  реализации отдельного Code Repository.
- Общую ответственность и границу репозитория фиксировать кратко в
  `system-map.yaml`. При наличии `openspec-orch.yaml` использовать только
  зарегистрированные `repository-id`; запись в реестре подтверждает идентификатор,
  но не состояние кода.
- Сохранять существующий подтверждённый текст. Перед удалением или смысловой заменой
  показать текущее содержимое, конфликт и evidence, затем отдельно спросить,
  дополнять или заменять.
- Материалы `_raw/` — временный вход для извлечения кандидатов в факты, а не evidence
  и не источник, на который можно ссылаться.

## Процедура

1. Определить режим (`initialize` / `audit` / `update`).
2. Провести инвентаризацию: собрать фактический список файлов
   `openspec/context/`, сверить его с навигацией `00-start-here.md`, показать
   отсутствующие и неожиданные пути. Не делать вывод о наличии файлов из истории
   диалога.
3. Прочитать `00-start-here.md`, `system-map.yaml` и описанные навигацией файлы — в
   этом порядке, до применимой обработки `_raw/` и интервью.
4. В `initialize` и `update` заново найти все материалы `_raw/` и обрабатывать их по
   одному в устойчивом порядке путей. В `audit` не читать `_raw/`, если пользователь
   явно не запросил такую проверку. Не вести индекс обработанного. Для каждого
   прочитанного материала:
   - перечислить атомарные утверждения;
   - определить целевой файл по назначению из `00-start-here.md`;
   - указать недостающее постоянное evidence или решение владельца;
   - не использовать путь к raw-файлу как evidence.
5. Классифицировать кандидатов:
   - контекст уровня проекта → тематический файл, определённый навигацией
     `00-start-here.md`;
   - система или relationship → `system-map.yaml`;
   - локальный технический контекст одного репозитория → без записи в Store;
     вернуть целевой Code Repository в `open_questions`, если его локальный контекст
     отсутствует или устарел;
   - временное или избыточное → без записи.
6. При расхождении источников не выбирать победителя молча: показать утверждение и
   конфликтующие источники, запросить решение владельца и до решения оставить
   адресный TODO.
7. В режиме `audit` вернуть findings и завершить без записи.
8. В `initialize` или `update` группировать атомарные `proposed_changes` в логические
   блоки, обычно по одному целевому файлу. Для готового блока показать конкретный diff
   и вернуть `context_status: proposed`. Не изменять блок до отдельного явного ответа
   пользователя.
9. Получать одно подтверждение на весь показанный логический блок, затем записывать
   только его перечисленные `proposed_changes`. Новое или расширенное изменение блока
   требует повторного подтверждения. Не запрашивать отдельное разрешение на запись
   каждого атомарного утверждения и не редактировать неподтверждённые блоки.
10. Обновлять `00-start-here.md` последним и только как навигацию — без добавления в
    него нового предметного знания.
11. Проверить итоговую трассируемость evidence, список фактически изменённых файлов
    и отсутствие нарушений ограничений команды.

## Сбор фактов у владельцев

Когда разрешённых источников недостаточно, особенно в `initialize`:

- задавать ровно один вопрос за сообщение, без списков вопросов и объединения через
  «и»;
- строить маршрут по назначению файлов из `00-start-here.md` и существующим TODO, а
  не по фиксированной анкете;
- накапливать ответы для текущего логического блока, не смешивая разные целевые
  файлы; когда блок готов, показать его конкретный diff и получить одно подтверждение
  перед записью;
- учитывать самоназванную роль при маршруте диалога, но не принимать от неё решение
  за владельца другого блока;
- при подтверждении зафиксировать роль и дату ответа;
- следующий вызов дополняет уже подтверждённый контекст, а не начинает сбор заново.

## Самопроверка

Перед завершением проверить:

1. Ссылки из `00-start-here.md` разрешаются, а указанные им инвариантные файлы
   существуют.
2. `system-map.yaml` синтаксически корректен, ID уникальны и, при наличии
   `openspec-orch.yaml`, существуют в нём.
3. Нормативные файлы не содержат ссылок на `_raw/` ни в тексте, ни как `path:line`.
4. Контекст не содержит Requirements, Scenarios, Delta operations, прогресс задач,
   секреты и неподтверждённые выводы под видом фактов.
5. Каждый TODO имеет `owner` и `expected_source`; подтверждённое содержимое не
   потеряно.
6. Каждое repository-specific finding содержит `repository-id` и полный Git commit
   SHA.
7. Итоговый diff затрагивает только `openspec/context/` и ограничен явно
   подтверждёнными изменениями.

## Формат ответа

- `context_status: current` — изменений не требуется.
- `context_status: proposed` — подготовлены `proposed_changes`, запись ожидает
  отдельного явного подтверждения пользователя.
- `context_status: needs_confirmation` — отсутствует или конфликтует продуктовое,
  доменное либо governance-решение владельца.
- `context_status: updated` — контекст изменён после отдельного подтверждения
  конкретных `proposed_changes`.
- `context_status: blocked` — отсутствует обязательный scope, path, repository-id,
  revision либо техническая возможность безопасно продолжить.
- Перечислить `proposed_changes`, `changed_files`, `evidence`, `read_sources` и
  `open_questions`, сгруппированные по владельцам. До записи `changed_files` должен
  быть пустым.
- Статус описывает соответствие центрального context pack подтверждённым материалам
  Store и не подтверждает актуальность реализации во всех Code Repositories.

## Запреты

- Не ссылаться на пути внутри `_raw/` как на evidence или источник факта в
  нормативных файлах. Факт из `_raw/` требует постоянного источника либо явного
  подтверждения владельца.
- Не перечислять в context pack все репозитории по умолчанию.
- Не создавать `openspec/context/repositories/` и repository-specific технические
  файлы в центральном Store.
- Не создавать новые верхнеуровневые файлы контекста вне структуры, описанной в
  `00-start-here.md`.
- Не создавать отдельные workflow-файлы Changes/Specs/Tasks из этой команды.
- Не изменять поведение штатных OpenSpec команд и workflow.
