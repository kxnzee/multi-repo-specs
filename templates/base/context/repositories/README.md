# Контекст Code Repositories

Этот каталог разделяет долговечный технический контекст зарегистрированных Code
Repositories. Он помогает определить влияние Change, но не заменяет Specs, Design
или Tasks.

## Источники истины

- Если проект использует Orchestrator, `openspec-orch.yaml` является единственным
  реестром identity: точных `repository-id`, roles, remotes и default branches.
- `system-map.yaml` связывает `repository-id` с системами и ответственностью.
- `repositories/<repository-id>.md` хранит подтверждённые смысловые границы и
  устойчивые технические ограничения конкретного репозитория.
- Код, конфигурация, тесты и принятые ADR подтверждают фактическое поведение.

Не копируйте remote или default branch в этот каталог. При расхождении identity
приоритет имеет `openspec-orch.yaml`; при расхождении поведения нужны проверка
репозитория и явное исправление контекста.

## Файл одного репозитория

Создавайте файл только для подтверждённого `repository-id`:

```markdown
# <repository-id>

## Ответственность и границы

## Системы и capability

## Входящие и исходящие контракты

## Устойчивые технические ограничения

## Проверки и поставка

## Источники
```

Не храните здесь Requirements, текущий план Change, список изменяемых файлов,
прогресс Tasks или временную revision. Не приписывайте репозиторию ответственность
по его имени — подтверждайте её кодом, документацией, конфигурацией или владельцем.

## Использование в Change

Для каждого Change отдельно указывайте:

- затронутые `repository-id` из реестра;
- ожидаемый тип влияния: `implementation`, `tests-only`, `configuration`,
  `documentation` или `no-change`;
- изменение и его причина для каждого затронутого репозитория;
- межрепозиторные контракты и порядок реализации;
- Tasks и evidence, относящиеся к каждому `repository-id`.

Requirements и Scenarios разделяются по capability и наблюдаемому поведению, а не
по репозиториям. Repository impact описывает размещение реализации этого поведения.
